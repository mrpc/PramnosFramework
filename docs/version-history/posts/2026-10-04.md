## Change-log events can belong to a tenant, and be read back by it

A multi-tenant application could not ask the change log for one organisation's events.
The rows had `entity`, `itemid` and `userid` and nothing else. The workaround was a key
inside `details`, filtered with `details->>'organization_id'`, which on a compressed
hypertable decompresses every chunk in the window.

### Added

- `changelog_events.scope`: a nullable string column, added by the migration
  `2026_10_04_000001_add_scope_to_changelog_events`. On PostgreSQL its index on
  `(scope, created_at)` is partial (`WHERE scope IS NOT NULL`), so an application with no
  tenants pays nothing for it. MySQL, which has no partial indexes, gets no index. The column
  is not in the compression `segmentby`, because changing segmentby on a live hypertable
  means decompressing every chunk first. A test adds the column to a table whose chunks
  are already compressed.
- Why a column, and not a separate table or the organisation as the row's `entity`:
  the record (`entity`), the person who acted (`userid`) and the tenant are three
  different things, and only the tenant was missing. It is copied onto the event and not
  joined from the record, so `post.deleted` stays in the organisation's log and a post
  that moves to another organisation keeps its old history.
- `Model::changeScope(): ?string`, which returns null by default. `logEvent()` writes the
  scope only when the model returns one, so an unscoped application's rows are unchanged.
- `ChangelogReader::eventsInScope($scope, $entity = null, $limit = 50)`, which returns
  one tenant's events, newest first.

### Safety

A model that overrides `changeScope()` can be deployed before `migrate` runs. The events
transform drops the scope when the column is not there yet, so the event is still written,
and `eventsInScope()` returns `[]` instead of failing.

## `Permissions::allow()` and `deny()` with a list of privileges grant to the right subject

When `$privilege` was an array, `allow()` and `deny()` called themselves once for each
privilege and left `$resourceElement` out of the call. So every argument after it moved one
place left:
- the resource type was stored as the element;
- the subject type was stored as the resource type;
- the subject type fell back to `user`.

As a result, `allow('7', 'posts', ['read', 'update'], '', 'module', 'group')` granted both
privileges to the **user** with id 7. Even the plainest call,
`allow($userId, 'posts', ['read', 'update'])`, was stored on element `module` of resource
type `user`, where `isAllowed()` never looks.

### Fixed

- Both list forms pass all six arguments through. Characterization tests on MySQL and
  PostgreSQL cover a group grant, which must not reach the user with the same id, and a
  denial on one element. Both tests fail without the fix.

### Upgrading

Grants written with the list form are already wrong in the database. The
[Upgrade Guide](../../Pramnos_Upgrade_Guide.md#since-v12-unreleased) has the query that finds
them. Delete them, then run the code that wrote them again.
