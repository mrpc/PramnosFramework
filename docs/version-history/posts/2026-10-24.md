## Schema builder: choosing the ALTER algorithm (MySQL/MariaDB)

### Added

- `Blueprint::algorithm('INSTANT'|'INPLACE'|'COPY')` appends `, ALGORITHM=...` to every
  `ALTER TABLE` statement `SchemaGrammar::compileAlter()` emits for MySQL and MariaDB. If the
  server cannot honour the requested algorithm — e.g. `INSTANT` on a change that needs a table
  rebuild — the statement fails with the server's own error instead of silently falling back to
  a slower one. A no-op on PostgreSQL/TimescaleDB, where column changes are already
  metadata-only (FW-277).
- Lets a backfill of a column default on a table too large to rebuild unnoticed go through the
  query builder instead of raw SQL, closing the gap that had nannuka's visits/dailystats default
  migrations written by hand.

### Documentation

- Schema Builder guide: *Choosing the ALTER algorithm (MySQL/MariaDB)*, under *ALTER TABLE*.

## Conversations: link previews pruned, and history keeps its cards

### Added

- `conversations:unfurls-prune` (`Unfurls::prune()`) drops a link preview row not read again
  past `conversations.unfurl.keep_days` (30 by default — a cache, so it prunes even
  unconfigured), and the picture files no remaining row still names. Scheduled daily at 04:22.
  Before this, `pramnos.link_previews` and the `previews/` files beside the conversations'
  tree grew without limit.

### Changed

- `Messages::post()` now keeps a message's links (`Unfurls::remember()`) even when posted
  `quiet` — history imported from elsewhere used to get no card at all; it still gets no live
  update, mention or event, only the card it was missing.

### Documentation

- Conversations guide: *Link previews* — quiet history keeps its links; the prune command
  and its default retention.

## Moving from MySQL: the migration ledger is never copied in

### Fixed

- `db:migrate-from-mysql` left `schemaversion` out of every plan by default — a long-lived
  MySQL-origin install's own ledger has rows, and copying them flatly into a fresh target made
  `migrate` believe every framework migration had already run there, so it did nothing:
  `authserver`/`pramnos` schemas and hypertables were never built, everything stayed flat in
  `public`. `--tables=schemaversion` names it explicitly to move it anyway. The dry run now
  says so (`Migrator::plan()`'s new `ledger` key).

### Documentation

- Moving from MySQL guide: *schemaversion never moves*, under the table-creation rules — why,
  and why `migrate` must run to completion before this command's first copy.

## `Database::execute()` takes a literal argument now

### Fixed!

- `execute($sql, ...$arguments)`: the variadic was declared `&...$arguments` (by reference),
  which PHP has refused since 8.1 whenever a caller passes a literal instead of a pre-assigned
  variable — "Argument #n could not be passed by reference". `execute()` never wrote back into
  an argument for the caller to see, so the `&` bought nothing but that fatal. It also broke
  `mysqli_stmt::bind_param()`'s own by-reference requirement once the variadic stopped
  supplying references implicitly — the MySQL branch now takes explicit references to its own
  local copy of the arguments before `call_user_func_array()`.

#### What breaks in subclasses

A `Database` subclass or test double that overrides `execute()` keeping the old
`&...$arguments` fails to load ("Declaration ... must be compatible") — drop the `&` there too.
Nothing else: every ordinary call, with a literal or a variable, keeps working and now accepts
either.

### Documentation

- Upgrade Guide, *Since v1.2 — unreleased*: the signature change and the subclass action.

## Moving from MySQL: `--implicit-defaults` works in one pass

### Fixed

- `--implicit-defaults` gave 0 columns a default on a from-scratch target — `Migrator::plan()`
  reads the target's columns before `run()` makes the tables, so a table this same run creates
  had none to see yet. A second, identical run (target already made by the first) gave the
  right count, which is how the gap stayed hidden. `applyImplicitDefaults()` now re-reads the
  target's columns itself, after `run()`, instead of trusting the plan drawn before the table
  existed — one pass is enough on a from-scratch target too.

### Documentation

- Moving from MySQL guide: a note under *What MySQL filled in out of strict mode* — applied
  after the tables are made, and why a `--dry-run` against tables that do not exist yet counts
  none of it.

## `Database::execute()` rejects the wrong number of bound arguments

### Fixed

- `execute($sql, ...$arguments)` now counts the statement's own placeholders and throws a
  `QueryException` naming both numbers (*"This statement takes 2 bound argument(s); 1
  given."*) when `count($arguments)` disagrees, instead of letting a stale argument list reach
  the driver and come back as mysqli's own warning or PostgreSQL's *"bind message supplies N
  parameters, but prepared statement ... requires M"* — correct, but pointing at the
  framework's statement cache rather than the caller that built the wrong list. On
  PostgreSQL the count comes from the statement's native `$1`/`$2`/… placeholders when it was
  written with those directly, not only from the framework's own `%i`/`%d`/`%s`/`%b` tokens.
  Not a behaviour change for any call that was already passing the right number of arguments.

### Documentation

- Database API guide, *Error handling*: *A wrong argument count is rejected before it reaches
  the driver*.

## `Database::execute()`'s docblock, and three guide examples, point at the query builder first

### Documentation

- `execute()`'s own docblock had drifted onto `logFailedStatement()`, the private method
  inserted between them — moved back, and now says what it is: the engine under
  `QueryBuilder` and `preparedQuery()`, kept public for the one thing neither covers (reusing
  a prepared statement's cached plan across calls, by passing `prepare()`'s own handle to it —
  see `RunsReusablePlans` in a consuming application) and for existing direct callers.
- Three code examples that showed `$db->execute(...)` as the way to run a query — in the
  Database API guide (a `bytea` insert, and an `error_text` check) and the QueryBuilder guide
  (read/write routing) — now lead with `queryBuilder()`, which runs on the same `execute()`
  underneath. No behaviour changed; `execute()` is not going away.

## `whereLikeText()`: LIKE against a `bytea` column that is really text (FW-278)

### Added

- `QueryBuilder::whereLikeText()` / `orWhereLikeText()` compare a column with `LIKE` the way
  `whereLike()` does, except on PostgreSQL the column is decoded with
  `convert_from(column, 'UTF8')` first instead of cast with a bare `::text`. That bare cast —
  what `whereLike()` and `where($col, 'LIKE', …)` use — gives a `bytea`'s hex/escape *output
  format*, not its bytes read as text, so a pattern that is visibly inside a column a MySQL
  `blob` migration mapped straight across (without `--blob-as-text`) never matched. Throws on
  PostgreSQL when the column's bytes are not valid UTF-8 — a column of real binary data has
  no text to find, and that should fail loudly rather than silently match nothing. On MySQL
  it compiles the same as `whereLike()`, since a `blob`'s bytes already compare as text there.
- Reported by nannuka-52 while test-driving a full MySQL→PostgreSQL migration: a `LIKE` search
  found nothing in a column confirmed, by a debug dump, to hold the readable text being
  searched for.

### Documentation

- Database API guide: *Searching inside a `bytea` that is really text: `whereLikeText()`*,
  under *Bytes: `Binary`, and reading a `bytea`*.
- QueryBuilder guide: `whereLikeText()` / `orWhereLikeText()` reference entry, beside
  `whereLike()`.
- Moving from MySQL guide: a note under *Text kept in a blob* pointing a column already moved
  as `bytea` — one `--blob-as-text` cannot retype after the fact — at `whereLikeText()`.

## `Application::getInstance()` rethrows a failed construction instead of swallowing it

### Fixed!

- A maintenance-mode flag, or anything else the constructor threw on, was caught, logged,
  and swallowed — the caller got `null` with no indication why, and whatever ran next failed
  several layers away from the real cause. `getInstance()` now logs the same line and
  rethrows, matching this method's own long-standing `@throws Exception`. In production this
  changes nothing observable: maintenance mode's own page-and-`exit()` path runs first and
  ends the script before an exception could reach here either way — the gap only bit in a
  test or dev environment, where `close()` throws `ApplicationClosedException` instead of
  exiting, precisely so a test can assert on it.
- Reported by nannuka-52: a leftover `var/MAINTENANCE` file from an earlier experiment made
  `getInstance()` return nothing, and the actual symptom — "Database is not connected" —
  surfaced three layers away from the cause, costing about an hour to trace.

#### What breaks in subclasses

Nothing — no signature changed. A call site that relied on a silent `null` after a failed
construction now sees the exception instead; wrap that one call in `try`/`catch` if it
genuinely needs to continue past it.

### Documentation

- Framework guide, *`getInstance()` builds; `currentInstance()` only looks*: a failed
  construction throws, it never returns null.
- Upgrade Guide, *Since v1.2 — unreleased*: the behaviour change and what to do.

## Conversations: a new message's id comes from `RETURNING`, not a racy `currval()` (FW-280)

### Fixed

- `Messages::post()` read a new message's id with `Database::getInsertId()`, which on
  PostgreSQL runs `currval()` on the id column's own sequence as a second statement, after
  the INSERT. `conversation_messages` is a hypertable, and a row that opens a new chunk could
  leave `currval()` answering "not yet defined in this session" even though the INSERT that
  just ran is what defined it — intermittent, and only on the very first write to the table
  in a session. `post()` now asks PostgreSQL to `RETURNING` the id in the same statement as
  the INSERT, which has no such window; MySQL is unaffected (`getInsertId()` there is
  `mysqli_insert_id()`, with no session-sequencing question to race).
- Reported by nannuka-52: 2 tests failing only on PostgreSQL, intermittently, with exactly
  this driver error.

### Documentation

- None — `Messages::post()`'s return value and behaviour are unchanged; this is internal.

## A migration's guard no longer lets `name` stand in for `externalid` (FW-279)

### Fixed

- `AddFormerMembersToConversationMembers::up()` returned as soon as `conversation_members`
  had a `name` column, on the assumption that this migration is the only thing that could
  have put one there — so `name` and `externalid` always arrive, or are missing, together. A
  `name` column added by anything else first (an application's own migration, a hand-made
  `ALTER TABLE`) broke that assumption: the migration marked itself `Ran` without ever adding
  `externalid`, silently — the next query that read it failed with "Unknown column
  'externalid'", on a database migrated from zero, not a stale snapshot. `up()` (and `down()`)
  now check each column independently and act only on the one that is actually missing.
- Reported by nannuka-52, with a from-zero reproduction confirming it was not a caching
  artifact.

**An installation already marked `Ran` for this migration, missing `externalid`,** does not
get a retry from an ordinary `migrate` — the ledger already has the row. Either add the
column by hand (`ALTER TABLE conversation_members ADD COLUMN externalid VARCHAR(100) NULL`;
PostgreSQL: same, lower-cased), or delete that migration's row from the ledger
(`schemaversion`/the framework's migrations table) and run `migrate` again: with this fix,
the guard now adds only what is actually missing.

### Documentation

- None — the migration's own behaviour (what the table ends up with) is unchanged for every
  installation where nothing else ever added a `conversation_members.name` column; this
  fixes the one case where something did.

## Theme widgets, menus and banner locations no longer unserialize an object

### Fixed

- `Theme::loadWidgets()`, `assignMenus()` and `assignBannerLocations()` called `unserialize()`
  on the stored `theme_<theme>_{widgets,menus,bannerLocations}` settings with no
  `allowed_classes` restriction. Every write to these settings is `serialize()` of a plain
  array, so the fix has no effect on any value the framework itself ever writes — but
  `SettingsController::save()` writes an arbitrary setting key with no allowlist on which key
  an admin-floor request names, so a crafted value here was a PHP object injection a
  compromised or CSRF'd admin session could reach. All three now call
  `unserialize($value, ['allowed_classes' => false])`, which hands back
  `__PHP_Incomplete_Class` instead of instantiating a real class, so no constructor,
  `__wakeup()` or `__destruct()` of a gadget-chain class ever runs.
- Found during a local Psalm `--taint-analysis` pass (not run in CI).

### Documentation

- None — behaviour for every value the framework writes to these settings is unchanged;
  only a crafted non-array value is now neutralised instead of acted on.

## `LogManager::getLogFilePath()` strips any directory component from the file name it is given

### Fixed

- `getLogFilePath($filename, $ext)` is the one place every reading and writing method in
  `LogManager` builds its path through, but built it by direct string concatenation —
  `$filename` or `$ext` containing `../` would have climbed out of the log directory. Every
  current caller already restricts `$filename` to an admin screen's own whitelist, itself
  built from a scan of the real log directory, before it gets here — so this closes the gap
  for any future caller, rather than one this method currently lets through (Psalm
  `TaintedFile`, taint-analysis). Both arguments now go through `basename()`, which strips
  any directory component without changing a filename this is actually called with.

### Documentation

- None — every current call passes a plain filename, which `basename()` returns unchanged.

## `Logger::getLogPath()` strips any directory component, and is now the one place every log read/write builds its path through

### Fixed

- `log()`, `rotateIfNeeded()`, `truncateLogFile()` and `clearLog()` each built their own
  `$filepath` by direct string concatenation, duplicating the exact logic `getLogPath()`
  already existed to hold — so a path-traversal `$file`/`$ext` had four places to reach a
  read or write outside the log directory from, not one, and hardening only the already-named
  helper would have left the other three as they were (Psalm `TaintedFile`, taint-analysis;
  same class of finding as `LogManager::getLogFilePath()`, above). All four now call
  `self::getLogPath($file, $ext)`, which strips any directory component from both arguments
  with `basename()`.

### Documentation

- None — every current caller names a fixed channel or a value already validated upstream,
  which `basename()` returns unchanged.

## Moving from MySQL: `CAST(x AS SIGNED/UNSIGNED)` stays lenient on non-numeric text (FW-282)

### Fixed

- `translate_mysql` turned `CAST(x AS SIGNED)` / `CAST(x AS UNSIGNED)` into a plain
  `CAST(x AS bigint)`. MySQL's cast is lenient on a string: it reads the leading run of
  digits (an optional sign, skipping leading whitespace) and takes `0` where there is none —
  a warning, never an error. PostgreSQL's `bigint` cast refuses anything that is not entirely
  numeric, with `invalid input syntax for type bigint`, which fails the whole statement
  rather than the row — a `WHERE`/`JOIN` comparing a column where even one row holds a
  non-numeric value (a legitimate sentinel like a non-numeric billing marker, not corrupt
  data) returned nothing instead of every other row matching as it did on MySQL. The
  translation now reads the leading digit run itself —
  `CAST(COALESCE(substring((x)::text from '^[[:space:]]*([+-]?[0-9]+)'), '0') AS bigint)` —
  so `'3pay'` casts to `3` and `'pay3'` to `0`, matching what MySQL would have done rather
  than stripping non-digit characters from anywhere in the string, which would answer `3`
  for `'pay3'` too and get it wrong.
- Reported by nannuka-52: `users.subscription` holds a non-numeric sentinel for manual
  billing in among real packageid strings, and `CAST(NULLIF(a.subscription, '') AS UNSIGNED)
  = pac.packageid` appears 18+ times in one model alone.

### Documentation

- `docs/Pramnos_Database_API_Guide.md`'s `translate_mysql` table — "`CAST(x AS SIGNED)`, `… AS
  UNSIGNED`" now reads "the leading run of digits as `bigint`, `0` where there is none —
  never an error, as in MySQL".

## `Model::_save()`'s debug dump escapes `$_POST` instead of writing it raw

### Fixed

- `save($autoGetValues, $debug, $force)` with `$debug` true `var_dump()`s `$_POST` and the
  model straight into the response, with no HTML encoding — a value in `$_POST` containing
  markup rendered as markup (Psalm taint-analysis, `TaintedHtml`). `$debug` is public and
  opt-in, not reachable from any default path in the framework itself, but a consuming
  application wiring a debug toggle to a request parameter would have reflected whatever the
  request sent. The dump is now captured with `ob_start()`/`ob_get_clean()` and
  `htmlspecialchars()`-escaped before being echoed — same layout, markup survives only as
  text.

### Documentation

- None — the escaped text is the only change; `save()`'s own signature and the debug dump's
  presence are unchanged.
