## A comment inside a palette block became a colour token

`app/themes/theme.css` is a stylesheet a person edits, and the Theme Guide invites
annotating the colours in it. Doing that broke the build:

```css
@plugin "daisyui/theme" {
    name: "acme";
    /* The surfaces: white cards on a light grey page. */
    --color-base-100: #ffffff;
}
```

`ThemeTokens::parse()` split the block on `;` and read every piece as `name: value`, with
nothing that knew what `/* … */` was. So the comment's own text became a key in
`www/assets/theme-tokens.json` —

```json
"/* The surfaces": "white cards on a light grey page. */\n    --color-base-100: #ffffff"
```

— and the declaration on the line after it went with it. A SPA reading that file for
`--color-base-100` got nothing, and the only evidence was a JSON key nobody opens.

### Fixed

- **Comments are stripped before anything else looks at the file**, so `/* … */` is safe
  anywhere: beside a declaration, on its own line inside a block, or wrapped around a
  declaration being tried out. Stripping first rather than per line also means a
  commented-out `}` no longer ends a block early and takes every declaration below it —
  which was the same bug with a quieter failure.

### Documentation

- The Theme Guide's "One palette, every UI system" section now says comments are safe and
  shows one, instead of the palette file inviting something that did not work.


## The SPA shell's service-worker registration was a fatal

A scaffolded SPA with `--service-worker=y` ended every page with:

```
Fatal error: Uncaught Error: Undefined constant "sURL"
```

The registration snippet is built in PHP so the URL follows a subdirectory install, and
`sURL` is what knows the base. The theme footer has it — it renders inside a booted
application. The SPA shell does not: it `require`s the autoloader and nothing else, by
design, because it is not an MVC view.

It survived because of where it lands. The SPA had already booted by then, the page
looked right, and the only consequence was a worker that was never installed — which
leaves no trace anywhere.

### Fixed

- The shell's copy reads **`$siteUrl`**, the `getUrl()` call the shell already makes a
  few lines higher to derive the API key. Same value, same subdirectory behaviour, and
  it is a variable the file actually has. The theme footer's copy is unchanged.

### Documentation

- The Service Worker Guide's "Where the registration lives" now shows both forms and
  says why they differ.
