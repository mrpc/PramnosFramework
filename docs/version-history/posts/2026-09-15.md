## A comment inside a palette block became a colour token

`app/themes/theme.css` is a stylesheet a person edits, and the Theme Guide invites
annotating the colours in it. Doing that broke the build:

```css
@plugin "daisyui/theme" {
    name: "acme";
    /* The surfaces: white cards on a light grey page. */
    --color-base-100: #ffffff;
}
```

`ThemeTokens::parse()` split the block on `;` and read every piece as `name: value`, with
nothing that knew what `/* … */` was. So the comment's own text became a key in
`www/assets/theme-tokens.json` —

```json
"/* The surfaces": "white cards on a light grey page. */\n    --color-base-100: #ffffff"
```

— and the declaration on the line after it went with it. A SPA reading that file for
`--color-base-100` got nothing, and the only evidence was a JSON key nobody opens.

### Fixed

- **Comments are stripped before anything else looks at the file**, so `/* … */` is safe
  anywhere: beside a declaration, on its own line inside a block, or wrapped around a
  declaration being tried out. Stripping first rather than per line also means a
  commented-out `}` no longer ends a block early and takes every declaration below it —
  which was the same bug with a quieter failure.

### Documentation

- The Theme Guide's "One palette, every UI system" section now says comments are safe and
  shows one, instead of the palette file inviting something that did not work.


## The SPA shell's service-worker registration was a fatal

A scaffolded SPA with `--service-worker=y` ended every page with:

```
Fatal error: Uncaught Error: Undefined constant "sURL"
```

The registration snippet is built in PHP so the URL follows a subdirectory install, and
`sURL` is what knows the base. The theme footer has it — it renders inside a booted
application. The SPA shell does not: it `require`s the autoloader and nothing else, by
design, because it is not an MVC view.

It survived because of where it lands. The SPA had already booted by then, the page
looked right, and the only consequence was a worker that was never installed — which
leaves no trace anywhere.

### Fixed

- The shell's copy reads **`$siteUrl`**, the `getUrl()` call the shell already makes a
  few lines higher to derive the API key. Same value, same subdirectory behaviour, and
  it is a variable the file actually has. The theme footer's copy is unchanged.

### Documentation

- The Service Worker Guide's "Where the registration lives" now shows both forms and
  says why they differ.


## Bundled theme stylesheets read custom properties nothing declared

The tailwind theme's breadcrumb and pagination rules asked for `--primary-color`,
`--text-muted`, `--border-color`, `--text-main` and `--white`. The palette pipeline emits
daisyUI's names — `--color-primary`, `--color-base-content`, `--color-base-300`,
`--color-base-100` — and nothing anywhere declares the first set.

`var(--name, #literal)` never fails. The browser takes the fallback, renders it and says
nothing, so those two components were Tailwind blue on every project regardless of its
palette and stayed light under the dark theme. The rest of the same file already used
`--color-*`, which is what made it invisible: it read as a style choice rather than a
stylesheet asking for a vocabulary the page has not got.

### Fixed

- **tailwind** — the whole file now reads `--color-*`, including
  `--color-primary-content` for text on a primary background rather than white.
- **bootstrap** — the same class of defect across twenty-two rules, and that theme has
  its own vocabulary on the page: they now read `--bs-primary`, `--bs-body-color`,
  `--bs-body-bg`, `--bs-border-color`, `--bs-secondary-color` and `--bs-secondary-bg`.
- **plain-css** — it declares its palette itself, and read two names it had never
  declared. `--border-color` and `--bg-subtle` are now in its `:root` block.

### Added

- `tests/Unit/Theme/ScaffoldThemeStylesheetTokensTest.php` — every `var(--x)` in a
  bundled theme's `style.css` must be declared in that file, be a token of the palette
  `init` writes (read through `ThemeTokens::parse()`, so the check follows the palette),
  or carry a prefix the theme's page genuinely provides. It found three more dead names
  than the report did.

### Documentation

- The Theme Guide's table of bundled themes now has a third column — which vocabulary
  each one's stylesheet reads — and says what a rule in the wrong one looks like.


## The tailwind header showed the dark-ink logo on the dark theme

The scaffold copies two ink variants of the placeholder wordmark into
`www/assets/img/` — `logo.png` dark, `logo-inverse.png` light — and the tailwind header
hard-coded the first. That theme is the only one with a light/dark toggle, so under
`data-theme="<slug>-dark"` the brand was near-black on a near-black navbar: no error, no
broken image, just a header with nothing in the corner. Nothing referenced the inverse
file at all.

### Fixed

- The brand image carries `pf-logo`, and the theme's `style.css` swaps it:

  ```css
  [data-theme$="-dark"] .pf-logo { content: url("../img/logo-inverse.png"); }
  ```

  plus the same rule under `prefers-color-scheme: dark` scoped to
  `:root:not([data-theme])`, for a visitor who has not chosen — the scoping
  `theme-tokens.css` already uses. The suffix match is because the dark theme is named
  after the project and the stylesheet is static.

  No second `<img>` to keep in sync and no JavaScript in the path. bootstrap is
  unchanged — its navbar is dark in both directions and already gets the inverse file —
  and plain-css ships no dark theme.

### Documentation

- The Theme Guide's "The tailwind theme is a daisyUI theme" section says the logo
  follows the theme and that rebranding means replacing both files.


## A scaffolded front end arrived with two red tests and a build warning

Two defects in the shared Svelte components, both of which a newly scaffolded project
inherits and neither of which it caused.

### Fixed

- **`ConfirmDialog.test.js` asserted against an element the focus trap excludes.** The
  two wrap-around tests built their expected first and last element from
  `screen.getAllByRole('button')`, which includes the modal backdrop — a `<button>` for
  the click, held out of the tab order with `tabindex="-1"` on purpose. The component
  was right: `focusable()` filters `!el.disabled && el.tabIndex !== -1`. The test now
  filters the same way, through a `tabbableButtons()` helper, so the expectation mirrors
  the trap instead of re-querying the DOM with looser rules. Two tests red out of the
  box, for a component that worked.
- **`DataTable.svelte` warned on every `npm run build`.** `let searchBox = $state(search)`
  reads a prop at init and an `$effect` re-syncs it, which is exactly what
  `state_referenced_locally` is about. It is now `$state(untrack(() => search))` — the
  initialiser really is a one-shot read, and `untrack` is how you say so.

### Documentation

- The Console Guide's "The shared components" section says the scaffolded suite is green
  and the build warning-free, and explains both constructs — each reads like a slip and
  reverting either brings the failure back.


## The generated controller contract test named twelve classes that do not exist

`ControllersContractTest.php` is close to the first thing anybody runs in a new project,
and a scaffolded project opened with **24 errors**:

```
Error: Class "App\Controllers\Dashboard" not found
```

— and the same for `Users`, `Settings`, `Logs`, `Services`, `Organizations`, `Emails`,
`TokenActions`, `Tokens`, `Applications`, `Permissions` and `Queue`. Every one of those
is written to `src/Admin/Controllers`, under an `Admin\` namespace segment, and the
roster named all twelve under `App\Controllers`.

It drifted the other way as well, silently: `Register`, `Sso`, `Webhook` and `Messages`
were written and had no row, so the contract nobody thought to add was the contract
nobody was checking. Four real gaps, and they were the cheap half — twelve false
failures say the scaffold is broken, on the first command, about controllers that are
fine.

The cause is the shape rather than the list: the roster was maintained beside the code
that writes the controllers, guarded by the same feature flags, so keeping the two in
step was a thing somebody had to remember on every change.

### Fixed

- **The roster is read off the project's `src/` after the controllers are written.** Both
  directories, with the expected parent resolved from each controller's own `extends`
  clause and imports — the wrappers alias theirs (`use …\Controllers\Account as
  FrameworkAccount`), so the token alone would have named a class that exists nowhere.
- Rows are plain class-name strings rather than `::class` constants, so a controller that
  does not load fails an assertion with its name in the message instead of erroring
  inside the data provider.
- Names are the short class name, with the parent segment kept when two directories would
  collide (`Admin\Users` beside `Users`).

A project scaffolded with `auth`, `authserver`, `queue` and `messaging` now gets 33 rows,
all of which load — including the eight that were never checked before.

### Documentation

- The Console Guide has a new section, "The controllers `init` writes, and the test that
  names them": the two directories and their namespaces, and why the roster is read from
  disk rather than written down.
