## `pf-voice.js`: server dictation calls `onSilence` before `onEnd`, like the browser's own (FW-503)

With the browser's own speech recognition, a silence stops dictation and calls `onSilence`
synchronously; the recognition's own `onend` — which calls `onEnd` — arrives later, asynchronously.
A caller that follows the ordinary pattern, `onEnd: () => { if (listening) endConversation(); }`,
relies on that order: `onSilence` has already cleared `listening` by the time `onEnd` runs.

Dictation by a server (`createVoiceState({ listen: fn })`, FW-437 — Firefox, an installed app on
an iPhone) called them the other way round: `onEnd` fired as soon as the transcription promise
resolved, before `onSilence`. A caller using the same pattern read `listening` still `true` and
ended the conversation it had just restarted — invisible until server-based dictation started
working end to end, when the microphone that should have reopened never did.

### Fixed

- `serverDictation()`'s `finishServer()` now calls `opts.onSilence()` before `ended()` (which
  calls `opts.onEnd()`), matching the order the browser's own recognition path already used.

### Documentation

- `Pramnos_LLM_Analyst_Guide.md`, "Voice": the ordering made explicit, with why it matters for a
  caller's own `onEnd`.

## A client-side wrapper can tell the model its own device state, for one question (FW-504)

A desktop wrapper (Electron, a native shell) can know things the server never does — a model
downloading, a script it is running on the person's own word — kept entirely in its own IPC
today. Asked "what are you doing right now?", the model had no way to know, and no hook existed
to tell it without inventing a new field of the conversation's own history.

### Added

- `extra['local']` — a short string an application's own `TakesQuestions::extra()` override adds
  from whatever its own channel carries, told in zone 3 (`ContextAssembler::dynamicTail()`) for
  that question alone: `Happening on the person's own device right now, not said by them: …`, cut
  at `ContextAssembler::MAX_LOCAL` (200 characters). Like the time and the page, never part of the
  conversation's own history, and the model is told plainly it is not something the person said.

### Documentation

- `Pramnos_LLM_Conversations_Guide.md`, "The context, in three zones": `extra['local']` added.

## `json_query`: a table artifact's rows, filtered and projected, without reading it whole (FW-505)

`read_artifact` cuts a long artifact at a fixed number of characters — fine for a document, not
for a table of hundreds of rows the model is asked a specific question about ("which orders are
still open?"), where the cut lands mid-row and the one row that mattered may already be past it.

### Added

- `json_query` (`Artifacts::workspaceTools()`, the `artifacts` skill): a table artifact's rows,
  `where` (column => value, exact match, case-insensitive; every pair given must match) and
  `select` (which columns to keep). `limit` caps how many rows, 50 by default, 500 at most.
  Refused for a kind that is not a table — a list or a chart is short enough for `read_artifact`
  to read whole — and for one that is not this person's own or shared with them, like every other
  artifact tool.

One more always-on tool nudges every installation's own tool count up by one — close enough to
`Conversations::SKILLS_FROM` (20) that two tests relying on staying under it by a margin started
failing once this one landed (`SkillsTest::testOffEveryToolIsOffered`,
`ConnectionsTest::testAServerWithAToken`). Fixed by saying `'chat' => ['skills' => false]]`
outright where the test's own point is "every tool, ungrouped" — the same workaround the file
already used once, for the same reason, where `chat.web`'s two tools did it first. Not a bug in
either feature: `SKILLS_FROM` is doing exactly what it is for. An installation sitting close to
the threshold may see skills grouping turn on a tool sooner than before.

### Documentation

- `Pramnos_LLM_Conversations_Guide.md`, "A workspace across conversations": `json_query` added to
  the tools table.
- `Pramnos_LLM_Tools_Guide.md`: `json_query` added to the `artifacts` skill's tool list.

## `read_storage_document`: the words of a file sent in a team conversation (FW-506)

The harness spec named a generic `read_storage_document` tool and it went unbuilt: letting the
model read an arbitrary stored file needs a permission model deciding whose files it may open,
and none existed. `Conversations\Files::pathFor()` already is one — the same rights as reading
the conversation the file was sent in, which `conversation_summary` already answers through for a
conversation's words rather than its files.

### Added

- `read_storage_document` (`Analyst::tools()`, alongside `conversation_summary`, wherever
  `Conversations::installed()`): the words of a file sent in a team conversation this person can
  read, through `DocumentText` — Word, OpenDocument, CSV/TSV, plain text, Markdown or a saved
  email. `file` is its id. A picture, video, PDF or archive — nothing `DocumentText` reads the
  words of — says so rather than nothing; a file from a conversation this person cannot read
  answers the same as one that does not exist.

### Documentation

- `Pramnos_LLM_Analyst_Guide.md`: `read_storage_document` added to the tools table, beside
  `conversation_summary`.

## `schema` can see more than one PostgreSQL schema, for an application split across several (FW-507)
- `code_exec`: sandboxed Python for the analyst, a prototype (FW-508)

`SchemaBuilder::tableNames()` only ever listed the connection's own schema, which is right for the
ordinary public-vs-private split but breaks for an application organised into several PostgreSQL
schemas by module on purpose — a table of any schema but the connection's own was invisible to
`schema`, and so to the model, even though `sql` could already query it by a qualified name once
it somehow knew the name. Found wiring up audit-log questions in an installation split into
`public`, `authserver`, `backend` and others, each a module of one application.

### Added

- `SchemaBuilder::tableNamesIn(array $schemas = [])`: every table across the PostgreSQL schemas
  named, a table of the connection's own kept bare, a table of any other `schema.table`-qualified,
  a system schema (`information_schema`, `pg_catalog`, `pg_toast`, `topology`, `_timescaledb_*`)
  left out whether or not it was named. A new method, not a new parameter on `tableNames()` —
  `SchemaBuilder` is not `final` and an overridden `tableNames()` elsewhere would fatal at class
  load on a new argument. Empty, or on MySQL (no second schema the way this is), the same as
  `tableNames()`.
- `'llm' => ['analyst' => ['schemas' => [...]]]`: `SchemaTool` reads it and calls `tableNamesIn()`
  in its place. Without it, nothing changes.

### Documentation

- `Pramnos_LLM_Analyst_Guide.md`: `schemas` added to the SQL/export config example and explained
  beside `schema`.

## `code_exec`: sandboxed Python for the analyst, a prototype (FW-508)

For analysis no SQL statement does cleanly — comparing numbers across a file, a pandas-style
groupby or pivot — the assistant had nothing: a provider's own code-execution tool is that
provider's alone, and the assistant is multi-provider on purpose (OpenAI, Google, Mistral, a local
model), so using one would mean building it again for each, or giving up being provider-agnostic
the moment this capability is needed. A framework-level design assessment this week concluded a
WebAssembly runtime (Pyodide — CPython compiled to WASM, under Node.js) over a Docker container
per call: no container image to build and ship, no docker-socket access to hand a worker, and a
fork bomb is not even possible (WebAssembly has no `fork()` syscall). The design's own spike
measured what actually bounds Pyodide's memory (a cgroup — `node`'s own flags and `ulimit -v` both
turned out not to work) before any of this was built.

### Added

- `code_exec` (`'llm' => ['analyst' => ['code_exec' => true]]`): Python, run in
  `Pyodide` under Node.js (`resources/js/sandbox-runner/`, `npm install` once there), wrapped in a
  `systemd-run --user --scope` cgroup for memory/CPU and killed outright past its own
  wall-clock seconds. Never run by the request answering the question: `CodeExecTool` only writes
  a row to the new `pramnos.llm_code_exec_runs`, queues a `code_exec` task, and polls it until a
  worker finishes or its own wait runs out — refused outright past that, never falling back to
  running the script itself.
- `pramnos.llm_code_exec_runs`: state, not history, the same shape as `llm_tool_runs`
  (`ParallelTools`) — a row only while its call is answered.
- `code_exec`'s task type is deliberately **not** in `Worker::FRAMEWORK_HANDLERS`: unlike a
  parallel tool call, which any worker may run since it only reads, this needs Node.js, `pyodide`
  and cgroup tooling most workers will not have. An application points a worker at it explicitly —
  `'queue' => ['handlers' => ['code_exec' => \Pramnos\Llm\Sandbox\CodeExecTask::class]]]` — and
  nothing answers a call until one does.
- `code_exec_wait`, `code_exec_seconds`, `code_exec_memory_mb`: how long the answer waits for a
  worker, how long the sandbox itself may run, and its memory ceiling — `CodeExecTool::DEFAULT_WAIT`
  / `PyodideRunner::DEFAULT_TIMEOUT_SECONDS` / `PyodideRunner::DEFAULT_MEMORY_MB` (512, measured:
  loading pandas alone uses close to 400 MB) otherwise.
- The sandbox runs inside its own network namespace (`unshare --net --map-root-user`), where the
  worker's kernel allows an unprivileged one. Not for Python's own `socket`/`urllib` — both were
  measured not to move real bytes under Node.js at all, isolated or not — but for `js.fetch(...)`,
  Pyodide's own escape hatch into Node's **real** `fetch()` through its JavaScript interop:
  confirmed reaching a real site without this, and failing with `TypeError: fetch failed` with it.
  Where an unprivileged namespace cannot be made at all — a container's own seccomp profile can
  refuse it outright, found running `code_exec`'s own tests inside this framework's own
  `./dockertest` image — `code_exec` still runs, unisolated, rather than refusing outright; its
  own test asserts whichever is true here honestly, rather than assuming one.
- `systemd-run --user --scope` is probed for real the same way, past a peer's own question before
  trying this in a Docker dev container: a binary on the `PATH` is not enough — an ordinary
  container runs no `systemd` at all, so `systemd-run` there reaches no session to ask for a
  cgroup and used to fail every `code_exec` call outright rather than running uncapped in memory
  with the wall-clock timeout as the only limit left, the same class of mistake the network-
  namespace probe above already existed to avoid.
- `code_exec_max_pending` (5 by default — `CodeExecTool::DEFAULT_MAX_PENDING`): a peer's review —
  the wait itself holds the request's own PHP worker open, which a missing or overloaded `code_exec`
  worker turns into an unbounded cost on the web tier, never reaching the sandbox at all. Once this
  many calls are already waiting or running across everybody, a new one is refused at once, before
  a row is even written.
- Two ideas borrowed from reading [openworker](https://github.com/andrewyng/openworker)'s own
  sandboxed tool runner for comparison: `code_exec_require_isolation` fails a call closed rather
  than degrading silently, where a worker cannot actually make its own network namespace (off by
  default — the second line of defence it drops is past an already-measured stub, Python's own
  networking under Node.js). And `PyodideRunner::run()` now answers `isolated`/`scoped` on every
  call, so a result says which protections actually applied rather than leaving the caller to
  assume the strongest case — a `code_exec` answer carries a `[sandbox note: ran without …]` line
  when either was missing, silent on the ordinary path.

**Still a prototype** — see the guide for what it does not yet do: no pre-bundled packages for a
worker meant to run fully offline.

### Documentation

- `Pramnos_LLM_Analyst_Guide.md`: new section, "`code_exec`: sandboxed Python (prototype)", with
  the `queue.handlers` wiring, the measured resource-limit findings, and what is still missing.

## A queued task can hand a child task its own priority, capped below it (FW-509)

A task spawning a child task from inside its own `execute()` — one step of a pipeline queuing the
next — had no way to say "run this one ahead of the ordinary backlog too": a child left at the
default priority fell flat to the back of the queue, behind every default-priority task already
waiting, however urgent its parent was. Asked for by a peer migrating an app-level queue of its
own into this one, which already has the same feature behind a custom `QueueManager`.

### Added

- `Pramnos\Queue\AmbientPriority`: the priority of the task a worker is running right now, in this
  process. `Worker::processNextTask()` sets it around a task's own `execute()` and clears it after,
  success or failure alike.
- `'queue' => ['priority_inheritance' => true]`: `QueueManager::addTask()`/`addKeyed()` read it — a
  call left at the literal default (10) with an ambient priority available becomes
  `min(parent + 1, 10)`, one step below the parent, never past the ordinary default. A priority
  asked for explicitly, 10 or otherwise, is never touched; only "nothing asked for" is. Off by
  default, additive where it is not.
- The cap, not a flat copy, is deliberate: a priority-1 task's child running flat at priority 1
  would race ahead of the parent's own siblings and everything else as urgent; one step down each
  time a chain goes a layer deeper keeps a long chain from drifting toward the front of the queue
  on its own.

### Documentation

- `Pramnos_Queue_Guide.md`: new section, "A child task's own priority".

## `QueueManager::summariseHistory()`/`worstWaits()`: the arithmetic a queue statistics page needs (FW-510)

`history()` answers one row per task type per hour; a statistics page summarising it over a whole
window had to write its own arithmetic to roll those rows up — and the obvious way to do it,
averaging the hourly means, is silently wrong: it lets a quiet hour with four tasks weigh the same
as a busy one with sixteen thousand, dragging the figure toward whatever the idle hours did.
Asked for by a peer whose own application-level queue manager already carried exactly this
arithmetic for its own Queue Statistics page, migrating onto this framework's queue.

### Added

- `QueueManager::summariseHistory(array $rows): array`: `history()`'s rows rolled up per task
  type over the whole window, busiest first — means weighted by each bucket's own task count,
  maxima taken as-is, counts added. Pure: no database, no `$this`.
- `QueueManager::worstWaits(array $rows, int $limit = 8): array`: the buckets that waited longest,
  worst first, capped at `$limit` — its own list, since a single bad hour disappears into a
  window's weighted mean the moment enough ordinary hours surround it.

### Documentation

- `Pramnos_Queue_Guide.md`: both added under "Statistics — last 48 hours".

## A leaked tool-call protocol is sanitised and tagged; a capability gap is tagged by its own words (FW-511)

Found reviewing production conversations: a self-hosted model's own serving layer, intermittently,
emitted its reserved-token tool-call protocol (a fullwidth-pipe tag, `<｜tool▁calls▁begin｜>` and
the like) as plain answer content instead of routing it through the structured field
`Client::askWithTools()` reads — the admin saw raw JSON and reserved tokens in place of an answer.
Investigated: the framework never had any token-level tool-call parsing to fail here, by design —
every provider is trusted to use the structured field, and this was the upstream server's own
protocol bug reaching the person verbatim. The same pass also surfaced a gap with no bug behind
it: nothing recorded when the model said plainly it had no tool for a question (its own system
prompt already asks it to say so), unlike a thumbs-down, which already waits in a review queue — a
full manual read of ninety-seven conversations was the only way to find these.

### Added

- `Pramnos\Llm\AnswerTags`: patterns checked against an answer's own text, once it is written,
  never asked of the model. `leaked()` knows the fullwidth-pipe tag shape by default —
  `'llm' => ['leaked_patterns' => [...]]` adds an application's own local model's spelling of it.
  A match replaces the answer with a plain refusal before it is shown or stored, and sets
  `extra.malformed` — a fix, not merely a tag, since this one reached production as raw garbage.
- `'llm' => ['chat' => ['capability_gap_patterns' => [...]]]`: a plain substring (case-insensitive)
  or a `~`-prefixed regular expression; a match sets `extra.capability_gap` on the stored message
  without changing a word of what the person reads. Empty by default. Turns a manual read of a
  conversation export into `WHERE extra->>'capability_gap' IS NOT NULL`.

### Documentation

- `Pramnos_LLM_Conversations_Guide.md`: new section, "Tagging an answer by its own words, after it
  is written", beside "Rating answers, and the queue of bad ones".
