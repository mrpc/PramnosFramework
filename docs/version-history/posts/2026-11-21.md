# 21 November 2026

Two entries today:

- A fenced code block's own numbers are read as JSON, not by the prose number check (FW-573)

## A figures correction's round budget grows with the chain it actually takes (FW-572)

### Fixed

After a figures correction (`Client::FIGURES`), the retry's round budget was a flat `$round + 2`
— enough for one tool call and the answer, whatever the actual chain to a correct number needed.
Reported live from exactly that: the retry correctly read a `schema` tool first, but had no round
left to call `sql` with what it learned, and was forced to answer with nothing new to show for it.

Now each round after the correction that still genuinely calls a tool earns one more: the chain
gets as many rounds as it actually takes, not a ceiling fixed the moment the correction fired. The
existing over-budget check still stops it growing forever once the answer's cost or token budget
is spent.

### Documentation

`docs/Pramnos_LLM_Tools_Guide.md`'s figures section now describes the grown-as-needed round
budget.

## A fenced code block's own numbers are read as JSON, not by the prose number check (FW-573)

### Fixed

`Figures::untraced()`'s number regex is built for how people write a number by hand — grouped by
thousands, one decimal mark — and reads a fenced code block in the answer the same way. A chart's
own JSON, written as a compact array with no spaces after its commas (`"data":[4676,2111,658,...]`),
has no thousands-grouping marks at all to tell its elements apart from one long number, so the
regex glued them into one bogus figure and named it as invented. Reported live from exactly that:
one real typo among seventeen numbers in an answer, sixteen of them real figures inside a chart
block, all seventeen flagged together — and because the rejection was that wide, the model
abandoned an already-correct tool result for improvised SQL instead of fixing the one real mistake,
giving a different wrong answer on each of two runs of the same question.

Every fenced code block (` ```…``` `) in the answer is now read as JSON first, the same way a
tool's own result already is: each of its numeric leaves is checked against the known figures
exactly, with no grouping ambiguity, and excluded from the prose check that follows. A block that
is not valid JSON is left to that check as before.

The same gluing happens outside a fence too, in a markdown table cell that holds nothing but a
bare, comma-separated list ("4676,2111,658,559,474", no formatting around it at all) — reported
as the same underlying bug (FW-527). Such a cell is now read one number at a time as well, unless
every group after the first happens to be exactly 3 digits, in which case it is as honestly one
large formatted number as it is a list, and is left to the ordinary check rather than risk
splitting a real one apart.

### Documentation

`docs/Pramnos_LLM_Tools_Guide.md`'s figures section now describes fenced-code-block and
table-cell numbers being read this way.
