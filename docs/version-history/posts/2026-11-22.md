## `Memory::keep()`/`amend()`/`forget()`/`forgetShared()` log their own changelog event (FW-575)

### Added

`Pramnos\Llm\Chat\Memory` is not a `\Pramnos\Application\Model` — it writes `assist.chat_memory`
raw through the query builder — so it got nothing from the `$emitChanges` trait, and nothing a
memory went through (kept, corrected, forgotten) ever reached `pramnos.changelog_events`. A
reliability study of the assistant's memory had no way to answer "how many corrections has this
memory had" or "how often does learning forget what it just kept".

`keep()` now raises `ChangelogWriter::event('chat_memory', $id, …)` on the existing
`changelog_events` table — `model` or `learned` for a new memory depending on how it was told,
`corrected` for a correction — and `forget()`/`forgetShared()` raise `forgotten`. No new table: the
framework already has one for this (rule 14). `itemid` is the memory's own id; a new memory's event
carries only its kind and topic, never its content.

## A correction or a forget also logs what it changed or lost — and `amend()` is logged too (FW-576)

### Added

Follow-up to FW-575, from the same reliability study: a `corrected` or `forgotten` event now
carries the memory's previous content (`old`) and, for a correction, its new one (`new`) — not a
new exposure of it, since the same person already sees it through `remember`/`correct`/`forget`;
the log just keeps what they already see. A generic restore primitive for the model-diff half of
the changelog system was considered and set aside at the time — nothing had yet needed to *act* on
a logged old value programmatically, only to show it. A concrete need turned up the same day; see
FW-577, below.

Also fixed in the same pass: `amend()` — the person's own correction of their memory's words or
topic, via `PATCH {chat}/memory/{memory_id}` — raised no event at all before this. It now logs
`corrected` too, with the same `old`/`new` shape.

## A model can reverse one of its own recorded updates, through its own save (FW-577)

### Added

A concrete case for a generic restore, the day FW-576 set it aside: an application's `users`
model already had `$emitChanges` on, so a wrong edit (an operator's mistake, or a disputed change)
was sitting in `pramnos.changelog` with its old value already recorded — with no way to put it back
except reading the row by hand and writing the old value back over SQL or an ad hoc admin action.

`Pramnos\Application\Concerns\EmitsModelChanges::restoreFromChangelog(int $logid, ?int $ifLogid =
null): bool` reads one `pramnos.changelog` row, reverses its fields back onto an already-loaded
record, and saves through the record's own save path — `_save()` for a `Model`, `save()` for
`User`, whichever it actually has — so validation and the usual hooks run like any other update,
and the restore becomes its own fresh `updated` row rather than a write the log never saw.

**Optimistic guard.** Refused when the record changed again after the row being restored — a
restore onto a state nobody looked at is how a legitimate later edit would get silently undone.
The caller names a later state it already knows about as `$ifLogid` to go past it deliberately.
Only an `updated` row of the exact same record applies; a `created` row, one for a different
record, or one outside the table's own retention does nothing.

**Why no entity→class registry.** The first design this was evaluated against — a bare
`restore($entity, $itemid, $logid)` that would instantiate the right model itself from the stored
`entity` string — turned out to need a registry mapping that string back to a PHP class, and
nothing in the framework does that today; building one would have been the larger, riskier half of
this feature for a need nobody had yet. The caller already holds a loaded instance by the time it
decides to restore something, so the primitive works on that instead and needs no registry at all.

**Why not `abstract`.** The obvious shape — an abstract method each host class must implement, like
`changeKey()`/`changeDefaultEntity()`/`changeTable()` already are — would fatal at class load for
any application class using this trait directly without overriding it, the same failure rule 6
describes for a changed signature. The default tries `save()` then `_save()`, which covers both
`Model` and `User` without asking anybody for anything new; only a host with neither has to
override it.
