## A mail the server refused is no longer reported as sent

### Fixed

- `UsersController::sendnotification()` (*Send a message* on a user's page) said *Message sent
  on mail* when the SMTP server refused the mail. `Email::send()` reports a refused send by
  returning `false` and writing a failed row to the mail log; `MailChannel` ignored the
  return value, and the `Notifier` catches every channel's exception anyway, so the
  controller's own `catch` never ran. The screen now reports *Not sent on mail:* with the
  mailer's reason, and which of the other ticked channels did go out. The activity-log entry
  records `sent` accordingly and the channels that `failed`.
- `MailChannel::send()` throws a `RuntimeException` with `Email::getLastError()` when the
  mailer answers `false`, so a refused mail is logged to `notifier.log` like any other channel
  failure instead of passing as delivered.

### Added

- `Notifier::failures()` — the channels that failed during the last `sendNow()`, as
  name => message. A caller that has to report an outcome reads it after the send without
  `throwOnChannelFailure()` abandoning the channels after the failed one.
- `UsersController::notifier()` — protected, the `Notifier` the operator's message is sent
  through, for an application that registers a channel of its own.

### What breaks

- Code that calls `throwOnChannelFailure()` now receives an exception for a refused mail;
  code that calls `MailChannel::send()` directly must catch `RuntimeException`. See the
  Upgrade Guide.

## `OAuth2Middleware` validates the JWT access tokens this server issues

### Fixed

- `OAuth2Middleware::validateAccessToken()` refused every access token this installation's
  OAuth2 server issued, even a second after issue. The tokens are RS256 JWTs whose
  `usertokens` row is stored under `sha256(jti)`; the middleware looked up `sha256` of the
  whole presented string, which matches no row. It now tries the token as itself, then — when
  the JWT's signature verifies against this installation's key — its `jti`. A JWT signed by
  any other key is not trusted for its `jti`. `revokeToken()` had the same lookup, so revoking
  a JWT reported failure and left the token working; it is fixed the same way.
- When `app/keys/public.key` is missing, the verification key is the public half of
  `private.key`, which is what the tokens are signed with.

### Documentation

- *Tokens* guide: a section on validating this server's OAuth2 access tokens.

## Introspection, revocation, logout and token exchange read only a verified `jti`

### Changed

- `/oauth/introspect`, `/oauth/revoke`, logout and the token-exchange grant found a presented
  JWT's row by a `jti` read **without** checking the signature, while `OAuth2Middleware`
  checks it. They now share one rule, `OAuth2ServerFactory::accessTokenId()`: the `jti` of a
  JWT whose RS256 signature verifies against this server's key, or nothing. A JWT signed by any
  other key — including the pair replaced by `oauth:keys --force` — is no longer introspected
  as active, revoked or exchanged. `Oauth::extractJwtId()` keeps its signature and delegates.
- `TokenExchangeGrant` takes an optional `OAuth2ServerFactory` in its constructor; the
  factory passes itself.

### Fixed

- `JWT::decode()` refused a token whose `nbf` or `iat` was a fractional time earlier in the
  current second (`1793872289.83` against `time()` = `1793872289`) as issued in the future —
  which the OAuth2 server's tokens are. `nbf` and `iat` are now compared by their whole second.

### Added

- `OAuth2ServerFactory::accessTokenId(string $token): ?string`.

## `/oauth/authorize` can answer a custom-scheme callback with a page instead of a bare 302

### Added

- `applications.app_return_page` (migration `2026_11_05_000001`, default 0) and a **Return
  to the app** switch on the application form. When it is 1, a callback whose scheme is not
  `http(s)` (a desktop application's, `myapp://oauth/callback`) gets a page after the consent
  screen instead of a `302`: a script opens the callback and a button links to it, sent
  `no-store` and `no-referrer`. A bare redirect to a scheme the machine has not registered left
  the system browser on a blank tab after a sign-in that had worked. Applies to both the code
  and the `access_denied` answer.
- At 0, the default, nothing changes: every callback is a `302`, which is what an in-app
  browser on a phone intercepts as the user's own navigation. A script on a page loaded
  afterwards may need an extra tap there, so the page is a per-client choice.
- `Oauth::appReturnPage(string $url): string`, protected, to word or style the page.

## A user-addon login gets its web-session token and the CSRF tag; dashboard and resync fixes for mvc applications

### Fixed

- An application signing in through a user addon (`Addon\User\User`) got no web-session token:
  `Auth` created it only on the built-in path. With none, `<meta name="csrf">` was never printed,
  so every write `pf-utils.js` sends — saving a dashboard's layout, marking a notification read —
  was refused, and no request was attributed in `usertokens`. The token is now created after
  either path. `Document::csrfHeadMarkup()` also prints the tag for a session that holds an
  account id (`$_SESSION['uid'] > 1`) and no token, which covers sessions signed in before the
  update.
- The dashboard's catalogue `<dialog>` stood open under the board in a theme whose `.card` is
  `display: flex`, which outranks the browser's `dialog:not([open])`. `components.css` hides it
  while closed. The grip's ⠿ falls back to a symbol font where the theme's font has no Braille.

### Added

- `'dashboard' => ['framework_default' => false]`: the framework's cards stay in the catalogue
  and off a new dashboard, without listing their ids; `cards.<id>.default => true` still places
  one.
- `project:resync --css` takes `bootstrap`'s `components.css` when `scaffold_theme` is unset, for
  an mvc application that draws the framework's components (`--all` adds it the first time).

## A dashboard card added live runs its scripts and styles

### Fixed

- A card added from the catalogue or redrawn after its settings was put in with `innerHTML`, so
  its `<script>`s never ran, and its `<script>`s and `<style>`s carried the card request's CSP
  nonce rather than the page's, so the page's policy refused them without any error. A card with a
  map stayed empty, and 0px tall, until a reload. `pf-utils.js` now re-creates each of them in
  order with the page's nonce, waiting for a script with a `src` before the next.

### Added

- The `pf:dashboard:card` event, fired on a card (bubbling, `detail.id`) once it is on the board
  and its scripts have run.

## Dashboard boards, presets and sharing

### Added

- **Boards.** `'dashboard' => ['boards' => ['wcm' => [...]]]` gives a screen a dashboard of its
  own: its `widgets`, `framework`, `framework_default`, `cards` (merged by id over the top
  level's) and `default`, the ids a new board has, in order. `Widget::boards()` puts a card on
  named boards only. `WidgetRegistry::all()`, `available()`, `get()` and `byDefault()`, and
  `Layouts::defaults()` and `clean()`, take an optional board. A board app.php does not list is
  the top level, so nothing changes for an application that has no boards.
- **A board inside any screen.** `Dashboard\Board::render($board, $title)` draws a board in another
  screen. Its controls reach the dashboard controller with `?board=`, which names only a listed
  board. A board's `min_role` limits who may use it, and `Board::render()` reaches the controller
  through the static `DashboardController::boardFor()`.
- **Presets and sharing.** Named layouts per board: the application's, from `presets` in app.php,
  and people's own, saved from the *Presets* dialog into `pramnos.dashboard_presets` (migration
  `2026_11_05_000002`). Each is visible to its owner only, from a role up, to an organisation's
  members, or to everyone. Applying one is a copy, cleaned for the receiver, and the cards that
  were dropped are counted. An administrator can make a preset a role's default for new boards,
  copy their board to another account (audit event `dashboard.board_copied`), and list every
  preset at `Dashboard/presets`. `Dashboard\Presets` is the API. Greek text for all of it is in
  `el.php`.
- **A dashboard of one's own.** People make dashboards for themselves (*Presets and dashboards* →
  *A new dashboard of your own*), empty or from a preset, with the administration dashboard's
  cards. Each appears under Dashboard in the owner's menu, and in the menus of whoever it is shared
  with (the same choices as a preset). A viewer starts from the owner's arrangement and then
  keeps their own. Boards are kept in `pramnos.dashboard_boards` (migration `2026_11_05_000003`)
  and named `my-{id}`. `Dashboard\UserBoards` is the API.
- **`NavRegistry::provide()`** adds menu items that depend on who is looking, and the new
  `NavItem::$ability` names the ability that decides an Admin item when it is not its id.

### Fixed

- A preset's delete and default, and a board's update and delete, reported success by whether the
  query ran, not by whether it changed a row. They now count the rows, so "deleted" is not said
  for somebody else's preset.

## Dashboard cards as tabs

### Added

- A layout item can be a group of cards shown as tabs:
  `{id: 'tabs:…', size, tabs: [{id, settings}], active, title}`. It can also be written in a
  board's `default` and `presets` as `['tabs' => [...ids], 'title' => '']`. Only the active tab is
  drawn, and the others load when first opened through `card?id=…&part=body`. Each person's active
  tab is saved with their layout. Cleaning per viewer drops tabs they may not have, turns a group
  with one card left into that card, and removes an empty group.
- While customising: *Group into tabs with the next card*, and on a group, move the active tab
  left or right or take it out of the group.
- `pf:dashboard:shown` fires on a card's element (bubbling, `detail.id`) when its tab becomes
  visible and after a resize, so a card's script can redraw at its new size.
- `views/dashboard/tabs.html.php` in each theme draws a group. A theme copies it to use its own
  tabs. `Layouts::cards()` and `isGroup()`, and `WidgetRegistry::defaultEntries()`, are the API.
- Grouping by dragging: a card dropped on a group's strip of tabs joins the group, a tab dragged
  along its strip changes place, and a tab dragged out of its group becomes a card again.
- A card in a group is set from the group's gear, with the same form as on its own card, extracted
  into `card_settings.html.php`. The tab is redrawn in place.

## Skills with a method: skill files for Ask

### Added

- `'llm' => ['chat' => ['skills_path' => 'app/skills']]`: each `<slug>.md` there is a skill, with
  front matter `name`, `description` and `tools`, and a Markdown body. When the model turns the
  skill on, `use_skill` returns the body after `Turned on X: …`, so the method enters the context
  only when it is needed. A skill of instructions alone, with no tool, is offered, and one whose
  tools the person lacks is offered for its instructions. Skill files turn skills on unless
  `'skills' => false`. A tool of no skill that a file lists stays offered all the time.
  `ToolRegistry::defineSkill()` and `Chat\Skills` are the API.
- `Support\FrontMatter` parses a Markdown file's front matter. The help pages now use it too, with
  no change in how they are read.

## Skill folders: references on demand, and evals per skill

### Added

- A skill can be `<slug>/SKILL.md` beside `<slug>.md`. Its `references/*.md|*.txt` are listed by
  `use_skill` but not handed over. `read_skill_reference(skill, file)` reads one, is offered only
  while a skill with references is on, reads only listed files inside the folder (links followed
  and checked), and stops at 64 KB.
- `llm:eval --skills` / `--skill=<slug>` asks each skill folder's `evals/*.json` with the setup's
  tools grouped into skills. `use_skill` runs for real, and the tools it adds answer canned
  results. A new score, `skill_used`, records whether the model turned the expected skill on.
  Baselines are kept per skill in `evals/baseline.json`.
- Plain-language `assertions` on a case, graded by the model as a judge (score `assertions`,
  `unmet` listed), and the public Agent Skills eval shape (`{"evals": [{"id", "prompt",
  "expected_output", "assertions"}]}`) read as cases. `Report` gates `skill_used` and `assertions`
  over the cases that score them.

- `llm:eval --repeat=N` asks each case N times and scores the mean (`Report::average()`), because
  a judge's grades vary from run to run. `-v` prints what each case called and its unmet
  assertions. A case that stopped at the limit of rounds is marked so (`out_of_rounds`), and a
  skill's cases are asked with 16 rounds, as a conversation is.

### Fixed

- A person's own dashboard opened after *Make it* at `Dashboard/display?board=…`. It now opens at
  `Dashboard?board=…`, the address its menu item names.

## The presets and dashboards dialog: the application's user types and organisations, a person picker, tabs

### Changed

- *From a user type up* offers the application's own user types (`usertypes` in app.php,
  `UserTypes::labels()`), from the board's floor up, and stores the type's number. A role's name
  saved earlier is still read.
- Sharing with an organisation goes through `Dashboard\OrganizationSource`:
  `'dashboard' => ['organizations' => Class::class]` gives the application's own grouping, with its
  own name for it, and `false` removes the choice. Without either, the framework's organisations are
  offered when there are any.
- *Copy to a user* picks the person by name, username or email from `Dashboard/people?q=…`, which
  offers only active accounts that can open the board and never oneself. The server applies the
  same rule to the id that is posted.
- The dialog is in tabs, a field for one choice shows only for it, and a form coming back reopens
  the dialog on its tab. It is 640 px wide in every theme.

### Fixed

- The framework's organisations were read by a column `id` that the table does not have. The column
  is `organization_id`, and only active organisations are offered.
- A field shown for one choice stayed visible under a theme utility such as Bootstrap's `d-block`,
  which outranks `[hidden]`. `components.css` now hides `[data-pf-show-when][hidden]`.
- An organisation source that threw left the dialog with no organisation choice and nothing in any
  log. Its `choices()`, `label()` and `isMember()` failures are now logged to the `dashboard` log,
  with the class and the line, and a failing `isMember()` answers no instead of failing the page.
- The person picker repeated an email used as name and username. It now shows the name, the
  username in brackets only when it differs from both name and email, always one identifier (the
  email, or the username without one, unless it is the name), and the type, so two people with the
  same name stay distinguishable when their username is their email.
- The dashboard tools' symbols (⧉ ⇱ ⚙) fall back to a symbol font, as the grip does.

## Skills from catalogues: taken, locked, off until read

### Added

- `skill:search`, `skill:add owner/repo/path[@ref]`, `skill:enable [--off]`, `skill:outdated`,
  `skill:update [--ref] [--force]` and `skill:list [--setup]`. They read GitHub at one commit and take
  only `SKILL.md`, `references/*.md|*.txt` and `evals/*.json`. Scripts and everything else are listed
  as left out and never written. `skills.lock.json` records each skill's source, commit, hash and
  licence. A skill that is taken is off until a person turns it on, and off again after each update. A
  skill changed here is not overwritten: upstream's copy goes to `.pf-upstream/`, with a three-way
  report against `.pf-base/`.
- `Chat\SkillCatalog`, `Chat\SkillLock`. `Skills::load()` leaves out a locked skill that is off.
- Tool names a skill lists that nobody declared are logged once, and listed by `skill:list --setup`.

## A subclass of `User` loaded after the base class keeps its own columns; `deviceinfo` without escapes

### Fixed

- **`User::load()` from its cache gave a subclass the base class's object.** The static cache
  held a snapshot of whichever object loaded the account. A column the base class does not
  declare goes through `__set()` into `otherinfo`, so the snapshot `new \Pramnos\User\User($id)`
  took — which sign-in has run since the web-session token moved into `Auth` — had none of an
  application's own columns at the top level. The application's `User` subclass, loading the
  same account later in the request, restored that snapshot, kept its declared columns at their
  defaults, and its next `save()` wrote the defaults back; the diff saw nothing, because its
  baseline came from the same snapshot. An application lost paid subscriptions that way. The
  cache now keeps the `users` and `userdetails` rows, and a hit is built by the same code as a
  load from the database.
- **`deviceinfo` is written unescaped.** `json_encode()` escaped a translated label
  (`Chrome σε Windows`) to `\u03c3…`, and a `bytea` `deviceinfo` column refused the backslashes,
  so every sign-in failed to record its token. It is written with
  `JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES`.

### Upgrade

Code that reads entries of `User::$_usercache` reads `$entry['row'][$column]` — see the
[Upgrade Guide](../../Pramnos_Upgrade_Guide.md). A workaround that dropped cache entries lacking
a subclass's column can be deleted.

## `User::save()` writes only what changed since the load

### Changed

- **An existing user's save updates only the columns that changed since the object loaded.**
  The `UPDATE` wrote every column, so any column the object held wrongly was written over the
  stored value without the code touching it — which is how the cache fault above turned into lost
  data. The baseline is what the object held when it loaded, not the database row: diffed
  against the row, a column a load left at its default would count as a change and be written
  anyway. A save that changed nothing in the row runs no `UPDATE`, still writes the details, and
  still refuses a user deleted since it loaded. A subclass with a `load()` of its own that does not
  call the base class's keeps writing every column.
- **What counts as a change is `Model`'s rule.** Values are compared as text, not as numbers, so a
  leading zero added to a mobile is written; booleans, nulls and floats are covered by a test of
  every combination the drivers return and callers set.
- **A column a method writes to the row itself becomes the save's baseline.** `activate()`,
  `deactivate()` and the password rehash on login update the row directly; a later `save()`
  setting the column back to its loaded value saw no change — `deactivate()`, then `active = 1`
  and `save()`, left the user inactive. They now record what they wrote.

### Upgrade

Code that saved a stale `User` to overwrite a column changed in the database since now leaves
that column alone; assign it before saving. See the
[Upgrade Guide](../../Pramnos_Upgrade_Guide.md).

## `DashboardController::cardFor()` keeps its two-parameter signature

### Fixed

- **`cardFor()` had gained a third parameter, `bool $draw`, with the tabs** — and PHP refuses to
  load a subclass that overrides a method with fewer parameters than its parent, so an
  application overriding `cardFor($widget, $item)` failed with *Declaration … must be compatible*
  on its dashboard. The signature is back to two parameters; whether a tab is drawn travels in the
  item, `$item['draw']`. An override that added `bool $draw = true` and passes it on keeps loading
  and is honoured.

## Skills of a role, and each person's own

### Added

- **Skills kept in the database** (`'llm' => ['chat' => ['stored_skills' => true]]`, off by
  default). An administrator can write one for a role, offered to everybody from that role up as
  `role:<name>`. A person can write their own, offered in their own conversations as
  `mine:<name>`. Both have the same shape as a skill file. Ask is given them beside the
  application's files. A stored skill opens only tools the answer already has, and its method is
  marked as a role's or the person's own.
- **My skills** at `chat/skills` and `Ai/skills` (`Pramnos\Llm\Chat\Web\KeepsSkills`), in all three
  themes and in Greek. It is used to write, edit, turn on and off, delete and offer skills to a role,
  and administrators use it to write role skills and approve or turn down offers. These decisions
  are recorded in the audit log.
- **`propose_skill`**: Ask keeps a way of working from a conversation as a draft of the person's
  own, which does nothing until they turn it on.
- An answer others read too, and a scheduled run, take only role skills, for the role of the least
  privileged reader.
- Migration `2026_11_05_000004_create_chat_skills_table` (`pramnos.chat_skills`).
- The page's headings use their own phrases, `Your own skills` and `No role skills yet.`, not the
  general `Yours` and `None yet.` that other pages share. An application can translate them without
  changing those pages, in a language where the word agrees with what it refers to.
- In Greek they are called *skills* (`Τα skills μου`), not *ειδικότητες*. That word is the
  usual one for a professional's specialty, which an application may already use for something
  else.

## A new-sign-in alert names the OAuth client signed in to

### Fixed

- **A sign-in through an OAuth client was described only by the browser it embeds.** A desktop
  client (Electron, authorization code with PKCE) showed up in the "new sign-in" mail and push as
  *Chrome on Linux*. When `oauth/authorize` sends somebody to sign in, it now remembers the
  client's registered name (`NewSignInAlert::rememberClient()`, for half an hour, used once).
  The alert then reads *Acme Desktop (Chrome on Linux)*.
  `NewSignInNotification` takes the name as an optional fourth argument, and its stored template
  gets `{device}`. Whether a device is new is still decided by the browser-and-platform
  fingerprint.
