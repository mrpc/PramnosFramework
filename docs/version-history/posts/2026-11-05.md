## A mail the server refused is no longer reported as sent

### Fixed

- `UsersController::sendnotification()` (*Send a message* on a user's page) said *Message sent
  on mail* when the SMTP server refused the mail. `Email::send()` reports a refused send by
  returning `false` and writing a failed row to the mail log; `MailChannel` ignored the
  return value, and the `Notifier` catches every channel's exception anyway, so the
  controller's own `catch` never ran. The screen now reports *Not sent on mail:* with the
  mailer's reason, and which of the other ticked channels did go out. The activity-log entry
  records `sent` accordingly and the channels that `failed`.
- `MailChannel::send()` throws a `RuntimeException` with `Email::getLastError()` when the
  mailer answers `false`, so a refused mail is logged to `notifier.log` like any other channel
  failure instead of passing as delivered.

### Added

- `Notifier::failures()` — the channels that failed during the last `sendNow()`, as
  name => message. A caller that has to report an outcome reads it after the send without
  `throwOnChannelFailure()` abandoning the channels after the failed one.
- `UsersController::notifier()` — protected, the `Notifier` the operator's message is sent
  through, for an application that registers a channel of its own.

### What breaks

- Code that calls `throwOnChannelFailure()` now receives an exception for a refused mail;
  code that calls `MailChannel::send()` directly must catch `RuntimeException`. See the
  Upgrade Guide.

## `OAuth2Middleware` validates the JWT access tokens this server issues

### Fixed

- `OAuth2Middleware::validateAccessToken()` refused every access token this installation's
  OAuth2 server issued, even a second after issue. The tokens are RS256 JWTs whose
  `usertokens` row is stored under `sha256(jti)`; the middleware looked up `sha256` of the
  whole presented string, which matches no row. It now tries the token as itself, then — when
  the JWT's signature verifies against this installation's key — its `jti`. A JWT signed by
  any other key is not trusted for its `jti`. `revokeToken()` had the same lookup, so revoking
  a JWT reported failure and left the token working; it is fixed the same way.
- When `app/keys/public.key` is missing, the verification key is the public half of
  `private.key`, which is what the tokens are signed with.

### Documentation

- *Tokens* guide: a section on validating this server's OAuth2 access tokens.

## Introspection, revocation, logout and token exchange read only a verified `jti`

### Changed

- `/oauth/introspect`, `/oauth/revoke`, logout and the token-exchange grant found a presented
  JWT's row by a `jti` read **without** checking the signature, while `OAuth2Middleware`
  checks it. They now share one rule, `OAuth2ServerFactory::accessTokenId()`: the `jti` of a
  JWT whose RS256 signature verifies against this server's key, or nothing. A JWT signed by any
  other key — including the pair replaced by `oauth:keys --force` — is no longer introspected
  as active, revoked or exchanged. `Oauth::extractJwtId()` keeps its signature and delegates.
- `TokenExchangeGrant` takes an optional `OAuth2ServerFactory` in its constructor; the
  factory passes itself.

### Fixed

- `JWT::decode()` refused a token whose `nbf` or `iat` was a fractional time earlier in the
  current second (`1793872289.83` against `time()` = `1793872289`) as issued in the future —
  which the OAuth2 server's tokens are. `nbf` and `iat` are now compared by their whole second.

### Added

- `OAuth2ServerFactory::accessTokenId(string $token): ?string`.

## `/oauth/authorize` can answer a custom-scheme callback with a page instead of a bare 302

### Added

- `applications.app_return_page` (migration `2026_11_05_000001`, default 0) and a **Return
  to the app** switch on the application form. When it is 1, a callback whose scheme is not
  `http(s)` (a desktop application's, `myapp://oauth/callback`) gets a page after the consent
  screen instead of a `302`: a script opens the callback and a button links to it, sent
  `no-store` and `no-referrer`. A bare redirect to a scheme the machine has not registered left
  the system browser on a blank tab after a sign-in that had worked. Applies to both the code
  and the `access_denied` answer.
- At 0, the default, nothing changes: every callback is a `302`, which is what an in-app
  browser on a phone intercepts as the user's own navigation. A script on a page loaded
  afterwards may need an extra tap there, so the page is a per-client choice.
- `Oauth::appReturnPage(string $url): string`, protected, to word or style the page.

## A user-addon login gets its web-session token and the CSRF tag; dashboard and resync fixes for mvc applications

### Fixed

- An application signing in through a user addon (`Addon\User\User`) got no web-session token:
  `Auth` created it only on the built-in path. With none, `<meta name="csrf">` was never printed,
  so every write `pf-utils.js` sends — saving a dashboard's layout, marking a notification read —
  was refused, and no request was attributed in `usertokens`. The token is now created after
  either path. `Document::csrfHeadMarkup()` also prints the tag for a session that holds an
  account id (`$_SESSION['uid'] > 1`) and no token, which covers sessions signed in before the
  update.
- The dashboard's catalogue `<dialog>` stood open under the board in a theme whose `.card` is
  `display: flex`, which outranks the browser's `dialog:not([open])`. `components.css` hides it
  while closed. The grip's ⠿ falls back to a symbol font where the theme's font has no Braille.

### Added

- `'dashboard' => ['framework_default' => false]`: the framework's cards stay in the catalogue
  and off a new dashboard, without listing their ids; `cards.<id>.default => true` still places
  one.
- `project:resync --css` takes `bootstrap`'s `components.css` when `scaffold_theme` is unset, for
  an mvc application that draws the framework's components (`--all` adds it the first time).

## The dashboard in Greek

### Fixed

- 46 phrases of the dashboard had no line in `resources/language/el.php` and showed in English
  on a Greek site: the customise bar, the catalogue and the card controls, and every framework
  card's title and description.
- `FrameworkGreekCatalogueTest` now sweeps every dashboard view and `src/Pramnos/Dashboard/`,
  and checks each framework card's `title()` and `description()` — returned as plain strings and
  translated where they are drawn, which the `t()` sweep could not see.

## A dashboard card added live runs its scripts and styles

### Fixed

- A card added from the catalogue or redrawn after its settings was put in with `innerHTML`, so
  its `<script>`s never ran, and its `<script>`s and `<style>`s carried the card request's CSP
  nonce rather than the page's, so the page's policy refused them without any error. A card with a
  map stayed empty, and 0px tall, until a reload. `pf-utils.js` now re-creates each of them in
  order with the page's nonce, waiting for a script with a `src` before the next.

### Added

- The `pf:dashboard:card` event, fired on a card (bubbling, `detail.id`) once it is on the board
  and its scripts have run.

## Dashboard boards, presets and sharing

### Added

- **Boards.** `'dashboard' => ['boards' => ['wcm' => [...]]]` gives a screen a dashboard of its
  own: its `widgets`, `framework`, `framework_default`, `cards` (merged by id over the top
  level's) and `default`, the ids a new board has, in order. `Widget::boards()` puts a card on
  named boards only. `WidgetRegistry::all()`, `available()`, `get()` and `byDefault()`, and
  `Layouts::defaults()` and `clean()`, take an optional board. A board app.php does not list is
  the top level, so nothing changes for an application that has no boards.
- **A board inside any screen.** `Dashboard\Board::render($board, $title)` draws a board in another
  screen. Its controls reach the dashboard controller with `?board=`, which names only a listed
  board. A board's `min_role` limits who may use it, and `DashboardController::renderBoard()` is
  what `Board::render()` calls.
- **Presets and sharing.** Named layouts per board: the application's, from `presets` in app.php,
  and people's own, saved from the *Presets* dialog into `pramnos.dashboard_presets` (migration
  `2026_11_05_000002`). Each is visible to its owner only, from a role up, to an organisation's
  members, or to everyone. Applying one is a copy, cleaned for the receiver, and the cards that
  were dropped are counted. An administrator can make a preset a role's default for new boards,
  copy their board to another account (audit event `dashboard.board_copied`), and list every
  preset at `Dashboard/presets`. `Dashboard\Presets` is the API. Greek text for all of it is in
  `el.php`.
