# 5 November 2026

Three entries today:

- A mail the server refused is no longer reported as sent
- `OAuth2Middleware` validates the JWT access tokens this server issues
- Introspection, revocation, logout and token exchange read only a verified `jti`

<!-- more -->

## A mail the server refused is no longer reported as sent

### Fixed

- `UsersController::sendnotification()` (*Send a message* on a user's page) said *Message sent
  on mail* when the SMTP server refused the mail. `Email::send()` reports a refused send by
  returning `false` and writing a failed row to the mail log; `MailChannel` ignored the
  return value, and the `Notifier` catches every channel's exception anyway, so the
  controller's own `catch` never ran. The screen now reports *Not sent on mail:* with the
  mailer's reason, and which of the other ticked channels did go out. The activity-log entry
  records `sent` accordingly and the channels that `failed`.
- `MailChannel::send()` throws a `RuntimeException` with `Email::getLastError()` when the
  mailer answers `false`, so a refused mail is logged to `notifier.log` like any other channel
  failure instead of passing as delivered.

### Added

- `Notifier::failures()` — the channels that failed during the last `sendNow()`, as
  name => message. A caller that has to report an outcome reads it after the send without
  `throwOnChannelFailure()` abandoning the channels after the failed one.
- `UsersController::notifier()` — protected, the `Notifier` the operator's message is sent
  through, for an application that registers a channel of its own.

### What breaks

- Code that calls `throwOnChannelFailure()` now receives an exception for a refused mail;
  code that calls `MailChannel::send()` directly must catch `RuntimeException`. See the
  Upgrade Guide.

## `OAuth2Middleware` validates the JWT access tokens this server issues

### Fixed

- `OAuth2Middleware::validateAccessToken()` refused every access token this installation's
  OAuth2 server issued, even a second after issue. The tokens are RS256 JWTs whose
  `usertokens` row is stored under `sha256(jti)`; the middleware looked up `sha256` of the
  whole presented string, which matches no row. It now tries the token as itself, then — when
  the JWT's signature verifies against this installation's key — its `jti`. A JWT signed by
  any other key is not trusted for its `jti`. `revokeToken()` had the same lookup, so revoking
  a JWT reported failure and left the token working; it is fixed the same way.
- When `app/keys/public.key` is missing, the verification key is the public half of
  `private.key`, which is what the tokens are signed with.

### Documentation

- *Tokens* guide: a section on validating this server's OAuth2 access tokens.

## Introspection, revocation, logout and token exchange read only a verified `jti`

### Changed

- `/oauth/introspect`, `/oauth/revoke`, logout and the token-exchange grant found a presented
  JWT's row by a `jti` read **without** checking the signature, while `OAuth2Middleware`
  checks it. They now share one rule, `OAuth2ServerFactory::accessTokenId()`: the `jti` of a
  JWT whose RS256 signature verifies against this server's key, or nothing. A JWT signed by any
  other key — including the pair replaced by `oauth:keys --force` — is no longer introspected
  as active, revoked or exchanged. `Oauth::extractJwtId()` keeps its signature and delegates.
- `TokenExchangeGrant` takes an optional `OAuth2ServerFactory` in its constructor; the
  factory passes itself.

### Fixed

- `JWT::decode()` refused a token whose `nbf` or `iat` was a fractional time earlier in the
  current second (`1793872289.83` against `time()` = `1793872289`) as issued in the future —
  which the OAuth2 server's tokens are. `nbf` and `iat` are now compared by their whole second.

### Added

- `OAuth2ServerFactory::accessTokenId(string $token): ?string`.
