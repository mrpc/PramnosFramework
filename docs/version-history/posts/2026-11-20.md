## `Markdown::inline()` now recognizes Slack mrkdwn's own link syntax (FW-565)

### Fixed

A conversation imported from a former Slack chat carries its links in Slack's own mrkdwn
syntax, `<https://…|label>` or a bare `<https://…>`, and a bare `mailto:…` with no angle
brackets at all — none of which `inline()` recognized, so they fell straight through to
`htmlspecialchars()` and showed as raw text (`<mailto:foo@example.com|foo@example.com>`)
instead of a clickable link, reported from an application importing old chat history.
`inline()` now also matches `<(https?://|mailto:)…(\|label)?>` and a bare `mailto:…`,
turning both into the same link `[text](url)` and a bare `https://…` already produce.

### Documentation

`docs/Pramnos_Conversations_Guide.md`'s "Text is markdown-lite" paragraph and the
`Markdown` class docblock now describe the Slack mrkdwn syntax and the bare `mailto:`
autolink.

## A message can link to a conversation, `<#id>`, as Slack's `#channel` (FW-566)

### Added

`<@id>` already mentions a person by name, resolved at render time so the name shown
stays current even if the person renames themselves; there was no equivalent for linking
to another conversation by name. `Markdown::render()`/`inline()` take a second, optional
resolver, `?callable(int): ?string $conversation`, for a new `<#id>` token — shown as a
plain `<a class="pf-conv-channel-ref" href="#/c/id">#slug</a>`, not a hover-card `<span>`
like a person mention, since a conversation has no card of its own to show on hover and
the app already navigates on `location.hash` alone. `Messages::present()` wires it to
`Conversations::names()`, the same resolver every other conversation name already goes
through, batched once per call the same way `mentionedIn()`'s person mentions already are.

### Documentation

`docs/Pramnos_Conversations_Guide.md`'s "Mentions" section now describes `<#id>`, and the
`Markdown` class docblock's mark table gets a row for it.

## A bare `#slug` links to its conversation too, not only `<#id>` (FW-567)

### Added

FW-566's `<#id>` only ever covers a message composed after the fact — a composer turns a
typed `#slug` into `<#id>` before sending, but nothing rewrites a body already sitting in
the database, so an older message that just says `#financial` in plain text stayed plain
text forever, even with FW-566 shipped. `Markdown::render()`/`inline()` take a third,
optional resolver, `?callable(string): ?array{id: int, slug: string} $channelBySlug`,
called once per `#word` actually found in the text (no preload of every channel) — a
match becomes the same `<a class="pf-conv-channel-ref" href="#/c/id">#slug</a>` `<#id>`
already produces; a `#word` that resolves to nothing stays plain text, exactly as before.
`Messages::present()` wires it to the already-existing `Conversations::bySlug()`.

The existing `#type:id` reference mark (`Messages::refs()`) is unaffected: its colon stops
a slug match before it would ever reach it, so `#user:48211` still becomes that reference,
never a channel-link attempt on the word `user`. The client's own compose-time `#slug` →
`<#id>` rewrite stays too, deliberately — a message composed today keeps linking correctly
even if the channel is later renamed, since `<#id>` carries the id, not the name; the new
bare-`#slug` matching only ever catches what still says the channel's current name.

### Documentation

`docs/Pramnos_Conversations_Guide.md`'s new conversation-link paragraph now covers the
bare `#slug` case and why both it and `<#id>` stay.

## A private conversation's link shows 🔒, not `#`, as Slack shows one (FW-568)

### Added

Both FW-566's `<#id>` and FW-567's bare `#slug` carried a private conversation's `#slug`
through unchanged, the same as a public channel's — no visual difference once rendered,
though the rest of the application already marks a private one with 🔒 in three other
places. `Conversations::names()` — already the one place that turns a conversation into
`#slug`, used by both `<#id>`'s resolver and everywhere else a conversation's name is
shown — now writes `🔒 slug` instead of `#slug` when the conversation's `kind` is
`private`, so every caller gets this for free. `<#id>`'s own fallback for an unknown id
(`#id`, no name to show at all) is unchanged, since there is nothing to carry a lock for.
The bare-`#slug` path (`Markdown::inline()`) checks the resolved conversation's own `kind`
the same way, since its resolver (`Conversations::bySlug()`) already returns the whole row.

### Documentation

`docs/Pramnos_Conversations_Guide.md`'s conversation-link paragraph and `Conversations::names()`'s
own docblock now mention the 🔒 prefix.

## A conversation link shows its own picture, where it has one (FW-569)

### Added

A channel that already has its own picture elsewhere in the application (set through
`Images::set()`, or an application's own default-per-slug image) showed only `#`/`🔒` and its
slug on a message's conversation link (FW-566/567/568) — reported after an owner asked why a
channel's own image, already visible in its own sidebar entry, never showed up there. Both
`<#id>` and a bare `#slug` now show that picture, as an `<img class="pf-conv-channel-icon">`,
in place of the `#`/`🔒` character rather than beside it — a conversation with no picture of
its own keeps exactly what FW-568 already showed.

For the bare-`#slug` path, nothing needed resolving further: `Conversations::bySlug()`
already returns the full row, `image` included ({@see Conversations::row()}), and
`Markdown::inline()` simply hadn't read it. The `<#id>` path had no such row to read from —
its resolver was `Conversations::names()`, which only ever builds a display string, never a
row — so a new sibling, `Conversations::many(array $ids): array<int, array<string, mixed>>`,
answers several ids with the same shape `get()` answers one, and `Messages::present()` now
wires `<#id>`'s resolver to both `names()` (for its already-correct display name — a dm or a
group has no slug and no picture, so it still needs this) and `many()` (for `slug`/`kind`/
`image` where the conversation has them). `Conversations::names()` itself is unchanged, so
every other place that only ever wanted a display string is unaffected.

### Documentation

`docs/Pramnos_Conversations_Guide.md`'s conversation-link paragraph now describes the
picture and when it does, and does not, show.
