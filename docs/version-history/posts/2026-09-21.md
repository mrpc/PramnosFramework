## A generated controller could serve another tenant's row

A model that scopes itself to a tenant does it by overriding `load()`: call
`parent::_load()`, look at the row, and refuse it when it belongs to somebody else. The
refusal is written as *return a different object* — and `_load()` has already written every
column onto `$this` by the time the override gets to look.

So this, which is what `create:crud` generated:

```php
$model = new Thing($this);
$model->load((int) $id);           // return value discarded
if ($model->thing_id == 0) {       // populated, so this passes
    return ['status' => 404];
}
$data = $model->getData();         // somebody else's row
```

One project had it in nine call sites, two of them MCP tools an outside assistant can
reach. **The model's own isolation test passed throughout**, because a test naturally
writes `$found = (new Thing())->load($id)` and uses the return value, which is correct. The
defect lived in the gap between the contract the model documents and the shape the
generator emits — and the generator's shape is the one every project has, in every
controller, by default.

### Fixed

- Every generated `load()` is an expression: `$model = (new Thing($this))->load($id);`.
  Six call sites across `api-controller.stub` and `crud-controller.stub`, and **two more
  the guard found in `crud-model-test.stub`** — the generated test asserted on
  `$gone->{{ primaryKey }}` after discarding the return value, so on a scoped model it was
  asserting about the wrong object too.
- `Model::forget()`, the other half: it restores every column the load wrote to what a
  fresh instance has, empties `_initialData` and marks the model new, so a later `save()`
  would insert rather than update the row that was refused. With both, the refusal holds
  whichever shape the caller was written in.

`forget()` clears exactly the columns `_initialData` names — not a list the model declares,
because a hand-written list is right until somebody adds a column and then leaks exactly
that one, and not every public property, because a model may carry state that is not a
column. A property declared with a default goes back to it; a typed one with no default is
unset, since assigning null to `public int $organization_id` is a TypeError.

### Added

- `GeneratedCrudSafetyTest::testEveryGeneratedLoadUsesTheReturnValue`, which is what found
  the two extra sites, and `ModelForgetTest` — seven tests including the three property
  declarations that each take a different branch.


## GDPR erasure had no extension point — and could not run at all without `authserver`

The export half of Article 17 has always been extensible: `buildExportData()` fires
`account.data_export` and merges what listeners return. The deletion half was a hard-coded
list of six framework tables plus `users`, so an account deleted under Article 17 left its
organisation, its content and its connected accounts behind — **and orphaned them**, every
`created_by` pointing at a user id that no longer exists.

### Added

- `account.data_erase`, fired with the user id **before** the framework's own deletes. An
  application's rows almost always carry a foreign key to `users`; fired afterwards, the
  framework's own `DELETE FROM users` would already have failed on the children, and what
  is left is an account half erased — worse than one that was never started.
- A listener returning `false` stops the erase. `Event::fire()` short-circuits at the first
  one, so the listeners after it do not run either — two listeners where one has already
  deleted its rows is exactly the half-erase the ordering exists to avoid.

Two things the framework deliberately does not decide, and the guide says so: in a
multi-tenant application the data belongs to the *organisation* rather than to the person,
and **nothing cascades into a table with no foreign key** — which is most hypertables, and
usually the largest thing left behind.

### Fixed

- **A table this installation does not have is skipped rather than fatal.** Five of the six
  are `authserver.*`, and `authserver` is a feature: an installation that never enabled it
  has never had them, so the delete raised, `deleteaccount()` caught it, and every user got
  *"An error occurred while deleting your account. Please try again."* — an erasure that
  could not be performed at all, reported as something transient. The skipped tables are
  logged, because "this installation has no such table" and "the erase missed something"
  look identical from outside.

  Found by the new test, in a full run where the table happened to be absent; running the
  file alone did not reach it. The test builds the table and drops it now, so the branch is
  exercised deliberately rather than by luck.


## The generated list endpoint disagreed with the read of the same row

`create:crud` emitted `getApiList(..., useGetData: false)`, **overriding its own model's
default** — `getApiList()` declares `$useGetData = true`.

With `false` the list returns raw database rows while every other action on the resource
returns `getData()`. Any column the model transforms — a `timestamptz` turned into Unix
seconds, a `tinyint` into a boolean, a cast, a computed field — then has two shapes
depending on which endpoint was asked, and the front end formats one of them with
`new Date(value * 1000)` and draws **1 January 1970**. It reads as a rendering bug for about
a week.

It is found once per resource, by whoever happens to open that screen: one project fixed it
in one model in September and hit the same thing in another four days later, with a comment
in the first file explaining the second.

### Fixed

- `true`, with the reasoning at the call site and the opt-out named: if a listing is
  measured and hot, pass `false` deliberately. Correctness is the default.
- A guard asserts both the emitted argument and that the model's own default agrees, so a
  controller cannot go back to compensating for it.


## The scaffolded SPA client could not send a file

`lib/api.js` set `Content-Type: application/json` whenever there was a body and
`JSON.stringify`d it. `JSON.stringify(new FormData())` is the two characters `{}`, so an
upload arrived with no file and the server answered "no file arrived" — which is then
looked for on the server, where nothing is wrong.

The cost is larger than an upload. Without this, the way to send a file is a bare `fetch`
beside the client, which then misses the `apiKey` header, the access token,
`credentials: 'same-origin'` and the debug recording — the four things the client exists
for.

### Fixed

- A `FormData` body is passed through unencoded and **carries no declared content type**:
  multipart needs a boundary the browser generates, and one set by hand cannot have it, so
  declaring it makes the body unparseable even once it is sent intact.
- The debug panel records `FormData{caption=…, file=(file "shot.png", 2 bytes)}` instead of
  `[object FormData]`. The contents are deliberately not read — a second copy of an upload
  in memory, to display something nobody can read. What is worth seeing is whether the
  field is there and whether the file has a size, which is the whole of "did it attach".

Three tests in `tests/js/spa-api-client.test.js`, including the JSON control — without it,
a client that never encoded anything would pass the other two.


## `sURL` is the script's base, so the framework now has a site root

`getUrl()` ends in `dirname($_SERVER['SCRIPT_NAME'])`, which is the site root right up until
a project grows a second front controller:

```
www/index.php      →  sURL = https://example.com/
www/api/index.php  →  sURL = https://example.com/api/     ← same site, same request
```

So an asset built during an API request as `sURL . 'uploads/x.jpg'` is
`https://example.com/api/uploads/x.jpg` — a 404. **The expensive part is that it is
absolute and well-formed**, so every "is this a fetchable address" guard passes it: one was
handed to an external service, which fetched it, got a 404, and answered with a container
error that never mentioned the URL. The visible half of the bug was a broken thumbnail; the
half that cost the afternoon was silent.

And `getUrl()` cannot answer at all from the command line — cron has no `SERVER_NAME` — so
a scheduled task putting a public URL in an email, a webhook payload or a feed builds
`http:///uploads/x.jpg`.

### Added

- `Pramnos\Http\SiteUrl`. `SiteUrl::to('uploads/x.jpg')` resolves `APP_URL`, then
  `'site_url'` in `app/config/app.php`, then the request — and from the request it derives
  the **document root** rather than the script's directory, by removing the part of
  `SCRIPT_FILENAME` that sits below `DOCUMENT_ROOT` from `SCRIPT_NAME`. So `www/api/index.php`
  under `www/` answers `/`, and a site mounted at `/shop` keeps its `/shop`.
- With nothing configured and no request it answers `''`, and `to()` returns the path
  unchanged. Empty rather than a guess: a relative path is visibly incomplete to whatever
  receives it, where a wrong absolute URL is accepted by everything and fetched by
  something.
- A `site_url` health check, registered by default. It reports **degraded** while the value
  is only inferred, because a web request almost always infers a usable one — so "it works
  on the site" says nothing about whether the scheduler can build a URL. It reports the
  resolved address either way, since the common mistake is not leaving it unset but setting
  it to a staging host, or to `http` behind a TLS-terminating proxy.
- `init` writes `APP_URL` into `.env` and `.env.example`, **blank**. A development URL
  written there is copied into production by the first person who copies the file, and a
  wrong absolute URL is the failure the whole key exists to prevent.

### Documentation

- `getUrl()`'s own docblock now says what it returns and what it is not, with the example
  above — which was the first of the two things the report asked for.
