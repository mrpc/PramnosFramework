## Claude.ai and ChatGPT can connect to the MCP endpoint

The tools, the scopes, PKCE and the consent screen all existed, and no assistant outside the
machine could reach any of them. glideday measured the chain against production and found it
broken in five places, each of which stopped a remote connector before the next one mattered.

### Fixed

- **The endpoint asked for an API key first.** `init` scaffolds `POST /mcp` into the API routes,
  and `ApiAuthMiddleware` answered `403 APIKeyMissing` before the controller ran. A connector
  cannot send an `apiKey` header, so it never reached the `401` that starts OAuth discovery.
  Listing the path in `public_api_paths` removed the key check **and** bearer validation, and
  the controller then found nobody for every call.

    Two changes. On a declared-public path, a bearer token that verifies now identifies the
    caller, and one that does not leaves the call anonymous rather than refused — the endpoint
    is open, so the anonymous answer is its decision. And `Api` puts `/<version>/mcp` on the
    public list itself, so nothing has to be declared.

- **`WWW-Authenticate` pointed under the API.** It was built from `sURL`, which inside the API is
  `https://host/api/`, so it named `/api/.well-known/oauth-protected-resource` — a 403.
- **The resource metadata named the site, not the endpoint.** `"resource": "https://host"`, and the
  path-suffixed form RFC 9728 §3.1 defines was a 404. MCP clients check that `resource` is the URL
  they were given. The `401` now names
  `https://host/.well-known/oauth-protected-resource/api/1.0/mcp`, built from the site's origin,
  and `Discovery` answers that address with the endpoint as its `resource`. A suffix that is not a
  plain path answers 404 rather than being echoed into a public document.
- **Discovery omitted what a public client looks for.** `oauth-authorization-server` lacked
  `code_challenge_methods_supported`, although S256 was implemented, and had no `none` among the
  auth methods. Both are there now.
- **`registration_endpoint` was the sign-up page.** A JSON POST to it answered `200` with HTML.

### Added

- **Dynamic client registration, RFC 7591** — `POST /oauth/register`, opt-in with
  `'oauth_dynamic_registration' => true` in `app.php`. `init` writes that line for an
  `authserver` project, and the discovery documents publish the endpoint only when it is on.

    It admits **public clients only**: `token_endpoint_auth_method` must be `none` (the RFC's
    default, `client_secret_basic`, is refused), grants are the code grant and refresh, and
    callbacks are `https` or loopback `http`. A confidential client is refused because it could
    use `client_credentials`, which needs no person — open registration would have been open
    issuance of machine tokens. Twenty registrations an hour per address.

- **The scaffolded `.htaccess`** routes `/.well-known/oauth-protected-resource/<path>` to
  `Discovery` with the suffix.

### What breaks

Three rows in the Upgrade Guide. An open API endpoint called with a token now sees that token's
user instead of the website session; an unrelated `/mcp` route in an application's API is now
reachable without a key; and a project scaffolded before today needs the registration switch and
one rewrite rule before a remote client can connect — both are spelled out there.

### Tests

A public client — no secret, PKCE, `is_confidential = 0` — completes the code exchange against the
real League server, which is the claim `none` in the discovery document makes. Registration writes
its row on MySQL and PostgreSQL/TimescaleDB, and both `validateCredentials()` and the League
client repository read the row as public. Every refusal is a unit test.

### Documentation

- **MCP Guide** — the connection chain step by step, what an older project has to add, and the
  subdirectory case.
- **AuthServer Integration Guide** — dynamic client registration: the request, what is admitted
  and why, the error shapes; the suffixed resource document; the complete rewrite block.
- **API Guide** — what a bearer token does on a `public_api_paths` route.
- **Upgrade Guide** — the three rows above.

## The authorization endpoint's codes could not be redeemed, and tokens name the resource they are for

### Fixed

- **No code from `/oauth/authorize` could be exchanged, ever.** The controller wrote a 64-character
  hex code into `usertokens` itself; `/oauth/token` hands every code to League's `AuthCodeGrant`,
  which decrypts it, and refused each one with `Cannot decrypt the authorization code` — after
  the person had approved the consent screen. It had been so since the controller was added.
  Every test of the flow drove League's own authorize step and never the controller's, so both
  halves were tested and the seam between them was not.

    The controller still validates the request itself — client, redirect URI, scopes, PKCE
    format — and then has League issue the code, so what it decides about who gets one is
    unchanged. This is what the previous entry's MCP connection would have hit at its last step,
    and what any relying party of an authorization server built on the framework hits today.

### Added

- **Resource indicators, RFC 8707.** `resource` on a token request adds that URI to the access
  token's `aud`, beside the client id; a resource that is not on this site's origin is
  `invalid_target`. The MCP endpoint then refuses a token bound only to another resource, as
  the MCP authorization spec requires. A token with no URL in `aud` — every token requested
  without `resource`, and every token issued before today — is accepted, so no configured
  connection breaks.

### Tests

The regression test issues a code through the controller and redeems it through League with a
PKCE verifier and a `resource`, then reads the audience off the signed token. The audience check
is covered for a token bound to the endpoint, to another resource, to another host and to none.

### Documentation

- **AuthServer Integration Guide** — binding a token to one resource.
- **MCP Guide** — which tokens the endpoint takes.
- **Upgrade Guide** — two rows: codes are now League's, and `resource` is read.

## A client that cannot keep a secret needs a registered redirect URI

### Fixed

- **`/oauth/authorize` accepted any `redirect_uri` for a public client with nothing
  registered.** For a confidential client that is harmless — a code at the wrong address is
  useless without the secret — and registration stays optional for it. For a public client,
  or one with no secret stored, the registration is the only thing tying the code to the
  client: a link carrying the client's public id and somebody else's `redirect_uri`, opened by
  a signed-in user who had approved the app before, delivered a code with no consent screen,
  and its holder exchanged it with no secret. PKCE does not help, because the link's author
  chooses the challenge. RFC 6749 §3.1.2.2 makes registration a MUST for these clients, and
  the endpoint now refuses without one.

    "Cannot keep a secret" means `is_confidential = 0`, or an empty `apisecret` — which the
    token endpoint accepts with no secret at all, whatever the Client Type says. It is one
    function, `Auth\Application::needsARegisteredCallback()`, used by the endpoint and by the
    screens.

### Added

- **A warning on the application's page and edit form**, in all three bundled themes, for a
  client in that state, with a link to the guide. The **Client Type** and **Redirect URI**
  fields carry a hover explanation of the difference and the same link.

### Documentation

- **AuthServer Integration Guide** — a new section, *When a redirect URI is required*:
  confidential and public in practice, the two conditions, the attack the registration stops,
  what the refusal looks like and how to fix it. The *Public clients* section no longer says
  the admin screen issues a public client no secret; it issues every new client one.
- **Upgrade Guide** — a row, with the query that finds the affected clients.

## Redirects the framework issues can be seen by a test

An application's test of the authorization-code flow approved the consent screen and got back a
302 with no `Location` — the one header that carried the code. `Oauth` redirected with a bare
`header()`, which PHP does not keep on the CLI, so no test of the framework or of an application
could read where the endpoint sent anybody; the framework's own flow test drove League directly
for that reason.

### Fixed

- **`Oauth` (the code, and `access_denied`), `Emailclick` and `FormRequest::failWith()`** go
  through `Application::redirect()`. The destination is recorded in `getRedirect()`, which
  `TestClient` answers as `Location`. `Oauth` sets it and calls `redirect()` with no argument,
  because `redirect($url)` writes the URL to the development `redirects` log and this URL carries
  the code.
- **`failWith()` stopped the test run.** It sent the header and called `exit`, which ends the
  PHPUnit process with status 0. It now ends the request the way everything else does, and has
  a test.

### Added

- **`RedirectsAreRecordedTest`** fails on a `header('Location: …')` anywhere in `src/` outside
  `Application::redirect()`. The one other exception, `RequireFactorEnrolmentMiddleware`, is
  listed with its reason: middleware stops a request by returning null.

### Documentation

- **Routing Guide** — *A redirect is `$this->redirect()`, not `header()` and `terminate()`*.
- **Upgrade Guide** — a row: tests that expected `…Oauth::terminate() called` catch
  `ApplicationClosedException` instead.

## The suite runs clean: no failure, warning or deprecation, and it fails on the next one

A full run was green with two PHP warnings and two deprecations in it, and a filtered run could
error on a class that passed on its own. Each had been there long enough to read as noise.

### Fixed

- **`$_SERVER` leaked between tests.** Fourteen test classes started with `$_SERVER = []` and
  none restored it. `OauthRefreshCommandTest` then warned on Symfony Console's missing
  `PHP_SELF`, and the session-tracking tests on a `SERVER_PORT` with no `SERVER_NAME`.
- **`Request::getURL(false)` read `SERVER_NAME` bare when a port was set.** The branch without a
  port already treated it as empty.
- **`UserCoverageTest` errored after certain classes.** It loaded the fixture settings and then
  took whatever Database singleton existed; one built before any settings pointed at `localhost`,
  and mysqli answered "No such file or directory" looking for a socket. It rebuilds the
  connection once, in `setUpBeforeClass()`, as the other database tests do.
- **`PasswordResetTokenTest::testATokenExpiringNowIsStillAccepted` failed across a second
  boundary** — storing at `time()` and consuming a moment later are two readings of the clock.
  It starts early in a second.

### Added

- **`ServerGlobalIsolation`**, a PHPUnit extension beside the other three: `$_SERVER` as it was
  after the bootstrap script, restored before every test. `pramnos init` registers it.
- **`failOnWarning` and `failOnDeprecation`** in the framework's `phpunit.xml`, so the next one
  fails the run instead of joining the noise. `ignoreIndirectDeprecations` keeps out one
  dependency's deprecation in another — `league/oauth2-server` calling a `league/uri` method
  version 7 deprecated — which is not ours to fix.

### Documentation

- **Testing Guide** — *Isolating process-wide state* lists the fourth extension.


## A token from `/oauth/token` never authenticated an API call

### Fixed

- **The last step of the code flow.** `AccessTokenRepository` stores an access token by its
  identifier — its `jti` — and `User::loadByToken()` looks a token up by its whole text, so a
  token from `/oauth/token` was verified, matched no row, and left the call anonymous. A remote
  MCP client got through registration, sign-in, consent and the token exchange, and was refused
  with `401` on its first call. glideday found it against production-equivalent code, with the
  cause and the fix; `Oauth::resolveStoredTokenValue()` already tried the `jti` second, which is
  why introspection and revocation worked while authentication did not.

    `ApiAuthMiddleware` and `UnifiedAuthMiddleware` now look a token up by its `jti` when the
    literal lookup finds nothing, reading the `jti` from the claims `JWT::decode()` has just
    verified. The fallback is **not** in `loadByToken()`: `Gdpr::resolveActor()` calls it with
    an unverified bearer, and there a forged JWT carrying a real `jti` would have been enough.

### Tests

The test the earlier ones lacked: a token from the full code flow, sent to the real
`ApiAuthMiddleware` and `UnifiedAuthMiddleware`, reaches the endpoint as the approving user.
The earlier end-to-end tests asked League's resource server, which never reads `usertokens` —
that is how this passed. It fails with the fix removed.

### Documentation

- **AuthServer Integration Guide** and **API Guide** — how a bearer from `/oauth/token` is found.
- **Upgrade Guide** — one row.

## Two administrators can be given different administration areas

Every administration screen was opened by usertype: 80 for most, 90 for Roles, Permissions,
Applications and Tokens. Two administrators at 90 saw the same area, and there was no way to give
one of them Users and Logs and the other Roles and Tokens. The menu could carry a permission, but
silence there meant "shown", so a role could never be what opened a screen.

### Added

- **`admin_access`**: `usertype` (the default, unchanged) or `permissions`. Under `permissions`
  each screen opens for whoever holds its ability — named after its menu item, `admin.users` — granted
  directly or through a role; nothing granted means closed. **`admin_superuser_usertype`**, 98 by
  default, opens everything, so switching modes cannot lock the last administrator out.
- **`Pramnos\Auth\AdminAccess`** — `allows()`, `abilities()`, `grantsFor()`, `setGrants()`,
  `landingFor()`.
- **An "Administration screens" panel** on a user's page and on a role's page, in all three themes,
  with what the user can open in the end beside their direct grants. Editable by the superuser or a
  holder of `admin.permissions`, and only for the screens the editor can open.
- **`Controller::$adminAbility`**, checked in `exec()` before any action — inside the
  administration area, where there is one, so a public page built on a screen outside it keeps
  answering — and `$adminPublicActions` for the ones that answer without it. `Permissions::clearCache()`, and `NavRegistry::all()`.

- **`admin_access = mixed`**: the floor, with decisions on top — an allow opens a screen below
  its floor, a deny closes it above. With nothing decided it is `usertype`, so it can be switched
  on a running installation. The panel offers **Default / Allow / Deny** per screen;
  `AdminAccess::setDecisions()`, `decisionsFor()` and `mode()`. A deny wins in every mode.

### Fixed

- **The log viewer checked nothing itself** and relied on the area's floor alone. It is now behind
  `admin.logs` like every other screen.

### Documentation

- **Authorization Guide** — *Administration screens: by usertype or by permission*.

## Registration by invitation, within a domain list, and with a confirmed address

Registration was on or off for everybody. An installation that wanted only its own staff had
nothing between the two, and a self-registered account was created `validated = 1` with nobody
having checked the address — so the ID token told every relying party `email_verified: true`.
The Authentication Guide showed a `require_email_verification` key that nothing read.

### Added

- **Invitations** — `Pramnos\Auth\Invitations` and `authserver.invitations`. A link opens
  registration for one address while it is closed; used once, atomically; 48 hours
  (`auth_invitation_ttl_hours`); the token stored only as `Token::lookup()`; one live invitation per
  address. Accepting joins the organisation, gives the role and fires `invitation.accepted` with the
  row. An **Invitations** screen (`admin.invitations`, 98 under usertype) in all three themes;
  `pramnos init` scaffolds its wrapper.
- **`auth_registration_domains`** limits open registration to whole domains.
- **Address confirmation** — `Pramnos\Auth\EmailVerification`, `auth_registration_verify_email`,
  always on under a domain list. Sign-in answers the new `LoginFlowResult::EMAIL_UNVERIFIED`
  (after the password, so it reveals nothing) and mails a fresh link at most every ten minutes;
  the API login answers `403 email_unverified`. One row in the Upgrade Guide.
- Mail templates `auth.invitation` and `auth.verify_email`; `Pramnos\Auth\RegistrationPolicy`.

### Documentation

- **Authentication Guide** — *Registration: open, by domain, by invitation*; the config example no
  longer shows a key nothing reads.
- **Account Guide** — what an invited person and one asked to confirm see.

## A subset of the suite runs as clean as the whole of it

The full run was green, and a `--filter` run over the same tests was not: classes errored with
"the database refused the query", "No such file or directory" or a sequence collision, and which
ones depended on what ran before them. Two of the causes were in the framework.

### Fixed

- **`add_unique_constraint_to_settings_table` failed a second run on MySQL** — "Duplicate key
  name 'uq_settings_name'" — because MySQL has no `ADD INDEX IF NOT EXISTS`. It returns when the
  index is already there, as a migration re-applied by `Testing\Schema` expects.
- **A changelog row written without the service provider stored the array raw.** The JSON
  encoders for `changes`, `details` and `context` were registered in
  `ChangelogServiceProvider::boot()`, so `ChangelogWriter` used on its own — or after
  `WriteSpool::reset()`, or on the synchronous path when the spool is unavailable — handed an
  array to the insert. `ChangelogWriter::registerEncoders()` now runs before every append, and
  `Model::logEvent()` calls it too.

### Tests

- Fixtures that left shared tables in another shape, or gone: `SessionTest` built a four-column
  `users` and kept it; `UsersControllerTest` dropped `users` and `usertokens` on the way out; tests
  that only needed a setting in memory wrote it to `settings`. Each suite that needs `users` or
  `settings` now ensures its production shape (`Testing\Schema::table('settings')` is new), and
  the PostgreSQL registration test brings the `applications` sequence level with the table.
- A unit test that relied on there being no database now makes one that cannot connect, and a
  source scan reads `src/Pramnos` rather than the fixtures other suites generate into `src/`.


## Invitations: the four gaps glideday found moving onto them

glideday moved its beta invitations onto `Pramnos\Auth\Invitations` and filed what it had to
work around.

### Added

- **`InvitationsController::inviteOptions()`** — what an application adds to an invitation made
  on the screen, `metadata` usually, read from its own fields in its own copy of the view. It is
  merged under the screen's options, so it cannot change who invited, the organisation, the
  role or the note.
- **`Invitations::notification()`** — the seam the mail is built through, so an application can
  return it `withPreheader(…)` or replace it. `InvitationNotification` gained `withPreheader()`
  and `mailPreheader()`, which the mail channel already reads.
- **`{days}`** for the `auth.invitation` template, beside `{hours}`: a 21-day link read "504
  hours". The built-in text says days whenever the lifetime is a whole number of them.

### Fixed

- **Mail categories added after the first seeding never got an editor row.**
  `seed_system_mail_templates` ran once, on 26 September, before `auth.invitation` and
  `auth.verify_email` existed, so on those installations **Administration → Mail templates**
  did not list them. The seeding is now `SystemMailTemplates::seedMissingRows()`, a dated
  migration calls it for the two, and a test pins the list of built-in categories so the next
  one cannot be added without its migration.
- **Erasing an account left its invitations.** The unaccepted ones it sent held other people's
  addresses attributed to a user who no longer existed, and the one it came from held its own.
  `Account::eraseUserData()` now calls `Invitations::forgetUser()`.

### Documentation

- **Authentication Guide** — attaching data from the screen, the mail's variables and
  preheader, and what an erase does to invitations.
- **Notifications Guide** — the two categories in the table, and why a new category needs a
  migration.
- **Upgrade Guide** — one row, for the erase.

## `/oauth/userinfo` refused the token `/oauth/token` had just issued

### Fixed

- **The same `jti` gap, in the endpoint the earlier fix missed.** `userinfo()` looked the token up
  by its whole text and answered "Token expired or invalid" for every token from the code flow,
  so neither OIDC way of reading the signed-in user's identity worked. msdauthserver found it
  running the full flow; it is a sibling caller of the lookup fixed earlier today in the two
  middlewares, and it should have been fixed with them.

    This endpoint verifies nothing else about the token, so the `jti` is taken from League's
    resource server — which checks the signature, the expiry and the revocation — rather than
    read off the token. A token with a real `jti` and a broken signature still gets `401`.

### Tests

A code-flow token with `openid` gets `200` and the user's `sub`; the same token with its
signature altered gets `401`. The first assertion fails with the fix removed.

## The deploy webhook answered twice when it answered first

### Fixed

- With `respondFirst()` on — the default — `flushResponse()` sends `202` and releases the
  caller, and the run still ended in `respond()`, which set a status and two headers on a
  response already sent. Three warnings per deploy in production's PHP log; glideday counted
  174. The deploy worked, and the warnings were noise in the log somebody reads when it does
  not. `respond()` now writes nothing once the answer has been flushed, and the `exit` it ends
  with is a seam of its own (`finish()`), so a test runs the real `respond()` after a flush.

### Documentation

- **Deploy Webhook Guide** — nothing more is written once the answer is out.

## A new continuous aggregate froze its open bucket

### Fixed

- **`createContinuousAggregate()` materialised the open bucket.** It ran `CREATE MATERIALIZED
  VIEW … WITH (timescaledb.continuous …)` with no data clause, and PostgreSQL's default is
  `WITH DATA`: every bucket was materialised, the open one included, which moved a real-time
  aggregate's watermark to that bucket's end. Rows arriving later in it were invisible until it
  closed, and the refresh policy could not help because it refreshes only closed buckets.
  glideday lost a day of site statistics that way — 37 views with a browser showed as none.

    It is now created `WITH NO DATA` and refreshed up to `now()`. TimescaleDB materialises only
    buckets wholly inside the window, so the closed ones are filled in and the open one stays
    live, with no need to know the bucket width. Over an integer time column the first refresh
    is refused; the aggregate is created empty and the `migrations` log says so.

### Tests

On TimescaleDB: rows in a closed and in the open hour, the aggregate created, one more row
arriving in the open hour — the open hour counts two. With the old statement it counts one,
which is the reported symptom reproduced. And an integer-time aggregate is created although its
first refresh is refused.

### Documentation

- **Schema Builder Guide** — what is materialised when an aggregate is created, and why.
- **Upgrade Guide** — one row.
