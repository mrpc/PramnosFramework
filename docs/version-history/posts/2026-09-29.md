## Claude.ai and ChatGPT can connect to the MCP endpoint

The tools, the scopes, PKCE and the consent screen all existed, and no assistant outside the
machine could reach any of them. glideday measured the chain against production and found it
broken in five places, each of which stopped a remote connector before the next one mattered.

### Fixed

- **The endpoint asked for an API key first.** `init` scaffolds `POST /mcp` into the API routes,
  and `ApiAuthMiddleware` answered `403 APIKeyMissing` before the controller ran. A connector
  cannot send an `apiKey` header, so it never reached the `401` that starts OAuth discovery.
  Listing the path in `public_api_paths` removed the key check **and** bearer validation, and
  the controller then found nobody for every call.

    Two changes. On a declared-public path, a bearer token that verifies now identifies the
    caller, and one that does not leaves the call anonymous rather than refused — the endpoint
    is open, so the anonymous answer is its decision. And `Api` puts `/<version>/mcp` on the
    public list itself, so nothing has to be declared.

- **`WWW-Authenticate` pointed under the API.** It was built from `sURL`, which inside the API is
  `https://host/api/`, so it named `/api/.well-known/oauth-protected-resource` — a 403.
- **The resource metadata named the site, not the endpoint.** `"resource": "https://host"`, and the
  path-suffixed form RFC 9728 §3.1 defines was a 404. MCP clients check that `resource` is the URL
  they were given. The `401` now names
  `https://host/.well-known/oauth-protected-resource/api/1.0/mcp`, built from the site's origin,
  and `Discovery` answers that address with the endpoint as its `resource`. A suffix that is not a
  plain path answers 404 rather than being echoed into a public document.
- **Discovery omitted what a public client looks for.** `oauth-authorization-server` lacked
  `code_challenge_methods_supported`, although S256 was implemented, and had no `none` among the
  auth methods. Both are there now.
- **`registration_endpoint` was the sign-up page.** A JSON POST to it answered `200` with HTML.

### Added

- **Dynamic client registration, RFC 7591** — `POST /oauth/register`, opt-in with
  `'oauth_dynamic_registration' => true` in `app.php`. `init` writes that line for an
  `authserver` project, and the discovery documents publish the endpoint only when it is on.

    It admits **public clients only**: `token_endpoint_auth_method` must be `none` (the RFC's
    default, `client_secret_basic`, is refused), grants are the code grant and refresh, and
    callbacks are `https` or loopback `http`. A confidential client is refused because it could
    use `client_credentials`, which needs no person — open registration would have been open
    issuance of machine tokens. Twenty registrations an hour per address.

- **The scaffolded `.htaccess`** routes `/.well-known/oauth-protected-resource/<path>` to
  `Discovery` with the suffix.

### What breaks

Three rows in the Upgrade Guide. An open API endpoint called with a token now sees that token's
user instead of the website session; an unrelated `/mcp` route in an application's API is now
reachable without a key; and a project scaffolded before today needs the registration switch and
one rewrite rule before a remote client can connect — both are spelled out there.

### Tests

A public client — no secret, PKCE, `is_confidential = 0` — completes the code exchange against the
real League server, which is the claim `none` in the discovery document makes. Registration writes
its row on MySQL and PostgreSQL/TimescaleDB, and both `validateCredentials()` and the League
client repository read the row as public. Every refusal is a unit test.
