## A working single server was being shown a red badge for a correct choice

Yesterday's `notice` status stopped `/health/check` answering 503 for a correct
installation. It did not stop the dashboard putting this beside `session_storage`, in a
red pill, at full width:

> Sessions are on "files", which is local to this machine. Correct on a single server; on
> more than one a visitor is signed out whenever the load balancer sends them to a
> different node.

Two separate mistakes, and the second one is the one that matters.

### The check was reporting a correct choice as a fault

**The existence of a shared-store option does not make not using it a fault.** On one
machine `files` is PHP's default: free, no dependency, nothing to configure, and right.
This check answered `degraded`, then `notice`, and both were a way of saying "you have not
configured the thing you do not need".

It answers **`ok`** now, with the store still named — because the value of this check was
never the severity. It is the *detail*: `details.handler` and `details.path` are how
somebody finds a Redis pointed at the wrong host, and that works identically under `ok`.

It becomes `degraded` when the application says there is more than one node:

```php
// app/config/app.php — only a deployment with more than one server needs this
'servers' => 2,
```

**Declared rather than detected**, because it cannot be detected: a node has no way to
count its siblings behind a balancer, and guessing from the environment would make the
answer depend on which machine answered the probe. One is assumed until you say otherwise,
which is the default that decides what every scaffolded project sees on the day it is
generated.

A handler the check does not recognise — `user`, or an extension it has not heard of —
stays a `notice`. It may reach a second server and it may not, and either answer would be
a guess. That is now the only thing `notice` is for.

### And the dashboard widget was rendering every non-`ok` status as red, with the whole message inside the badge

```php
<?php if ($result['status'] === 'ok'): ?>
    <span class="badge badge-success">OK</span>
<?php elseif ($result['status'] === 'warn'): ?>
    …
<?php else: ?>
    <span class="badge badge-error"><?php echo $result['message']; ?></span>
<?php endif; ?>
```

**`warn` is not a status this framework produces.** `HealthStatus` is `ok`, `notice`,
`degraded`, `down` — so that branch has never once executed, and everything that was not
`ok` fell through to the red one. `degraded`, which has a yellow colour defined for it
everywhere else, rendered red on this widget; so did `notice`, the status whose entire
purpose is not to alarm anybody.

And the message went *inside* the badge, so a check with a sentence to say became a
paragraph in an alarm colour stretched across the card.

Fixed in all three themes: the badge carries the **status**, coloured from the four real
ones, and the message sits beside it in ordinary text — and only when there is something
to say, so a green row stays a green row.

### Documentation

- **Health Guide** — why `session_storage` is `ok` on files, the `servers` declaration,
  and a rewritten rule for choosing a status: before reaching for anything above `ok`, ask
  what the reader is supposed to *do*. If the answer is "nothing, this installation is
  correct", it is `ok`, and whatever an operator might want goes in `details`.
- **One server to several** — declaring `'servers'`, since the framework cannot find out
  and this is the page somebody is reading when it becomes true.
- **Upgrade Guide** — a row: declare `'servers'` if you run more than one node, or this
  check will not tell you that local session files have stopped being correct.
