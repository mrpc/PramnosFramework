## The screen sweep's seeder invented values for generated and foreign keys

Yesterday's `seedFrameworkRows()`, reported back the same day by the project it was written
for. Four of the seven tables refused:

```
passkey_credentials: duplicate key value violates "passkey_credentials_pkey"
mails:               duplicate key value violates "mails_pkey"
pushsubscriptions:   duplicate key value violates "pushsubscriptions_pkey"
tokenactions:        violates foreign key constraint "fk_tokenactions_urlid"
```

Each was absorbed — correctly, that is the design — so **the sweep stayed green and said
nothing**, and the person card rendered four fewer panels than it could. Measured
elsewhere: 399 of 605 statements against 495 with the refusals gone.

The cause is one this repository has now met three times. The "fill required columns by
type" loop checked `Default` and `Key`, which are the **MySQL** spellings:

| | MySQL | PostgreSQL |
|---|---|---|
| default | `COLUMN_DEFAULT` | `column_default` |
| primary key | `Key` = `PRI` | `PrimaryKey` = `true` |
| auto-increment | *(absent; `Key` says `PRI`)* | `column_default` = `nextval(…)` |

On PostgreSQL both keys were absent, `null` read as "no default, not a key", and an integer
placeholder went into a `bigserial` primary key — colliding with everything a week of
testing had left in the table.

### Fixed

- `SchemaBuilder::columnDetails()`: one column shape on both engines — `nullable`,
  `hasDefault`, `isPrimary`, `isForeign`, `foreignTable`. Code written against one driver's
  spelling works on one engine and silently does nothing on the other, because a missing
  array key is `null` and `null` reads as "no". That is what bit the migration widening, the
  schema test and now the seeder.
- The seeder skips `hasDefault`, `isPrimary` **and `isForeign`**. The last is the line worth
  keeping separate: `tokenactions.urlid` points into the route table, and a value invented
  for it cannot point anywhere. A row so the loop runs is the point; a row claiming
  something untrue about another table is not.

### Added

- `ColumnDetailsTest` on both lanes. The generated-key assertion is deliberately the
  *disjunction* a caller uses — `hasDefault || isPrimary` — because the two engines describe
  the same column differently and neither is wrong: PostgreSQL reports `nextval(…)` and no
  auto-increment marker, MySQL reports `PRI` and a null default. Asserting one flag would
  pass on the engine it was written against.
- Two edge cases with a double, for the paths a real database will not produce: a driver
  answering `false`, and a connection that has gone away. Both are declared by
  `getColumns()`'s contract and neither is reachable from an integration test.
- A guard on the stub, forbidding the raw driver keys.


## A capped fetch threw away everything it had already read

`OutboundUrl::readCapped()` enforced the ceiling as a **failure**: past `$maxBytes` it
returned `false` and discarded the body, including the part the caller capped the fetch in
order to reach.

A caller reading an OpenGraph card asked for 512 KB, which is generous for a `<head>`. The
page was 783 KB — an ordinary WordPress front page — so the fetch refused and the screen
said *"That page could not be read. The response is larger than 512000 bytes."* The
`og:title` and `og:image` were at byte 4,000.

A cap exists so a hostile or careless server cannot fill memory. It does not exist to make a
large page unreadable — and the things anybody caps a fetch for, meta tags and feed headers
and manifests, are at the top of the file by construction.

### Added

- `fetch(..., allowTruncated: true, truncated: $truncated)`. Off by default, because half a
  JSON document is the shape the caller expects and the failure surfaces somewhere else; on,
  it returns what it read and says it was cut short, and the caller decides.
- **Exactly the ceiling**, not the ceiling plus the rest of the 8 KB block it was noticed
  in. A caller that sized the cap against a limit it has to respect gets the number it asked
  for, with a test for each of three sizes.
- `$truncated` is `false` rather than unset when nothing was cut, so `if ($truncated)`
  around a re-fetch does not re-fetch every small page ever read.
