# 30 October 2026

Three entries today:

- An answer can be given a budget for what it spends
- A question being answered can be stopped
- Reads asked for at once run at once, on the orchestrator's workers

<!-- more -->

## An answer can be given a budget for what it spends

### Added

- `Client::withTurnBudget(maxCost:, maxTokens:)`, or `'llm' => ['turn_budget' => [...]]` for every
  answer, caps what one answer spends over all its rounds. The rounds already capped how many
  times a model could call tools, but not what those calls cost. Once the budget is passed, the
  next round is the last: tools are forbidden and the model is told (`Client::OVER_BUDGET`) to
  answer with what it has and say what is left. The answer carries `over_budget: true`. No budget
  is set by default. See the
  [LLM guide](../../Pramnos_LLM_Guide.md#what-one-answer-may-spend).

## A question being answered can be stopped

### Added

- A Stop button on the conversations page, the analyst's page and the SPA's `Chat.svelte`
  while a question is answered. `Asks::cancel()` marks the ask `cancelled`; the worker looks
  before every round and every tool and stops there, so nothing more is spent. A question
  stopped before the worker reaches it is never sent. Nothing is kept from a stopped answer.
- `POST /chat/asks/{id}/cancel` in the conversation API, `asks/{id}/cancel` under
  `/admin/Ai/api/`, and `cancel/{id}` beside `asked/{id}` for `pf-chat.js`.
- `Client::cancelWhen(callable)`, the same hook for a client used directly, and
  `Conversations::stoppable()`.

### Upgrading

- An application with its own copy of the chat view gets the button without changing it.
  `pf-chat.js` and the SPA component come with `project:resync`. The words are `stop` and
  `stopped` in the view's `$say`; without them the button says "Stop".

See the [LLM guide](../../Pramnos_LLM_Guide.md#stopping-an-answer).

## Reads asked for at once run at once, on the orchestrator's workers

### Added

- A tool marked `'parallel' => true` reads and changes nothing. When a model asks for two or
  more such tools in one round, and for no tool that writes, they run at once. This happens where
  the application turns it on (`'llm' => ['parallel_tools' => true]`). Each call is a row of
  `pramnos.llm_tool_runs` and an `llm_tool` queue task, which `queue:process` runs with no
  registration. The answer claims calls itself while an orchestrator pool's workers claim others,
  so with no workers nothing waits, and a slow call no longer holds up the rest. Results reach
  the model in the order it asked.
- The analyst's tools are marked parallel.
- `Conversations::toolsFor(Turn)`, the tools an answer is given, which a worker builds again.
  `Client::inParallel()` takes a runner of its own.

### Upgrading

- Run `php bin/pramnos migrate` for `pramnos.llm_tool_runs`. Without it, every call runs in the
  answer, as before.

See the [LLM guide](../../Pramnos_LLM_Guide.md#tools-that-run-at-once).
