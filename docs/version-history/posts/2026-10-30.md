## An answer can be given a budget for what it spends

### Added

- `Client::withTurnBudget(maxCost:, maxTokens:)`, or `'llm' => ['turn_budget' => [...]]` for every
  answer, caps what one answer spends over all its rounds. The rounds already capped how many
  times a model could call tools, but not what those calls cost. Once the budget is passed, the
  next round is the last: tools are forbidden and the model is told (`Client::OVER_BUDGET`) to
  answer with what it has and say what is left. The answer carries `over_budget: true`. No budget
  is set by default. See the
  [LLM guide](../../Pramnos_LLM_Guide.md#what-one-answer-may-spend).

## A question being answered can be stopped

### Added

- A Stop button on the conversations page, the analyst's page and the SPA's `Chat.svelte`
  while a question is answered. `Asks::cancel()` marks the ask `cancelled`; the worker looks
  before every round and every tool and stops there, so nothing more is spent. A question
  stopped before the worker reaches it is never sent. Nothing is kept from a stopped answer.
- `POST /chat/asks/{id}/cancel` in the conversation API, `asks/{id}/cancel` under
  `/admin/Ai/api/`, and `cancel/{id}` beside `asked/{id}` for `pf-chat.js`.
- `Client::cancelWhen(callable)`, the same hook for a client used directly, and
  `Conversations::stoppable()`.

### Upgrading

- An application with its own copy of the chat view gets the button without changing it.
  `pf-chat.js` and the SPA component come with `project:resync`. The words are `stop` and
  `stopped` in the view's `$say`; without them the button says "Stop".

See the [LLM guide](../../Pramnos_LLM_Guide.md#stopping-an-answer).

## Reads asked for at once run at once, on the orchestrator's workers

### Added

- A tool marked `'parallel' => true` reads and changes nothing. When a model asks for two or
  more such tools in one round, and for no tool that writes, they run at once. This happens where
  the application turns it on (`'llm' => ['parallel_tools' => true]`). Each call is a row of
  `pramnos.llm_tool_runs` and an `llm_tool` queue task, which `queue:process` runs with no
  registration. The answer claims calls itself while an orchestrator pool's workers claim others,
  so with no workers nothing waits, and a slow call no longer holds up the rest. Results reach
  the model in the order it asked.
- The analyst's tools are marked parallel.
- `Conversations::toolsFor(Turn)`, the tools an answer is given, which a worker builds again.
  `Client::inParallel()` takes a runner of its own.

### Upgrading

- Run `php bin/pramnos migrate` for `pramnos.llm_tool_runs`. Without it, every call runs in the
  answer, as before.

See the [LLM guide](../../Pramnos_LLM_Guide.md#tools-that-run-at-once).

## A change is made once per answer

### Added

- A tool marked `'writes' => true`, called again in the same answer with the same arguments, is
  not run again. The model is told it was done and what it returned the first time.
  `Client::answering($key)` names the answer. A queued question is named by its ask, so if it is
  answered again it does not repeat a change it already made. Keys live in
  `pramnos.llm_tool_idempotency` for a day. A failed run gives its key back.

### Upgrading

- Run `php bin/pramnos migrate` for `pramnos.llm_tool_idempotency`. Without it, every call runs,
  as before.

See the [LLM guide](../../Pramnos_LLM_Guide.md#a-change-is-made-once-per-answer).

## A gate before every tool call, and approvals given in advance

### Added

- `Policy\ToolGate`, a policy like limits and consent (`'llm' => ['tool_gate' => …]` or
  `Llm::use('tool_gate', …)`). It is asked before every tool call the model asks for, and a call
  it refuses never runs. Its reason goes to the model instead. The default `OpenGate` lets
  everything run.
- `Policy\GrantGate` and `Grants\ToolGrant`: an approval for one tool given in advance, limited
  by typed matchers on its arguments (`DomainMatcher`, `MaxNumberMatcher`, `PrefixPathMatcher`,
  `OneOfMatcher`) instead of a pattern over JSON. A grant must account for every argument a call
  carries, so an approved `to` does not cover a `cc` outside it. Gated are the tools that write
  and any marked `'gated' => true`.

See the [LLM guide](../../Pramnos_LLM_Guide.md#approvals-given-in-advance).

## A tool registry, and skills turned on during an answer

### Added

- `ToolRegistry`: tools declared once (`register()`, `registerMcp()`, `add()`) with metadata
  (`writes`, `idempotent`, `untrusted`, `gated`, `permissions`, `skills`, `tags`, `cost_weight`,
  `latency_tier`). It hands them to the client per person and per skill. The client's flags come
  out of the metadata: an idempotent read runs at once with others, and a write never does.
- Skills turned on during an answer: `skillTool()` is a `use_skill` tool, and `manifest()` is the
  prompt's line naming the skills. A tool with an `expands` callable adds tools to the answer from
  the next round. A tool added this way runs in the answer, not on a parallel worker.

See the [LLM guide](../../Pramnos_LLM_Guide.md#declaring-tools-once-the-registry).

## Tools from other MCP servers

### Added

- The framework as an MCP client: `Pramnos\Llm\Mcp\Client` over `StdioTransport` (a server run
  as a process) or `HttpTransport` (Streamable HTTP, with JSON or server-sent events answers, and
  the session the server names). `Mcp\Servers` reads `'llm' => ['mcp_servers' => …]`, an array
  or an `mcp.json` file, and hands the servers' tools over as the framework's, or into a
  `ToolRegistry`.
- Every external tool is `untrusted`. One the server marks `readOnlyHint` is idempotent; any other
  is taken to write. A server that cannot be reached is logged and its tools left out.

See the [LLM guide](../../Pramnos_LLM_Guide.md#tools-from-other-mcp-servers).

## Artifacts as a workspace across conversations

### Added

- The model reads, changes, finds and pins what a person kept, from any conversation:
  `read_artifact` (by id or title), `update_artifact` (`replace`, `append`, `patch`),
  `list_artifacts` (kind, entity, tag, words in the title) and `pin_artifact`. A change is checked
  whole against the limits a new artifact has. `Artifacts::update()`, `search()` and `asText()`
  are the same in code.
- What a person pinned in a space is in the context of every question there, as it stands at the
  start of that question.

See the [LLM guide](../../Pramnos_LLM_Guide.md#artifacts-tables-lists-and-texts-kept-from-an-answer).

## The context in three zones, for the provider's cache

### Changed

- A conversation's context is laid out by `Chat\ContextAssembler` in three zones. Zone 1 is the
  system prompt: the assistant's role and rules, the same for every question. Zone 2 is a system
  message ahead of the history: what is remembered, what is pinned, the summary. Zone 3 is a
  system message just before the question: the time on the assistant's clock, the page, and an
  attached document's notice. The time and the page used to be in the system prompt, so no two
  questions shared a cached prefix.
- `BaseAssistant::systemPrompt()` no longer says today's date, and `AnalystAssistant`'s no longer
  says the date or the page. The new `volatileContext(Turn)` hook is where an assistant puts
  what changes per question.

### Added

- A warning in the `llm` log when the static prompt changes between two questions of a
  conversation while the code and settings did not, with the first line that differs. Another
  warning when a question that followed others got less than 80% of its prompt from the cache.

### Upgrading

- An assistant that builds a date or a page into `systemPrompt()` moves it to
  `volatileContext()`. A row in the [Upgrade Guide](../../Pramnos_Upgrade_Guide.md#since-v12-unreleased).

See the [LLM guide](../../Pramnos_LLM_Guide.md#the-context-in-three-zones).

## Answers in a given shape, and tool calls checked against their schema

### Added

- `Client::askForJson()` returns an object of a JSON schema, decoded and checked. Where the
  provider takes `response_format: json_schema` (the new `json_schema` provider key: OpenAI,
  Gemini, Mistral) it asks in that shape and sends a wrong answer back once. Elsewhere it uses one
  tool whose arguments are the schema. `Extractor` now asks through it.
- `JsonSchema::errors()`, a check of the schema keywords tools and answers use.

### Changed

- A tool call whose arguments are not JSON, or do not fit the tool's `parameters`, is not run.
  The model is told what is wrong and calls again corrected. A number written as text still
  counts as a number. A row in the [Upgrade Guide](../../Pramnos_Upgrade_Guide.md#since-v12-unreleased).

See the [LLM guide](../../Pramnos_LLM_Guide.md#an-answer-in-a-given-shape).

## A model for each question: fast and frontier tiers

### Added

- `'llm' => ['tiers' => ['fast' => feature, 'frontier' => feature], 'cascade' => …]` answers each
  question in a conversation on the tier it needs. Each tier is a feature, with its provider and
  model set on the administration screen. `Policy\ModelCascade` decides with one short call on
  the fast tier. `Policy\Cascade` is the interface for an application's own rule, and
  `NoCascade` is the default, which changes nothing.
- A frontier tier that cannot answer hands the question to the fast tier, which is told it
  answers in the stronger model's place (`Conversations::DEGRADED`).

See the [LLM guide](../../Pramnos_LLM_Guide.md#a-model-for-each-question-tiers).

## A failed upsert no longer leaves the transaction aborted

### Fixed

- `Database::upsert()` on PostgreSQL returned `false` when its statement failed — a value too
  long for its column, say — and left the transaction it ran in aborted. Every later statement on
  the connection, in code unrelated to it, then failed with *current transaction is aborted*.
  `User::save()` writes a user's details through it, so one over-long detail broke the rest of
  the request. It now rolls back a transaction opened with `startTransaction()` and throws a
  `QueryException`, as the MySQL branch already threw and as `Model::_save()` does. A statement
  PostgreSQL could not prepare is no longer remembered as prepared.

## Subagents: a task with a context of its own, and a result it always gives back

### Added

- `Pramnos\Llm\Subagent` hands a task to a model with its own instructions, tools, rounds and
  client, and nothing of the conversation that asked. `run()` always returns a
  `SubagentResult` (`success`, `partial` or `failed`, with a reason: `completed`,
  `max_rounds_reached`, `budget_exceeded`, `tool_error`, `provider_error`, `cancelled`) and never
  throws. The summary is never empty: a failure says what went wrong and which tools had been
  called.
- With an `Artifacts` store it gets `save_artifact`. What it saves is a draft, checked when it
  is called, and kept only when the task ends in `success`; otherwise it comes back in
  `draftArtifacts` for somebody to confirm.
- `asTool()` makes it one tool of a parent's answer. The parent reads the status, the summary
  and titles (`forParent()`), never the content, and the tool carries the `writes`, `untrusted`
  and `gated` flags of the tools inside it.
- `Artifacts::check()` says what is wrong with an artifact without keeping it.
- `askWithTools()` answers `rounds` and `out_of_rounds`, how many rounds it took and whether the
  last one was forced.

### Fixed

- An answer whose provider failed after earlier rounds had called tools returned no `calls` and
  no `usage`, though those tools had run and the tokens were spent. It returns both now, as the
  other failures did.

## Evals: a change to a prompt, model or tool measured before it ships

### Added

- `Pramnos\Llm\Eval\Suite` asks a set of cases (JSON: `user_query`, `available_tools`,
  `tool_results`, `expected_tool_calls`, `expected_arguments`, `expected_final_state`) and scores
  each one: tool accuracy, argument fidelity, whether the answer holds what it should, and rounds.
  No tool runs. Each answers its canned result, so only the model varies.
- `Eval\Report::regressions()` compares the scores with a baseline. It fails when accuracy or
  argument fidelity falls by more than 5 points, or the mean of rounds rises by more than a fifth.
- `llm:eval <dir> --setup=… --baseline=… [--write-baseline]` runs the suite with the
  application's own prompt and tools, and exits 1 on a regression, for a CI step.

## A model loaded by a key that is not a number finds nothing, on every database

### Fixed

- `Model::_load()` passed its key to the query as given. For an integer primary key, `'abc'`
  became `0` on MySQL, and on PostgreSQL the statement failed with *invalid input syntax for type
  bigint*: an exception on a page that only had a bad id, such as a crawler's slug, plus an
  aborted transaction. Applications had put the same `ctype_digit()` guard into model after
  model. A key that is not a whole number now loads nothing for an integer key, with no query.
  A whole number costs nothing extra; anything else reads the table's columns once per process,
  and a text key is looked up as before.

## A profile of the person that changes only on their word

### Added

- `Chat\Profile`, in the new `chat_dossier` table, on with `'llm' => ['chat' => ['profile' => true]]`:
  who the person is, what they value, what they work towards, and the people in their life (one
  entry per person). It also holds how they feel lately, only with their consent
  (`ai_profile_feelings`). A person's own conversations only — never the analyst's space, never
  a shared answer.
- The model proposes (`note_profile`) and the person confirms in a later message
  (`confirm_profile`, `reject_profile`). A proposal cannot be confirmed in the answer that made
  it. Background learning proposes too, from what the person plainly said.
- Every confirmed change is a version, its before and after in the changelog
  (`Profile::history()`).
- `recall_person` finds somebody by name. The tools' results are tagged `personal`, for a data
  rule.

## A person's calendar for the assistant: appointments and tasks, conflicts with free slots, live on the page

### Added

- `Chat\Calendar`, in the new `chat_calendar` table, on with `'llm' => ['chat' => ['calendar' => true]]`:
  the person's own appointments and tasks. The tools are `calendar_create_event`,
  `calendar_list_events`, `calendar_update_event`, `calendar_delete_event`, `task_create`,
  `task_list`, `task_update` and `set_busy`, all on the person's clock.
- Today's appointments and the tasks due are in every prompt, in the cached second zone.
- An appointment that would overlap another is not made. The tool answers
  `{"error": "conflict", "existing": …, "free_slots": ["14:30", "17:00"]}`, the nearest free
  starts before and after, so the model can offer them.
- `feed()` and `move()` are the two endpoints of a `pf-calendar`.
- Every change is announced as `calendar.changed` on the person's private channel, and
  `pf-calendar` takes `data-channel` to refetch when it hears it.
- `llm:routines` sends a reminder 30 minutes before each appointment (`Calendar::remind()`), once.

## A user loaded from the cache is the same object as one loaded from the database

### Fixed

- `User::load()` cached `(array) $this`, which names protected and private properties with PHP's
  NUL-byte mangling (`"\0*\0originalOtherinfo"`). On a second load of the same user, each such
  key became a new public property under that literal name, and the real property kept its
  default.
- So `originalOtherinfo` was empty after a cached load, and a save wrote every detail again.
  `get_object_vars()` inside the class listed keys with a NUL byte in them. One application
  serialised those into its audit log, and a PostgreSQL `LIKE` over the column then failed with
  *invalid byte sequence for encoding UTF8: 0x00*.
- The cache now holds `get_object_vars($this)`, plain names, and a cached load rebuilds exactly
  what a fresh one built. A password waiting for its first save is never copied into it.

## The assistant reaches out with manners: quiet hours, a daily limit, and not while busy

### Added

- `Llm::proactivity()` (`Policy\Proactivity`, by default `Policy\QuietProactivity`) decides
  whether the assistant may reach out to a person now, later, or not this time. It applies once
  the application sets `'llm' => ['proactivity' => …]` (`Llm::proactive()`). The defaults:
  - no pings in quiet hours (`22:30-07:30`), held until they end;
  - at most `daily` (3) a day;
  - none while the person is in an appointment, or busy by their word through `set_busy`.
  An alarm (`critical`) goes regardless.
- `llm:routines` asks it before a scheduled question in a person's own conversations. A held
  question asks no model and waits: until the given moment, or for its next turn.
- A calendar reminder the policy holds is passed and does not count.

## A journal a day, a morning plan and an evening review, and a warm answer when the frontier is down

### Added

- `Chat\Journal`, on with `'llm' => ['chat' => ['journal' => true]]`: `journal` writes an entry
  in today's page, one text artifact a day (`Journal Y-m-d` on the person's clock), made on the
  first entry and added to after it. Tagged `personal`.
- `Routines::templates()` offers `daily_plan` (08:00, with the calendar on: today's plan, kept as
  an artifact and pinned) and `evening_review` (21:30, with the journal on). The application's own
  `routine_templates` win by key.

### Changed

- The fast tier, answering in the frontier's place (`Conversations::DEGRADED`), is told to answer
  warmly first when the person is upset or confiding.

## A conversation's tools in skills, turned on as the model needs them

### Added

- `'llm' => ['chat' => ['skills' => true]]` (off by default) groups a conversation's tools. A
  tool marked `'skills' => [...]` is offered once the model turns one of its skills on with
  `use_skill`, and a tool of no skill is always offered. An assistant says what its own skills
  are for in `BaseAssistant::skills()`.
- The framework's tools are marked already (`Conversations::SKILLS`): `tasks`, `artifacts`
  (all but `save_artifact`), `profile`, `calendar`, `journal`, `web`.
- `ToolRegistry::add()` keeps the keys it does not read itself (`expands`, an application's own),
  and `use_skill` says what each skill is for.



## The web for the assistant: searching it and reading a page, safely

### Added

- `'llm' => ['chat' => ['web' => true]]` offers `web_search` and `fetch_url` in conversations,
  in the `web` skill. Both are `untrusted` and `parallel`.
- `Web\Search` asks the providers the application has keys for, in its order (Brave, Tavily,
  Exa, Serper, Jina), passing a refusal to the next, and falls back to Bing's own search as a
  feed (`'bing' => false` turns that off). It searches the web or recent news.
- `Web::page()` fetches through `Client::forUserSuppliedUrl()`, so nothing on the server's own
  network is reached. `Web\PageText` reads a page's own words: its declared `articleBody`, the
  paragraphs of its `<article>`, or its paragraphs, without the menus.
- An opt-in reader (`'web' => ['reader' => true]`) asks again for a page that refuses servers.
  It is never given an address the guard refused.

## A token action on a URL longer than 255 characters is written

### Fixed

- `Token::urlId()` inserted the whole URL into `urls.url`, which is `varchar(255)`. A call with a
  list of ids in its path failed the insert, aborted the drain's transaction on PostgreSQL, and
  every token action of that call ended in the spool's parked file. The row now keeps the first 255
  characters; the lookup was already by the hash of the whole URL, so it is still one row per URL.

## The nightly 2FA setup cleanup works on an older table shape

### Fixed

- `auth:twofactor-cleanup` (`TwoFactorAuthService::cleanupExpiredSessions()`) compared `used` with
  `1` and `expires_at` with a Unix time. An installation whose `authserver.twofactor_setup`
  predates the framework's migration can have `used` boolean and `expires_at` a timestamp, and
  PostgreSQL compares neither with an integer — the task failed every night and expired setup
  sessions stayed. It now reads the two columns' types and compares each in its own kind.

## An erased account takes the person's profile and calendar with it

### Fixed

- `AccountErasure::erase()` did not reach the profile's and the calendar's tables. It now deletes the person's
  `chat_dossier` entries together with every earlier version of them in `pramnos.changelog_events` — what
  they said about their values and the people close to them is exactly what an erasure is for —
  and their `chat_calendar`.

### Added

- `Profile::erase('userid' | 'organization_id', $id)` erases a person's or an organisation's
  profile together with its versions in `pramnos.changelog_events`, for an application erasing an
  organisation: written by hand, a delete against `changelog_events` without the schema matches
  nothing and reports nothing. `AccountErasure` uses it.

## The email screens fit the page and speak the reader's language

### Fixed

- A list's per-column search boxes (`footerTextSearch`) carry an inline `width:100%`. On a page
  without the theme's stylesheet each took the browser's own width, about 260px, and the email
  list ran to nearly 2,000px in a 1,366px window, its date, status and actions cut off. The email
  list's status filter is sized the same way, and under the Bootstrap theme the list is in a card,
  in Bootstrap's table styling.
- A message's page, under the Bootstrap and plain-CSS themes, drew its report — tracking,
  structured data, links, the text-only part — below the page's column, bare, in English. It is
  now in cards inside the column, every phrase through `t()`, `MessageReport`'s notes included,
  and a long link breaks instead of running off the page. The Tailwind theme's tabs are
  translated the same way. The Greek catalogue carries every phrase.

## Profile, calendar and journal turned on one by one; MCP servers offered in conversations on request; a cut answer goes on where it stopped

### Changed

- The profile, the calendar and the journal are three capabilities any application turns on by
  itself — `'llm' => ['chat' => ['profile' => true, 'calendar' => true, 'journal' => true]]` —
  in `Pramnos\Llm\Chat` (`Profile`, `Calendar`, `Journal`). Earlier today they were one
  `companion` switch in `Pramnos\Llm\Companion`; that switch and namespace are gone, and the
  settings are `ai_profile_feelings` and `ai_busy_until`.
- The manners (`Llm::proactivity()`) apply once `'llm' => ['proactivity' => …]` is set, to a
  person's own scheduled questions and to calendar reminders. Without it everything goes at its
  time.
- The ready-made routines are `daily_plan` (with the calendar: the plan is pinned) and
  `evening_review` (with the journal: the plan is unpinned).

### Added

- Today's appointments and the tasks due are in every prompt's second zone, with the calendar on
  (`Calendar::context()`).
- Background learning proposes to the profile, with it on: a proposal the next answer asks the
  person to confirm.
- `artifact.changed` on the person's private channel when one of their artifacts is changed or
  pinned (`Artifacts::CHANGED`), and `BroadcastingManager::toUser()` to tell a person's open pages
  anything.
- `'llm' => ['chat' => ['mcp' => true]]` offers the configured MCP servers' tools in conversations;
  configuring them alone does not.
- An answer cut at its turn budget or its rounds is remembered as cut: the next question's
  history names the calls it already made (`Conversations::whereItStopped()`).
