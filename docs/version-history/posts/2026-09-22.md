## The scaffolded translation endpoint has never once answered

Three causes in one feature, and each is enough on its own.

**The route could not match.** `LanguageController` declared
`#[Route('/api/1.0/language')]` — the only endpoint in a scaffolded project declaring its
own route rather than being registered in `src/Api/routes.php`. The web server strips
`/api` before the API application sees a request (`www/api/index.php` serves `/1.0/…`,
which is why `routes.php` groups everything under the version alone), so that path matched
nothing from the day it was written, in every environment.

**The client could not authenticate.** `lib/i18n.svelte.js` sent a bare `fetch` with no
`apiKey` header, and `ApiAuthMiddleware` refuses anything without one **before** routing.
So even with the path fixed the answer was 403.

**And the two ends spoke different vocabularies.** `Language::getLanguages()` answers the
**file names** in `app/language/` — a project shipping `en.php` gets `['en']` — while the
controller's fallback and `default_language` were both the word `english`, which is in no
such list. Every request fell through to a name with no file behind it, *including a
request for a language the project genuinely ships*. The two agreed only where the file
happened to be called `english.php`.

**Why none of it surfaced.** The i18n client treats any non-ok answer as "no translation
available" and returns `false`, so the SPA falls back to English silently. A product that
has never rendered a translated string looks exactly like one nobody has translated yet —
the failure has a plausible innocent explanation, which is the most expensive kind.

### Fixed

- The route is registered in `src/Api/routes.php` beside `/status` and the rest, and the
  `#[Route]` attribute is gone. **The endpoint that was not declared where the others are
  is the one that did not work**, which is the argument for declaring it there — and two
  declarations of one route is a second thing to keep in step.
- `i18n` sends the application key, read from `window.__PRAMNOS__`. Not imported from
  `lib/api.js`: that file imports `t` from i18n, and the cycle is why the module imports
  nothing.
- The fallback is `$available[0]` — a language this installation actually ships — and an
  installation with no language files at all is answered with an empty catalogue rather
  than a name pointing at nothing. `default_language` is validated against the list rather
  than trusted.

### Added

- `tests/js/spa-i18n.test.js`, which renders the stub and drives the real module against a
  stubbed `fetch`: the key is sent, a named language skips the token, a refused request
  falls back without throwing, and the reported language is the server's rather than a
  literal. The framework shipped this module without ever running it, which is how all
  three causes survived.
- Two guards in `GeneratedSpaPathsTest`: the language route is registered with the others
  and carries no attribute, and **no generated route path starts with `/api`** — the same
  mistake in the shape it would take next time.


## Two scaffolded views landed where the resolver never looks

`init` wrote `src/Views/account/dashboard.html.php` and `profile.html.php`. Neither has
ever been rendered: `Account::display()` calls `getView('dashboard')` and `profile()` calls
`getView('profile')`, which resolve to `src/Views/dashboard/` and `src/Views/profile/` — so
a directory called `account` is one nothing looks in.

Worse than dead code, because they look like the account screens. Somebody wanting to
change the account page finds them, edits them, reloads, and nothing happens — and they
were raw Tailwind where every other view is daisyUI, so even that was not a visible hint.

### Fixed

- They are not written at all, and **not moved to the right directory either**, which is
  the tempting fix. `scaffolding/themes/*/views/dashboard/` and `.../profile/` already ship
  working versions in the project's own theme; a copy under `src/Views/` would take
  precedence over them and replace a maintained screen with a frozen one.
  `project:publish-views` is how a project takes ownership of a view, and it copies the
  version that actually renders.

### Added

- A guard in `PublishedViewsAreReachableTest`: every `src/Views/<dir>/` the scaffold
  creates or writes into must be a `<dir>` some controller asks for with `getView()`.

  Writing it cost two attempts at one regex — `\\\\?` is the regex `\\?`, a *literal*
  question mark, in either PHP quoting style — and both times the only thing that said so
  was the emptiness assertion the sweep carries. Which is the argument for carrying it.
