## `Result::getInsertId()` works on PostgreSQL, and `Result` is now `Countable` (FW-295)

### Fixed

- `Result::getInsertId()` called `pg_last_oid()` directly on PostgreSQL. PostgreSQL tables have had no OID by default since 8.1, so it always returned `0`/`false` there — every `$db->queryBuilder()->table(...)->insert($values)->getInsertId()` call on PostgreSQL silently got a useless value. It now delegates to `Database::getInsertId()`, which already resolves the right value per dialect (`currval()` on the inserted row's own sequence on PostgreSQL, `mysqli_insert_id()` on MySQL). Reported from a media-library module doing `addUsage()`/`getMediaUsages()` on PostgreSQL.

### Added

- `Result` implements `Countable`: `count($result)` now reads `$numRows` instead of throwing `TypeError: count(): Argument #1 ($value) must be of type Countable|array, Pramnos\Database\Result given`. Also reported from the same module.

### Documentation

- `docs/Pramnos_QueryBuilder_Guide.md`: `$result->getInsertId()` row corrected (both dialects, not just MySQL), and a `Countable` note added under the `Result` properties/methods table.

## `MediaObject`: a module's uploads can be routed outside the document root

### Added

- `MediaObject::privateStorageModules()`: a new overridable protected static method, empty by default, so every application's uploads keep landing under `www/uploads/` exactly as before. An application that lists a module here gets that module's uploads written under `var/uploads/` instead — outside the document root, unreachable by a guessed or crawled URL. `createPath()` now resolves the storage root through the new `storageRoot()` method, which consults the hook. Reported from a media-library module that keeps its own fork specifically to route identity/verification documents outside the public upload tree, which a direct `MediaObject` extension could not do.
- This hook only decides *where* a file is written — an application that uses it is responsible for serving those files itself (checking who may see one, then streaming it), the same as it would for any other private data it owns.

### Documentation

- `docs/Pramnos_Media_Guide.md`: new "Routing a Module's Uploads Outside the Document Root" section under *File Upload*.

## `MediaObject::uploadFile()` accepts SVG, sanitized before it ever reaches disk

### Added

- `uploadFile()` accepts `.svg`/`image/svg+xml` (and the older `image/svg` some browsers still send) alongside the existing raster formats. The upload's own bytes are never written: the content is sanitized by [`enshrined/svg-sanitize`](https://github.com/darylldoyle/svg-sanitizer) first, which strips `<script>`, event-handler attributes (`onload`, `onclick`, ...), `<foreignObject>` and external references — the things that make an SVG able to run script once it is opened from this application's own origin. A `.svg` whose content fails to parse as valid SVG at all is refused outright, not stored unsanitized. The package is a `composer.json` `suggest`, not a `require` — an application that never accepts SVG uploads keeps carrying nothing extra — and `uploadFile()` refuses every `.svg` with a clear error naming the missing package when it is absent.
- Requested from a media-library module whose own fork added SVG support without any sanitization; declined to port that version as-is (see the 2026-10-26 entry on `whereLike()` for the same shape of decision — the faster/simpler proposal had a real defect) and shipped this instead.

### Fixed

- `processImage()` read `getimagesize()`'s width/height unconditionally, which returns `false` for a vector (no raster header to read) — `$media->x`/`$media->y`, both `NOT NULL` columns, ended up `null` and every `save()` after an SVG `addImage()`/`uploadFile()` call failed outright. Latent since the framework first supported SVG rendition policy; SVG uploads are what finally exercised it. Now falls back to `0`, the same way a remote image whose size could not be read already did.

### Documentation

- `docs/Pramnos_Media_Guide.md`: new "SVG Uploads" section under *File Upload*.

## `MediaObject::uploadAsJpeg()` normalizes a WebP/PNG/etc. upload to JPEG, in place

### Added

- `MediaObject::uploadAsJpeg(array $file): array` rewrites a `$_FILES` entry's content to a JPEG before it is handed to `uploadFile()`/`uploadImage()` — an application opts in upload by upload (`$media->uploadImage(MediaObject::uploadAsJpeg($_FILES['photo']))`), it is never automatic. The type is read from the file's own bytes, not its name or declared Content-Type. It rewrites the upload's temporary file **in place** (same path), so `uploadFile()`'s own `move_uploaded_file()` call needs no special handling for the result.
- Left exactly as it came in when: it is already a JPEG or a GIF (a GIF may be animated — flattening would always take the first frame); any of it is see-through (a logo on a template — flattened onto white it would stop being see-through, which is worse than not converting it); or GD cannot decode the content at all.
- Requested as a general "WebP → JPEG" normalizer; generalized to any format GD can decode (PNG, AVIF, ...) rather than special-casing WebP, since the same reasoning — read the bytes, flatten unless it would lose something — applies regardless of the source format.

### Fixed

- `processImage()`'s two `getimagesize()` reads (also touched by the SVG entry above) are both now defensive against a `false` result, for every caller — not only a vector, also content a decoder could not read for any other reason.

### Documentation

- `docs/Pramnos_Media_Guide.md`: new "Normalizing an Upload to JPEG" section under *File Upload*.

## `MediaObject::fixStaticPath()` rebuilds a stale row's path through the same root `createPath()` writes under

### Fixed

- `fixStaticPath()` remaps a `filename` written on another server (or another install directory) by replacing everything before `uploads` with the current root. With no explicit `$root` it rebuilt from bare `ROOT`, which drops the `www`/`var` segment `createPath()` and the `privateStorageModules()` hook above both write under — so a stale row for a module routed to `var/uploads` resolved against `ROOT/uploads/...` instead, nowhere a file has ever lived. It now rebuilds through `storageRoot()`, the same root `createPath()` itself uses.
- Also added an explicit guard for a path with no `uploads` segment at all: the old implementation reached PHP's `str_replace('', ...)` empty-needle behavior here (`substr($original, 0, false)` is `''`), which inserts the replacement before every character instead of leaving the path alone. Returns the original path unchanged now.
- No behavior change for an explicit `$root` (every real caller passes none; the `$root` parameter exists for tests) — the two guards above are the only difference.

## `MediaObject` builds its own sibling objects as `new static()`, so extending it works

### Fixed

- Eleven places inside `MediaObject` build a sibling object of itself — `getInstance()`, `getMediaUsages()`, `staticGetUsages()`, `getList()`, `clearUsage()` and `removeUsage()`'s own sibling-promotion when a media row's last usage goes, `multipleUsageUpdate()`, `urlFor()`, and the upload-time duplicate-by-`md5` check in both `processImage()` and `uploadFile()`. All eleven built a hardcoded `new MediaObject()` (one, `urlFor()`, built `new self()`), so an application extending `MediaObject` directly — rather than forking the file, as every existing consumer of this class has so far — got the base class back from any of these methods it did not itself override: its own `publicUrl()`, its own `storesPrivately()` check, any other override, silently never ran on the objects these methods handed back or acted on. All eleven now build `new static()`, so an inherited method builds the calling subclass instead.
- Reported from an application doing exactly this extension for the first time, method by method, against the methods this and the preceding FW-295 entries converted.

### Documentation

- `docs/Pramnos_Media_Guide.md`: new "Extending `MediaObject`" section under *File Upload*.

## `MediaObject`'s internals a subclass needs are `protected`, not `private`

### Added

- `createPath()`, `_checkFilePath()`, `_checkThumbPaths()`, `fixJpegOrientation()` and `protectUploadDirectory()` were `private`. A private method is never visible from a method a subclass defines itself, whether or not the subclass overrides it — PHP resolves the call in the *calling* method's own class scope, so a subclass's own `addImage()`-style override calling `$this->createPath(...)` failed with `Call to private method` rather than reaching the inherited implementation. All five are `protected` now: unreachable from outside the class or its subclasses, exactly as before, but reachable from a subclass's own methods.
- Reported from the same application completing its real extension after `new static()` above — a working extend surfaced this on the next method it needed to call its own copy of.

### Documentation

- `docs/Pramnos_Media_Guide.md`: a note on the `protected` internals, in the "Extending `MediaObject`" section.

## `MediaObject::load()` runs decoded thumbnails through a new `afterLoadThumbnails()` hook

### Added

- `afterLoadThumbnails(array $thumbnails): array` — no-op by default — runs on what `load()` decoded from the stored row, before it is assigned to `$media->thumbnails`. An application whose history carries thumbnail filenames that are no longer accurate (a server migration, a storage-root split that postdates when the row was written) overrides this to fix them up, without needing its own copy of `load()` — or of the JSON/legacy dual-format decode behind it, which that copy would otherwise have to duplicate too.
- `load()` converted from raw `prepareQuery()`/`query()` to the query builder (rule 12 — touched for the hook anyway) while here. Same behaviour, same caching.
- Requested from the same application that has been extending `MediaObject` through this thread: adopting the JSON thumbnail format outright, with this one hook, means its own `load()` override — which existed only to rewrite stale absolute paths after an old storage split — goes away entirely.

### Documentation

- `docs/Pramnos_Media_Guide.md`: new "afterLoadThumbnails()" example under *Extending `MediaObject`*.
