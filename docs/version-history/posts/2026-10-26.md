## The rich editor: the toolbar and its panel share one sticky wrapper, panels can float under the selected block, and a site's own picture actions hang off a hook instead of a copied file

### Fixed

- The toolbar alone was sticky; the link/picture panel under it was not, so scrolling a long article put an open panel's Address bar off-screen the moment a link or picture deep in the text was edited. The toolbar and the panel now share one sticky wrapper, `.pf-rich-head`.

### Added

- `panels: 'docked' | 'floating'` on `createRichEditor()` (`data-pf-rich-panels` for one field, `'panels' => 'floating'` in `messaging.rich` for the application, `panels` for the Svelte component): floating puts the link and picture panels over the text, just under the block they are about, instead of docked under the toolbar — useful where the toolbar sits far from a long article's middle.
- `pictureActions` on `createRichEditor()`: a list of `{ label, run({ node, at, editor, upload }) }`, drawn as buttons on the picture panel after its address. A site's own picture editing — cropping, filters, swapping a picture already in the text — hangs off this instead of a change to the copied core file.
- A docblock note at the top of `core.js` ("FRAMEWORK-OWNED, refreshed by every `project:resync`"), matching the one already on `lib/debug.js` and other framework-owned project files.
- Reported by an application: three changes written straight into a project's copy of `core.js` were overwritten by the next resync. The sticky wrapper was a bug fix for every project and moved into the core as it was; the panel placement and the picture actions became the two options/hooks above, so the same result no longer needs editing the copy.

### Documentation

- `docs/Pramnos_Rich_Editor_Guide.md`: the `panels` option and attribute, and a `pictureActions` example under *Adding a site's own*.

## `whereLike()` on PostgreSQL: ~30x faster on a large text column, same rows

### Fixed

- `whereLike()` on PostgreSQL compiled to `translate(col::text, …) LIKE translate(?, …)` — two whole-column rewrites, with no index able to help either. Reported by an application: 10.8s for one search on a 30k-row, 29 MB text column. It now compiles to a single `col::text ~ ?` — a native regular-expression match built from the pattern, with every ambiguous letter (`Α`/`Ά`/`ά`/`α`, `Σ`/`ς`/`σ`, …) spelled out as its own character class instead of asked of `translate()`. Same rows, same case/accent-insensitive behaviour, one native operator per row instead of two function calls plus a `LIKE`.
- `ILIKE` was considered and measured faster still, but was not safe to ship as the fix: it folds case through the database's locale, which under the `C` locale (very common, often the `initdb` default) does not touch Greek at all — exactly why `whereLike()` existed in the first place. The character-class regex gets the same speed-up without depending on the server's locale.

### Documentation

- `docs/Pramnos_QueryBuilder_Guide.md`: `whereLike()`'s compiled-SQL example, updated from `translate(…) LIKE translate(…)` to `col::text ~ ?`.
