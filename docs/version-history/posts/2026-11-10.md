## The administration's screens under the API, for a SPA of a part of it

### Added

- **`ScreenApi::mount($r, $path, Screen::class)`** puts an administration screen's actions
  under the API, run through the screen's own `exec()`:
  - `GET {path}` is the list, `GET {path}/{action}/{id?}` a read, `POST {path}/{action}/{id?}`
    a write.
  - The floor, the ability, `auth()` and the screen's own checks hold.
  - A read answers the data its view was given. A write answers its messages and where the page
    would go next. The screen's errors are a 422, in its own words.
- **`AdminApi::routes($r)`** mounts the framework's screens under `/admin/{name}`, every one or
  some (`['rules', 'segments']`). It is opt-in: `init` writes it as a commented line, because
  an administrator's token then reaches the administration too.
- **`Controller::answerTheApi()`** is the mode behind it. `redirect()`, a refusal and the view's
  `display()` end the action with a `ScreenAnswer` instead of a page. An application's screen
  is mounted the same way, with no change of its own.

### Documentation

- Six screen actions that had no docblock now have one, so every route says what it does in the
  API's document.

  See the [API guide](../../Pramnos_API_Guide.md#the-administrations-screens-under-the-api).

## A conversation summed up by the analyst, for its reader

### Added

- **`Summary::of($conversationId, $reader, $since, $language)`** sums up what a reader has not
  read, the last hours, or what came since a time. It answers markdown citing `[#id]`, the
  cited ids, `from`, `to`, `count` and `cut`.
  - It reads only what the reader may read: threads in, deleted messages out.
  - The newest 400 messages and 60,000 characters go to the model.
  - Nothing to sum up is an empty answer with no call.
  - The call is costed to the reader, and the summary is kept nowhere.
- **`summarize/{id}`** on the conversations' screen and API (POST: `since`, `hours`,
  `language`).
- **`conversation_summary`**, the analyst's tool for the same, with the same rights.
- **The summary's language**, when none is asked for, is the messages' own, decided by their
  letters: Greek where Greek letters are the most, English otherwise. The writers' names do not
  count. Asked for "the language most messages are in", a model summed up English messages
  between people with Greek names in Greek. The prompt now names the language, and the answer
  carries it as `language`.

  See the [Conversations guide](../../Pramnos_Conversations_Guide.md#a-summary).

## `timescale:ensure` removes the retention policy app.php says to keep for ever

### Fixed

- **`'retention' => null` in an app.php override was never applied by `timescale:ensure`.** The
  registry's `apply()` removes the installed policy for it. But the command first reads each
  table's state to decide what needs work, and that check knew only about a policy to add or
  change. So it reported "Nothing to do", and `apply()` was never called. The state now reports
  the policy as drift, `retention policy removed (2 years → kept for ever)`, and the run
  removes it. An installation that set this and ran the command still has the policy, and
  the next run removes it.

  See the [Hypertable guide](../../Pramnos_Hypertable_Guide.md).

## A conversation's automations: a message on a schedule, a welcome, a question to the analyst

### Added

- **`Automations`**, what a conversation does by itself:
  - `repeat` posts a message every day, on weekdays, on days of the week or once a month, at a
    time on the installation's clock that stays put across summer time;
  - `welcome` greets whoever comes in, each time they come in, in the conversation or to them
    alone;
  - `ask` puts a question to the analyst on a schedule, answered in the conversation's thread.

  A message is from "Automation", or from whoever set it up. Each one can be paused, changed
  and deleted by those who manage the conversation's tabs. The changes are
  `conversation.automation_*` events in the changelog. `conversations:send-scheduled` runs
  them.
- **The screen's and the API's actions:** `automations/{id}`, `addautomation`,
  `changeautomation`, `pauseautomation`, `deleteautomation`.
- **`Events\MemberJoined`** (`conversation.member_joined`): somebody came into a conversation,
  each time they come in.
- **Migration** `chat.conversation_automations`. Run `migrate`.

  See the [Conversations guide](../../Pramnos_Conversations_Guide.md#automations).

## The site's own traffic, step 3: page views and clicks out written, with where from, place and device

### Added

- **The `visits` feature.** It adds `pramnos.sites` and `pramnos.page_hits`, an append-only
  hypertable on `at`, compressed by site and kept for good.
- **`Visits::tag()`** prints `pf-hits.js` and a `<noscript>` image:
  - a page view when the page is shown (a prerendered page when it is shown);
  - the clicks out, sent as the page is left;
  - `POST /Hits` and `GET /Hits/pixel`, which answer 204 and ask nothing of the session but who
    is signed in.
- **`Hits::take()`** and **`Hits::record()`**, the second for an existing tracker writing beside
  its own:
  - the visitor and the visit: `pf_vid` / `pf_visit` cookies, or a cookieless daily hash;
  - where it came from (`Source::classify()`: direct, search, social, ai, email, campaign,
    referral, internal);
  - the place (`GeoIp`, DB-IP City Lite or the application's own file), device, browser, OS
    and the application's own `dimension`;
  - written through the write spool.
- **Refused:** a foreign origin, a spam referrer, over 60 a minute per visitor, over 20 a
  request. A bot or a page without JavaScript is kept, flagged.
- **`visits:update`** fetches the GeoIP database and Matomo's referrer spam list. It is
  scheduled on the 3rd of each month.
- **`UrlRegistry`:** a table can declare several columns, and `columns()` lists them. `urls:prune`
  keeps what `page_hits` refers to.

  See the [Site traffic guide](../../Pramnos_Visits_Guide.md).

## Web Vitals: the application's dimension, the page's look, the element, no robots

### Added

- **`vitals.dimension`** (`fn (string $path, array $report, array $server): ?string`) fills the
  new `dimension` column: a market, an area, a CDN's country.
- **`ClientVitals::tag(['ui' => …])`** sends the page's look with every report, into the new
  `ui` column, so one theme's numbers can be set against another's.
- **`target`:** for LCP, INP and CLS, `pf-vitals.js` sends the element the attribution build
  names, up to 100 characters.
- **A migration** adds the three columns. Run `migrate`; until then reports are kept without
  them.

### Fixed

- **A lab or a robot is no longer kept as a visitor.** Lighthouse, PageSpeed, GTmetrix, Pingdom,
  WebPageTest, headless and automated browsers, and known crawlers are dropped in `record()`
  (`ClientVitals::isRobot()`). A report with no device takes it from the user agent.
- **The vitals' rate limit was shared with the browser's errors.** They are now counted apart,
  30 a minute per address each, answered with 429 beyond that.

  See the [Logging guide](../../Pramnos_Logging_Guide.md#how-fast-pages-are-for-real-visitors).

## The site's own traffic, step 4b: the daily rollup of pages, referrers, clicks and campaigns

### Added

- **`stats.visit_pages_daily`** (`Visits\Rollup`) keeps people's page views and clicks out per
  UTC day, by site, page, link out, referrer, source and campaign, with the visits that began
  there.
  - On TimescaleDB it is a continuous aggregate over the `page_hits` hypertable, kept by its own

  - Elsewhere it is a table filled by **`visits:rollup`**, scheduled every 30 minutes for
    yesterday and today; `--from`/`--to` fills older days.

  answers `views` and the `visits` that began there; a click out answers its `clicks`.

## Web Vitals and browser errors keep a page's path masked, not its tokens

### Fixed

- **A page's path was kept as the browser sent it**, so a password-reset link, an invitation or
  an RSVP left its live token in `client_vitals.path` and in the browser errors' `page`, for as
  long as the rows were kept.

### Changed

- **Paths are now masked (`Pramnos\Logs\PagePath`):** lower case, six segments at most; a
  segment with a digit, an `@` or over 60 characters becomes `:id`; one with other characters
  becomes `:x`.
- **`vitals.groups` match the masked path**, so a pattern names `:id`, not `\d+`.
- **`vitals.path`** (`fn (string $path): string`) replaces the masking for an application that
  wants its own.

### What breaks

- A `vitals.groups` pattern written with `\d+`. See the
  [Upgrade guide](../../Pramnos_Upgrade_Guide.md#since-v12-unreleased).

  See the [Logging guide](../../Pramnos_Logging_Guide.md#how-fast-pages-are-for-real-visitors).

## A token of the OAuth server stands for the API key

### Added

- **`ApiAuthMiddleware`:** a request with no `apiKey` but a bearer token that this
  installation's OAuth server issued (RS256) is let through as the token's client, read from its
  `client_id`, else its `aud`.
  - The calling application is that client, for its limits and its logs.
  - A public client (PKCE, no secret) needs no key of its own.
  - A client switched off is a 401.
  - A token that does not verify, or an HS256 one, still needs the key.
- **`ApiAuthMiddleware`'s `publicKeyPath`** names the OAuth server's public key where it is not
  `app/keys/public.key`.

  See the [API guide](../../Pramnos_API_Guide.md#a-token-of-the-oauth-server-stands-for-the-key).

## The area's and the assets' addresses on the site's root, from any front controller

### Fixed

- **An administration area's addresses built in an API request pointed under the API.** With
  an API served from `www/api/`, `sURL` ends in `api/`, and `adminUrl()` gave
  `…/api/admin/Conversations`. The same went for the links a write through the API puts in a
  notification, a push or a card. With the site's root configured (`site_url` or `APP_URL`),
  the area is now built on it.
- **`assetUrl()` pointed under the API too.** With no base given, a file found at the site's
  root, above the front controller, is now under the configured site root; one found beside the
  front controller stays under `sURL`.
- **`SiteUrl` no longer makes an application to read `site_url`.** It reads the one running.
  Making one reset what the request had set up, the administration area among it, once
  `adminUrl()` came to ask.

  See the [Routing guide](../../Pramnos_Routing_Guide.md#siteurl-is-the-site-root) and the
  [Upgrade guide](../../Pramnos_Upgrade_Guide.md#since-v12-unreleased).

## `api:docs` reads apidoc's `@api` blocks

### Added

- **`Routing\ApidocReader`** and **`OpenApiGenerator::withApidoc()`.** A route registered with
  nothing said of itself takes the apidoc `@api` block of the same method and path:
  - the title, `@apiDescription` and `@apiGroup`;
  - `@apiParam` as path, query or body parameters;
  - `@apiSuccess` and `@apiError` as responses.

  The version prefix is left out of the match, and `:id` and `{userid}` count as the same
  place. `describe()` and `#[Route]` still win. `api:docs` reads the controllers' directory, or
  `--apidoc=<dir>`.

  See the [Routing guide](../../Pramnos_Routing_Guide.md).

## `api:docs` keeps Greek text whole, and writes nothing it cannot encode

### Fixed

- **A docblock's Greek text was cut at every «υ».** The apidoc reader and
  `Route::fromDocblock()` split lines with `\R` without the `u` flag. Without it, the byte
  `0x85` is a line break, and it is the second byte of «υ» (`CF 85`). The text was left
  invalid UTF-8, and the whole document could not be encoded as JSON. Every pattern over a
  docblock's text now reads it as UTF-8.
- **`api:docs` wrote one byte over a good document and reported success.** A document that
  cannot be encoded now writes nothing: the command names `json_last_error_msg()`, fails, and
  leaves the file as it was.

## `api:docs`: one tag for one thing

### Fixed

- **A route with no description was tagged by its path in lower case** (`account`), beside the
  `Account` of the `@apiGroup` blocks of the same controller, and a viewer showed two sections. A
  tag is now written as the document spells it elsewhere, the first spelling with a capital.

## Two spool drains at once no longer write each row twice

### Fixed

- **A file spool read by two drains at once was written twice.** A drain takes a file by
  renaming it to `….draining`, and takes such a file again when a drain before it left one
  behind. Nothing said whether that drain was still reading. So a second drain started meanwhile
  read it too, and every row was written twice. This happened with the scheduler's `spool:drain`
  every minute beside a migration's own drain: 113,536 duplicate rows on one installation.
  - A drain now holds a lock on the file while it reads, and passes by a file another drain
    holds.
  - It removes the file before letting go, so a drain that was waiting finds it gone.
  - A file whose drain died has no lock, and is taken again.

  The Redis spool was not affected: a list is renamed atomically, so only one drain ever has it.
  Rows already written twice are not removed by this fix.

  See the [Workers guide](../../Pramnos_Workers_And_Daemons_Guide.md#1d-the-write-spool-rows-written-out-of-the-request-path).

## The traffic's sources count visits, and the mean visit leaves out tabs left open

### Fixed

- **The `visits` tool's sources showed most of the traffic under "(none)".** Where a visit came
  from is kept on its landing page alone, so the views of the pages after it had no source. On
  one installation's month that was 782,000 views with no visit. Sources, campaigns and
  referrers now count visits only, on the landing pages.
- **The mean visit was hours long**, pulled up by a few tabs left open. `visits.duration` and
  the tool's `mean_visit_seconds` are now the mean of the visits up to 4 hours, and the tool
  counts the longer ones apart (`visits_over_4_hours`).

## A metric's open month or year computed less often than its day

### Added

- **`Metric::refresh(['month' => '1 hour', 'year' => '1 day'])`**, and `metrics.refresh` for
  every metric. An open period of a grain computed lately enough is passed by, while the day is
  still computed at every run and a period that ends is closed as ever.

### Changed

- **The site traffic's metrics** compute their open week and month hourly, their quarter every
  six hours and their year daily (`visits.refresh` changes it). Every run read the open month
  and year of raw hits again. On one installation that took `metrics:compute` from 3.2 s to
  7.6 s a run (`visits.visitors` alone 16 s), and the run had to be scheduled less often.

  See the [Metrics guide](../../Pramnos_Metrics_Guide.md#computing-and-closing-periods).

## A distinct metric's breakdowns read in one query on PostgreSQL

### Changed

- **`metrics:compute` reads every breakdown of a period at once on PostgreSQL.** A distinct
  metric or a mean keeps its total and each dimension apart, and each was a scan of the period.
  The site traffic's visitors, with nine, made forty-five scans across the five open periods
  (day to year), though each scan took a fraction of a second. A declared source now reads them
  with `GROUPING SETS`, and a closure source can do the same through
  **`Metric::sourceSets()`**, as the per-visit metrics now do. MySQL reads them one at a time as
  before. The figures are the same either way.

  See the [Metrics guide](../../Pramnos_Metrics_Guide.md#computing-and-closing-periods).

## A distinct metric from daily HyperLogLog sketches, where TimescaleDB's toolkit is

### Added

- **`Metrics\Store::sketched()`.** Where the database has TimescaleDB's toolkit, a distinct
  metric declared with `countDistinct()` over a hypertable on a time column, and kept for the
  whole installation, is read from daily HyperLogLog sketches.
  - `metrics:compute` makes a continuous aggregate for each breakdown it keeps, once.
  - A week, a month or a year rolls its days' sketches up, approximate to about 0.6%.
  - Hours, and every other metric, are counted exactly as before.
  - The site traffic's `visits.visitors` is such a metric: the open month and year of raw hits
    were its whole cost.

### Fixed

- **A live metric with no dimension had no aggregate made.** Its `GROUP BY` counted columns
  `2, 1` instead of none, so the aggregate was refused and the metric read its source.

  See the [Metrics guide](../../Pramnos_Metrics_Guide.md#computing-and-closing-periods).

## A token saved again keeps its device label unescaped

### Fixed

- **`Token::save()` wrote `deviceinfo` with `\uXXXX` escapes.** The label was issued unescaped,
  but a token loaded and saved again (its `lastused`, its `actions`) re-encoded it with escapes,
  which a `bytea` column refuses — so the UPDATE failed and the page showed the error. Every
  write and the use-snapshot comparison now encode it the same way, letters and slashes as they
  are.

  See the [Auth Tokens guide](../../Pramnos_Auth_Tokens_Guide.md).

## The messages' to-do marks ask nothing where there is no to-do list

### Fixed

- **`Todos\Chat::messageIds()` queried `pramnos.todos` on every conversation opened**, also on an
  installation without the table. The failure was caught, so the page stood, but the database and
  the application logged an error each time. It now answers no marks without a query when
  `Todos::installed()` says the table is not there (FW-388).

  See the [Todos guide](../../Pramnos_Todos_Guide.md).

## A prepare refused for its own SQL fails once, without a DEALLOCATE

### Fixed

- **On PostgreSQL, a refused prepare outside a transaction was always retried**: a `DEALLOCATE` of
  the statement's plan, then a second prepare. For a statement on a table or column that is not
  there, the plan never existed, so one failure wrote three errors to the server's log. The retry
  now happens only when a plan of that name is on the server (FW-388).

  See the [Database API guide](../../Pramnos_Database_API_Guide.md#a-statement-that-failed-inside-a-transaction-on-postgresql).

## A scheduled run's Greek output no longer loses its run's row

### Fixed

- **The last 4 KB of a run's output were cut by byte**, and a cut inside a multi-byte letter left
  half a character that PostgreSQL refused as invalid UTF-8 — losing the whole finishing update:
  result, exit status and duration, not only the output. The tail now starts on a whole character
  (FW-389).

  See the [Workers and Daemons guide](../../Pramnos_Workers_And_Daemons_Guide.md).

## The conversations' sidebar in a few queries, however many conversations

### Fixed

- **`Conversations::forPerson()` asked five queries per conversation**: two counts, two lookups
  of where the last read message stands — `beyond()` asked for it once per count — and a direct
  conversation's members. Over a hypertable of many chunks each query's planning alone was
  ~16 ms, and a person in 114 conversations waited about two seconds on every refresh. The sidebar
  is now read in at most six queries: the positions in one, the unread in one — asked only of the
  conversations whose newest message stands after what was read — the mentions in one and the
  members in one. The numbers are those `counts()` gives each conversation (FW-390).

### Added

- **`Messages::positions($ids)`, `Messages::standsAfter()` and `Messages::beyondPosition()`**:
  where many messages stand in one query, a comparison of two already read, and `beyond()` with
  the position in hand. `counts()` now reads its position once, not once per count.

  See the [Conversations guide](../../Pramnos_Conversations_Guide.md).

## Underline in a message: `++text++`

### Added

- **`Conversations\Markdown` underlines `++text++`** as `<u>text</u>`, under the same rules as
  `~~`: no space inside the marks, and not against a letter or another `+`, so `C++` and `i++`
  stay text. A preview or a notification (`Messages::plain()`) leaves the pair out (FW-391).

  See the [Conversations guide](../../Pramnos_Conversations_Guide.md).

## A bell without some groups, and told at once when notifications are read

### Added

- **`NotificationBell::render(['except' => [...]])`** leaves groups out of a bell: its count, its
  list and its "mark all read", which leaves them unread. The bell sends `except=` to
  `/Notifications`, and `Feed::list()`, `unreadCount()`, `unreadByGroup()` and `markAllRead()`
  take the same list. For a page whose own screen shows those notifications — the conversations'
  (FW-392).
- **`notification.read`.** `Feed::markRead()`, `markAllRead()` and `settleAbout()` broadcast it on
  the channel of each person whose notifications they read, and the bell in `pf-utils.js`
  refreshes on it, as on `notification.created`. A conversation read in one window clears its
  notifications from a bell in another at once, not at the next poll.

  See the [Notifications guide](../../Pramnos_Notifications_Guide.md).

## A conversation opened at a message: `around`

### Added

- **`Messages::around($conversationId, $messageId, $limit)`** and `around=` on `messages/{id}`: a

## A conversation's push no longer costs a phone its subscription

### Fixed

- **Chrome on Android cancelled the conversations' push subscriptions within hours.** A
  conversation's push asked the worker (`unlessFocused`) to show nothing while a page of the site
  was in front — and the push went to the client the person was in, which was usually in front. A
  push that shows no notification is counted against the subscription, and after a few Chrome
  cancelled it: the server got `410` and dropped it, and the page asked to switch push on again.
  Now no push is sent while that client is in front (`Clients::inFront()`): it tells of the
  message itself from the realtime connection (FW-395).
- **A notification nobody showed.** With another page of the site in front — the administration
  beside the conversations' window — the worker kept the push from showing, and that page did not
  show it either, since it was meant for the other client. A conversation's push no longer asks for
  `unlessFocused`, so it is shown.
- **`unlessFocused`, where a notification still asks for it,** shows a quiet notification under the
  tag `pf-quiet` and closes it at once, rather than nothing, in `pf-push-worker.js` and the
  scaffolded `sw.js`. An application with a copied `sw.js` picks it up with `project:resync --js`.

  See the [Push guide](../../Pramnos_Push_Guide.md) and the
  [Conversations guide](../../Pramnos_Conversations_Guide.md).

## A join on a subquery: `joinSub()` and `leftJoinSub()`

### Added

- **`QueryBuilder::joinSub($query, $alias, $first, $operator, $second, $type)` and
  `leftJoinSub()`**: a derived table joined, as `fromSub()` reads one — a builder or a closure,
  the conditions as `join()` takes them, a closure for several. The subquery's bindings go into the
  `join` slot, before the WHERE's. Until now a join took only a table, and `joinRaw()` no bindings,
  so a grouped count joined to its list had to be two queries sorted in PHP (FW-398).

  See the [QueryBuilder guide](../../Pramnos_QueryBuilder_Guide.md#subqueries).

## The QueryBuilder guide: what a column takes, ordering by an expression, joining a subquery

### Documentation

- **What a column takes**: a bare name, `table.column`, `column AS alias` and an expression, and
  which of them is quoted and why, in `select()`, `where()`, `groupBy()` and `orderBy()` alike. The
  guide showed `orderBy()` with names alone and sent anything else to `orderByRaw()`, and an
  application concluded twice in a day that the builder could not do what it does: order by
  `coalesce(x.c, 0)`, and join a subquery. A test now holds the guide's examples to the grammar.
- **`orderByRaw()`** is for a clause beyond a column and a direction (`NULLS LAST`); neither binds a
  value.
- **Joining a subquery** is in the Joins section, and `joinRaw()` points to `joinSub()`.

  See the [QueryBuilder guide](../../Pramnos_QueryBuilder_Guide.md#what-a-column-takes).

## Rotating a picture that cannot be read answers false, and a WebP named .jpg is rotated

### Fixed

- **`MediaObject::rotateLeft()` / `rotateRight()` ended in a `TypeError`** from `imagerotate()`

## An insert on a builder that asked first writes its row

### Fixed

- **`insert()` on a builder that had a WHERE failed every time.** `table('x')->where('k', $k)`, then
  `exists()`, then `insert()` on the same instance sent the WHERE's bindings after the insert's
  values: the arguments no longer matched the placeholders, the statement failed with "wrong number
  of arguments", and nothing was written. An INSERT has no WHERE, JOIN or ORDER of its own, and
  `insert()`, `insertOrIgnore()`, `upsert()`, `insertMany()` and `upsertMany()` now bind their own

## HEIC photos, and an iPhone's colours, where Imagick is installed

### Added

- **`Pramnos\Media\Imaging`**. Imagick is optional, and is used where it is installed. A HEIC,
  HEIF or AVIF upload, which GD cannot read, is stored as a JPEG (a PNG when transparent), upright
  and without its metadata (GPS among it). A Display P3 photograph is rewritten in sRGB, so GD's
  thumbnails keep its colours. The format is read from the bytes, so a PDF, an SVG or a script
  named as a picture never reaches Imagick. Each call is limited to 256 MB, 64 MP, 30 s and one
  thread. `Imaging::uploadExtensions()`, `convertibleExtensions()`, `readable()` and `format()` say
  what this server takes. Without Imagick nothing changes (FW-402).
- **`Pramnos\Media\IccProfile`**: sRGB and Display P3 built from their numbers, so no `sRGB.icc`
  is needed on the server.
- **The test image has Imagick** (3.8.1, ImageMagick 7.1.1 with HEIC/AVIF decoding), so this path
  runs in the suite. It is a layer of its own in the `Dockerfile`, and `docker-compose build
  php-apache-environment` rebuilds it.

### What changes

- Where Imagick is installed, a non-sRGB photograph's metadata is removed at upload. See the
  [Upgrade Guide](../../Pramnos_Upgrade_Guide.md#since-v12-unreleased).

  See the [Media guide](../../Pramnos_Media_Guide.md#pictures-gd-cannot-read-imagick-where-it-is-installed).
