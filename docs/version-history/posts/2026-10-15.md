## "Saved." is shown

### Fixed

- The bundled admin screens flash "Saved." and redirect, and the screen they land on does not
  print the flash; neither did any scaffolded header. The message was written, carried across
  the redirect, and never seen. `Html\Flash::render()` draws the flash, escaped and taken so
  it is shown once. Every scaffolded `theme.html.php` calls it above `[MODULE]`, and every
  scaffolded stylesheet styles `pf-flash`.
- A view that shows the flash itself takes it first, so the layout repeats nothing.
  `ApplicationsController`, which read it without taking it, now takes it.

A project scaffolded before adds the one line to its layout. See the Upgrade Guide.

## `project:switch-ui` keeps what it replaces

### Fixed

- `project:switch-ui` wrote the default theme's layout files and `style.css` over whatever the
  application had made of them, with no copy and no word. A file whose contents it changes is
  now copied to `var/switch-ui/<time>/` first, and the output names each one.
- It installed into `www/` whatever the project served from. It now uses the project's web root
  (`public/`, …).
- It names the views copied with `project:publish-views`, which keep the old system's markup,
  and how to take the new copy.
- Switching to Tailwind with no CSP `style-src` to update now says what to add, instead of
  reporting the CSP as updated.

## Smaller things the documentation review found

### Fixed

- **`Html\Datatable`'s column picker.** It was a Bootstrap 3 dropdown under every UI system,
  so it opened nothing under Bootstrap 5 or Tailwind. `$bootstrap` now follows
  `scaffold_theme`, and the Bootstrap dropdown carries both 3's and 5's attributes.
- **The scaffolded Tailwind header** filed a child whose parent the visitor may not see under that
  missing parent, and never printed it. It is promoted to the top level.
- **Unread badges.** The scaffolded headers drew none: only template files `init` does not use
  had them. All three now print `NavItem::badgeHtml()`, a `pf-nav-badge` styled by every
  stylesheet.
- **The Help menu item** took its floor from app.php's `admin` block only. An application that is
  the area, through `AdminArea::serve()`, listed it to every member. It takes the area's floor.
- **`Theme`:**
    - a layout without `[MODULE]` lost its first eight characters to the foot and had no head;
      it is now all head;
    - a missing theme layout is logged to the `theme` log;
    - `get_search_form()` reads `searchform.php`;
    - `front-page` is an element by name. It was written with a comma for its arrow.
- **Tailwind `.form-control`.** The Tailwind stylesheet styles `form-control`, the class
  `Html\Date` carries.
- **Docblocks:**
    - `NavItem::$icon` is an icon name, not a CSS class;
    - `AdminArea::reset()` has its own docblock;
    - `FieldStyles::for()` has its own;
    - `scaffold_theme`'s `plain-css` is said to resolve to the `plain` preset.
- **Examples.** The Components Guide's `Field` examples follow the UI system, with
  `FieldStyles::configured()`, instead of naming one.

## An administration that is its own application, declared in its config

### Added

- `'admin' => ['serve' => true, 'prefix' => 'admin', 'min_usertype' => 90]` in the config of an
  administration with its own front controller: the application serves the area from its
  constructor on. Its navigation and the area's language are built inside it, `src/Admin/` is in
  scope as for an area, and `admin.theme` and `admin.default_controller` apply.

### Fixed

- `AdminArea::serve()` called from `init()` had four faults, each fixed:
    - **The navigation linked to the site**, because it is built in `init()` before the call.
      `serve()` now builds it again, and logs that the config is the place for it.
    - **`src/Admin/` was never in scope.** It now is.
    - **A front controller in `www/admin/` linked to `/admin/admin/…`.** The area's URL is now
      `sURL` itself when `sURL` already ends in the prefix.
    - **From the second request one process served, the area was forgotten.** So was a sign-in
      page set with `useLogin()`. `Application::beginRequest()` now resets only the request's
      state, with `AdminArea::resetRequest()`.

## Testing an application's JavaScript with the framework's runner and helpers

### Added

- `test:js`: `node --test` over the application's `*.test.js`, from `js_tests_dir` in `app.php`
  (default `tests/js`). The framework's helpers are on `NODE_PATH`.
- `lint:js`: ESLint with the framework's rules, which are defects only. It uses the application's
  `eslint.config.mjs` when there is one, and that config extends
  `resources/js/pramnos-testing/eslint.base.mjs`.
- `require('pramnos-testing')`:
    - `createDom()`, a small DOM whose events bubble to the document and window;
    - `loadScript()`, which runs a classic page script in it;
    - `stubFetch()` and `installApiHeaders()`;
    - `installJquery()`, a jQuery-shaped stub for legacy code.

  They are shipped in the package, under `resources/js/`, so an application uses them rather
  than copying them.

## A SPA section inside a server-rendered page

### Added

- `spa_sections` in `app.php` and `Controller::spaSection($name, $props)`: one part of a
  server-rendered application runs as a single-page section inside the theme's page.
    - The controller returns a mount element (base, API configuration and props as attributes,
      no inline script) and the entry's tags: dev server, manifest, or the file.
    - A declared `ability` is checked first.
    - The page is never page-cached.
    - Every address under the controller reaches `display()`, so deep links and reloads open
      the section where they point.
- `lib/section.js` gives a section its mount element and a router under its base.
  `lib/page.js` gives it the layout's flash, the title, and the side panel's record.
- Every `frontend/sections/<name>/main.js` is an entry of the scaffolded Vite build.
- The scaffolded `lib/api.js` sends the page's CSRF token from `<meta name="csrf">`, so a
  section's writes are accepted with the page's session.
- `pramnos-testing`: `window.dispatchEvent`.

## The SPA's shared components follow the UI system

### Added

- `lib/ui.js`: the classes `DataTable`, `Pagination`, `ConfirmDialog`, `Field`, `Omnibox` and
  `HelpPanel` draw with, per UI system: daisyUI, Bootstrap 5, or plain-css. Each part is asked
  for by name, and the system is the page's (`window.__PRAMNOS__.ui`). A SPA section takes it from
  `scaffold_theme`, so a section inside a Bootstrap or plain-css page draws in that system's
  classes and follows `project:switch-ui`.
- `pf-ui-*` hooks in the scaffolded `bootstrap` and `plain-css` stylesheets cover what those
  systems have no class for: layout, the modal, the side panel, a sticky table header.

### Fixed

- The Svelte `Omnibox` showed nothing beside a group from a source with `'count' => false`.
  It shows `5+`, as the server-rendered search box does.

## The side panel's buttons and look are the theme's

### Added

- **Openers.**
    - `pf-assist.js` treats every `[data-pf-assist-open]` as an opener; `="help"` or `="ask"`
      opens the panel on that tab.
    - `Panel::opener($tab, $label, $class, $attributes)` draws one such button, and
      `Panel::template($ask, $askUrl)` draws the panel without one.
    - `Analyst::canAsk()` says whether to offer Ask.
- **`'assist' => ['styles' => 'theme']`** drops the panel's inline styles. It then carries only
  its `pf-assist-*` classes, which every scaffolded stylesheet styles. `init` writes the key; a
  project without it keeps the inline look.

## The notification feed, and a bell for it

### Added

- `Pramnos\Notification\Feed`: one person's notifications, read back from what the `database`
  channel stored.
    - `list()` returns a page, unread only or not, by group.
    - `unreadCount()` and `unreadByGroup()` return the counts.
    - `markRead()` and `markAllRead()` touch only that person's rows.
    - Groups come from `'notifications' => ['groups' => …]` (by class) or from the stored
      `group`.
    - `Feed::badge()` is a NavItem badge.
- `NotificationsController` (`/Notifications`): the feed as JSON with the page's session, with the
  CSRF token on writes. `init` writes the wrapper with `auth`.
- `Html\NotificationBell` and its behaviour in `pf-utils.js`.
    - Polling runs only while the tab is visible.
    - A click on an item marks it read, then follows its link. Read-all and tabs by group are
      there too.
    - `pf:notifications:refresh` and a realtime channel refresh it at once.
    - The scaffolded stylesheets style `pf-notify-*`.
- `pramnos-testing`: `contains()`.

### Documentation

- The Notifications Guide's **Showing the feed** replaces "reading is the application's job".

## A whole Svelte SPA follows the UI system

### Added

- The shell `App.svelte`, the admin, chat, scheduled-report and consent screens, and the screens
  `create:crud` generates ask `lib/ui.js` for their parts, like the shared components already did.
  So a Svelte SPA in a `bootstrap` or `plain-css` project draws with that system's classes.
    - New parts include `navbar`, `brand`, `nav.link`, `card.raised`, `card.title`,
      `alert.success`, `alert.warning`, `badge.*`, `input.inline`, `select.inline` and
      `table.zebra`.
    - Sizes and shapes combine with a variant: `ui('btn.primary', 'size.sm')`.
- `frontend/ui.css`, imported by `app.css`, is the stylesheet of the project's UI system:
    - `tailwind`: daisyUI.
    - `bootstrap`: Bootstrap from npm, plus the theme's tokens and stylesheet.
    - `plain-css`: the theme's tokens and stylesheet.
    - The last two also include the daisyUI components neither has (chat, dock, stats, join,
      divider, tabs, loading).
    - `init` writes it, and `bootstrap` is in a Svelte SPA's `package.json` whatever the system.
- The SPA shell reads `scaffold_theme` from app/app.php when it runs. It publishes it as
  `window.__PRAMNOS__.ui`.
- `project:switch-ui` rewrites a Svelte SPA's `ui.css`, keeping the previous copy. It then says
  what is left to do:
    - run `npm run build`;
    - in an `app.css` that registers daisyUI itself, replace `@plugin "daisyui";` with
      `@import "./ui.css";`;
    - in a project without the package, `npm install -D bootstrap`.
- A framework test fails on a Svelte stub that writes a class two systems define (`btn`, `card`,
  `table`, …) instead of asking `ui()`.

### Documentation

- In the Application Styles Guide, **The whole SPA follows the UI system** replaces the section on
  the shared components alone.

## The log screens under another address, and a search box with its term

### Added

- `LogController` builds every link from `logsRoute()`: breadcrumbs, redirects, the toolbar,
  "Go back", the viewer's address and the `stats`/`dashboard` views. By default that is the
  subclass's class name; `protected ?string $logsRoute` sets another.
    - So an application with a `Logs` controller of its own mounts the viewer as
      `class Logfiles extends LogController`, with nothing to override.
    - Under any address but `Logs`, the bundled `logs` views come before the application's.
- `Html\SearchBox::$value`: the term already in the box, escaped.

### What breaks in subclasses

- A `LogController` subclass not named `Logs` that is still served at `/Logs` now links to its
  own name. Add `protected ?string $logsRoute = 'Logs';`.

### Documentation

- The Logging Guide has a new section, **Under another address**. In the HTML Components Guide,
  `SearchBox` shows `$value`. There is a new row in the Upgrade Guide.

## Charts with no inline script, in the theme's colours

### Added

- `Html\Chart::render($type, $labels, $datasets, $options)` renders a figure:
    - the data as JSON in a `<script type="application/json">`, which no CSP blocks;
    - a hidden canvas;
    - a table of the same numbers;
    - and it enqueues `chartjs` where it is registered.
- `pf-utils.js` draws each figure:
    - in the theme's colours (`--color-*`, `--bs-*` or `--primary-color`), again when
      `data-theme` or the OS colour scheme changes;
    - with numbers in the page's language through `Intl.NumberFormat`;
    - and the table is kept for screen readers once the chart is drawn.
- Every `components.css` styles `pf-chart-*`.

### Changed

- The log dashboard in all three themes draws its two charts with `Html\Chart`. It had an
  inline `<script>` with hard-coded colours.

### Documentation

- The HTML Components Guide has a new section, **Chart**.

## A template cannot change the render that included it

### Fixed

- Before, a template was included inside `View::getTpl()`, so it could assign that method's
  locals. A template with `$render = [...]` of its own made `getTpl()` return the page instead of
  keeping it, and the page came out blank with nothing in any log.
- Now a template runs in a scope of its own, with copies of `$lang`, `$model`, `$_url`, `$doc`,
  `$tpl` and `$type`. Its variables still reach the layout it declares.

### Documentation

- The Framework Guide has a new section, **What a template sees**.

## Settings forms no longer turn checkboxes on or blank settings

### Fixed

- **An unchecked checkbox was saved as checked.** A checkbox is rendered with a hidden `0`
  before it. `Field::readSubmitted()` read anything but an empty string as on, so the hidden `0`
  became `'1'`. It now reads `''` and `'0'` as off.
- **A rejected submission could blank every setting.** `SettingsForm::getData()` returned `[]`
  when the form's own token was missing, and a caller that saved it wrote empty values over the
  stored ones. That included a page that embedded the fields in a form of its own and sent only
  the synchronizer token.
    - `getData()` now accepts the synchronizer token too (`_csrf_token` or the `X-CSRF-Token`
      header), as `Controller::isVerifiedWrite()` does.
    - When no token checks out, it throws `Html\Form\TokenRejected`.
    - `Theme::saveSettings()` catches it and saves nothing.

### Documentation

- The Theme Guide's **Rendering and saving** covers both tokens and `TokenRejected`.
- There is a new row in the Upgrade Guide.

## Errors in the browser are recorded

### Added

- **`pf-utils.js` reports what a page hits.** It sends uncaught errors and unhandled rejections to
  the address in `<meta name="pf-client-errors">`, with `sendBeacon()`.
    - Each distinct error goes once per page, and at most ten per page.
    - `window.pfReportError(error)` reports one the page caught.
    - Every theme's `head.php` written by `init` carries the tag.
- **The scaffolded service worker reports its own errors** to the same address.
- **`ClientErrorsController` (`/ClientErrors`) takes the reports.** It is open to visitors who are
  not signed in, and accepts only a same-origin request, a body of up to 16 KB and 30 reports a
  minute per address. `init` writes the wrapper.
- **`Logs\ClientErrors` stores one row per distinct error**, with a count, first and last seen,
  the latest page, browser and user, and the stack.
    - It accepts the older `{error, agent}` shape under the hash applications computed for it.
- **A `javascripterrors` migration** creates the table. Where an application already has its
  six-column table, the migration adds only the new columns, so the rows and the screens
  written against them stay.
- **The log screens have a Browser Errors page**, with delete and clear.

### Documentation

- The Logging Guide has a new section, **Errors in the browser**, with the steps for an existing
  project.

## The service worker can replace an application's own

### Added

- **An offline page.** A navigation that fails for want of a network shows `offline.html`, or
  the page named with `?offline=` in the registration. It is stored on install in a cache of its
  own. Pages themselves are still never stored.
- **An "offline" placeholder** for an image with no cached copy and no network.
- **A `{command: 'broadcast', message}` message**, relayed to every page the worker controls as
  `broadcastOnRequest`.
- **The worker reports its own errors** to `ClientErrors`.

### Fixed

- **Another worker's stale copy could be served.** The worker read assets with `caches.match()`,
  which searches every cache on the origin, so a copy an earlier worker stored came first. It
  now reads its own cache only.
- **An earlier worker's caches are deleted on activation.** These are the hand-versioned
  `…::static`, `…::pages` and `…::images`; the `pages` one holds signed-in pages.

### Documentation

- The Service Worker Guide has two new sections: **The offline page, and an image with no
  network** and **Replacing a worker of your own**.

## Data tables draw with daisyUI or the plain stylesheet

### Changed

- Under `scaffold_theme` `tailwind` or `plain-css`, `Html\Datatable` gives DataTables that
  system's classes for the controls it writes itself:
    - the search box and the page-length select;
    - the page buttons, the processing note and Buttons' buttons.

  It also uses DataTables' own pager renderer and the `lfrtip` layout, replacing a Bootstrap

  It is wrapped in `.pf-datatable`.
- Every `components.css` styles DataTables' DOM under `.pf-datatable`: the controls, the

### Documentation

  Datatable.

## A Redis token bucket refills whatever the float precision

### Fixed

- `Http\TokenBucket` on Redis passed the time and the rate to its script as PHP floats. phpredis
  writes a float as text by the `precision` ini setting, so at a low setting the time reached Redis
  rounded to whole seconds, and a token due within the second did not come back. Both are now
  formatted to the microsecond.
- The token bucket tests waited with one `usleep()`, which a signal can cut short. The suite has
  workers with async signals, and a refill test failed under a full run that way. They now wait
  until the time has actually passed.

## A dashboard each administrator arranges

### Added

- **`Pramnos\Dashboard\Widget`** describes one card: id, title, `allowed()`, size, whether a
  new dashboard has it, a link, and `render()`.
- **`WidgetRegistry`** holds the widgets: the framework's four (active users, API, database,
  health), those listed under `'dashboard' => ['widgets' => […]]`, and those registered in
  code. `'framework' => false` leaves the framework's four out.
- **`Layouts`** keeps each person's layout per area in `user_dashboards`, from a new migration.
  A layout is cleaned of what its owner may not have whenever it is read or written.
- **`DashboardController::display()`** draws the person's widgets in their order and widths.
  The new actions `savelayout` and `resetlayout` are POST-only.
- **In all three themes, `admin_dashboard` is arrangeable.** "Customise" shows tools to move,
  resize, hide and add cards. They are buttons, so a keyboard can do all of it, and a mouse can
  drag. `pf-utils.js` saves each change at once.
- **`pramnos-testing`'s `createDom()`** has `nextSibling` and `previousSibling`.
- **A widget has the controller drawing it**, as `$this->controller` (`setController()`), for a
  model.

### Changed

- The dashboard's figures are worked out once per request, and a view of the older shape still
  receives them.

### Documentation

- A new **Dashboard Guide**.
