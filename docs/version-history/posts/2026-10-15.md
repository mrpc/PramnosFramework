## An administration area theme, in the Theme Guide

### Documentation

- The Theme Guide's **An administration area theme** covers:
    - what `'admin' => ['theme' => …]` changes;
    - that the admin screens and their partials are not the theme's;
    - a checklist of what the theme must provide (the layout, `[MODULE]`, the UI system's CSS,
      the palette tokens, `renderCss()`/`renderJs()`, `pf-utils.js`, the admin menu and the
      flashed messages) and what goes wrong without each;
    - the optional parts (search box, side panel, badges);
    - a minimal four-file theme that reuses the site's head and footer.

## Writing views that survive a UI switch

### Documentation

- The Theme Guide's **Writing views that survive a UI switch** covers:
    - what `project:switch-ui` changes and leaves alone, including that it overwrites the
      default theme's layout files and `style.css` and never touches the application's views;
    - which components adapt on their own and which do not: `Datatable` with its default
      `$bootstrap = true` draws a Bootstrap 3 column picker, `Date` uses `form-control`, and
      `component_classes` is one map for every system;
    - what stays tied to a system;
    - a recommended approach, a before/after example, and a decision rule for a project with
      many templates.

## "Saved." is shown

### Fixed

- The bundled admin screens flash "Saved." and redirect, and the screen they land on does not
  print the flash; neither did any scaffolded header. The message was written, carried across
  the redirect, and never seen. `Html\Flash::render()` draws the flash, escaped and taken so
  it is shown once. Every scaffolded `theme.html.php` calls it above `[MODULE]`, and every
  scaffolded stylesheet styles `pf-flash`.
- A view that shows the flash itself takes it first, so the layout repeats nothing.
  `ApplicationsController`, which read it without taking it, now takes it.

A project scaffolded before adds the one line to its layout. See the Upgrade Guide.

## `project:switch-ui` keeps what it replaces

### Fixed

- `project:switch-ui` wrote the default theme's layout files and `style.css` over whatever the
  application had made of them, with no copy and no word. A file whose contents it changes is
  now copied to `var/switch-ui/<time>/` first, and the output names each one.
- It installed into `www/` whatever the project served from. It now uses the project's web root
  (`public/`, …).
- It names the views copied with `project:publish-views`, which keep the old system's markup,
  and how to take the new copy.
- Switching to Tailwind with no CSP `style-src` to update now says what to add, instead of
  reporting the CSP as updated.

## Smaller things the documentation review found

### Fixed

- **`Html\Datatable`'s column picker.** It was a Bootstrap 3 dropdown under every UI system,
  so it opened nothing under Bootstrap 5 or Tailwind. `$bootstrap` now follows
  `scaffold_theme`, and the Bootstrap dropdown carries both 3's and 5's attributes.
- **The scaffolded Tailwind header** filed a child whose parent the visitor may not see under that
  missing parent, and never printed it. It is promoted to the top level.
- **Unread badges.** The scaffolded headers drew none: only template files `init` does not use
  had them. All three now print `NavItem::badgeHtml()`, a `pf-nav-badge` styled by every
  stylesheet.
- **The Help menu item** took its floor from app.php's `admin` block only. An application that is
  the area, through `AdminArea::serve()`, listed it to every member. It takes the area's floor.
- **`Theme`:**
    - a layout without `[MODULE]` lost its first eight characters to the foot and had no head;
      it is now all head;
    - a missing theme layout is logged to the `theme` log;
    - `get_search_form()` reads `searchform.php`;
    - `front-page` is an element by name. It was written with a comma for its arrow.
- **Tailwind `.form-control`.** The Tailwind stylesheet styles `form-control`, the class
  `Html\Date` carries.
- **Docblocks:**
    - `NavItem::$icon` is an icon name, not a CSS class;
    - `AdminArea::reset()` has its own docblock;
    - `FieldStyles::for()` has its own;
    - `scaffold_theme`'s `plain-css` is said to resolve to the `plain` preset.
- **Examples.** The Components Guide's `Field` examples follow the UI system, with
  `FieldStyles::configured()`, instead of naming one.

## An administration that is its own application, declared in its config

### Added

- `'admin' => ['serve' => true, 'prefix' => 'admin', 'min_usertype' => 90]` in the config of an
  administration with its own front controller: the application serves the area from its
  constructor on. Its navigation and the area's language are built inside it, `src/Admin/` is in
  scope as for an area, and `admin.theme` and `admin.default_controller` apply.

### Fixed

- `AdminArea::serve()` called from `init()` had four faults, each fixed:
    - **The navigation linked to the site**, because it is built in `init()` before the call.
      `serve()` now builds it again, and logs that the config is the place for it.
    - **`src/Admin/` was never in scope.** It now is.
    - **A front controller in `www/admin/` linked to `/admin/admin/…`.** The area's URL is now
      `sURL` itself when `sURL` already ends in the prefix.
    - **From the second request one process served, the area was forgotten.** So was a sign-in
      page set with `useLogin()`. `Application::beginRequest()` now resets only the request's
      state, with `AdminArea::resetRequest()`.
