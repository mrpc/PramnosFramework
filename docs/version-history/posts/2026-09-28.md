## Two of the three paths that run a migration left the column cache stale

`getColumns()` caches a table's schema for an hour. `MigrationRunner::run()` has flushed it
since a raw `ALTER TABLE … ADD COLUMN` left every reader an hour behind — but it is not the
only way a migration runs, and the other two had nothing.

### `rollback()`

`run()` flushed and its mirror did not. A `down()` that **drops** a column is the more
confusing direction: every reader goes on believing the column is there, so code selects one
the database no longer has and the failure is a query error a long way from the rollback.

It became reachable in more cases two days ago, when the runner started emptying the
`addQuery()` queue on that path too — before that, a `down()` written against the queue
changed nothing at all.

### `Application::runMigration()` — and it had the other bug too

The legacy loader, which `upgrade()` uses and which `exec()` reaches on its own when the
version check fails. It had **neither** of the two things `MigrationRunner` learned:

- **`addQuery()` queued and nothing emptied the queue.** A legacy migration that queued its
  statements and returned was recorded in `schemaversion` and changed nothing — precisely
  the defect fixed two days ago, in the caller nobody looked at. Two callers, one fix, and
  only one of them had it.
- **No flush**, so the column a migration added stayed invisible for an hour.

The flush is in a `finally` rather than after the insert, because a migration that raised
**half way** is the worst of the three outcomes: some of its DDL ran, the ledger has no row,
and the cache is now wrong about a table nobody knows changed. There is a test for exactly
that case.

### What is still on you

A schema changed by hand outside `migrate`, and — on more than one node — the other
machines, whose caches none of this can reach. `cache:clear` after `migrate` in a deploy
script was never wrong to.

### Documentation

- **Migration Guide** — a table of which path flushes when, why the rollback matters for the
  opposite reason to the rest, and that emptying the queue now holds on both paths.

## …and the cache they flush was keyed by table only, so two databases answered for each other

`schema_columns_<table>`, with the prefix resolved into the key and **the database not**. So
two databases behind one cache — an installation's test and dev, or two installations on one
Redis — shared a column list per table name.

The symptom is the quiet kind. A model saved against a test database silently dropped three
columns a migration had just added: a command run against the dev database on the same
Redis, with that migration not yet applied, had rewritten `schema_columns_properties` with
its older list, and `Model::_save()` used it. The columns read back as null and nothing
refused anything.

**Test and dev is the common case and the worst one**, because the two are *meant* to differ
while a migration is being written — which is exactly when somebody is reading the result
and drawing conclusions from it.

### The same shape as the half that was already fixed

That method's doc-block already tells this story about the **prefix**: the `#PREFIX#` marker
used to reach the cache unresolved, so `alpha_users` and `beta_users` shared one entry, and
"two installations with different prefixes shared one entry" was written down as the reason
to resolve it. The database was the other half of the same sentence and was left.

### Fixed

- `columnCacheCategory()` takes the connection, and the key is
  `schema_columns_<database>_<schema>_<table>`. The schema is in it because PostgreSQL holds
  two tables of one name in two schemas, which is what `authserver.x` relies on.
- **Empty when the connection cannot say which database it is on.** A hand-built connection
  or a test double has nothing to scope by, and inventing something would be worse than the
  bug: two callers that invented differently would stop sharing an entry they are entitled
  to.
- Entries under the old key become unreachable rather than wrong. They expire on their own,
  so the change is a one-time invalidation nobody has to run.

### Two tests, because the key and the wiring fail differently

The unit test holds the **format**. The integration test creates the same table in two real
databases with different columns, reads through two connections in **both orders**, and
holds the **wiring** — because a key that is right while the caller passes nothing is the
shape these failures keep taking, and it would pass every assertion about the format.

Both orders, because a cache bug is usually only wrong one way round: reading the shorter
list first drops a column silently, reading the longer one first claims a column that does
not exist and fails as a query error instead.

### Documentation

- **Migration Guide** — "the key carries the connection", with what the failure looked like.
- **Upgrade Guide** — a row: nothing to run, but a subclass of `Database` overriding
  `columnCacheCategory()` is a fatal at class load until its signature matches.
