## The mail-template editor had no way in for an application's own categories

Yesterday's registry gave the framework's four categories a title, a description and a
placeholder list, and taught the editor to show all three. The reason it was written:

> an operator opening Administration → Mail templates saw an empty list and had no way to
> learn that `auth.twofactor_code` exists, let alone that `{code}` and `{minutes}` are the
> things it may say.

An application sending its own mail through `MailChannel` got precisely that — a category
name, an empty body and nothing else. The sentence the registry exists to make false was
left true for everybody except the framework.

**And `placeholdersFor()` said so in its own doc-block**: an empty list is returned "for one
the framework does not declare — an application's own category, which it documents itself".
There was nowhere to do that documenting. An invitation to a door that was not there.

### Three locked doors, each locked in a way that looked open

- `all()` was a hard-coded literal with no registration.
- `MailTemplatesController::placeholders()` is `public static` and was called as
  **`self::`**, not `static::`. `Init.php` generates a subclass of that controller for every
  application and its doc-block invites overriding — so the override was reachable only by
  calling it directly, which is the one caller the framework never uses.
- `view()` and `edit()` return the rendered HTML, so an override calling `parent::view()`
  adjusts a string after the page has been produced.

The reporting project had a subclass with a placeholder override, view overrides and **a
unit test that passed** — because the test called the static method directly.
`empty($string->categoryNote)` does not warn, so three dead methods read as a working
feature for as long as nobody opened the screen.

### Fixed

- **`SystemMailTemplates::register()`**, merged behind the framework's own. An application
  registers from a service provider's `boot()` and the editor answers for its categories the
  same as for the framework's — no subclass, no override.
- **The framework's own win a collision.** An application cannot redefine what
  `auth.twofactor_code` advertises: the notification supplying those variables is the
  framework's, and a disagreeing entry would put `{like_this}` in somebody's email with the
  screen's blessing.
- **`builtIn()`** for the two callers that must not see registrations — the seeding
  migration, which would otherwise invent rows for mail the framework does not send, and the
  drift test, which would fail on any category no framework notification answers to.
- **`self::placeholders()` → `static::`** in `view()`, `edit()` and `test()`. A `public
  static` method on a class the framework generates a subclass of is an extension point
  whether or not it was meant as one, and late static binding is what makes it one.

### The test that would have caught it

`RegisteredMailCategoryReachesTheScreenTest` asserts on **what the screen is handed**, not
on what the registry answers. A registry that is right while the controller never asks it is
exactly the shape this failed in, and the reporting project's passing unit test is what that
shape looks like from inside. It also holds the subclass override, for the same reason.

### Documentation

- **Notifications Guide** — "registering your own category": the call, where to make it,
  that the framework's own win a collision, and that registering is about what the editor
  shows rather than whether a row exists.
