## `db:migrate-from-mysql`: the dry run names a backfill time column without an index

### Added

- **`--dry-run --time-column=…` names every table whose time column no index in MySQL starts
  with**, and gives the `CREATE INDEX` to run before the backfill. A backfill window is a range
  on that column. Without such an index, every window reads the whole table, which for years of
  history means days. A column that comes second in a composite index is named too, since that
  index does not serve a range on it.

## `db:migrate-from-mysql --defer-indexes`

### Added

- **`--defer-indexes`**, for `full` and `operational`, drops a migration-made table's plain
  indexes for the load and makes them again once the rows are in.
    - Each definition is recorded in `pramnos_migration_progress` before the index is dropped.
      A load that dies leaves what is needed, and the next run of any phase makes the indexes
      again, with or without the option.
    - Unique indexes and those behind a constraint stay, because `ON CONFLICT` and the keys
      need them.

## `db:migrate-from-mysql --zero-date`, NUL bytes counted, one conversion for move and verify

### Added

- **`--zero-date='1970-01-01 00:00:00'`** names what MySQL's zero date becomes in a column that
  takes no NULL. Such a row used to be refused, with no way around it but editing the source.
  The result counts the replacements.
- **Values that lose a NUL byte on the way are counted.** PostgreSQL text cannot hold one, so it
  is dropped, and that used to happen without a word.

### Changed

- **One conversion, `Pramnos\Database\FromMysql\RowConverter`, serves the move, the key
  comparison and the window digest.** Each had its own copy of the encoding repair, so a fourth
  rule would have had to be added three times. What is verified is now what was written, by
  construction.

## `db:migrate-from-mysql`: the dry run names triggers, views, routines and events

### Added

- **The dry run names MySQL's triggers, views, procedures, functions and events.** None of them
  moves, because their logic is in MySQL's dialect and belongs to the migrations. The dry run
  says, for each, whether the target already has one of that name, so the one the migrations
  forgot stands out.

## `db:migrate-from-mysql`: an enum keeps its list

### Changed

- **An `enum` column in a table the command makes is `text` with a `CHECK` on its list.** It used
  to be plain `text`, so any word would do.
    - The list takes `''` too. Outside strict mode, MySQL stores `''` for a value not on the list,
      and an installation's old rows hold it.

## The MCP endpoint lists only the scopes it takes (FW-157)

### Changed

- **A protected resource's `scopes_supported` lists what that resource takes.** An MCP connector
  asks for everything listed there, and the user's role allowed all of it. A Root user connecting
  to `/api/1.0/mcp` got a token carrying `system:admin`, `system:audit_read` and the rest, to
  call tools that needed `mcp`. Now:
    - the MCP endpoint lists `mcp`, the scopes its offered tools require, and `offline_access`;
    - a path named in `'oauth' => ['resource_scopes' => [...]]` lists those;
    - the site itself, and any other path, list every scope, as before.
- **The MCP endpoint's `401` names the same scopes in `scope="…"`**, which the MCP spec has a
  client prefer.

### What breaks

A client that connected through the MCP endpoint and relied on getting other scopes as well. It
asks for them, or the path is given its list. The Upgrade Guide has the row.

## MCP `initialize` carries the analyst's instructions (FW-161)

### Added

- **`McpServer::setInstructions()`.** The text is sent as `instructions` with `initialize` (MCP
  2025-03-26), and a client passes it to its model.
- **The HTTP endpoint sets it from the application's analyst**, through
  `AnalystAssistant::mcpInstructions()`. It carries `about()`, the analyst's clock, its rule about
  people, that masked values stay masked, and which tool to reach for. That is
  `toolGuidance()`, new, or by default "schema and sql are the last resort".

Over MCP, everything the analyst knew was lost. Asked about an application's visits, a model
wrote SQL against the schema instead of calling the tool made for visits.

## A loopback redirect matches on any port (FW-159)

### Changed

- **`/oauth/authorize` matches a loopback callback on any port** (RFC 8252 §7.3).
    - A native client (Claude Code, an MCP inspector, a CLI) listens on a port it is given each
      run, so none could be registered for it. An installation had to pin one.
    - Where `http://127.0.0.1/…`, `http://[::1]/…` or `http://localhost/…` is registered, a
      request with the same scheme, host, path and query matches whatever its port.
    - Only the port is free, and only on loopback. Every other near miss is still refused, as
      the tests list them.

## Public MCP tools: roles and gates, hooks around every call, a missing scope named (FW-158)

Points 1 and 2 of FW-158. The others follow in their own entries.

### Added

- **Who sees a public tool, beside its scope.** An application where the role decides had to
  rebuild the endpoint's server. Now there are two ways, and every one of them has to allow a tool:
    - `ScopedTool::wrap($tool, $scope, minRole: Roles::ROOT)`;
    - `PublicRegistry::gate(callable(?object $user, ScopedMcpTool $tool): bool)`.
- **`PublicRegistry::around()`** runs hooks around every public tool call.
    - `PublicRegistry::audited()` writes an `mcp.tool_call` audit row: user, tool, client, and
      parameter names, never values.
    - `PublicRegistry::redacting()` passes every string of a result through the analyst's
      `Redactor`.
    - Applications no longer wrap each tool themselves.

### Changed

- **A call to a tool whose scope the token lacks names the scope.** The answer is `403`, with
  `WWW-Authenticate: Bearer error="insufficient_scope", scope="…"`, and the JSON-RPC error
  carries the scope in `data`.
    - It used to be "Unknown tool", which told an assistant nothing it could act on.
    - A tool the user may not reach at all still answers as no tool, so its existence is not
      disclosed.

### What breaks

A client or test that read "Unknown tool" for a missing scope reads the scope from the error
instead. The Upgrade Guide has the row.

## MCP scopes declared in app.php, for consent served by another application (FW-158 §3)

### Added

- **`'mcp' => ['scopes' => [...]]`** declares the MCP scopes in `app.php`, so an application that
  holds none of the tools knows them too.
    - The fix is for authorization and MCP endpoint running as two applications. Consent there
      refused `mcp:diagnostics` as unknown, and the endpoint's metadata listed only `mcp` while
      its `401` asked for five.
    - Name the framework's scopes, or give your own with a description, such as
      `'mcp:people' => 'Find…'`. No `Scopes` provider is needed.
    - Each declared scope inherits `mcp`.

## `oauth.scope_refusal => 'drop'`: scopes a role may not grant left out, not refusing (FW-158 §4)

### Added

- **`'oauth' => ['scope_refusal' => 'drop']`** leaves out the scopes an account may not grant,
  and the request goes on with the rest (RFC 6749 §3.3).
    - The consent page asks for the rest, and the code carries those.
    - A refresh after a role was taken away narrows the token instead of ending the connection.
    - A request of nothing but such scopes is still refused.
    - The default stays `refuse`. Before this, an assistant asking for every listed scope could
      not connect at all for an administrator below the role of any one of them.

## A box per scope on the consent page (FW-158 §5)

### Changed

- **The bundled consent views have a ticked box per requested scope.** What stays ticked is what
  the code, the token and the stored consent carry. Consent had been all-or-nothing.
    - `openid` and `mcp`, or what `oauth.consent_required` names, have no box and are always
      granted.
    - Granting nothing, with nothing required, is a refusal.
    - A consent view an application published earlier sends no `scope_choice`, and grants
      everything asked for, as before.
    - The scope list on the page is open by default, so the boxes are seen without a click.

## `audited()` names the account and the outcome; `redacting()` spares `user` (FW-162)

### Added

- **`PublicRegistry::audited()` records the account a call was about, and whether it
  succeeded.** It writes the row once the call is over, whichever way it ended.
    - The account defaults to the input's `userid`, or its `id`, so an audit screen's "who
      looked at this person" finds MCP calls.
    - `audited($event, $target)` names another event or decides the account.
- **`Redactor::SELF_REDACTING`** lists the tools that redact themselves (`user`). The analyst and
  `redacting()` both read it.

### Fixed

- **Over MCP, `redacting()` masked the one email `user` had been asked for.** The analyst had
  spared that tool all along, so Ask and MCP gave different answers to the same question.

## `database.translate_mysql`: MySQL-written SQL run on PostgreSQL (FW-160, phase 1)

### Added

- **`'database' => ['translate_mysql' => true]`** translates SQL written for MySQL on its way to
  PostgreSQL, through `Pramnos\Database\Dialect\MysqlToPostgres`.
    - It applies in `query()`, `execute()`, `prepare()` and `prepareQuery()`, and to the query
      builder's raw fragments, so the admin datatables' hand-written conditions are covered.
    - Translated: backticks, `IFNULL`, `IF`, `ISNULL`, `LCASE`/`UCASE`, `RAND()`, `LIMIT a, b`,
      `UNIX_TIMESTAMP`, `FROM_UNIXTIME`, `CURDATE`/`CURTIME`, `DATE_FORMAT`,
      `DATE_ADD`/`DATE_SUB`, `GROUP_CONCAT`, `INSERT IGNORE`, `ON DUPLICATE KEY UPDATE` and
      `REPLACE INTO`.
    - An upsert's conflict target is the table's one unique key among the inserted columns.
      With two, or none, it is refused with `DialectException` rather than guessed.
    - Only constructs invalid in PostgreSQL are touched, string literals and comments never, so
      a statement translates the same twice and PostgreSQL-written SQL passes untouched.
    - What would change meaning silently (a case-blind `LIKE`, a loose `GROUP BY`) is left for
      the dialect linter, phase 2.

Off by default. It is a bridge for an application moving from MySQL.

## `PRAMNOS_TEST_SETTINGS`: an application's suite against PostgreSQL (FW-160, phase 3)

### Added

- **`PRAMNOS_TEST_SETTINGS`** names the settings file a test run uses in place of the
  bootstrap's, through `TestEnvironment::settingsPath()`.
    - A relative path is read from the project's root.
    - A name that is not a file stops the run, rather than letting it fall back to the database
      it was meant to avoid.

### Documentation

- **The Testing Guide shows how to run an application's MySQL suite against PostgreSQL before
  the move**: a profile-gated PostgreSQL service, a settings file with `translate_mysql`, the run,
  and how to read what fails only there.

## `db:dialect-lint`: SQL that would mean something else on PostgreSQL (FW-160, phase 2)

### Added

- **`db:dialect-lint [paths] [--json]`** names, by file and line, the SQL the translator leaves
  alone because it would run on PostgreSQL and mean something else.
    - `like`: case ignored on MySQL, not on PostgreSQL.
    - `group-by`: a column neither grouped nor aggregated.
    - `double-quoted-string`: `"…"` used as a value.
- It reads the code's string literals, statements and datatable fragments alike, through
  `Pramnos\Database\Dialect\DialectLinter`.
    - Markup and an operator's name alone are not taken for SQL.
    - `// dialect-ok` marks a line that has been looked at.
    - It exits `1` while anything is found.

## `AuthorizedApplications`: one place to list and revoke what a person authorized (FW-163)

### Added

- **`Pramnos\Auth\AuthorizedApplications`**, with `forUser()`, `byClientId()` and
  `revoke($userId, $appId, ?$byUserId)`. The account screen and an administrator acting for a
  person now do the same thing. `byUserId` lands as `revoked_by` in the activity record.
- **`Account::applicationsUrl()`**: where revoking returns to, for an area that serves the screen
  elsewhere.

### Fixed

- **A consent with no live token was invisible, and could not be withdrawn.** It still approved
  the next authorization without asking. The list now includes it, with `consented_at` and
  `scope`. `last_used` is the latest of last use and creation.
- **A deactivated application could not be revoked** ("Application not found"), while it stayed
  listed and its refresh tokens stayed live. It is now found and revoked.
- **`EndSession` revoked with status 0, the account screen with 3.** Both write 3 with
  `removedate`.
- **The revocation messages were not translatable.** They go through `t()`.

## A test that left organisations in the shared test database

### Fixed

- **`TaskHandoverTest` failed now and then in a full run.** `RoleAssignmentTest` and
  `PermissionResolverOrganizationTest` wrote organisations 3, 5 and 99 into the shared test
  database and never removed them. A later test relying on an installation that keeps no
  organisations then found organisation 3, depending on the order the suite ran in. Both now
  remove what they wrote. This was the intermittent failure of a full run seen two days running.

## A refused query says why, to a developer (FW-165 §4)

### Changed

- **`QueryException::getMessage()` carries the driver's text on a developer's machine and in an
  application's test run.** A failing test used to read «The database refused the query» and
  nothing more.
    - "A developer's machine" means `APP_DEBUG` or `DEVELOPMENT`. `TestEnvironment` turns it on
      for an application's run.
    - `QueryException::$detailed` overrides either way.
    - Production names nothing, as before. `getDetail()` says everything once, either way.

### Fixed

- **A datatable whose query PostgreSQL refused said only «query returned no result».** Its
  message now carries the driver's reason beside the SQL it already had.

## A statement that failed inside a transaction no longer breaks the next one (FW-165 §1)

### Fixed

- **On PostgreSQL, one failed statement inside a transaction broke that statement for good.**
  The sequence:
    1. The failure aborted the transaction.
    2. The aborted transaction refused the `DEALLOCATE` of the statement's plan.
    3. The connection forgot the plan while the server kept it.
    4. In a later transaction, preparing the same SQL collided with it: «prepared statement
       already exists». That error aborted the later transaction too, so the recovery that
       follows could not run.

  One application counted 1,034 such errors, from a user save after a duplicate e-mail.
- **Now:**
    - A plan whose `DEALLOCATE` the transaction refuses stays known, and is reused.
    - Inside a transaction, a plan is looked for on the server before it is prepared, so no
      collision is raised.
    - A plan found there under the SQL's hash is used.

## Wrong second-factor codes are limited (FW-164 §1)

### Fixed

- **A pending login took any number of wrong second-factor codes.** A password was enough to
  guess a six-digit code for as long as the challenge lived.
    - Each wrong code now counts against the pending login, and against the account's lockout
      like a wrong password.
    - After `auth.second_factor_attempts` codes (default 5) the pending login is ended, and the
      next try starts from the password.
    - A lockout the failures set off is answered as `LOCKED`.
    - This covers TOTP, backup codes, mailed codes and every registered factor. A factor whose
      gateway is down refuses without counting.

## `second_factor_everywhere`: the second factor owed by the whole session (FW-164)

### Added

- **`'auth' => ['security' => ['second_factor_everywhere' => true]]`**, off by default.
    - A session the login flow did not finish, for an account with a second factor, is not
      counted as signed in. It becomes a pending login, and the login page shows the second step.
    - The check is in `Session::staticIsLogged()`, so it holds for pages, controllers,
      `/oauth/authorize` and the API's session path alike.
- **`Pramnos\Auth\SecondFactorGate` and `LoginFlow::demandSecondFactor()`** implement it.
    - A finished login settles the session.
    - An account with no factor, or a trusted browser, is settled.
    - Impersonation settles the account it becomes.
    - A login already waiting keeps its wrong-code count.

Before this, where one session served a site, an administration and an API, a password alone
signed in through a door that did not ask for the factor.

## The lockout fails open, the two-factor reset forgets trusted browsers, sign-in devices translate (FW-164 §2–§4)

### Fixed

- **A login lockout whose table could not be reached failed every sign-in.** It now goes on
  without the lockout, logging the problem once per request.
  `auth.security.lockout_fails_closed` refuses instead, for an application that would rather
  close.
- **`auth:twofactor-reset` left the account's trusted browsers trusted.** One would go on
  skipping the factor enrolled next. The command also:
    - writes `auth.twofactor_reset` to the audit log, with the administrator given by `--by`;
    - promised a mailed code even where the application has no email factor. It now says what the
      next sign-in asks for.
- **`SignInFingerprint::describe()` was English in every language.** It goes through `t()`, so
  «Chrome on Windows» in a security mail can read as the language reads.

## Bytes on PostgreSQL: `Binary`, `bytea` read as bytes, text kept in a blob named (FW-165 §5)

### Added

- **`Pramnos\Database\Binary`** binds bytes as bytes. On PostgreSQL that goes through
  `pg_escape_bytea()`, which a bound string could not do: bytes that are not UTF-8 were refused,
  and a backslash was read as an escape. One application's single binary INSERT failed 1,343
  tests.
- **The dry run of `db:migrate-from-mysql` names a blob that holds text**, and says whether it
  is JSON too, so the migration can make it `text` or `jsonb`.
- **`--blob-as-text=table.column`** makes such a column `text` in a table the command creates.

### Changed

- **A `bytea` is read back as the bytes**, through `query()`, `execute()` and the builder alike.
  It used to be PostgreSQL's hex text, where MySQL gave the bytes. The PostgreSQL value
  conversion, which had four copies, is now one (`Result::fromPostgres()`).

### What breaks

Code that decoded the hex of a `bytea` itself drops that decoding. The Upgrade Guide has the row.

## `db:migrate-from-mysql --implicit-defaults` (FW-165 §6)

### Added

- **The dry run reads the MySQL server's `sql_mode`.** Out of strict mode, it counts the target's
  `NOT NULL` columns with no default on either side. MySQL fills an insert that leaves one of
  them out, and PostgreSQL refuses it. One application had 1,809 of them. Keys are not counted.
- **`--implicit-defaults`** gives those columns MySQL's default: `''`, `0`, `false`, an empty
  `bytea`. Dates are named rather than defaulted, because MySQL's zero date has no PostgreSQL
  value.

## The crop dialog's tools are icons

### Changed

- **Rotate left, rotate right, flip and reset in `pf-image.js`'s crop dialog are icons.** Each
  button's words are its `title`, shown on hover, and its `aria-label`, so a screen reader still
  names it. The inline SVG is drawn in `currentColor` and follows the theme. Cancel and "Use
  this picture" stay as words. Each theme's `components.css` styles `.pf-image-icon`.

### Added

- **`document.createElementNS()` in `pramnos-testing`'s DOM**, so a page script that draws SVG
  can be tested. The element keeps its name's case and its `namespaceURI`.
