# 26 November 2026

Two entries today:

- A mention delivered as a reply in a thread is now read once the thread's own pointer passes it,
  not just the conversation's (FW-581)
- The shared imported service worker (`pf-push-worker.js`) now survives the browser rotating a
  push subscription, same as the scaffolded one, and the check for missing handlers reads what a
  worker `importScripts()`s too (FW-582)

## A mention delivered as a reply in a thread is now read through the thread's own pointer (FW-581)

### Fixed

`Conversations::counts()` and `Conversations::forPerson()` counted `mentions` only from the
conversation-level read pointer (`conversation_members.lastreadid`) — never consulting a thread's
own (`chat.thread_reads`, `Threads::read()`, FW-498). A conversation's `lastreadid` only ever moves
with its top-level messages, never with a reply, so a mention delivered as a thread reply stayed
counted as unread for ever unless some later top-level message in the same conversation happened to
be read afterward, which incidentally moved `lastreadid` past the reply's own position.

`Inbox::unseenActivity()` already consulted the thread's own pointer for a reply; `counts()` and
its batched sibling, `forPerson()`'s `mentionsIn()`, did not know threads existed at all. Both now
leave a mention out once its own reply's position no longer stands after that thread's read point —
in addition to, never instead of, the existing conversation-level check, which still is what a
top-level mention is read by.

## The shared imported service worker survives a rotated push subscription too (FW-582)

### Fixed

`pf-push-worker.js` — the worker a project without its own handlers `importScripts()`s instead of
writing `push`/`notificationclick`/`notificationclose` itself — had no `pushsubscriptionchange`
handler, even though the scaffolded `sw.js` stub has had one since web push was added and
`Pramnos\Push\ServiceWorker::HANDLERS` itself documents it as "the one people leave out, and it is
the one that fails later". Root-caused against a real bug report: an installed PWA kept asking an
already-subscribed visitor to re-enable notifications on every open — the browser rotates a push
subscription's keys on its own, far more often on Android than on desktop, and with nothing
listening for it the old subscription died silently and nothing ever re-subscribed until the
visitor noticed the prompt again.

`pf-push-worker.js` now re-subscribes and posts the new subscription to `push/subscribe` the same
way the stub's own handler does — with no page open and no CSRF token to read, which is exactly
what `Push::fromThisSite()` accepts a plain `Sec-Fetch-Site: same-origin` for instead, a header the
browser sets on this fetch itself.

Separately, `Pramnos\Push\ServiceWorker::missing()` — the check behind `push:setup` and the one
`HANDLERS`'s own docblock is about — read only the project's own worker file, so a worker that
`importScripts()`s `pf-push-worker.js` rather than writing the handlers itself was reported as
missing all three, even the two it already had through the import. `missing()` now reads a local
file an `importScripts()` call names alongside the worker's own source; a remote one (a CDN,
another origin) is left alone, and a file that cannot be found or read simply contributes nothing.
