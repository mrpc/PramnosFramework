## A migration that queued its statements reported Ran and changed nothing

Found by measuring production after shipping a column widening: two `varchar` columns were
still their old width on development, on the test database **and** on production, while all
three ledgers recorded the migration as having run.

`addQuery()` queues. `executeQueries()` is what empties the queue, it is `protected`, and
**no framework code called it** — so a migration that queues two `ALTER TABLE`s and returns
is a migration that reports success and does nothing.

The care had gone into the wrong half. `executeQueries()` documents itself carefully: it
runs statements tolerantly, because a re-run whose `ADD COLUMN` is already applied must not
abandon the eleven behind it, and it records every rejection so the runner can write "ran,
with N rejected". The runner already reads `failedStatementSummary()` and has
`RESULT_RAN_WITH_ERRORS` for exactly that. All of it was unreachable.

**The recovery is the expensive part.** A no-op that is *recorded* cannot be re-run, so
correcting the migration file helps nobody who already has the row — the fix has to be a
second migration. One mistyped line costs two migrations and a paragraph explaining why
there are two.

### Fixed

- `Migration::runQueuedQueries()`, called by the runner immediately after `up()` and after
  `down()`. **Inside the transaction**, so a queued statement is committed with the rest of
  the migration's work.
- A new public method rather than widening `executeQueries()` to public: an application's
  migration may override it as `protected`, and a parent that became public would make that
  override illegal — a fatal at class load, for every such installation.
- **A migration that empties its own queue is not run twice.** `executeQueries()` clears the
  queue, so the runner's call finds nothing left. That has its own test, because the failure
  it prevents is silent for `IF NOT EXISTS` and is not for an `INSERT`.
- The tests are integration tests against the real database and they assert the **schema**,
  not the call. "The runner invoked a method" is not the claim; "the column is wider
  afterwards" is. Without the fix, two of the three fail — the first with the message this
  entry is named for.

### Documentation

- **Migration Guide** — "queued statements run when `up()` returns", with the warning that
  anybody holding a migration from before this should check the schema rather than the
  ledger.
- **Upgrade Guide** — a row saying the same, since a recorded no-op is invisible until
  somebody measures.
