## A generated detail view renders a picture, and a guard keeps it asking for the address

Yesterday's media-to-storage work ended with *"in views, use `publicUrl()`"* — and the
question that followed was the right one: had the views been fixed?

**There were none to fix.** Every `<img>` the framework ships points at a QR data-URI, a
brand logo string, `application->logourl` or `user->avatar`, and not one of them goes
through `MediaObject`. The two `grep` hits for `sURL . 'uploads/'` are both *comments* — the
ones written to explain why that line is wrong. The media system is used only by
applications, which is why the Upgrade Guide row addresses them.

That answer is also the problem: a framework that emits no media URL has nowhere to set the
example, and no guard can forbid a shape that does not occur.

### Added

- `MediaObject::urlFor($mediaid, $reason)` — the one line a view needs. An id that is zero,
  null or gone answers `''`, because a row can outlive its picture and an empty `src` is the
  caller's decision rather than a broken image the framework invented.
- `create:crud` renders a picture in the detail view of all three themes, for **columns
  whose foreign key references `media`**. From the keys rather than from column names: a
  foreign key to `media` *is* the framework's statement that a column holds a picture, where
  a name-based rule would catch a column somebody called `logo` and meant as a word, and
  miss `header_id`.
- A table with no such column emits `[]`, which is most tables.

### The guard

`GeneratedMediaUrlsTest` forbids `sURL . $x->url` and `sURL . 'uploads` in any stub, and —
the half that matters more — asserts the detail view *does* call `urlFor()`. A sweep that
only forbids the wrong thing passes perfectly over generated code that renders no pictures
at all, which is what it did until yesterday.

It is narrow on purpose: `sURL . 'Things/edit/'` is a link to a page of this application and
is exactly what `sURL` is for. What is forbidden is joining it to a stored **file** path.

First run flagged three files — all three of them the guard's own explanation, which quotes
the forbidden line in order to explain it. Comments are stripped now. That is the second
guard in this repository to report its own documentation on the day it was written.

## A guide for taking a monolith to more than one server

`Pramnos_Multi_Server_Guide.md` — the checklist, in the order the failures actually arrive,
with how to verify each rather than how to hope.

It opens with **what already works and needs nothing**, because that is most of the system
and a guide that starts with a list of problems misrepresents it: the queue claims jobs with
`FOR UPDATE SKIP LOCKED`, the WebSocket server has a Redis backplane with periodic
reconciliation, `ClientIpResolver` reads the proxy chain.

Then the six that do need something — sessions, cache, scheduled tasks, `migrate`, uploads,
`APP_URL` — each with its **symptom first**, because that is how somebody arrives at the
page. Sessions read as an expiry. Cache reads as a page that is right on one refresh and
stale on the next. Scheduled tasks do not read as anything at all, which is why they run
doubled for months.

Four of the six report themselves in `health:check`, and the guide says to run it first and
last — and on *each* node, because a check that is green on the machine you deployed from
says nothing about the other one's filesystem.

### And what the framework does not solve

Stated plainly at the end, because a guide that only lists what works is not a guide: local
logs, `var/cache/`, deploy consistency between nodes, and the database — one connection, no
replication or read splitting. A shared mount is named as the *right* answer for uploads
wherever it is available, ahead of the object storage the framework now supports.

## Three of the four things that guide said were not solved, are

The multi-server guide above ended with a short "what this framework does not solve for
you" — local logs, `var/cache/` and the file spool, deploy consistency, and the database,
where it said *"replication, failover and read splitting are out of scope; the framework
talks to one connection"*.

Three of those four were wrong, and the last one was wrong in the way that matters most:
**read/write splitting has shipped since v1.2**. `Database` takes a `read` and a `write`
block, routes every statement by its first keyword, and keeps the two links as separate
sessions with their own time zone and their own reconnect. The guide told a reader to go
and solve, outside the framework, something the framework does.

It could say that because the feature was documented **only in `1.2-new-features.md`** —
the frozen v1.2 reference — and in a DevPanel table. No guide owned it, so nothing
described it as current behaviour, which is the repository's own documentation rule failing in the exact
shape rule 1 describes: a feature that is present, works, and reads as absent.

### Fixed

- **`Pramnos_Database_API_Guide.md` now owns read/write replicas** — configuration for both
  roles, which keywords pick which link (`SELECT`, `SHOW`, `EXPLAIN`, `DESC`, `DESCRIBE`
  read, everything else writes, so an unrecognised statement reaches the primary rather
  than a read-only replica), and the three things to know before turning it on: replica lag
  against reading your own write, that two hostnames are configuration rather than failover,
  and that an installation declaring neither block gets exactly what it has today.
- **`Pramnos_Multi_Server_Guide.md`** replaces its closing section with "the three that look
  like gaps and are not":
    - **Logs** — `PRAMNOS_LOG_MODE=both` keeps the file for `LogViewer` and sends the same
      line to STDERR for whatever collects it. Per process, so a node can differ without a
      deployment.
    - **`var/cache/` and the write spool** — both have a Redis driver, and neither announces
      that it is not using it. `CacheBackendCheck` reports the running backend against the
      configured one, which is the check to watch before a second node goes live.
    - **Database** — the section above.

What remains under "does not solve" is one item: nothing here can tell you that two nodes
are running the same commit, because each node answers correctly for the code it has.
