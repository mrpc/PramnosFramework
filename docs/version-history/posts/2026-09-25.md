## Scheduled tasks can run on one server instead of on each of them

`withoutOverlapping()` takes a `WorkerLock`, which is a **file** — and the class says so:
it records the holder's `host` and checks the holder's pid *on the same host*. On one
machine that is right and free.

On two web servers each has its own `var/` and its own `sys_get_temp_dir()`, so each takes
its own lock and every scheduled task runs **once per node**. Two copies of a nightly
email, two of a billing run. **Nothing fails**, which is why it can run for months
unnoticed — and why the only remedy was an operational rule somebody has to remember:
*cron on exactly one machine*.

### Added

- `Scheduler::command('reports:nightly')->dailyAt('02:00')->onOneServer()`. It takes a
  `SharedLock` — a row in `pramnos.locks` whose **primary key is the exclusion**. An
  `INSERT` of a name already present is refused by the engine, not by a check the class
  makes, so there is no window between looking and taking.
- It composes with `withoutOverlapping()`: that one stops a slow run on *this* machine
  starting again, this one keeps the other machines out. A task that wants both says both.

### The database rather than the cache

A shared cache is the usual answer to this, and it is **optional here**. The default
adapter is local files — which would be a lock that excludes nothing in exactly the same
way, and just as quietly. A lock that works only when somebody remembered to configure
Redis is worse than no lock, because it looks like one. Every installation has a database.

### Three things the tests settled

- **Takeover is delete-then-insert, not a guarded `UPDATE`.** The guarded update is atomic,
  but knowing whether it matched means reading the affected-row count — and
  `QueryBuilder::update()` hands back a `Result` whose `numRows` came back **null** for an
  `UPDATE` that had plainly worked. Read as a boolean that would make every takeover
  "succeed", including ones that matched nothing: two holders of a lock that exists to
  prevent exactly that. Measured, not assumed. So the delete clears an expired lease and
  the **insert stays the atomic step** — one mechanism rather than two.
- **The owner is `host:pid:token`, not `host:pid`.** `release()` is scoped to the owner so
  an evicted holder cannot delete the lock its successor is working under — and `host:pid`
  does not separate two locks in one process, including a process that took the lock, lost
  the lease and took it again. The test for that failure is what found it.
- **A closure has to be named.** `describeHandler()` answers the constant `Closure` for
  every closure, so two unrelated closure tasks would share one lock and take turns not
  running — the silent shape this whole feature removes. `onOneServer()` raises instead:
  `->onOneServer(name: 'metrics:rollup')`.

`SharedLock` is at 100% line coverage, including what it does when the database is
unreachable: **it does not hand out the lock**. Answering "free" because nobody can be
shown to hold it would let every node run at once, which is the opposite of the point.

## Sessions can be put in a shared store without touching `php.ini`

PHP keeps sessions in local files unless told otherwise. On one server that is correct and
free; on two it is the quietest failure in a deployment. A visitor whose next request lands
on the other node has **no session**, so they are signed out at random on a site that is
otherwise working — and it reads as an expiry, a cookie problem, a `SameSite` mistake.
Everything except a load balancer.

The framework said nothing about it, and the remedies were sticky sessions at the balancer
or a `php.ini` a deployment may not control.

```php
// app/config/app.php
'session' => ['handler' => 'redis'],
```

`APP_SESSION_HANDLER` and `APP_SESSION_PATH` in the environment win over it, so a
deployment can switch stores without editing a committed file.

**The handler is settable at run time** as long as it is set before `session_start()` —
which is the window `Session::start()` already runs in, next to `use_strict_mode` and for
the same reason. Verified rather than assumed: `session_module_name('redis')` returns the
previous handler, and the session lands in Redis under `PHPREDIS_SESSION:<id>`.

### With no path, the cache's host is reused

An application that configured Redis for its cache has already said where Redis is. A
second copy of a hostname is a second thing to get wrong — silently, because a wrong
session host signs people out rather than erroring. Give `'path'` explicitly when the two
are genuinely different servers.

### It never fails the request

A handler PHP has not registered, a store that is down, a misspelling — all of them leave
sessions on files and log why. A working single server is a better failure than a site that
will not boot, and the check below is what stops the fallback being silent.

## …and `health:check` says when they are not

- **`session_storage`** — `degraded` on `files`, naming the store either way, because the
  common way to get this wrong is not leaving it on files but pointing it at a Redis the
  other nodes do not use. It cannot see sticky sessions at a load balancer, so on that
  arrangement it stays yellow deliberately.
- The save path is **redacted** past the `?`. `tcp://redis:6379?auth=hunter2` is a valid
  Redis save path and `health:check` output is pasted into tickets.

Writing the test for it turned up the reason the seam exists: `session.save_handler` cannot
be changed once a session is active, so a test driving it through `ini_set()` **passed
alone and failed in a full run**, where something earlier had started one. The check takes
its two values through the constructor now — the same seam `CacheBackendCheck` takes its
cache through, for the same reason — and there is a test that with nothing injected it
still reads the live settings, because a seam nobody exercises from the real path reports
on nothing.

### Documentation

- A new section in the Workers and Daemons guide: what is already shared across servers
  (the queue claims jobs with `FOR UPDATE SKIP LOCKED`, the WebSocket server has a Redis
  backplane, `ClientIpResolver` knows about proxies), what is not and how each one fails.

  The honest remaining gap is **uploads**: `www/uploads/` is local disk and there is no
  object-storage layer, so a picture uploaded on one node does not exist on the other.
  Shared storage is the answer today.

## The session store setting was never read

Shipped an hour earlier in this same day's work, and it did not work.

`Settings::getSetting()` casts an **array** setting to a `stdClass` on the way out. The code
read it with `is_array()`, which is false for an object — so
`'session' => ['handler' => 'redis']` in `app.php` read as **no configuration at all** and
sessions stayed on local files. Silently, on the one feature whose entire purpose is to stop
a silent single-server assumption.

`Cache` has `(array) Settings::getSetting('cache')` and has had it for years. Not reading
how the neighbour does it was the mistake; the cast was one line away.

### Fixed

- Both reads cast, and `SessionStoreConfigTest` covers them: a configured handler is seen,
  the environment wins over the file, and the path falls back to the cache's host. Verified
  by removing the cast and watching the first one fail.
- `sessionPathFromCache('memcached')` has no `tcp://` scheme, which is memcached's own
  format rather than an oversight — a scheme there is not parsed and the store is silently
  not used.

## `Pramnos\Storage` was unreachable, and that is why nobody used it

The framework has shipped a storage abstraction since v1.2: `StorageManager`, a `Storage`
façade proxying twenty methods, and `local`, `s3` and `ftp` drivers — **at 93–100% line
coverage**, across 83 tests.

Nothing in `src/` uses it. Not one reference outside its own namespace.

The reason is one line:

```php
throw new \RuntimeException(
    'Storage has not been initialised. Call Storage::init($config) during bootstrap.'
);
```

`init()` is never called by the framework, and never by anything it scaffolds. So the
façade answered with an exception for every application that had not already read the class
and wired it up — and an application reads the class only after it knows the class is
there. A well-built, well-tested subsystem with no way in.

### Fixed

- `Storage::getManager()` builds itself from the `storage` block of `app/config/app.php`,
  and falls back to **one `local` disk rooted at `www/`** when there is none — where
  uploads already are, so nothing moves and nothing has to be configured for the façade to
  work. That is the whole of "optional": available without being imposed.
- The settings are cast on the way in, nested `disks` included. `Settings::getSetting()`
  hands back a `stdClass` for an array setting, and reading it with `is_array()` is how a
  configured block silently reads as none — the same mistake as the session store above, in
  the same day.
- `init()` still works and still wins, for an application that would rather configure in
  code.

### Documentation

- The Workers and Daemons guide now names `Pramnos\Storage` as the alternative to a shared
  mount, with a worked `s3` disk and the note that `aws/aws-sdk-php` is the application's
  dependency rather than the framework's.
- And a warning that **the media system does not use it yet**: `MediaObject` still writes to
  `www/uploads/` directly — twenty filesystem calls, and GD writing with
  `imagejpeg($image, $path)`, which needs a real path a bucket does not have. Configuring a
  disk today gives an application somewhere to put its own files; it does not move the
  framework's uploads. A shared mount is still the answer for media on more than one server.

### What this cost to find

Two false starts, both the same mistake. `ls src/Pramnos/` truncated at thirty entries and
`Storage` was below the fold, so a whole parallel implementation got written — interface,
local driver, S3 driver with hand-rolled SigV4 — before the coverage report named files
that should not have existed. Then the tests: `tests/Unit/Storage/` is empty and
`tests/Unit/Pramnos/Storage/` holds all 83, so "this subsystem has no tests" was said out
loud and was wrong.

Nothing wrong reached a commit, and the SigV4 work was thrown away rather than kept beside
an SDK that already does it. The rule it breaks is the oldest one here: **look at what is
there before writing what is next.**

## The media system can publish to a storage disk

The other half of the one above. `Pramnos\Storage` is reachable now; this is what uses it.

**Name a disk `media` and uploads go to it. Name it anything else, or none at all, and
nothing changes** — the file stays in `www/uploads/`, served by the web server exactly as
before, and nothing is copied. Every existing installation is that case.

A disk name rather than a new setting, because a name is discoverable — somebody reading
`app.php` sees what it is for — and one concept is cheaper than two.

### The work stays local; only the result is published

GD writes with `imagejpeg($image, $path)`, a real filesystem path a bucket does not have. So
the resize pipeline is untouched: upload, resize and thumbnail locally, then publish what
came out. A stream wrapper would have hidden that difference until it surfaced as a warning
from inside GD.

The local copies **stay**. They are the origin a later resize reads, and on a single server
they are also what is served — deleting them would make rendering a page depend on the disk
being reachable, which is a worse failure than the one this is for.

`$media->url` was already the key: the path relative to `www/`, `uploads/2026/09/x.png`,
which the media system has stored since long before there was a disk. Nothing about the
database changes.

### Added

- `publishToStorage()`, called after `save()` in `uploadFile()` — after, because the row is
  the record and the disk is a copy of it, and a publish that fails must not lose an upload
  the application has accepted.
- `republishToStorage()`, which puts what is missing and skips what is there, so a backfill
  over ten thousand pictures is cheap to run twice.
- `deleteFromStorage()`, wired into `delete()`. A row whose files are gone locally and
  present on the disk is the worse half of the two: the disk is what a CDN reads and keeps
  serving.
- `publicUrl($reason)` — the disk's address when there is one, the site's own when there is
  not. A view concatenating `sURL` with the stored path keeps working and keeps pointing at
  the server the file may no longer be on.

### The catch is `\Exception`, not `\Throwable`, and a mutation is why

Publishing absorbs failures: a disk that is down does not fail an upload already accepted.
Written with `catch (\Throwable)` that absorbed too much — deleting the null-disk guard left
every test green, because `Call to a member function put() on null` was swallowed and
`publishToStorage()` returned 0, which is also what "no disk configured" returns.

Two indistinguishable answers, one of them a bug. `\Exception` is a disk that will not
write; `\Error` is a fault in this code, and it belongs in the open. With the narrower catch
the same mutation fails immediately.

### Added tests

Ten, and the ones that matter most are the *without a disk* half: nothing published, nothing
copied, and `publicUrl()` unchanged. A feature that is optional in the docblock and not in
the code is not optional.

Also pinned: a rendition whose `filename` **is** the original — `reason = 'original'` — is
published once, because the files are keyed by `url` rather than by local path. Keyed the
other way it would copy the same bytes twice and try to delete the same key twice.
