## Registering a redirect URI is recommended, not required

Yesterday's `redirect_uri` validation went further than the report asked and further than
it should have: a client with an **empty** `callback` was refused outright, which would
have stopped authorization requests that work today on every installation whose column is
empty.

That was not in the filing. The filing was explicit about the opposite, in the sentence
describing how the reporting application had resolved the same question:

> a client with a registered callback contributes only that origin, **a client with none
> contributes what it asked for** — which is what the OAuth layer already permits

And the reasoning behind it is the part worth keeping: **whether a client has a callback on
file is the operator's decision about their own clients**, the way it is on every large
authorization server. Registration is what buys exact-match protection; an operator who has
not made one has not asked the framework to refuse their traffic on their behalf.

### Fixed

- **A client with nothing registered is no longer refused.** It works exactly as it did
  before. The condition is written to `oauth.log` once per request, carrying the
  recommendation and naming the client, so the registration can be filled in deliberately
  rather than under a login that has stopped working.

- **The `!` is withdrawn.** There is nothing to check before upgrading, and yesterday's
  *"What breaks in subclasses"* section now says so — somebody reading it would otherwise
  run a SQL query for a break that does not exist.

A registration that *disagrees* with the request is still refused, exactly as before. That
is the registration doing its job, and every near miss a prefix or host comparison would
accept is still a test.

### And what keeps that from being a hole

An unregistered client gets **no `form-action` widening**. `form-action 'self'` has been
accidentally preventing such a client's delivery all along — badly, at the cost of blocking
every legitimate login that goes through the sign-in form, but preventing it. Widening the
policy for a destination no registration vouches for would convert a broken feature into a
working attack, which is the ordering problem the original report was explicit about.

The distinction, because it decides the design: the CSP is not being used to block a
redirect the OAuth layer permits. It is simply not being *opened* for one the OAuth layer
cannot vouch for. That is also the practical argument for registering — it is what makes an
SSO login through the login form complete.

### Documentation

- **`Pramnos_AuthServer_Integration_Guide.md`** — *The redirect URI must be registered* is
  now *Register your redirect URI — recommended, and matched exactly*, and says what
  registering buys rather than what omitting it costs you in refusals: exact-match
  protection, and the `form-action` widening that lets a form-based sign-in finish.

- It also gains ***Two ways to stop `form-action` cancelling an SSO login*** — a table
  comparing registering the callback against listing the origins under `csp: form-action`
  in `app.php`, by scope, by what else each buys, and by whether it needs a deploy.

  Worth spelling out because "registration is optional" reads as "the CSP problem is
  gone", and for a client with nothing registered it is not: no registration means no
  widening, so that flow stays cancelled exactly as it was. The `app.php` route is the
  other half of the answer and is **not** a workaround — it is the extension point the
  original report asked for, and an application is entitled to widen its own policy. It
  simply checks nothing: the origin is trusted because somebody wrote it down.

## An array as a cache id put every such call in one entry

Reported from an installation as `PHP Warning: Array to string conversion` at
`Cache.php:1114`, **38,081 times in a day**, at a rate unchanged across the reporter's own
deploys — so not caused by anything they had just shipped, and worth a separate look.

`load()`, `save()`, `delete()` and `increment()` take `$id` untyped, so an array travelled
all the way to the concatenation that builds the cache name, and PHP wrote the literal
`Array` into it.

### The warning was the smaller half

Every array-keyed call produced the **same** name — `<category>_Array.<ext>` — so they all
shared one entry, and a `load()` could return whatever another caller had saved under a
different array. Thirty-eight thousand reads and writes of one key, which is a correctness
bug wearing a warning's clothes.

### And why it appeared when redis was switched on

It did not start then. `load()` returns at its second line when `$this->caching` is false,
before any name is generated — so with no cache configured the array never reached the
concatenation. Turning the store on made an existing call path *reachable*. The reporter's
instinct that the timing was suspicious and the cause was elsewhere was right on both
counts.

### Fixed

- **A non-string id is normalised at the one place all four methods go through.** Distinct
  values now get distinct keys, so the calls are at least correct while the caller is being
  fixed. Strings pass through untouched, and `int`, `float` and `bool` keep exactly the
  names they have always produced — an upgrade must not orphan an installation's existing
  entries.

  A `string` type declaration is not available as a fix: `$id` is public API on four
  overridable methods, so adding one is a fatal at class load for any application that
  overrides them (rule 6), and it would turn a wrong cache entry into a broken page for
  whoever is passing the array.

- **The log names the caller.** All 38,081 lines named a line inside the framework, which
  says where the conversion happened and nothing about who asked for it — and every caller
  in the framework passes a string, so the report was unanswerable from inside. It now
  writes one line per call site, with the file and line that passed the array:

  ```
  Cache id is a array, not a string, from /var/www/app/Controllers/Foo.php:212
  (category "views"). It is hashed into a stable key, but until it is fixed there…
  ```

  Once per call site per process, because 38,081 identical lines is the shape of the
  problem and must not be the shape of the answer.

An id that will not `serialize()` — a closure inside the array — falls back to its type
name and collides exactly as before, deliberately: there is no stable name to give it, and
a shared cache entry is better than a request that dies inside the cache layer. The log
line has already named the caller by then.

### Documentation

- **`Pramnos_Cache_Guide.md`** gains *The id is a string, and the framework says so if
  yours is not* under Basic Usage — why the parameter is untyped, which conversions are
  safe, what an array used to do, and the log line to grep for.
