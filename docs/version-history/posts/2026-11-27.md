# 27 November 2026

Three entries today:

- The Scheduler and Email dashboard cards' tiles that have no count of their own to click
  through from now open the same screen the card's heading does (FW-587)
- The emoji picker's "hearts" category listed `💟` twice, which broke that one tab's keyed
  rendering (FW-588)
- A `withoutOverlapping()` command task run under a supervised `work` process reported
  "already running" on every single invocation, because it inherited the worker's own job
  lock path instead of resolving its own (FW-589)

<!-- more -->

## Every Scheduler and Email dashboard tile now opens its screen, not just the first one (FW-587)

### Fixed

`ScheduleStatus::present()` gave `link()` only to the "Late" tile; "Last run failed" and "Running
now" rendered as plain, unclickable `<div>`s. `EmailActivity::render()` gave `$this->link()` only
to "Sent"; "Failed" and "Queued" were the same. A reader drawn to the card by exactly the number
that is wrong — the failed run, the bounced mail — had no way to click through to it, while the
one number that is usually fine (the first tile) was the only one that led anywhere. Every tile
now carries the same `link()` the card's own heading uses; there is one screen behind each card,
not one per tile, so there was never a second link to choose.

### Documentation

No guide change: both widgets' own doc-blocks already describe opening the scheduler/email screen
as the card's behaviour, not one tile's — this closes a gap between that description and the code.

## The emoji picker's "hearts" tab no longer gets stuck on another category (FW-588)

### Fixed

`emoji-data.js`'s `hearts` category listed `["💟","heart decoration"]` twice — once after
`💝`, again after `⚛️` — the only one of the eight categories with a repeated emoji in its own
list. `EmojiPicker.svelte` renders a tab's emoji with keyed `{#each shown as item (item.emoji)}`,
and two items sharing one key broke Svelte's reconciliation for that tab: clicking "❤️" updated
`aria-selected` (a separate binding) but left the grid showing whichever category was open before
it, exactly the report — every tab worked except the heart. Removed the duplicate entry.

### Documentation

No guide change: the emoji picker's own section already describes one entry per emoji; this was a
data bug, not a documented behaviour. A new check in
`tests/js/conversations-logic.test.js` ("emoji are found by name…") now asserts every category's
emoji are unique, so a repeat like this fails the suite instead of only a browser.

## A scheduled command's own overlap lock no longer resolves to its supervisor's (FW-589)

### Fixed

`CommandBase::resolvedJobLockFilePath()` reads `CommandBase::LOCK_FILE_ENV`
(`PRAMNOS_JOB_LOCK_FILE`) before falling back to the command's own
`getJobLockFilePath()` — set by `DaemonOrchestrator` when it spawns a supervised worker, so
that worker's own lock agrees with the path the orchestrator tracks it under (see that
method's own docblock). `work`, the framework's schedule process, is exactly such a worker
when run under `daemons:start`. `ScheduledTask::runShellCommand()` and `spawnDetached()`
spawn a scheduled `command` task's own process with `popen()`/`exec()`, which inherit the
calling process's *whole* environment — including that same env var, still pointing at
`work`'s own lock file, not the task's.

A command task with `withoutOverlapping()` that also calls `CommandBase::beginJob()` inside
itself — most do, to guard a direct CLI run the same way — then resolved its lock to
`work`'s lock file instead of its own. `work` holds that file for as long as it runs, so
`beginJob()` always found it "already running" — not occasionally, under real overlap, but
on *every* invocation, since the thing it found running was always the very process asking.
Reported from a live installation: `billing:run` and `reminders:send`, both
`withoutOverlapping()`, had failed this way on every single scheduled run since the day
`work` started running under `daemons:start` — neither had reached its own `execute()` once
in that time, and neither failure said why in a way that pointed here, since the printed
message ("Command is already running") was, in the narrowest sense, true.

Both call sites now run the child with `env -u PRAMNOS_JOB_LOCK_FILE` ahead of the real
command, clearing only that one variable for the child — the parent `work` process's own
env, and its own later lock checks, are untouched.
