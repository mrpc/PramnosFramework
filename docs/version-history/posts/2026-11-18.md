## A "show all" Datatable request now stops at a cap instead of running with no `LIMIT` (FW-525)

`Datasource::getList()` deliberately skipped `LIMIT` for `iDisplayLength = -1` — the "show
all" value sent by the page-length menu's "All" option, and the one the DataTables Buttons
extension's `copy`/`excel`/`pdf`/`csv`/`print` buttons send by default on a `serverSide: true`
table to export every filtered row in one request. With no cap, a heavy query plus per-row
PHP post-processing turns that into unbounded work — a hang well before a timeout gives a
useful error.

### Fixed

- `Datasource::$unlimitedCap` (default `5000`) now bounds every `length = -1` request with a
  real `LIMIT`. Raise it per instance for a light query, or set it to `0` to restore the old
  unlimited behavior.

## A `Datatable` can export every filtered row through the queue instead of in one request (FW-526)

A table that genuinely needs to hand every filtered row to a user — not capped at FW-525's
`unlimitedCap` — now has a generic way to do it, instead of each application writing its own
queue task, controller actions and polling JS.

### Added

- `Datatable::$backgroundExport = true` turns off the native tableTools buttons and the
  "All" length-menu entry, and renders a generic "Export CSV" button that queues the export,
  polls while it runs, and swaps in a download link when it is done.
- `Pramnos\Html\Datatable\Exportable`: the one method (`exportBatch($filters, $limit,
  $offset)`) a model implements to make itself exportable — the same rows its grid's own
  AJAX action already produces, as a plain LIMIT/OFFSET fetch.
- `Pramnos\Queue\Tasks\DatatableExportTask` (`datatable.export`, a framework handler — no
  registration needed): batches `exportBatch()` into a CSV inside one transaction set to
  `REPEATABLE READ`, so a row written between two batches cannot be skipped or duplicated.
- `Pramnos\Application\Concerns\DatatableExportActions`: a controller trait adding
  `queueexport()`/`exportstatus($id)`/`exportdownload($id)`, with an `exportableModels()`
  allow-list (the model class arrives in the POST body, so this is the one check standing
  between a signed-in user and queueing an arbitrary class) and an ownership check (the
  requester, or a `super`+ user, may poll or download a given export).

### Documentation

- "Background CSV export" in the Html Components Guide; a short mention of the new task
  type in the Queue Guide.

### Fixed

- The export button's own request now carries what `DatatableExportActions::queueexport()`
  actually reads. It posted `table.api().ajax.params()` as the whole body — no `class`, no
  `filters` key — so every click answered `403`, caught by a peer review before this shipped
  further. `columns` is now built server-side from `aoColumns` (DataTables' own
  `ajax.params().columns[]` has no label to put in a CSV header). A rendering bug in the
  same two commits, not a behavior change since nothing worked before it.
- `filters` now merges the page's own query string with `table.ajax.params()` (the latter
  winning a key both carry), via the new `Datatable::$exportIncludesQueryString` (default
  `true`). A page-level prefilter — a group, a date range, anything an admin screen reads
  from `$_GET` rather than a column search box — never reached `ajax.params()` on its own,
  so an export would silently drop exactly the filters the admin had on screen: a wrong
  result, not an error. Also caught by review before this shipped further.
- The export button's request now carries the session's `_csrf_token`. `queueexport()`
  starts a background job, so a controller is expected to put it in `addWriteAction()` —
  which `Controller::isVerifiedWrite()` checks against `_csrf_token`/`X-CSRF-Token` — and
  the button's POST carried neither, so every click would answer `419` on a controller
  that did the right thing and protected the action. Also caught by review.
- Every column's exported value came back empty for a model whose `exportBatch()`
  delegates to `Datasource::getList()` — the Guide's own recommended pattern, since that
  is the same method already serving the grid. A column's `key` was `aoColumns`'s array
  key (`addColumn()`'s display label, e.g. `"Name"`), not a key any row actually has:
  `Datasource::getList()` returns numeric-indexed rows. `Column::$exportKey` now defaults
  to the column's position among `aoColumns` instead — the same positional index
  `renderJs()` already injects as `"data": N` for server-side mode — and can be set to a
  field name for an `exportBatch()` that returns assoc rows instead. Found end-to-end,
  running a real export through the queue.
- `exportdownload()` always answered `404`, once an export actually finished.
  `DatatableExportTask::execute()` set the finished CSV's path on `$this->lastMessage`,
  but *returned* a different, human-readable string (`"N rows exported"`) — and a task's
  return `message` is what the Worker writes to `success_message`, not `lastMessage`. The
  controller read `success_message` expecting a path. The file's name is already
  deterministic (`<taskid>.csv`): `DatatableExportTask::csvPath()` computes it from the
  task id, and neither side reads it out of `success_message` any more — which now holds
  only the human-readable count, as the admin queue screen already showed it. Also found
  end-to-end.

### Changed

- `backgroundExport = true` no longer turns `tableTools` off. `Datasource::$unlimitedCap`
  (FW-525) already bounds a native "export all" click, so the two toolbars are free to
  coexist — the native buttons for a quick copy/print of what is on screen, the background
  button for a full filtered export. `tableTools` keeps its own switch: set it `false` for
  a table that wants the background button alone, as before.

### Fixed

- A `datatable.export` task's CSV in `var/exports/` was never deleted — not by
  `queue:cleanup`, which only ever removed the row. Its row gone, the file was also
  unreachable through the application (`exportdownload()`'s ownership check reads a row
  that no longer exists), but stayed on disk anyway, growing without bound.
  `purgeOldTasks()` now deletes a `datatable.export` row's file along with the row: it
  collects the matching task ids before the `DELETE` (same `WHERE`, so the two cannot
  drift onto different rows), then unlinks their files only once the transaction commits
  — a file is never removed ahead of a row that turns out to survive.

## The background export modal: scope, format, an email notice, and a list of your own exports (FW-527)

The export control from FW-526 queued an export the moment it was clicked, with no way to
ask for just the current page, to be told by email when a large one finishes, or to find
a queued export again after leaving the page.

### Added

- Clicking the export control now opens a small modal instead of queuing at once: a
  `format` select (today only CSV — the one value validated server-side, additive ground
  for a future format rather than a redesign), a `scope` choice (`'all'`, every filtered
  row, or `'page'`, just what is already on screen), a "notify me by email when ready"
  checkbox, and a "My downloads" link.
- `scope: 'page'` is one `exportBatch()` call using the `start`/`length` already in the
  table's own AJAX params — not re-batched, and not wrapped in the `REPEATABLE READ`
  transaction `scope: 'all'` still uses: a single query has no concurrent-batch problem to
  guard against.
- `notify_email` queues (`Email::queue()`, not a synchronous send) a download-link email
  to the requester once the export completes — through the mail outbox, so one slow SMTP
  round trip never holds up the worker. The address is captured once, from the signed-in
  user at request time, not reloaded later.
- `DatatableExportActions::myExports()` lists the signed-in user's own `datatable.export`
  tasks — status, and a download link where completed — no `super`+ needed, the same
  ownership `exportstatus()`/`exportdownload()` already enforce one task at a time.

### Changed

- `tableTools` and `backgroundExport`, told to coexist earlier today, now share ONE
  toolbar instead of rendering two side by side: `excel`/`csv` drop out of the native
  `buttons` array and the export control (the modal's trigger) takes their place in that
  same array — `copy`/`pdf`/`print` stay. A table with `tableTools = false` still gets the
  standalone button before the table, as it always has.

### Documentation

- "Background CSV export" in the Html Components Guide covers the modal's fields; the
  Queue Guide notes `scope: 'page'` skipping the transaction wrap.

### Fixed

- "My downloads" inside the modal always answered "Export failed". The request called
  `/myexports` (all lowercase) against `DatatableExportActions::myExports()` — routing to
  a controller action by name is not guaranteed case-insensitive, so the request fell
  through to the controller's default action and got back a full HTML page instead of
  JSON, which `jQuery.getJSON()` then failed to parse. No PHP-side test caught it: every
  existing test called `myExports()` directly, never through its route name. Found
  end-to-end.
- "My downloads" listed a bare `#<taskid> — status`, nothing to tell apart which of a
  person's own exports a row even was. `myExports()` now returns a `label` per row — the
  model's short class name, the format, when it was queued, and, once completed, the row
  count already sitting in `success_message` — and the modal shows that instead.

## The export modal's format select can write Excel, not only CSV (FW-528)

### Added

- `format: 'excel'` alongside `'csv'`. Rows are always written as CSV first;
  `Pramnos\Export\Xlsx::fromCsv()` — already in the framework, needing only `ext-zip`, no
  third-party library — converts that into the finished `.xlsx`. No new Composer
  dependency, hard or suggested: an application does not have to decide whether to carry
  `phpoffice/phpspreadsheet` in `vendor/` just because this feature exists.
- `DatatableExportTask::filePath($taskId, $format)` picks the extension by format
  (`csvPath()` stays, now a thin wrapper for `format: 'csv'`). `exportdownload()` reads
  the finished task's own `format` (from its payload, never `success_message`) to serve
  the right file with the right `Content-Type` and filename extension.
- The modal's format select leaves "Excel" out when `ext-zip` is missing
  (`class_exists(\ZipArchive::class)`), rather than queuing an export that would fail
  after it is already running on a worker.

### Fixed

- `purgeOldTasks()`'s export-file cleanup (FW-526) only ever tried the `.csv` path, so an
  `.xlsx` export's file outlived its row the same way every export's file used to before
  that fix. `DatatableExportTask::allFilePaths()` now tries every known format's path —
  cleanup does not decode a row's payload just to learn which one it used.

### Changed

- The button/toolbar entry and the "ready" link both said "...CSV" (`Export CSV`,
  `Download CSV`), left over from before `format: 'excel'` existed. Both are now just
  `Export`/`Download`, since which format a given export actually used is no longer a
  safe thing to print on the button that chooses it.

## The export modal's format select can write JSON too (FW-529)

### Added

- `format: 'json'` alongside `'csv'`/`'excel'`. Rows are written as CSV first, same as
  every format; `DatatableExportTask::csvToJson()` turns that into a JSON array of
  `{label: value}` objects. `json_encode()` is core PHP, so the option always appears in
  the modal — no runtime guard the way `'excel'` needs one for `ext-zip`.
- `exportdownload()` serves it as `application/json`/`.json`. `purgeOldTasks()`'s export
  cleanup (FW-526/FW-528) needed no change at all: `DatatableExportTask::allFilePaths()`
  is already generic over every known format.

## The export modal stays open and shows its own progress, result and retry (FW-530)

### Changed

- Clicking "Start export" closed the modal immediately, and progress/the download link
  showed up beside whichever button opened it — the standalone button, or the native
  toolbar's custom button, which the modal itself was now covering. The modal stays open
  instead: its controls (format/scope/notify/My downloads) hide, a progress area inside
  the same modal polls while the export runs, and that same area shows the download link
  when it is done, or a failure with a "Try again" that goes back to the controls. The
  modal's own `×`/Cancel/Escape/backdrop-click still close it at any point — closing does
  not cancel an export already queued.

### Fixed

- The "all filtered rows" / "current page only" radios had no shared `name` attribute, so
  the browser never treated them as one group: clicking the second just checked it too,
  leaving both checked at once. Both now declare `name="pf40-export-scope-<table>"`.

## Live progress while an export runs, and its "ready" notice now reaches push too (FW-531)

### Added

- `QueueManager::updateProgress($task, $current)` — a direct, single-column `UPDATE` of a
  new `queueitems.progress_current` (migration `2026_11_18_000001_...`), for a long-running
  task to report how far it has gotten without saving the whole row back on every batch.
  General, not datatable.export-specific: any task handler can call it, and a poller reads
  the column back the same way.
- `DatatableExportTask` reports rows written after every batch of a `scope: 'all'` export;
  `exportstatus()` carries it as `progress`. The modal's status line becomes "N rows so
  far" once a figure arrives, instead of a static "Exporting…" for a run that takes
  minutes. `scope: 'page'` never reports one — a single query finishes before the first
  poll would land.
- A small note in the progress area: the export keeps running even if the window closes,
  and "My downloads" finds it again later.

### Changed

- The "ready" notice (`notify_email`) is now `DatatableExportReadyNotification`, dispatched
  through the framework's own `Notifier`, not a raw `Email::queue()` call. Mail still
  always goes out; a requester with a live browser push subscription — the same permission
  the admin already asks for elsewhere — now also gets it there, with no further wiring.
  Same pattern as `Todos\TodoNotification` and `Auth\Notifications\SignInApprovalNotification`.
  The checkbox and its behavior are otherwise unchanged.

## A push notice is skipped while the requester is already watching (FW-532)

### Added

- `QueueManager::recordPoll($taskId)` / `recentlyPolled($taskId, $withinSeconds = 10)` —
  a new `queueitems.last_polled_at` (migration `2026_11_18_000002_...`) records the last
  time a task's status was successfully polled; `recentlyPolled()` reads it back fresh
  (never trusting a `QueueItem` a worker has held in memory) to answer "is somebody
  watching this right now". Generic, like `updateProgress()` beside it.
- `exportstatus()` calls `recordPoll()` on every successful check. `DatatableExportTask`
  calls `recentlyPolled()` (10 seconds — double the modal's 3-second polling interval)
  before sending the "ready" push: a push would only repeat the download link already on
  the requester's screen if they are still looking at the modal. Mail is unaffected — it
  always goes out when `notify_email` is set, watched or not.

## The export modal can export only the columns currently visible in the grid (FW-533)

The export modal built the `columns` it posts from `aoColumns`' server-rendered `bVisible` —
whatever was visible when the page loaded — completely ignoring a `showHide` picker's own
live state. An admin who hid a column on screen (or revealed one hidden by default) got an
export that disagreed with what they were looking at.

### Added

- A second radio pair, "All columns" / "Selected columns", next to the existing row-scope
  one — only rendered when the table's `showHide` picker exists (true by default); without
  one there is nothing to choose between. Defaults to "All columns", so a table that already
  exports keeps posting exactly what it did before this choice existed.
- "Selected columns" reads the picker's LIVE visibility at the moment "Start export" is
  clicked — `fnSettings().aoColumns[n].bVisible`, the same property `fnSetColumnVis()`
  toggles — from a lookup built once per table (`pf40_allExportColumns_{var}`) that, unlike
  the "All columns" default, also lists a column hidden at render time, since the picker can
  reveal one of those too.
