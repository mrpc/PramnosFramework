## The DevPanel's policy callback decides the development route only

### Documentation

- A policy callback set by a `DevPanelController` subclass replaces the development route's
  usertype floor, and nothing else. An account `app.php` admits on any deployment (the `root`
  role, `usertypes`, `userids`) is let in before the callback is asked, so a callback that says
  no does not keep root out.
    - This was always the behaviour. It is now stated in the DevPanel Guide and on the property.
    - To keep an account out, narrow the lists.

## `schedule_task` requires a kind

### Fixed

- **A reminder no longer becomes a question.** Asked "remind me in 2 minutes: …", a model called
  `schedule_task` without `kind`. The task was made as `ask`, and two minutes later a model was
  asked the words instead of the person being reminded of them.
    - `kind` is now required in the tool's schema, and a call without it is refused with an error
      that says which kind is which.
    - The model then calls again with the kind.

## A page left open refreshes its CSRF tokens

### Added

- **`pf-utils.js` refreshes a page's CSRF tokens once they are ten minutes old**, when the tab
  comes back into view and before a form carrying one is sent.
    - It updates every `_csrf_token` field, `<meta name="csrf">`, and every form-token field.
    - A form signed in on another tab, or one left open past its session, is no longer refused
      with what was typed lost.
    - There is no timer, so an idle session still expires.
- **`GET /Csrf`** (`Pramnos\Application\Controllers\Csrf`) answers the current tokens. It is
  served by the framework and never cached, and refuses a cross-site request.
- **`<meta name="csrf-refresh">`** on every page names it.
- **`window.pfRefreshCsrf()`** asks at once.
- **`pramnos-testing`'s `Event`** has `stopImmediatePropagation()`.

### Documentation

- The Security Guide has a new section, **A page left open: the token is refreshed**.
- There is a new row in the Upgrade Guide.

## The analyst's scheduled page: its buttons, its floor, its words and its links

FW-137 and FW-138, from an application serving the analyst's scheduled page.

### Fixed

- **Pause and Resume answer on the analyst's page.** `SchedulesTasks::scheduledupdate()` read the
  person through `scope()`, which only the chat page has, so on `Ai/scheduled` it failed with a
  500. It reads `taskScope()`, as the other actions do.
- **The scheduled actions in `AiController` are behind the admin floor.** The trait's six actions

- **`next_run_local` is in figures**, `19/10/2026 09:00`, not `Mon 19 Oct 2026, 09:00`, which an
  English month name made English on every page, and in what the model repeated.
- **An analyst report's link from the site's cron leads into the administration.** It used
  `AdminArea::url()`, which prefixes only in an application with an admin area, so a site's cron
  wrote `/Ai/report/N`. Report links and conversation links share `AnalystAssistant::areaUrl()`.

- **`'llm' => ['chat' => ['notify_via' => ['database']]]`** keeps scheduled-task notifications to
  the bell. `RoutineReady::channels()` decides for both `RoutineReady` and `TaskReminder`.
- **`AiController::settingsLink()`** — the Settings link under Ask's heading; return `''` to hide

  delete it.
- `RoutineReady`/`TaskReminder` subclasses whose `via()` only returned `['database']` can be

## `push:setup` finds the worker it is told about, and checks the icon and the routing

FW-141, from an application whose worker is `www/serviceWorker.js`.

### Fixed

- **The worker is found where it is.** `push:setup` looked only for `sw.js` and
  `service-worker.js`, so a worker called `serviceWorker.js`, with all three handlers, was reported
  as having none, and `--apply` would have written a second worker that nothing registers.
    - `'push' => ['service_worker' => …]` in app.php names it, and is looked at first.
    - `serviceWorker.js` is among the names looked for.
    - Each step names the file it checked.
- **A worker written where there was none has its placeholders filled**, `{{ APP_SLUG }}` among
  them, as `init` fills them (`Init::serviceWorkerValues()`). The run says nothing registers it
  yet.
- **A tapped notification takes an open tab where it leads.** The worker focused the tab and
  posted `notification-click`, and nothing listened. The browser script now navigates, within the
  site's own origin. A single-page application can cancel `pf:notification-click` and route for
  itself.
- **The browser script works in a folder install.** `push/key` and `push/subscribe` are worked
  out from where the script is loaded, or from `data-push-base`, not from the host's root. The
  worker's default icon and badge are resolved against its scope.

### Added

- **A routing step.** It GETs `push/key` under the site address and expects the push controller's
  answer: 200 or 503, as JSON. A 301 from an application's own routing used to leave every step
  green and nothing subscribed.
- **An icon step**, and `'push' => ['icon' => …, 'badge' => …]`, which every notification carries
  unless it gives its own (`PushChannel::iconSetting()`).

## Every enqueued script and stylesheet is on the page once

FW-143.

### Fixed

- **A theme that calls `renderCss()` and `renderJs()`, as the scaffolded ones do, printed each
  asset twice.** `processHeader()` put the stylesheets and head scripts into the head the document
  draws, and the theme printed them again. `render()` also appended the document's foot after the
  theme's foot, which `renderJs()` had already filled. jQuery, select2, jQuery UI, DataTables and
  pf-utils loaded twice on every screen that enqueued them.
    - A stylesheet now comes out where `renderCss()` is.
    - A head script comes out in the document's `<head>`, before the content, where an inline
      script in a screen can use it.
    - A footer or inline script comes out where `renderJs()` is.
    - A layout drawn without the document's head still gets the head scripts from `renderJs()`.

## Push subscriptions need this site's token; push.js speaks the page's language and survives a replaced URL; admin pages' assets are not cached

FW-144, and item 6 of FW-141.

### Fixed

- **`push/subscribe` and `push/unsubscribe` refuse a request from another site.** Only the
  session cookie protected them, and `SameSite=Lax` sends it on a POST from another subdomain of
  the same site, so a page there could attach its own endpoint to the signed-in account. They now
  need the session's token (`X-CSRF-Token`) or the browser's `Sec-Fetch-Site: same-origin`; the
  latter is what the worker's re-subscription has. `push.js` sends the token from
  `<meta name="csrf">` or `data-push-token`.
- **`push.js` no longer throws "URL is not a constructor"** on a page that declares
  `var URL = "…"`. It resolves addresses with an anchor when the constructor has been replaced.
- **The worker no longer caches what an administration page loads.** It used to skip admin and
  API requests by the request's own URL, so root assets that admin pages load, such as
  `pf-utils.js` and fonts, were cached stale-while-revalidate. After a deploy an administrator got
  last release's script beside this release's HTML. The page that asked now decides, by the
  request's referrer or by `clients.get(clientId)`. A worker that activates deletes its own asset
  cache.

### Added

- **`push.js` says its sentences in the page's language**, from `data-push-words`, which
  `Push\BrowserScript::attributes()` writes on its tag. The themes print it.
- `push:setup` reports a `push.js` without `data-push-words` or the token as out of date.

## Navigation preload, a worker address that versions itself, `mtime` asset versions, and a stored miss with its Cache-Control

FW-145, items 1, 2 and 7.

### Added

- **Navigation preload in the scaffolded worker**, switched on when it activates. A navigation
  answers with `event.preloadResponse` when the browser started one, and with the network
  otherwise. The offline page still stands in when both fail. A navigation into a skipped area
  uses the preload too, so the browser does not request it twice. Without preload, the worker's
  boot added about 50 ms to every navigation on a desktop and 250 ms or more on a phone.
- **`ServiceWorker::url($file, $params)`**: the worker's address with `?v=` its modification
  time, then its parameters. `init` writes it into the themes' registration.
- **A *Worker caching* step in `push:setup`.** It asks for the worker and says when it is served
  without `Cache-Control: no-cache` or with a `max-age` over five minutes.
- **`'mtime'` as a version** in `registerScript()`, `enqueueScript()` and `registerStyle()`: `?v=`
  the file's modification time, as `assetUrl()` stamps it. Another site's address is left alone.

### Fixed

- **PageCache's `cacheControl` reaches the miss that filled the cache**, not only the hits after
  it (`PageCache::storedResponse()`, from the middleware). It is not applied when PHP has a cookie
  queued. The bfcache value, `private, no-cache`, is documented.

## The sign-in credential is a token per device, not the password hash

FW-146, a security fix.

### Fixed

- **`$_SESSION['auth']`, the `auth` remember-me cookie and the login response's `auth` key no
  longer carry the stored password hash.** The hash had these problems:
    - it was a bearer credential for as long as the password stayed the same;
    - it was identical on every device, so one could not be signed out alone;
    - it was refreshed on every request;
    - it handed the hash, ready for offline cracking, to whoever read the cookie or a page that
      printed it.
- Each sign-in now gets its own `RememberTokens` token: random, stored only as a hash, expiring
  after 30 days (`auth.remember_days`).
    - It is issued in `triggerLogin()` before either path writes it, so an application's own user
      addon writes the token too.
    - `logout()` ends it.
    - A password change ends it, from any path.
- Signing in again from the cookies (`Auth::rememberLogin()`, also through the `UserDatabase`
  addon) uses the token once and issues a new one.

### Added

- **`Auth::signOutEverywhere($userId)`** ends every token and flags each live session to sign
  out.
- **`Auth::authCheck()` signs in from the cookies itself when no auth addon is registered.**
  Before this, remember-me needed the `UserDatabase` addon.
- **An old password-hash cookie still signs in once and is replaced**, so the upgrade signs
  nobody out. `'auth' => ['legacy_remember' => false]` refuses it.
- **A token is accepted where the stored hash was expected**
  (`auth($username, $auth, true, true)`, DatabaseAuthDriver's path 4). An application's own auth
  addon that signs in again from the cookie this way, and a mobile client re-authenticating with
  the `auth` it was given, keep working. Without this they would be signed out once their session
  ended.
- **Before `migrate`, a sign-in keeps the credential it had**, and the log says to migrate.
  `RememberTokens::issue()` answers null when it cannot store the token. It reads the insert's
  answer, since PostgreSQL reported the missing table as false rather than throwing.
- Migration `2026_10_16_000001_create_remember_tokens_table`.

### Documentation

- The Authentication Guide says never to print `$_SESSION['auth']` into a page.

## One broken browser can no longer fill the PHP pool with error reports

FW-147. In production, one browser with a broken CacheStorage sent about 840 reports to

### Fixed

  It used to send one report per error, with the session cookie.

- **The 30-a-minute limit holds without APCu.** It is counted in the application's cache

## A sign-in token is spent where the hash was expected, and "log in as" ends the token it replaces

Two findings from adopting FW-146.

### Fixed

## The page cache: cookies PHP queued, the remember-me cookie, and a CDN header

FW-145, items 10 and 11.

### Fixed

- **A page that queued a cookie with `setcookie()` is not stored.** `store()` used to see only the
  Response's own headers, and the queue that PHP's `setcookie()` writes to slipped past it. The
  framework's visitor tracking, written on every request, is harmless (`harmlessCookies`), and an
  application adds its own. The session cookie is not harmless.
- **The remember-me `logged` cookie bypasses the cache.** The framework keeps its cookies as an
  array under a prefix by an encoded name, so the default `#^(auth|remember|logged)#` pattern
  never matched them. A remembered visitor without a live session was served the anonymous page.
  Array-style cookies are now matched as `name[key]`, and the framework's by the name they were
  given.

### Added

- **`cdnCacheControl`**: on a HIT only, `CDN-Cache-Control` (or a header named,
  `Cloudflare-CDN-Cache-Control`) with what is left of the entry's TTL. Off by default.

## Signing in as somebody else, and back without a password

FW-149. Since "log in as" ends the administrator's token, getting back meant signing in again, and
one installation's staff do this about 250 times a month.

### Added

- **`Auth::impersonate($userId)` and `Auth::endImpersonation()`** (`Auth\Impersonation`).
    - The administrator's token ends on the way in, so nothing that signs them in stays in the
      browser.
    - The way back is a one-time key held only in the impersonated session. Its hash is kept in

      password.
    - Signing out while impersonating closes the way back.

- **Who may:** from `super` up, only as an account of a lower usertype
  (`'auth' => ['impersonation' => ['min_role', 'hours']]`).
- **`POST Users/loginas/{id}`** from the administration, and **`POST /Impersonation`** to come
  back, in every application.
- **`Impersonation::banner($action)`** shows the account being viewed, with the way back.

## Speculation rules

FW-145, item 8.

### Added

## Public pages in the service worker

FW-145, item 5.

### Added

  (JSON: `match`, `strategy` `network-first` or `swr`, `timeout`, `maxAge`), with `maxPages` and
