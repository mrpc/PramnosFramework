## Localized route groups and `Document` alternates — the first piece of hreflang

### Added

- `Router::get()`/`post()`/`put()`/`patch()`/`delete()`/`options()`/`head()` accept an array of
  `locale => path` instead of a string `$uri`, registering one route per locale that shares a
  name and a group — `$router->get(['el' => '/syxnes-erwthseis', 'en' => '/faqs'], $action)`.
  `Router::getLocaleSiblings($route)` returns every sibling of a matched route, keyed by locale.
  A string `$uri` behaves exactly as before, so this is additive.
- `Document::addAlternate($locale, $url)` adds an hreflang `<link rel="alternate">`, including an
  `x-default` derived from the `default_language` setting.
  `Document::addAlternatesFromRoute($router, $route)` adds every sibling of a localized route
  group automatically — the one line a page needs for hreflang the router already knows, with no
  slug map. Nothing is emitted unless one of these was called; existing pages are unaffected.
- This is step 2 of [hreflang and sitemaps — design](../../Hreflang-And-Sitemap-Design.md): the
  `Hreflang` registry for database-backed pages, `Document::$robots`, and the sitemap generator
  are still to come.

## The `Hreflang` registry — hreflang for a page the router can't derive alternates for

### Added

- `Pramnos\Html\Hreflang`, loaded from `app/hreflang.php` the same way `Search\Registry` loads
  `app/search.php`: `group()` for a hand-declared family of translated URLs, `resolver($key, fn)`
  for a database-backed one (the controller passes its own key, e.g. `'Jobs@view'`, and its
  params), and `singleLanguage($path)` to state explicitly that a page has no translations —
  distinct from a path nothing is registered for. A resolver that throws, or returns anything
  other than an array, answers with no alternates rather than fataling the page.
- `Document::addAlternatesFromHreflang($resolverKey, $path, $params)` feeds the registry's
  answer into the `<head>` in one call, trying the single-language check, then the resolver, then
  a group match, in that order. Independent of `addAlternatesFromRoute()` (added above) — a page
  uses whichever mechanism fits.
- Step 3 of [hreflang and sitemaps — design](../../Hreflang-And-Sitemap-Design.md) is now
  complete. Still to come: `Document::$robots` and the sitemap registry.

## `Document::setRobots()` — one home for a page's robots directive

### Added

- `Document::setRobots($directive)` — e.g. `$doc->setRobots('noindex, nofollow')` — sets both
  the `<meta name="robots">` tag and the `X-Robots-Tag` header from the same value, so the two
  can no longer disagree. `$doc->robots` stays `null`, and nothing is emitted, for a page that
  never calls it.
- `StandalonePage::themedPage()` — reached from an unsubscribe or mailing-list confirmation link
  rendered inside the site's theme — now calls `setRobots()` instead of sending the header by
  hand, which also gives it the `<meta>` tag it was missing before. The framework's other eight
  `header('X-Robots-Tag…')` call sites named in
  [hreflang and sitemaps — design](../../Hreflang-And-Sitemap-Design.md) §1 build their response
  without ever constructing a `Document` — a raw HTML string, a binary image, a redirect with no
  body — so there is nothing for `setRobots()` to set, and they keep their own `header()` call.
