## Localized route groups and `Document` alternates — the first piece of hreflang

### Added

- `Router::get()`/`post()`/`put()`/`patch()`/`delete()`/`options()`/`head()` accept an array of
  `locale => path` instead of a string `$uri`, registering one route per locale that shares a
  name and a group — `$router->get(['el' => '/syxnes-erwthseis', 'en' => '/faqs'], $action)`.
  `Router::getLocaleSiblings($route)` returns every sibling of a matched route, keyed by locale.
  A string `$uri` behaves exactly as before, so this is additive.
- `Document::addAlternate($locale, $url)` adds an hreflang `<link rel="alternate">`, including an
  `x-default` derived from the `default_language` setting.
  `Document::addAlternatesFromRoute($router, $route)` adds every sibling of a localized route
  group automatically — the one line a page needs for hreflang the router already knows, with no
  slug map. Nothing is emitted unless one of these was called; existing pages are unaffected.
- This is step 2 of [hreflang and sitemaps — design](../../Hreflang-And-Sitemap-Design.md): the
  `Hreflang` registry for database-backed pages, `Document::$robots`, and the sitemap generator
  are still to come.

## The `Hreflang` registry — hreflang for a page the router can't derive alternates for

### Added

- `Pramnos\Html\Hreflang`, loaded from `app/hreflang.php` the same way `Search\Registry` loads
  `app/search.php`: `group()` for a hand-declared family of translated URLs, `resolver($key, fn)`
  for a database-backed one (the controller passes its own key, e.g. `'Jobs@view'`, and its
  params), and `singleLanguage($path)` to state explicitly that a page has no translations —
  distinct from a path nothing is registered for. A resolver that throws, or returns anything
  other than an array, answers with no alternates rather than fataling the page.
- `Document::addAlternatesFromHreflang($resolverKey, $path, $params)` feeds the registry's
  answer into the `<head>` in one call, trying the single-language check, then the resolver, then
  a group match, in that order. Independent of `addAlternatesFromRoute()` (added above) — a page
  uses whichever mechanism fits.
- Step 3 of [hreflang and sitemaps — design](../../Hreflang-And-Sitemap-Design.md) is now
  complete. Still to come: `Document::$robots` and the sitemap registry.

## `Document::setRobots()` — one home for a page's robots directive

### Added

- `Document::setRobots($directive)` — e.g. `$doc->setRobots('noindex, nofollow')` — sets both
  the `<meta name="robots">` tag and the `X-Robots-Tag` header from the same value, so the two
  can no longer disagree. `$doc->robots` stays `null`, and nothing is emitted, for a page that
  never calls it.
- `StandalonePage::themedPage()` — reached from an unsubscribe or mailing-list confirmation link
  rendered inside the site's theme — now calls `setRobots()` instead of sending the header by
  hand, which also gives it the `<meta>` tag it was missing before. The framework's other eight
  `header('X-Robots-Tag…')` call sites named in
  [hreflang and sitemaps — design](../../Hreflang-And-Sitemap-Design.md) §1 build their response
  without ever constructing a `Document` — a raw HTML string, a binary image, a redirect with no
  body — so there is nothing for `setRobots()` to set, and they keep their own `header()` call.

## `sitemap:generate` and the `Sitemap` registry — hreflang and sitemaps, done

### Added

- `Pramnos\Html\Sitemap::provider($label, $provider)`, loaded from `app/sitemap.php` the same
  way `Hreflang`/`Search\Registry` load their own files: a generator yielding sitemap entries
  entirely on the application's own criterion — the framework offers no `latest N` / `changed
  since` shape.
- `php pramnos sitemap:generate` combines registered providers with two sources that need no new
  declaration: every localized route group in a `--routes` file, and every hand-declared
  `Hreflang::group()` — "one declaration, two consumers" now covers the sitemap too.
  `Pramnos\Html\SitemapWriter` streams the XML (never buffers the whole document), shards past
  50,000 URLs/50MB with a `<sitemapindex>`, rewrites every shard wholesale on each run (deleting
  any a previous, larger run left behind), and checks the all-or-nothing rule for a locale group
  at generation time — a warning naming the missing URL, not a failure, when one is broken.
- This closes [hreflang and sitemaps — design](../../Hreflang-And-Sitemap-Design.md) except the
  §5 development-mode warning, which needs `Document::$excludeFromSitemap` (not built) to fire
  from — and closes the matching item in `Roadmap.md`.

## Voice for Ask AI — dictation and read-aloud, no server side

### Added

- `llm.voice` (default off) adds a microphone and a "🔊 Listen" button to the chat page in every
  theme: dictation and read-aloud, entirely in the browser over the native Web Speech API —
  Phase 1 of the Roadmap's voice design, plus part of phase 3 (barge-in, gender-aware pitch).
- `pf-voice.js` — `window.PfVoice.createVoiceState()`: `startDictation()`/`speak()` and their
  `stop`/`toggle` forms, voice picking that never hands a female persona a voice detected as
  male (or the reverse), and barge-in — an interrupt word stops the assistant mid-sentence, with
  its own voice filtered out of the microphone first so it is never mistaken for a new question.
- `pf-speech-sanitizer.js` — `window.PfSpeechSanitizer`: strips Markdown/emoji, transliterates a
  Latin word to Greek phonetics rather than letting TTS spell it, and corrects Greek grammatical
  gender. `addGenderPhrases()`/`addTransliteration()` let an application register its own
  assistant's stock phrases and domain vocabulary instead of this file carrying one.
- `pf-voice-fillers.js` — `window.PfVoiceFillers`: 127 natural Greek filler phrases for a voice
  conversation to say while an answer is still being worked out.
- See the [Analyst Guide](../../Pramnos_LLM_Analyst_Guide.md#voice).
- A missing `.pf-chat-mic` style from the same change, in every theme: the mic button rendered
  but unstyled, the way `.pf-chat-attach` is, until now.

## `pf-tour.js` — a spotlight product tour

### Added

- `window.PfTour.start(steps, options)` / `.stop()`: dims the page, cuts a glowing window around
  one element per step, and shows a card with that step's own text — a driver.js-style
  walkthrough, zero dependencies, carrying no content of its own. A step is `{title, desc,
  selector?, avatarHtml?}`; `options.voice` (a [`pf-voice.js`](../../Pramnos_LLM_Analyst_Guide.md#voice)
  controller) adds an optional "🔊 Listen" button.
- See the [Components Guide](../../Pramnos_Html_Components_Guide.md#spotlight-tour-pf-tourjs).

## `pf-companion.js` — a floating companion dock: infrastructure, deliberately not content

### Added

- `window.PfCompanion.mount(options)` / `.unmount()`: a fixed-position dock for one avatar
  (typically `Assist\AvatarSets::render()`'s own output), idle detection
  (`pf-companion:activity`, active/away — the only idle vocabulary this defines), and a click
  event (`pf-companion:click`) that presumes nothing about what a click should do.
  `setPose(name)` passes any string through to the avatar's `data-pose` attribute, completely
  unvalidated — no pose list, no enumeration, no character content. `setPosition(corner)` is a
  convenience default for four named corners; `.pf-companion-dock` is plain CSS, overridable for
  anything else.
- `window.PfCompanionDebug.mount()` / `.unmount()`: a generic preview panel for whatever is
  mounted — a live copy of the avatar, the 9 `pfAssistant` states to audition, and a free-text
  box to try any pose name. An optional `data-poses="a,b,c"` on the avatar turns into quick-pick
  buttons; its absence breaks nothing.
- Built so that two applications — one with a dozen custom character poses, one with none — can
  build genuinely different companions on the same floor without either shaping what the other
  can do. See the [Analyst Guide](../../Pramnos_LLM_Analyst_Guide.md#the-floating-companion).

## `pf-chat.js`'s look stops depending on the host's Bootstrap/daisyUI version

### Fixed

- The example-question buttons, the answer bubble's Markdown typography (headings, lists,
  tables, code) and the `btn`/`btnGhost`/`input`/`card` structural classes used to render with
  no CSS of their own in `pf-chat.js` — their whole look rode on whatever the host page's loaded
  Bootstrap or daisyUI version defaulted `.btn`/`.form-control`/`.card` to, which is exactly
  where a page carrying an old Bootstrap (3.x) broke. Each now gets an explicit `pf-chat-*` class,
  scoped under `.pf-chat`, so it outranks the host's own class — the theme-native class stays in
  the markup alongside it, nothing is removed.
- The colours still come from the host page, through the `--pf-*` fallback chain
  (`components.css`'s existing token-bridge: daisyUI → Bootstrap → the project's own `theme.css`
  tokens → a hardcoded default) — only the *structure* stopped depending on which CSS framework,
  or which version of it, happens to be loaded.
- `components.css` is the one scaffolding file `project:resync --styles` re-pulls into an
  already-scaffolded project, so this reaches existing installations on the next resync; the
  `$c`-map change in `chat.html.php` is copy-once, so it only seeds new scaffolds correctly.
- See the [Components Guide](../../Pramnos_Html_Components_Guide.md#pf-chatjss-own-look-does-not-depend-on-your-bootstrap-version).
