# 25 November 2026

Three entries today; the first two are the same `Datatable` fix in two steps, the third is an
unrelated `Datasource` bug found investigating a production incident:

- A column filter control rendered outside the table's own footer is found again, falling back
  to the page-wide lookup FW-556 had replaced (FW-556 follow-up)
- That filter's `change`/`keyup` now delegate from `document` instead, which also reaches a
  column hidden by default once an admin reveals it (FW-556 follow-up, part 2)
- `Datasource::render()`'s `$whereStatement` no longer erases every occurrence of the word
  "where", only its own leading keyword

<!-- more -->

## A column filter control rendered outside the table's own footer is found again (FW-556 follow-up)

### Fixed

FW-556 scoped `Datatable`'s column-filter `change`/`keyup` binding to the table's own footer
(`jQuery(table.api().table().footer()).find('#id')`) instead of a bare `jQuery('#id')`, because
`scrollX` (always on) clones the footer into a second, hidden "sizing" row carrying the same id,
and the bare selector bound to that invisible clone rather than the one on screen.

That fix assumed the filter's control was always inside the footer it was rendered into (the 6th
argument to `addColumn()`). A control rendered elsewhere on the page entirely — the 9th argument
naming an id, with the 6th left `''` — was never cloned by `scrollX` in the first place, so it was
never the case FW-556 was fixing, but the scoped-only lookup found nothing there either, silently
dropping every value the admin picked. Reported against ~15 columns across two real screens that
upgraded past FW-556 without anyone checking that pattern.

The scoped lookup now falls back to the page-wide one **only when it finds nothing** — the
pre-FW-556 behaviour, restored for exactly the case FW-556 never touched, without reopening the
duplicate-id bug it fixed: a control `scrollX` actually cloned is always found by the scoped
lookup first, so the two cases never collide.

## That filter's `change`/`keyup` now delegate from `document` instead (FW-556 follow-up, part 2)

### Fixed

The scoped-lookup-with-fallback above still bound `change`/`keyup` once, to whatever element the
lookup found at init. A column hidden by default (`addColumn()`'s 1st argument, `visible`,
`false`) has no cells at all at that point — DataTables removes them from the DOM entirely, not
merely hides them — so neither the scoped lookup nor its page-wide fallback found anything, and
nothing was ever bound; when an admin later revealed the column from the column-visibility
picker, its control was created fresh, after the one-time binding had already run and nothing
re-triggered it. Same symptom as the original FW-556 bug — the admin picks a value and nothing
happens — a different cause. Reported against 6 columns hidden by default on two real screens.

`change`/`keyup` for the id-string filter (the 9th argument to `addColumn()`) are now delegated
from `document` by the id, rather than bound to an element found once: a delegated listener only
has to match whichever element actually dispatched the event, so it does not matter whether that
element exists yet when the listener is attached, or where on the page it ends up — covering a
hidden-by-default column, a control outside the table entirely, and the original duplicate-id
case together, the same way: the scrollX "sizing" clone that made a direct binding unsafe is
never itself clicked or typed into, so delegation was never exposed to it in the first place.

The filter's current value (the 10th argument) still needs an actual element to write to at
init, so the scoped-lookup-with-fallback from the first entry above stays, unchanged, for that one
purpose; a bookmarked filter on a column that starts hidden still only shows its value once the
column is revealed and the table state is restored again — a narrower, pre-existing gap, not
reopened by this fix.

## `Datasource::render()`'s `$whereStatement` no longer erases every occurrence of the word "where"

### Fixed

`$whereStatement` is passed with its own leading `WHERE` keyword (`'WHERE a.status = 1'`), which
`render()` strips before handing the rest to the query builder's own `whereRaw()`, which adds its
own keyword. It did that with `str_ireplace('where', ' ', $whereStatement)` — a blind,
case-insensitive substring replace with no position check and no occurrence limit, so it erased
**every** match anywhere in the fragment, not only that leading one.

Found investigating a production incident: a model's `$whereStatement` built a correlated
`EXISTS` subquery with its own, legitimately nested `WHERE` further in
(`exists (select 1 from x v where v.col = a.col and exists (select 1 from y e where …))`).
`str_ireplace` deleted both inner keywords too, turning it into `… from x v v.col = a.col …` — a
database syntax error, not merely a wrong filter — on every request to that screen. The same bug
would have corrupted any fragment where the four letters "where" appear anywhere past the leading
keyword at all: a string literal's value, a column or table name, a comment.

Now strips only a leading `WHERE`, once, with an optional following word boundary and whitespace
— anything after that first keyword is left exactly as the caller wrote it.
