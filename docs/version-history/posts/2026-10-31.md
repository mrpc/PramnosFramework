# 31 October 2026

Three entries today:

- Scheduled AI tasks move into `pramnos`, out of the application's schema
- `loadDotenv()` fills the process environment, not only `$_ENV`/`$_SERVER`
- `list-tables`'s PostgreSQL row count no longer overflows past 2.1 billion rows

<!-- more -->

## Scheduled AI tasks move into `pramnos`, out of the application's schema

### Fixed

- `ai_routines`, `ai_task_runs` and `ai_task_subscriptions` are scheduler and log state — exactly
  what `pramnos.*` is for — not application data; they were created in the application's schema
  by oversight. `ai_consents` (a consent list) and `llm_calls` (an application's own call log
  under this name before the framework adopted it) are unaffected: both are explicitly where
  they belong. The creating migrations now make the three as `pramnos.ai_routines`,
  `pramnos.ai_task_runs`, `pramnos.ai_task_subscriptions`; an installation that ran them before
  moves the tables once, by hand — see the Upgrade Guide.

## `loadDotenv()` fills the process environment, not only `$_ENV`/`$_SERVER`

### Fixed

- `loadDotenv()` called Symfony Dotenv without `usePutenv()`, so `getenv()` — the convention
  everywhere in this framework and its applications, matching docker-compose's `environment:`
  entries — kept returning `false` for every key a `.env` file had just loaded, even though the
  function reported success. A CLI command run over SSH, inheriting none of the web server's
  environment, read a `.env` that `loadDotenv()` said loaded and still failed to connect:
  silent, and easy to mistake for a real outage.

## `list-tables`'s PostgreSQL row count no longer overflows past 2.1 billion rows

### Fixed

- The MCP `list-tables` tool cast PostgreSQL's row count to `int`; a table past roughly 2.1
  billion rows — a TimescaleDB hypertable chunk, say — overflowed it ("value ... is out of range
  for type integer"), turning the whole tool into an error instead of a table list. Cast to
  `bigint` instead; PHP's own `(int)` cast on the result is 64-bit and was never the problem.
