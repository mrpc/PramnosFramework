## `Helpers::fileGetContents()` fetched with TLS verification off

Reported from a consuming application (FW-056). On the same day
`\Pramnos\Security\OutboundUrl` was written and `MediaObject::addRemoteImage()` was moved onto it,
this helper was left as it was — `src/Pramnos/General/Helpers.php`:

```
CURLOPT_SSL_VERIFYPEER => false     // no certificate was ever checked
CURLOPT_FOLLOWLOCATION => true      // to wherever the far end pointed
CURLOPT_MAXREDIRS      => 10
— no CURLOPT_PROTOCOLS, no size limit, only TIMEOUT => 10
```

The options appeared **twice**, once in each of the `$fakeRef` branches.

So: certificates unverified, a `302` leading anywhere the fetched server chose, `file://` and
everything else compiled into curl reachable, and a body capped nowhere. The reporter's question was
not «how do we secure it» but **«why does it exist»** — a general HTTP helper with TLS off, shipped
beside the class that does the same job properly. `grep -rn "fileGetContents(" src` gives only the
definition: no caller inside the framework, and it was the obvious choice for the next person who
wanted «download this URL».

### Fixed

It delegates to `OutboundUrl::fetch()`, which checks the scheme against an allow-list, resolves
every `A` **and** `AAAA` record and refuses private, loopback, link-local and reserved addresses,
connects to the address it approved while sending the name in `Host:` and validating the certificate
against that name, re-runs the check on every redirect hop, and stops reading at a byte ceiling
mid-stream.

Kept rather than deleted, because it is public API and there is a known caller outside the
framework. It carries an `@deprecated` tag pointing at `fetch()`, which takes the ceiling, the
timeout and the redirect budget as arguments and hands back a reason and a status — all of which a
wrapper has to decide for you.

Three behaviour changes, each of which can break a caller, and all documented in
[Pramnos_Security_Guide.md](../../Pramnos_Security_Guide.md):

- **A host on a private address is refused.** A caller fetching `sURL . $path` against its own site
  stops working — locally that name resolves to a private address. Read the file instead.
- **`$fakeRef` is ignored.** It sent a Google referer and a Firefox user agent, which is
  hotlink-protection evasion. The parameter stays so the signature does not change.
- **`allow_url_fopen` is required.** `fetch()` dials with a stream so it can connect to an approved
  address rather than a name; curl is what used to work without that setting. It fails closed —
  falling back to an unchecked curl fetch would undo the change.

### Found while fixing it: `checkUrlStatus()`, left alone on purpose

The same file has a second public fetch helper. It never disabled certificate verification and
follows no redirects, so it is not the same defect — but it does no address check, so it will report
whether something is listening on a private address, which is a host and port probe for anything
that can influence its argument. It also buffers the whole response into memory to discard it.

Left as it is, and documented instead, because «is this URL up» is a question people legitimately
ask about internal addresses — a health check for a service on the same subnet is the ordinary use,
and moving the guard inside would break the honest callers. The guide shows the `isPublic()` check
to put in front of it when the URL came from outside.

## A clamped rendition was never found again, and rebuilt on every request

Reported from a consuming application (FW-055), found because the media changes broke ten of their
tests and the new code had to be read line by line.

`resize()` clamping a request to the source's own size was the right change — a rendition larger
than the original it came from is the opposite of what a thumbnail is for. What it exposed is that
`MediaObject::get()` **looked renditions up by the size that was asked for and stored them under the
size that came out**. With `allowUpscale` off, which is the default, those differ for every source
smaller than the requested box.

So `get(177, 222)` on a 150×150 source wrote a 120×150 entry, and the next identical `get(177, 222)`
matched nothing. It rebuilt the image, appended another entry and saved the row — and because
`ResizeTools` prefixes `rand(1,9999)_` when the filename it wants already exists, that was a **new
file on disk and a new entry in the column on every call**, neither of them bounded. Measured by the
reporter: three identical calls, three files, three rows. Against their real data, 467 of 1023
images are under that box in at least one dimension — 46% of images rebuilt on every page view.

### Fixed

`Thumbnail` records `requestedX` and `requestedY` — the box that produced the rendition — beside `x`
and `y`, which stay what the rendition actually is. The lookup compares against the requested box
when an entry has one.

The alternative was to clamp the request the same way before comparing. Storing the request was
chosen because it keeps *what was asked for*, which is the information the clamp discarded, and it
survives a later change to the clamping rule; a lookup that re-derives the clamp has to stay in
lock-step with the resizer for ever.

**No migration, and nothing stored has to change.** The `thumbnails` column is JSON of the declared
fields, and the hydrator starts from a fresh `Thumbnail` and copies only the keys a row has — so
every existing row reads back with `0`, which the matcher treats as "not recorded" and compares on
`x`/`y` exactly as before.

The fallback also covers a case the JSON path does not: rows written before the column held JSON are
`serialize()` output, and the reader deliberately returns those **unconverted**, because an
application with its own thumbnail class has been getting its own objects back from them for years.
Those objects do not declare these fields at all, so the matcher reads them through `isset` — the
same reason `encodeThumbnails()` already did.

### The test that stopped one line short

`MediaRenditionPolicyTest::testARequestLargerThanTheSourceIsNotUpscaled` asked 512×512 of a 40×40
source and asserted the clamp. It never asked twice, which is why a green suite shipped this. There
are now three tests that do, including a third call — because a count growing by one per call cannot
be told from an off-by-one with only two.

### Documentation

[Pramnos_Media_Guide.md](../../Pramnos_Media_Guide.md) gains **What was asked for, and what came
out**: the two pairs of dimensions, which one to read for layout and which one the cache is keyed
on, and when `allowUpscale = true` is the right answer instead.

## Two migrations that could fail on real data now decline instead

Reported from a consuming application, and not because either one bit them: their `usertokens` is
small and their settings table has no duplicates. The deploy that prompted it is against a database
where neither has been verified — and the check that would have told them is one the framework
already knew how to write.

`canAddForeignKey()` had the pattern and nothing else used it: count the rows that would violate the
change, refuse, and name what has to be repaired. It cannot fail on dirty data; it declines and says
why.

### Added — the vocabulary, on `Migration`

`orphanCount()` moves to the base class, `duplicateGroups()` and `duplicateCount()` join it, and
`decline($reason)` records a refusal as its own state: `MigrationRunner::RESULT_DECLINED`.

`migrate` prints `Declined:` with the reason and a closing line saying these stay pending;
`migrate:status` shows `Declined` and prints the reason under the table. And because `getRanSlugs()`
counts only `RESULT_OK`, **a declined migration is attempted again next time** — repair the rows and
it applies itself.

`Declined` is deliberately not the `Skipped (cutoff)` a row can already carry. Those never ran; this
one ran, checked, and said no.

The constraint this was written against: a guard must not turn a real problem into silence. So a
count that cannot be taken — a missing table, a permission — is **zero, not a refusal**, because
declining there would make an unrelated fault look like dirty data; and a decline is recorded in
three places rather than logged and forgotten.

### Fixed — `add_unique_constraint_to_settings_table`

It drops the plain index *before* creating the unique one, so a duplicate value aborted
`CREATE UNIQUE INDEX` and left the installation with **neither** index on a column every settings
read uses. It now counts duplicates first and declines, naming the values and their row counts.

Declining rather than resolving: keeping the highest id per name is a decision about somebody's
configuration, and two rows for `sitename` may mean the wrong one has been in effect for months.

### Fixed — `add_token_lookup_to_usertokens`

Three problems, in ascending order of cost. It read the **whole table into PHP** before writing
anything — 48 MB at 50 000 rows, so around a gigabyte at a million, which is what turns "slow" into
"the deploy died". It had no `WHERE token_lookup IS NULL`, so a second deploy paid the whole cost
again. And it computed the digest in PHP row by row, which the reporter measured at 5 617 ms where
one `UPDATE … encode(sha256(token::bytea), 'hex')` takes 130.

Now: without an `APP_KEY` the whole backfill is **one statement** — which is also every installation
that has not run `key:generate`. With a key, encryption genuinely needs PHP (`encrypt()` uses a
fresh nonce per value), so it runs in batches of 2 000 behind a keyset cursor on `tokenid`, which
keeps the buffer flat and cannot skip rows the way an offset walk over a changing table does.

**And it fills only rows that can still authenticate** — `status = 1` and not expired. A revoked or
expired token is never looked up by value again, and on a long-lived installation those rows are
most of the table, because `usertokens` is an audit trail as much as a credential store. Safe
because nothing revives a token: no path sets a row's status back to active, every path that matches
on `token_lookup` and then acts also checks `status`/`expires`, and the paths that do not filter
treat a missing row as invalid — the same answer a dead row gives.

**Stated rather than left to be discovered:** rows outside that scope keep their token value as it
is, plaintext, on an installation where the rest of the column is encrypted. They cannot
authenticate and every lookup filters in SQL, so the exposure is smaller than it sounds — but it is
a real difference from "the column is encrypted", and an installation that wants the stronger claim
wants a sweep it can run when it chooses, not a migration holding a deploy open to encrypt
credentials that stopped working years ago.

A test asserts that the digest the database writes equals `Token::lookup()` exactly. If those ever
disagreed by so much as a case, every authentication lookup would miss and nothing else in the suite
would notice.

### Documentation

[Pramnos_Migration_Guide.md](../../Pramnos_Migration_Guide.md) gains **Check the data before you
change it**: the four methods, why an unaskable count is zero, why a decline is loud and comes back,
and a section on backfills — scope them, bound them, and let SQL do what SQL can.

## Saving a token through the model stored it in plaintext and unfindable

Found while verifying somebody else's reasoning about which `usertokens` rows a backfill could
skip — not reported, and not what was being looked for.

`Token::storageFor()` produces the two columns from one value: the token encrypted, and the
`sha256` digest that all fifteen authentication lookups match on. **`Token::save()` did not call
it.** It wrote `$this->token` exactly as it stood and never wrote `token_lookup` at all. So a token
inserted through the model was stored in plaintext *and* could not be found by any lookup.
`User::addToken()`, which INSERTs directly, had it right — which is why nothing in the framework
noticed.

The second half is `Token::load($value)`, which matched `WHERE token = %s`. Encryption is
non-deterministic, so the stored ciphertext never equals the presented value: that comparison
cannot match on any installation with an `APP_KEY`. It worked only where nothing was encrypted,
which is how it survived being split out.

### Fixed

`save()` goes through `storageFor()`, and `load($value)` looks up the digest with the plaintext
comparison kept as a fallback for rows written before the column existed.

**Only a plaintext value is converted.** `fillProperties()` copies the row as it is, so a *loaded*
token holds ciphertext; re-encrypting that would store something nothing can decrypt and a digest of
the ciphertext — an authentication outage rather than a bug. An already-encrypted value is written
back untouched. After a save `$this->token` holds the stored value, so a second `save()` does not
re-encrypt the plaintext under a fresh nonce and rewrite the column for no change.

**Both paths check the column exists first, cached once per process.** The first version did not,
and 25 tests failed with `Unknown column 'token_lookup'` — which is exactly what an installation
that has not run the migration would have got, on the save path, turning a token save into a failed
request on a database that is merely out of date. `hasColumn()` issues a query and `save()` runs
whenever a token's last-used moment is persisted, so asking once per process is the difference
between a guard and a tax.

## `get()` takes upscaling per call, so a template can fill its frame

`MediaObject::$allowUpscale` was the only control, and it is set on the *object* — so it governs the
derivatives `processImage()` generates as much as the rendition a template is asking for. Wanting a
150×150 avatar to fill a 177×222 slot therefore meant allowing invented pixels everywhere,
including in images being produced to store. A consuming application had already made exactly that
trade in its own copy.

### Added

`get($width, $height, $crop, $force, $debug, $resample, $allowUpscale = null)`. `null` means «what
the object says», so nothing that does not pass it changes behaviour.

| Caller | Upscale |
|---|---|
| a template with a fixed frame | **yes** — a gap is worse than a soft image |
| producing a derivative to store | **no** — a rendition larger than its source is not a thumbnail |

**The two are cached apart.** The same box asked for both ways produces two different images that
record the same requested box, so `Thumbnail::$upscaled` is part of the entry's identity. Without
it a lookup returns whichever was written first — and the direction that matters is handing
stretched blur to a caller that explicitly asked for none. Entries written before the flag read
`false`, which is what they were.

### Documentation

[Pramnos_Security_Guide.md](../../Pramnos_Security_Guide.md) gains the `save()`/`load()` contract
beside the split-column section; [Pramnos_Media_Guide.md](../../Pramnos_Media_Guide.md) gains the
per-call argument and the table above.

## An application on the legacy version ledger can say what already ran

The half of an earlier report that was left open. Both migration systems write to
`schemaversion` and key it differently: the legacy path — `Application::runMigration()` — stores a
migration's `$version` (`0.010`), the runner stores its slug (`migration0010`).

So an application that migrated for years through the old path has a full ledger the runner cannot
read a single row of. `migrate:status` calls every one of those migrations pending, and `migrate`
would run them again against a schema that already has their changes. Every such application was
writing its own one-off migration to fix it — after finding out that `migrate:status` had been
lying to it.

`migration_cutoff` is not the answer and it is worth knowing why: it filters on the filename
timestamp, and a legacy `MigrationNNNN` class has none. `filterCutoff()` lets a migration with no
timestamp through by design.

### Added

```bash
php pramnos migrate:adopt-legacy --dry-run   # what would be recorded
php pramnos migrate:adopt-legacy             # record it
```

The mapping is derivable rather than something each application hand-writes: a migration object
knows both its `$version` and its `getSlug()`, so «which of these already ran» is a lookup of the
first and a write of the second. `MigrationRunner::adoptLegacyVersions()` is the method under it.

**It records; it never executes.** The work was done by the other path years ago, and running it
again is the outcome this exists to prevent. Two refusals, both deliberate: a migration the ledger
has never heard of stays pending, because the only evidence it ran would be this inventing it; and
a slug the runner already knows is left alone, so a second run is a no-op. A migration with no
`$version` — every modern, timestamped one — is skipped, so pointing it at a mixed directory is
safe.

### Also written down: an adopter can be empty

A migration whose entire body is a `$dependencies` list is a supported way to say «this application
needs that one framework migration and nothing else». The on-demand dependency pool already did
this; what was missing is that the worked example in the guide had an `up()` that did work, so
whether an *empty* one was legitimate or an accident was stated nowhere.

It is legitimate — the dependency is pulled, ordered first, run, and both are recorded — and
`LegacyLedgerAdoptionTest` now pins it, including that the dependency actually creates its table
rather than merely being marked as run.

### Documentation

[Pramnos_Migration_Guide.md](../../Pramnos_Migration_Guide.md) gains **Coming from the legacy
version ledger** and the empty-adopter example beside the dependency-pool section.

## `crop` and `resample` are part of a rendition's identity too

Reported the same day (FW-057), from reading the commit that added `upscaled` — and the reasoning
quoted back was the one written in that commit message: *the same box asked for both ways produces
two different images which record the same requested box, so a lookup keyed on the request alone
returns whichever was written first.*

That argument applies word for word to `$crop`, and it was not applied. `get()` takes `$crop`,
passes it to `ResizeTools`, and the matcher never looked at it.

**Measured, and the first attempt at measuring it was wrong.** A probe with horizontal colour bands
showed all four combinations producing identical bytes — because a centre crop of a horizontally
symmetric image is indistinguishable from a squash. With vertical bands and a marker near one edge,
155×148 from an 800×400 source:

```
crop=true  resample=true  -> 155x148  md5=6116aa5c
crop=true  resample=false -> 155x148  md5=6116aa5c
crop=false resample=true  -> 155x148  md5=d94b13a9
crop=false resample=false -> 155x148  md5=6f320215
```

Three different pictures at one size, reproducing the reporter's numbers exactly.

### Fixed

`Thumbnail` records `crop` and `resample` beside `upscaled`, and all three have to agree before an
entry is reused. The reported caller is real and sits on both sides of one `if`: two admin
templates asking `get(155, 148, true, true)` in one branch and `get(155, 148)` in the other, for the
same media — so the cropped entry was being served to the branch that asked for the whole picture.

`resample` is recorded although it changes nothing when cropping, because an entry is identified by
what was *asked for* and a lookup cannot know that this particular source made the answer moot.
That was raised explicitly as «if it stays out, write why» — it did not stay out.

### Corrected: a claim in the previous commit

The `Thumbnail::$upscaled` docblock said entries written before it read `false`, «which is
correct: they were produced when clamping was the only behaviour». **That is not true for the
four-day window** between `allowUpscale` appearing on the object and being recorded on the entry:
an application that switched it on in that period wrote genuinely upscaled entries that now read
`false`.

The docblock now says what is actually the case — old entries get the class defaults, that is an
assumption rather than a fact, and guessing wrong costs one rebuild and one row, once. The
consequence was always small; the overclaim was the problem.

### Documentation

[Pramnos_Media_Guide.md](../../Pramnos_Media_Guide.md) gains **What identifies a rendition**: the
measured table, the five fields that must agree, and what an entry predating them is assumed to be.

## Maintenance mode can be raised and cleared from the console

Asked for: a way to put the site down by hand before a heavy migration, take it back up
afterwards, and have the automatic migrations stay out of the way in between.

Two of the three parts were missing, and one of them was a trap.

**The console did not survive the flag.** `Application::__construct()` answers the maintenance page
and exits when `var/MAINTENANCE` exists — correct for a request, and it applied to every console
command as well. Raising maintenance therefore broke `migrate`, which is the work maintenance is
usually raised *for*, and `maintenance:off`, which would have been the way back. The only exit was
deleting the file by hand, which is the state this feature exists to replace. Measured before the
change: `bin/pramnos migrate:status` printed an HTML page and stopped.

**And automatic migrations did not stand down.** `runAutoMigrations()` never looked at the flag.

### Added

```bash
php pramnos maintenance:on --reason="Adding an index to usertokens, ~20 minutes"
php pramnos maintenance:off
```

`maintenance:off` **takes down only a flag a person raised.** The flag now records its origin on a
line of its own — `manual` from the command, `automatic` from `runMigration()` and
`MigrationRunner`, `unknown` for a flag written before this existed. The last is refused rather
than assumed to be yours: there is no way to tell who raised it, and the safe reading of "no way to
tell" is "not yours". `--force` is for a batch that died and left its flag behind, and says that it
forced.

The refusal is the point of the feature. A flag the framework raised means a schema is in flux and
something is either still running or died half way; clearing it because you meant to clear your own
is the mistake worth making impossible.

### Fixed

`runAutoMigrations()` returns as soon as it sees the flag. An explicit `migrate` is unaffected — it
goes through `MigrationRunner` directly, and clears only a flag it raised itself.

`Application::__construct()` skips the maintenance page when `PRAMNOS_CONSOLE` is defined, which
`Pramnos\Console\Application` does before building the application. Keyed on that rather than on
`PHP_SAPI` on purpose: a cron worker or a deploy script booting an application under the CLI
*should* still be held off a schema in flux, and it does not define that constant.

The origin line is kept off the maintenance page. It is bookkeeping for whoever may clear the flag,
not something a visitor on a 503 has any use for.

### Documentation

[Pramnos_Framework_Guide.md](../../Pramnos_Framework_Guide.md) gains **Raising and clearing it by
hand** under maintenance mode: the two commands, the origin table, and why the console is exempt
while a worker is not.
