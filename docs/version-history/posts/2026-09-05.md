# 5 September 2026

3 changes:

- `Helpers::fileGetContents()` fetched with TLS verification off

## `Helpers::fileGetContents()` fetched with TLS verification off

Reported from a consuming application (FW-056). On the same day
`\Pramnos\Security\OutboundUrl` was written and `MediaObject::addRemoteImage()` was moved onto it,
this helper was left as it was — `src/Pramnos/General/Helpers.php`:

```
CURLOPT_SSL_VERIFYPEER => false     // no certificate was ever checked
CURLOPT_FOLLOWLOCATION => true      // to wherever the far end pointed
CURLOPT_MAXREDIRS      => 10
— no CURLOPT_PROTOCOLS, no size limit, only TIMEOUT => 10
```

The options appeared **twice**, once in each of the `$fakeRef` branches.

So: certificates unverified, a `302` leading anywhere the fetched server chose, `file://` and
everything else compiled into curl reachable, and a body capped nowhere. The reporter's question was
not «how do we secure it» but **«why does it exist»** — a general HTTP helper with TLS off, shipped
beside the class that does the same job properly. `grep -rn "fileGetContents(" src` gives only the
definition: no caller inside the framework, and it was the obvious choice for the next person who
wanted «download this URL».

### Fixed

It delegates to `OutboundUrl::fetch()`, which checks the scheme against an allow-list, resolves
every `A` **and** `AAAA` record and refuses private, loopback, link-local and reserved addresses,
connects to the address it approved while sending the name in `Host:` and validating the certificate
against that name, re-runs the check on every redirect hop, and stops reading at a byte ceiling
mid-stream.

Kept rather than deleted, because it is public API and there is a known caller outside the
framework. It carries an `@deprecated` tag pointing at `fetch()`, which takes the ceiling, the
timeout and the redirect budget as arguments and hands back a reason and a status — all of which a
wrapper has to decide for you.

Three behaviour changes, each of which can break a caller, and all documented in
[Pramnos_Security_Guide.md](../../Pramnos_Security_Guide.md):

- **A host on a private address is refused.** A caller fetching `sURL . $path` against its own site
  stops working — locally that name resolves to a private address. Read the file instead.
- **`$fakeRef` is ignored.** It sent a Google referer and a Firefox user agent, which is
  hotlink-protection evasion. The parameter stays so the signature does not change.
- **`allow_url_fopen` is required.** `fetch()` dials with a stream so it can connect to an approved
  address rather than a name; curl is what used to work without that setting. It fails closed —
  falling back to an unchecked curl fetch would undo the change.

### Found while fixing it: `checkUrlStatus()`, left alone on purpose

The same file has a second public fetch helper. It never disabled certificate verification and
follows no redirects, so it is not the same defect — but it does no address check, so it will report
whether something is listening on a private address, which is a host and port probe for anything
that can influence its argument. It also buffers the whole response into memory to discard it.

Left as it is, and documented instead, because «is this URL up» is a question people legitimately
ask about internal addresses — a health check for a service on the same subnet is the ordinary use,
and moving the guard inside would break the honest callers. The guide shows the `isPublic()` check
to put in front of it when the URL came from outside.

## A clamped rendition was never found again, and rebuilt on every request

Reported from a consuming application (FW-055), found because the media changes broke ten of their
tests and the new code had to be read line by line.

`resize()` clamping a request to the source's own size was the right change — a rendition larger
than the original it came from is the opposite of what a thumbnail is for. What it exposed is that
`MediaObject::get()` **looked renditions up by the size that was asked for and stored them under the
size that came out**. With `allowUpscale` off, which is the default, those differ for every source
smaller than the requested box.

So `get(177, 222)` on a 150×150 source wrote a 120×150 entry, and the next identical `get(177, 222)`
matched nothing. It rebuilt the image, appended another entry and saved the row — and because
`ResizeTools` prefixes `rand(1,9999)_` when the filename it wants already exists, that was a **new
file on disk and a new entry in the column on every call**, neither of them bounded. Measured by the
reporter: three identical calls, three files, three rows. Against their real data, 467 of 1023
images are under that box in at least one dimension — 46% of images rebuilt on every page view.

### Fixed

`Thumbnail` records `requestedX` and `requestedY` — the box that produced the rendition — beside `x`
and `y`, which stay what the rendition actually is. The lookup compares against the requested box
when an entry has one.

The alternative was to clamp the request the same way before comparing. Storing the request was
chosen because it keeps *what was asked for*, which is the information the clamp discarded, and it
survives a later change to the clamping rule; a lookup that re-derives the clamp has to stay in
lock-step with the resizer for ever.

**No migration, and nothing stored has to change.** The `thumbnails` column is JSON of the declared
fields, and the hydrator starts from a fresh `Thumbnail` and copies only the keys a row has — so
every existing row reads back with `0`, which the matcher treats as "not recorded" and compares on
`x`/`y` exactly as before.

The fallback also covers a case the JSON path does not: rows written before the column held JSON are
`serialize()` output, and the reader deliberately returns those **unconverted**, because an
application with its own thumbnail class has been getting its own objects back from them for years.
Those objects do not declare these fields at all, so the matcher reads them through `isset` — the
same reason `encodeThumbnails()` already did.

### The test that stopped one line short

`MediaRenditionPolicyTest::testARequestLargerThanTheSourceIsNotUpscaled` asked 512×512 of a 40×40
source and asserted the clamp. It never asked twice, which is why a green suite shipped this. There
are now three tests that do, including a third call — because a count growing by one per call cannot
be told from an off-by-one with only two.

### Documentation

[Pramnos_Media_Guide.md](../../Pramnos_Media_Guide.md) gains **What was asked for, and what came
out**: the two pairs of dimensions, which one to read for layout and which one the cache is keyed
on, and when `allowUpscale = true` is the right answer instead.

## Two migrations that could fail on real data now decline instead

Reported from a consuming application, and not because either one bit them: their `usertokens` is
small and their settings table has no duplicates. The deploy that prompted it is against a database
where neither has been verified — and the check that would have told them is one the framework
already knew how to write.

`canAddForeignKey()` had the pattern and nothing else used it: count the rows that would violate the
change, refuse, and name what has to be repaired. It cannot fail on dirty data; it declines and says
why.

### Added — the vocabulary, on `Migration`

`orphanCount()` moves to the base class, `duplicateGroups()` and `duplicateCount()` join it, and
`decline($reason)` records a refusal as its own state: `MigrationRunner::RESULT_DECLINED`.

`migrate` prints `Declined:` with the reason and a closing line saying these stay pending;
`migrate:status` shows `Declined` and prints the reason under the table. And because `getRanSlugs()`
counts only `RESULT_OK`, **a declined migration is attempted again next time** — repair the rows and
it applies itself.

`Declined` is deliberately not the `Skipped (cutoff)` a row can already carry. Those never ran; this
one ran, checked, and said no.

The constraint this was written against: a guard must not turn a real problem into silence. So a
count that cannot be taken — a missing table, a permission — is **zero, not a refusal**, because
declining there would make an unrelated fault look like dirty data; and a decline is recorded in
three places rather than logged and forgotten.

### Fixed — `add_unique_constraint_to_settings_table`

It drops the plain index *before* creating the unique one, so a duplicate value aborted
`CREATE UNIQUE INDEX` and left the installation with **neither** index on a column every settings
read uses. It now counts duplicates first and declines, naming the values and their row counts.

Declining rather than resolving: keeping the highest id per name is a decision about somebody's
configuration, and two rows for `sitename` may mean the wrong one has been in effect for months.

### Fixed — `add_token_lookup_to_usertokens`

Three problems, in ascending order of cost. It read the **whole table into PHP** before writing
anything — 48 MB at 50 000 rows, so around a gigabyte at a million, which is what turns "slow" into
"the deploy died". It had no `WHERE token_lookup IS NULL`, so a second deploy paid the whole cost
again. And it computed the digest in PHP row by row, which the reporter measured at 5 617 ms where
one `UPDATE … encode(sha256(token::bytea), 'hex')` takes 130.

Now: without an `APP_KEY` the whole backfill is **one statement** — which is also every installation
that has not run `key:generate`. With a key, encryption genuinely needs PHP (`encrypt()` uses a
fresh nonce per value), so it runs in batches of 2 000 behind a keyset cursor on `tokenid`, which
keeps the buffer flat and cannot skip rows the way an offset walk over a changing table does.

**And it fills only rows that can still authenticate** — `status = 1` and not expired. A revoked or
expired token is never looked up by value again, and on a long-lived installation those rows are
most of the table, because `usertokens` is an audit trail as much as a credential store. Safe
because nothing revives a token: no path sets a row's status back to active, every path that matches
on `token_lookup` and then acts also checks `status`/`expires`, and the paths that do not filter
treat a missing row as invalid — the same answer a dead row gives.

**Stated rather than left to be discovered:** rows outside that scope keep their token value as it
is, plaintext, on an installation where the rest of the column is encrypted. They cannot
authenticate and every lookup filters in SQL, so the exposure is smaller than it sounds — but it is
a real difference from "the column is encrypted", and an installation that wants the stronger claim
wants a sweep it can run when it chooses, not a migration holding a deploy open to encrypt
credentials that stopped working years ago.

A test asserts that the digest the database writes equals `Token::lookup()` exactly. If those ever
disagreed by so much as a case, every authentication lookup would miss and nothing else in the suite
would notice.
