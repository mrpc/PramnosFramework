## `SchemaBuilder::hasTable()`/`hasColumn()` — a 5-minute ceiling on "yes, forever"

### Fixed

- A table or column **found** used to be remembered for the life of the process, with three
  invalidation paths: every DDL method of the builder, a migration run, and a query that then
  fails on the missing relation. None of the three reaches a *different* process — a migration's
  own `forgetWhatExists()` clears that console run's memory, never a long-lived PHP-FPM worker's
  — and the query-failure path depends on recognising the driver's own wording for "no such
  relation", which is not guaranteed once `lc_messages` is not English. A worker that cached
  "yes" while a table existed, for a table a migration then dropped or merged away behind it,
  could believe it forever: one production installation found exactly this, as 3,500+ failed
  queries over four days against a table a hypertable migration had already removed, stopped
  only by restarting PHP-FPM.
- Every positive answer now also expires after 5 minutes, regardless of which of the three paths
  above did or didn't fire — the one invalidation that reaches another process without needing
  to be told. See the [Schema Builder Guide](../../Pramnos_Schema_Builder_Guide.md#introspection).

## `CalendarTest::testTodayIsInThePrompt` — a day-boundary race, not an application bug

### Fixed

- The test built its calendar fixture on a hardcoded Europe/Athens clock, but the real `ask()`
  calls it exercises resolve `BaseAssistant::timezone()` from the server's own default zone (UTC
  in CI). The two agree all day except the roughly two hours between UTC midnight and Athens
  midnight, where "today" has already turned over in one zone but not the other — which is
  exactly the window a CI run landed in. The test now pins the default zone to Europe/Athens for
  its own duration, matching the fixture, as `AnalystTasksTest` already does for its own
  timezone-sensitive assertions.
