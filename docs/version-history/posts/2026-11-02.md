## `SchemaBuilder::hasTable()`/`hasColumn()` — a 5-minute ceiling on "yes, forever"

### Fixed

- A table or column **found** used to be remembered for the life of the process, with three
  invalidation paths: every DDL method of the builder, a migration run, and a query that then
  fails on the missing relation. None of the three reaches a *different* process — a migration's
  own `forgetWhatExists()` clears that console run's memory, never a long-lived PHP-FPM worker's
  — and the query-failure path depends on recognising the driver's own wording for "no such
  relation", which is not guaranteed once `lc_messages` is not English. A worker that cached
  "yes" while a table existed, for a table a migration then dropped or merged away behind it,
  could believe it forever: one production installation found exactly this, as 3,500+ failed
  queries over four days against a table a hypertable migration had already removed, stopped
  only by restarting PHP-FPM.
- Every positive answer now also expires after 5 minutes, regardless of which of the three paths
  above did or didn't fire — the one invalidation that reaches another process without needing
  to be told. See the [Schema Builder Guide](../../Pramnos_Schema_Builder_Guide.md#introspection).

## `CalendarTest::testTodayIsInThePrompt` — a day-boundary race, not an application bug

### Fixed

- The test built its calendar fixture on a hardcoded Europe/Athens clock, but the real `ask()`
  calls it exercises resolve `BaseAssistant::timezone()` from the server's own default zone (UTC
  in CI). The two agree all day except the roughly two hours between UTC midnight and Athens
  midnight, where "today" has already turned over in one zone but not the other — which is
  exactly the window a CI run landed in. The test now pins the default zone to Europe/Athens for
  its own duration, matching the fixture, as `AnalystTasksTest` already does for its own
  timezone-sensitive assertions.

## `Controller::releaseSessionOnRead()` — an opt-in early release of the session lock

### Added

- PHP's default file session handler locks the session for the whole request. In an admin UI
  where one session routinely has 20-30 tabs and background requests open at once, that
  serializes all of them behind whichever one is slowest — measured in production at up to 150s
  behind a video stream. FW-309.
- A controller that has declared its write actions with `addWriteAction()` can now also call
  `releaseSessionOnRead()`: `Controller::exec()` then calls `session_write_close()` right after
  the write-action/CSRF check, for any action not on that list, instead of holding the lock for
  the whole run. A declared write action is unaffected and keeps the lock, since it may still
  need to write `$_SESSION` itself; a controller that doesn't opt in is unaffected too. See the
  [Security Guide](../../Pramnos_Security_Guide.md#releasing-the-session-lock-early-releasesessiononread).
- A write to `$_SESSION` after the lock is released is never persisted and PHP raises nothing for
  it, so as a backstop the framework now logs a warning (`session-lock` log) whenever that
  happens, instead of letting it vanish unnoticed.
- Not every session-writing action can be a declared write action: an OAuth callback a provider
  redirects back to with a `GET` carries no CSRF token at all, and a console re-authentication is
  the same shape. `addSessionAction()` declares such an action so it keeps the lock without being
  asked for a token it cannot carry.

### Fixed

- `Session::getCsrfToken()` writes `$_SESSION['csrf_token']` lazily, on whichever request first
  asks for one — a template calling `CsrfMiddleware::tokenField()` from a plain read action.
  Found in production the same day, by this feature's own safety net: a controller's read
  actions never called it themselves, so releasing the lock before they ran meant that first
  write never persisted — the token still rendered into the form from memory, but every write
  action submitted afterward then failed CSRF verification against nothing to compare.
  `_releaseSessionLock()` now seeds the token itself before closing, so this can't recur on any
  controller that opts in.

## `Model::_save()`'s column introspection — a 60-second ceiling, not "never cached"

### Fixed

- The write path queried `information_schema` on every `_save()`, uncached, on the stated
  grounds that a stale schema there is silent data loss — the loop never sees a newly added
  column, so a row is written without it. FW-310 measured the cost: ~165k calls over four days
  in one production install, 9.7ms mean, 0 cache hits by construction. Almost all of that was
  paid for schema that had not changed at all — `MigrationRunner::forgetAllColumns()` already
  flushes this exact cache (the same key, same Redis-backed store, the read paths use) the
  moment a migration runs, so that case was never actually the risk.
- The write path now caches too, for 60 seconds (`Model::WRITE_PATH_COLUMN_CACHE_TTL`) — the
  same ceiling-over-silent-trust shape as today's `SchemaBuilder::hasTable()`/`hasColumn()` fix
  above. A migration still invalidates it instantly; the 60s only bounds the one case no cache
  invalidation in this framework can ever observe — schema altered by raw DDL outside
  `migrate`/`SchemaBuilder`. See [Upgrade Guide](../../Pramnos_Upgrade_Guide.md#since-v12-unreleased).

## `create:crud` against PostgreSQL — real primary key and real FK class name, not a guess at either

### Fixed

- `createControllerAndViewsFromWizard()` asked the pure naming-convention helper for a table's
  primary key instead of `primaryKeyFor()`, which actually asks the table. Against a PostgreSQL
  table whose key is `id` (any migration using `$table->increments('id')`), the generated
  controller's DataTable `data()` field list and the edit view's `$isNew` check both addressed a
  guessed column (`<table_singular>id`) that does not exist — a list that fails on first load, and
  an edit that always inserts a duplicate row instead of updating. The model generator already
  asked `primaryKeyFor()` for the same table; only the controller/view path disagreed with it.
- The FK map feeding `fkOptions()`, and the matching variable name in the generated edit view's
  small-table `<select>` fallback, named a referenced table's model class with
  `getProperClassName()`, which only capitalises the first letter of a compound name —
  `server_groups` → `Server_group`, not `ServerGroup`. Fatal with "class not found" the first time
  that FK's picker loads. A new `getProperCompoundClassName()` PascalCases a compound name word by
  word and is now used at every place a foreign key's class name is resolved only from the
  referenced table's name (no explicit class name is available for it); `getProperClassName()`
  itself is unchanged, since several other generators (REST path segments, SPA resource slugs,
  table-name conventions) rely on its existing, deliberately-flattened output.

## `brand/logos/` ships in the dist package again — `init` can scaffold a default logo

### Fixed

- `.gitattributes` marked `/brand/logos export-ignore` on the stated grounds that it was
  docs-only art. It is not: `Init::scaffoldLogo()` copies `pramnos-logo-wide{,-inverse}.png` from
  it into every scaffolded project's `www/assets/img/`. Excluding it from the Packagist dist
  archive left that method's own "no-op when the brand directory is absent" branch firing
  silently on every project scaffolded from the published package — `logo.png`/`logo-inverse.png`
  were simply never written, the theme header's `<img>` 404'd forever, and nothing in `init`'s
  output said so. `brand/favicons/`, read the same way by `Init::scaffoldFavicons()`, was never
  excluded and kept working throughout.

## `Language::load()` skips an exact repeat instead of re-merging the file

### Fixed

- `load()` had no guard for "this language is already loaded on this instance" — `include` plus
  the merge in `addlang()` ran again even when the second call asked for the exact same language
  from the exact same path. FW-311: one application calls this twice per admin request for an
  unrelated legacy quirk of its own, and the second call's include+merge was measured as the
  single most expensive line in that application's admin bootstrap, at ~10.6ms on a warm worker.
- An exact repeat (same language, same path, already loaded) now returns immediately. Loading a
  *different* language is unaffected and still merges onto whatever is already loaded, exactly as
  before — including the footgun {@see \Pramnos\Translator\Language::using()}'s own docblock
  already warns about, which this does not touch.
