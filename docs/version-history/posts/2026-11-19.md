## The export modal's two radio pairs now carry a group label each (FW-534)

### Fixed

The "All filtered rows"/"Current page only" scope radios and the "All columns"/"Selected
columns" radios (FW-533) rendered as one unbroken block with nothing marking where the first
pair ends and the second begins — reported after an owner read all four as one
mutually-exclusive group instead of two independent decisions (which rows, which columns). A
small bold label — "Rows" above the scope radios, "Columns" above the columns radios — now
sits above each pair.

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s "Selected columns" vs "All columns" paragraph now
mentions the group labels.

## The export modal keeps a fixed title and size across every state (FW-535)

### Fixed

What looked like the modal's title ("Export") was actually the format `<select>`'s own
`<label>`, living inside `.pf40-export-controls` — so it disappeared along with the rest of
the controls the moment "Start export" switched the modal to `.pf40-export-progress`. The
modal was then left with no heading at all, just the progress text and the close button,
which an owner read as a different, smaller dialog rather than the same one changing state.
The title is now its own element, outside both `.pf40-export-controls` and
`.pf40-export-progress`, rendered once and visible through controls, progress, and a failure
alike. The format `<select>` gets its own "Format" label in its place. The modal's inner box
also carries a `min-width`/`min-height`, so it stops visibly shrinking when the controls give
way to a shorter progress message.

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s export modal section now describes the fixed
title and the inner box's minimum size.

## `NotificationBell` can link to the notification preferences page (FW-536)

### Added

`NotificationBell::render()` takes two new options, `settingsUrl` and `settingsLabel`
("Notification settings"). Given `settingsUrl`, a gear icon next to "mark all read" links
there — any application that already declares `notifications.types`/`Preferences` (FW-488)
has a settings page, but nothing in the bell pointed at it before now. Neither option is
required; without `settingsUrl` the panel renders exactly as before.

### Documentation

`docs/Pramnos_Notifications_Guide.md`'s `NotificationBell::render()` example and option list
now cover `settingsUrl`/`settingsLabel`.

## `Xlsx::write()` writes `[Content_Types].xml` as the ZIP's first entry (FW-537)

### Fixed

`Xlsx::write()` added `xl/worksheets/sheet*.xml` before `[Content_Types].xml`, so the ZIP's
first entry was a worksheet, not the content-types part. Every XML part was individually
well-formed, but the OPC spec requires `[Content_Types].xml` to be the package's first
entry, and Excel enforces it strictly — opening a file written this way produced "We found
a problem with some content" and offered to recover it. `[Content_Types].xml` is now
written before any worksheet.

## The export modal's "All columns" now really means all columns (FW-538)

### Fixed

"All columns" built `$exportColumns` by filtering on each column's initial `bVisible` — on a
grid where most columns start hidden by default (only revealed one at a time through the
show/hide picker), this meant "All columns" exported only the handful visible when the page
rendered, not the full set its own label promised. "All columns" now ignores `bVisible`
entirely and includes every exportable column (`pf-no-export` aside); "Selected columns"
(FW-533) is unchanged and still covers "only what I can see right now".

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s "Selected columns" vs "All columns" paragraph
now describes "All columns" correctly.

## `Xlsx::write()` declares the "Normal" default cell style (FW-539)

### Fixed

`xl/styles.xml` had no `<cellStyles>` element at all — optional in the OOXML schema, but
Excel expects it in practice, and its absence is a documented, common cause of the same
"we found a problem with some content" repair prompt a bad ZIP entry order (FW-537) also
produces, on a file whose entry order was by then already correct. `styles.xml` now
declares `<cellStyles count="1"><cellStyle name="Normal" xfId="0" builtinId="0"/></cellStyles>`
after `<cellXfs>`.

## A worksheet now declares its `dimension` and a `sheetViews` entry (FW-540)

### Fixed

A real export (2867 rows × 62 columns) still produced Excel's repair prompt after FW-537 and
FW-539, with every other structural check clean (ZIP entry order, `cellStyles`, well-formed
XML throughout, balanced rows/cells, valid cell references, no XML-illegal characters).
`<dimension>` and `<sheetViews>` are both optional in the OOXML schema and no parser outside
Excel itself seemed to require them, but they were the one remaining structural difference
against a file Excel writes itself. A worksheet now opens with
`<dimension ref="A1:<lastCol><lastRow>"/><sheetViews><sheetView workbookViewId="0"/></sheetViews>`
before `<sheetData>`.

## `Xlsx::write()` writes text through a shared strings table, not inline (FW-541)

### Fixed

A real 2867-row × 62-column export kept producing Excel's repair prompt after FW-537,
FW-539 and FW-540 each fixed a different structural issue, with a byte-for-byte diff of
Excel's own "repaired" copy confirming no data was ever lost or changed — only the
container. A small file with the same inline-string shape (`t="inlineStr"`) never
reproduced it. `Xlsx::write()` now writes every text cell through a workbook-level shared
strings table (`xl/sharedStrings.xml`, `t="s"` plus an index) instead — schema-valid either
way, but what Excel's own writer does, and the one remaining difference between this
writer's shape and Excel's own at the scale where the prompt actually appeared.

### Documentation

No user-facing option changed — `Xlsx::write()`/`fromCsv()` keep the same signature and
return the same kind of `.xlsx` bytes. The class docblock in
`src/Pramnos/Export/Xlsx.php` now describes the shared strings table instead of inline
strings.

## `exportdownload()` no longer lets the page template wrap a downloaded file (FW-542)

### Fixed

The real root cause behind FW-537/539/540/541: every download through
`exportdownload()` arrived with the admin page's own header/footer/script tags appended
after the downloaded file's own bytes — byte-identical to the real file up to that point,
confirmed by diffing a server-side copy against what the browser actually downloaded, but
unopenable as a result. `exportdownload()` never switched the document type away from the
default (`'html'`), so `render()` wrapped whatever `readfile()` had already streamed with
the theme's page template. `queueexport()`/`exportstatus()` already set it to `'json'`;
`exportdownload()` now sets it to `'raw'` before streaming, the same convention for binary
output. FW-537/539/540/541 were each a real, independently correct fix — none of them
were the actual cause of this symptom, since every static check (and a synthetic
reproduction at the same scale) only ever examined the clean server-side file, never a
real download that had gone through the HTTP response that was actually broken.

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s `DatatableExportActions` section now explains
why `exportdownload()` switches the document type before streaming.

## Starting the same export twice no longer queues it twice (FW-543)

### Added

`QueueManager::findActiveDuplicate(string $taskType, mixed $data): ?int` — the taskid of
an existing, still-active (pending/processing, never completed/failed/stopped) task with
the same type+payload hash `addTask(unique: true)` would reject, or null if there is none.
`addTask()` itself only ever answers null on a duplicate — enough to refuse queueing a
second one, not enough to tell the caller which run is already in flight.

### Fixed

`DatatableExportActions::queueexport()` queued every request independently, so clicking
"Start export" twice on the same screen (the same class, filters, columns, format and
scope) before the first run finished queued a second, identical `DatatableExportTask`.
It now calls `addTask(unique: true)`; on a duplicate, `findActiveDuplicate()` hands back
the run already in flight instead. The JSON response is now always `{taskid, duplicate}` —
on a duplicate, `taskid` is the existing run and `duplicate` is `true`, and the modal (which
already just polls whatever `taskid` it receives) wires straight into that run rather than
the requester seeing an error for clicking the same button twice.

### Documentation

`docs/Pramnos_Queue_Guide.md`'s `addTask()` example now shows `findActiveDuplicate()`.
`docs/Pramnos_Html_Components_Guide.md`'s "Background CSV export" section now describes
`queueexport()`'s `{taskid, duplicate}` response shape.

## `Figures::untraced()` also catches a fabricated name beside a traced number (FW-544)

### Added

`Figures::untraced()` is documented as checking only numbers — a deliberate boundary, not
an oversight, since a generic hallucinated-category detector would be far noisier than the
numeric check (no closed set of "valid" names the way sums/differences/percentages give one
for numbers, and Greek grammatical case endings make exact string matching unreliable). This
adds one narrow case the production incident that reported it reproduces exactly: a failed
database join leaves a tool with a real, correct id or count but no name for it, and the
model invents one in the final prose instead of saying it is not known.

A capitalized word sitting in the same sentence as a number that traces is now checked
against every string value anywhere in the results (`Figures::stemMatches()`, tolerant of a
different grammatical ending of the same word, not of a different word). Checked only where
the results carried a string worth comparing against at all — a tool answering with pure
numbers, the ordinary case, is entirely unaffected — and never for the sentence's own opening
word or a name the question itself already used. Flows through the existing `Client.php`
correction/footnote wiring unchanged: a name this catches is said back to the model the same
way an untraced number already was.

### Documentation

`docs/Pramnos_LLM_Tools_Guide.md`'s "Numbers that come from the figures" section now
describes the name check and its scope.

## A large export no longer locks out its own progress polling (FW-545)

### Fixed

Confirmed in production: a large export's own `exportstatus()` poll (`recordPoll()`'s
`UPDATE queueitems SET last_polled_at = …`, on the web request's own connection) blocked
for nearly 5 minutes — until the whole export's transaction finally committed — then timed
out, and the modal reported a still-running, perfectly healthy export as failed. The cause:
`reportProgress()` wrote `progress_current` through the SAME connection
`runInRepeatableReadSnapshot()` holds a `REPEATABLE READ` transaction open on for the whole
batch loop, taking and holding that row's write lock for the transaction's entire duration
— the bigger the export, the longer every poll in flight hangs on it. `reportProgress()`
now writes through a second connection instead, cloned from the one already in use (so it
always matches whatever dialect, host and credentials the task is actually running
against) and committing each report at once, the same way it always could before this task
held a transaction open around it.

A new integration test reproduces the exact failure — a concurrent `UPDATE`, mid-export,
with a short lock-wait timeout instead of the real poll's much longer one, so a regression
here fails in milliseconds instead of hanging the suite — and fails with the real
production error ("Lock wait timeout exceeded…" / "canceling statement due to lock
timeout") without this fix, on both MySQL and PostgreSQL.

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s export modal section and
`docs/Pramnos_Queue_Guide.md`'s `updateProgress()` paragraph both now explain why a long
transaction's own progress reports need a connection of their own.

## `Figures::untraced()` splits a markdown table's rows correctly (FW-546)

### Fixed

The sentence splitter FW-544 added, `(?<=[.!?\n])\s+`, needs a whitespace character AFTER
the boundary character it matches — a bare `\n` straight into the next line's first
letter, with no second space and no blank line, has none, so it never actually split
there. A markdown table (one `\n` per row) was then read as one giant "sentence", and the
header row's own words ("Περιοχή", "Κατάσταση") rode along into whatever data row's traced
number gated the check, flagged as fabricated names — reported from a live production
answer. The splitter now treats one or more newlines as their own boundary, separately
from `[.!?]` followed by whitespace, so each table row (and each ordinary line) splits on
its own regardless of what follows it.

### Documentation

`docs/Pramnos_LLM_Tools_Guide.md`'s name-check paragraph now mentions markdown tables.

## The export modal shows a visual progress bar while it runs (FW-547)

### Added

The export modal's progress area now carries a native `<progress>` with no `value` —
the browser's own animated, indeterminate bar, instead of only the "N rows so far" text

markup, so an application gets this on `composer update` alone.

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s "Live progress" section now describes the bar

## The export modal's progress bar shows a real percentage where one is known (FW-548)

### Added

FW-547's bar started indeterminate always, reasoning that a real percentage would need an
upfront `COUNT(*)` not worth its own cost. It does not: for `scope: 'all'`, the grid already
ran the server-side request behind its own "Showing 1 to 25 of 502,145 entries" footer
before "Start export" is ever clicked, so DataTables' own `page.info().recordsDisplay` — the
same filtered count "All filtered rows" exports — is read straight off the live table
instance at click time. No `COUNT(*)`, no change to `Exportable`, no backend involved at
all. The bar turns determinate (`value`/`max` set) and the status text gains a `(N%)` once
a progress figure arrives; `scope: 'page'` keeps the indeterminate bar, since a page export
finishes before a percentage would ever have time to show.

Not the SAME snapshot the export's own `REPEATABLE READ` transaction reads, so on a table
that keeps changing while the export runs the percentage can land slightly over 100% or
short of it — acceptable for a progress indicator.

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s "Live progress" section now describes where the
known total comes from and the one place it can be slightly off.

## A downloaded export's own filename is descriptive, not a bare task id (FW-549)

### Added

`exportdownload()`'s `Content-Disposition` filename was `"export-1234.csv"` — telling a
person nothing about which of several downloads sitting in their Downloads folder it even
was. It is now `"<ShortClassName>-<day queued>-<taskid>.<ext>"`, e.g.
`"Users-2026-11-19-1234.csv"`: the model's short class name, the day the export was queued
(`$item->createdat`, not today's date — so the SAME completed export keeps the SAME name
on a re-download), and the taskid at the end so two same-day exports of the same model
never collide into one browser-renamed file. `myExports()`'s own label already built the
short class name the same way; that logic is now one shared method (`exportShortName()`)
instead of two copies of it.

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s `DatatableExportActions` section now describes
the filename and where each part of it comes from.

## `Xlsx::write()` falls back to inline strings past Excel's own shared-strings ceiling (FW-550)

### Fixed

A 502,159-row x 62-column export (131MB, 2.36 million unique strings in
`xl/sharedStrings.xml`) still produced Excel's "we found a problem with some content"
prompt after FW-537/539/540/541 each fixed a different, smaller-scale structural issue —
confirmed, mechanically, with a full streaming parse of both large parts: well-formed XML
throughout, correct ZIP entry order, correct row/dimension counts, and the declared
`uniqueCount` exactly matching the real `<si>` count. 100% schema-valid, and Excel still
reported it as damaged. A Microsoft Q&A thread reports an unofficial ceiling somewhere
past 1,000,000 shared strings, past which a cell's own index stops resolving; this file's
2.36 million is well over twice that. `Xlsx::write()` now counts every unique string
across the whole workbook first, and past 900,000 (`MAX_SHARED_STRINGS`, comfortably under
the reported ceiling, overridable through a new optional `$maxSharedStrings` argument on
both `write()` and `fromCsv()`) rebuilds every sheet with inline strings instead of a
shared strings table — a second pass over the same rows, paid only in this rare case; every
smaller export still pays nothing extra, exactly as before.

### Documentation

`docs/Pramnos_Metrics_Guide.md`'s "A spreadsheet of anything" section now describes the
fallback and the override.

## "My downloads" names a failed or stopped export instead of showing a bare date (FW-551)

### Fixed

`exportLabel()` only ever added anything past the queued date for `status === 'completed'`
— every other status (`pending`, `processing`, `warning`, `failed`, `stopped`, `deleted`)
showed a bare "Model (FORMAT) · <date>", identical whether the export was still running or
had already failed. An admin had to open it to find out which. Each non-completed status
now gets the same word `QueueController::statusLabels()` already shows on the admin queue
screen ("· Failed", "· Stopped", "· Processing", …) — the same translation keys, so nothing
new needs translating.

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s `myExports()` paragraph now mentions the
non-completed status wording.

## One poll failing no longer shows the export as failed (FW-552)

### Fixed

The export modal's polling `jQuery.getJSON()` call treated ANY failure — a network
timeout, a 5xx, anything at the HTTP level — the same as the backend reporting
`status: 'failed'`: "Export failed", and no further polls. The task underneath keeps
running regardless of one lost poll, and the longer a busy queue makes it wait (a
worker-pool backlog, a large export's own many-minute batch loop), the more likely some
one poll hits a transient hiccup along the way. Confirmed in production: a small,
otherwise-successful export (`10469 rows exported`, completed moments later) was shown as
failed over exactly one such poll, queued behind an unrelated backlog. Only 3 consecutive
poll failures now show the export as failed; a successful poll resets the count.

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s "Live progress" section now describes the
retry tolerance.

## The "ready" email's download link no longer doubles the host when `exportBase` is absolute (FW-553)

### Fixed

`notifyByEmail()`'s link builder always prepended `sURL` to `exportBase`, unconditionally —
correct only when `exportBase` is relative (the default). The modal's own "ready" link and
`myExports()`'s download list both use `exportBase` directly as an `<a href>`, which a
browser resolves correctly whether it is relative or absolute; neither of them ever
prepends `sURL`. An application that makes `exportBase` absolute (so those two links keep
resolving correctly from anywhere, not just the page the export was started on) had its
"ready" email link doubled instead — reported from production, a correct, absolute
`exportBase` producing a download link pointing at the wrong address. `sURL` is now
prepended only when `exportBase` does not already start with `http://` or `https://`.

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s `exportBase` row now explains the difference
between the two uses.

## "My downloads" leaves out failed and stopped exports (FW-554)

### Changed

## Requesting and downloading an export are now audited (FW-555)

### Added

A bulk export of other people's data — a 502,159-row export of every column, say — left
the system with no trace of who asked for it or who actually downloaded it. CLAUDE.md
rule 14 means exactly this for the audit log, not a table of its own: `queueexport()` now
calls `AuditLog::record('export.requested', ...)` with the model class, scope, format,
column count and whether the request was a duplicate hand-off; `exportdownload()` calls
`AuditLog::record('export.downloaded', ...)` with the class, format, taskid and the
finished row count — a separate event, since a request and a download do not always both
happen. Neither names a `$target` account unless the downloader differs from the row's own
`requested_by` (a `super`+ user downloading someone else's export).

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s "Background CSV export" section now describes
both events.

## A column's custom-id footer filter now binds to the one on screen (FW-556)

### Fixed

A column filtered through an id string (the 9th `addColumn()` argument — a `<select>` or
other control the application rendered into the footer itself) wired its `change`/debounced
`keyup` to a bare `jQuery('#id')`. `scrollX` (always on) makes DataTables clone the footer
into a second, hidden "sizing" row carrying the SAME id attributes, which lands first in
the DOM — `jQuery('#id')` (`getElementById`'s fast path) binds to that invisible clone
instead of the one on screen, so nothing the admin picks ever reaches `fnFilter()`.
Reproduced live: a status dropdown filter that silently never applied, while a manual
request with the same value filtered correctly, proving the backend was never the problem.
The class already knew this exact failure mode for its own two other cases
(`fnInitComplete`'s state-restore, the auto-generated boxes' delegated binding) — only this
one, less-used branch was missing the same scoping. Both the state-restore and the
`change`/`keyup` bindings are now scoped to the table's own footer
(`jQuery(table.api().table().footer()).find('#id')`), the same pattern.

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s filter table now explains why the control has
to sit inside the rendered footer and why the binding is scoped.

## `Xlsx::write()` also leaves out the C1 control characters Excel itself refuses (FW-557)

### Fixed

A real 502,159-row export — every earlier structural issue already fixed (FW-537/539/540/
541/550), well-formed XML confirmed by a full streaming parse, row/dimension counts
consistent, zip integrity clean — still produced Excel's repair prompt. The repair log
named the actual cause this time: "Repaired Records: String properties from
…/sheet1.xml". `\x7F`-`\x9F` (DEL and the C1 control characters) are legal XML 1.0
characters, so `Xlsx::e()`'s existing filter (XML's own illegal character range) never
touched them — but Excel's own, stricter validation of a cell's text does not accept them,
and real free-text data occasionally carries one (a legacy encoding, a stray paste).
They are now stripped the same way the XML-illegal ones already were.

### Documentation

`docs/Pramnos_Metrics_Guide.md`'s "A spreadsheet of anything" section now mentions it.

## The "ready" email no longer sends when the notify checkbox was never checked (FW-558)

### Fixed

`queueexport()` read `notify_email` with a plain `(bool)` cast — but the modal posts a JS
boolean (`.pf40-export-notify` checkbox's `.is(':checked')`) through a form-encoded body,
which jQuery serializes to the literal string `"true"` or `"false"`, never a real boolean
and never absent. `(bool) "false"` is `true` in PHP, since it is a non-empty string — so
the "ready" email went out on every export, regardless of whether the notify checkbox was
ever checked, reported from production. Read with `filter_var(…, FILTER_VALIDATE_BOOLEAN)`
instead, which reads the string's actual meaning.

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s `notify_email` row now explains why the cast
matters.

## A table with thousands of pages no longer wraps its pagination onto two lines (FW-559)

### Fixed

`.pf-datatable .dataTables_paginate` floats and is itself a wrapping flex container — a
combination whose shrink-to-fit width can come out narrower than its unwrapped content
actually needs, so `flex-wrap` breaks the page buttons onto a second line they did not need
to. Reproduced live on a table with thousands of pages (287,686 rows, 5,754 pages), where the
extra "…" plus the last page's own button were enough content to trigger it; a smaller table
on the same page never did. `width: max-content` (bounded by `max-width: 100%`, so it still
wraps once genuinely out of room) sizes the float to its content's real width instead of
guessing — fixed in all three bundled themes (tailwind, bootstrap, plain-css), which keep
this rule identical.

### Documentation

`docs/Pramnos_Html_Components_Guide.md`'s `.pf-datatable` paragraph now mentions it.

## `Xlsx::write()` now writes a theme and document properties, same as Excel's own writer (FW-560)

### Added

A real 502,159-row export still produced Excel's repair prompt after every earlier fix
(FW-537/539/540/541/550/557), with content and structure both exhaustively verified
clean — a full streaming parse of the entire file found zero control characters, zero
Unicode noncharacters, well-formed XML throughout, correct ZIP entry order. Decisive test:
when Excel itself repairs the file and then resaves it, the resaved copy reopens cleanly —
ruling out a pure scale/memory ceiling, since Excel's own resave has the same data. Diffing
that resave against the original found two parts Excel always writes that this class never
did: `xl/theme/theme1.xml` (a default color/font/format scheme) and `docProps/core.xml`/
`docProps/app.xml` (document metadata). Both are optional per the OOXML schema — a
`styleSheet` with no theme-indexed color does not need a theme, and no outside parser ever
minded their absence — but `Xlsx::write()` now writes all three anyway, related from the
correct `.rels` (the theme from the workbook's own; the two docProps parts, being
package-level metadata, from the package root's `_rels/.rels` instead).

### Documentation

`docs/Pramnos_Metrics_Guide.md`'s "A spreadsheet of anything" section now describes them.

## A worksheet now declares `sheetFormatPr` and `pageMargins` too (FW-561)

### Added

The same 502,159-row export still failed after FW-560 added the theme and document
properties. Diffing it again against Excel's own resave found two more empty slots in a
worksheet's own required element order that this class always left out:
`<sheetFormatPr defaultRowHeight="15"/>`, between `<sheetViews>` and `<sheetData>`, and
`<pageMargins left="0.7" right="0.7" top="0.75" bottom="0.75" header="0.3" footer="0.3"/>`,
right after `<sheetData>`. Both optional per the OOXML schema, and no parser outside real
Excel seems to mind their absence — same pattern as `dimension`/`sheetViews` (FW-540) and
`cellStyles` (FW-539) before them — but `Xlsx::write()` now writes both anyway.
