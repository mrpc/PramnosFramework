## Person events are kept in the change log

### Changed

- Each occurrence of a person event is written to the change log's application events
  (`pramnos.changelog_events`, entity `user`) through the write spool, instead of a table of its
  own: one history of what people did, partitioned, compressed and kept two years on TimescaleDB.
  `person_events`, the per-person summary, stays (FW-234 B).
- `create_person_events_tables` creates `person_events` only; `audience.event_log_days` is gone.
- `audience:prune-events` prunes the rule run log and segment stays that ended more than
  `audience.segment_history_days` ago (365), and says so in one line when there is nothing to do.
- *Had it been on* for an event-triggered rule reads the summary.

### Added

- An index on `changelog_events (entity, event, created_at)` (`add_event_index_to_changelog_events`,
  `changelog` feature).

### What changes for an application

- Windowed conditions ("N times in the last M days") and A/B goals need the `changelog` feature;
  without it they are refused or shown as not counted. A `person_event_log` made by yesterday's
  migration is no longer written and can be dropped.

## Event transports, and events:status

### Added

- A queued listener's events go by a **transport**: `Pramnos\Event\Transport\EventTransport`,
  with the queue (`QueueTransport`) as every installation's and the default. `'events' =>
  ['transport' => …, 'listeners' => [Class => …]]` in app.php chooses one for the installation
  and per listener; one that is unknown or cannot carry events falls back to the queue, logged
  once (FW-235 P1). Nothing changes for an installation that sets nothing.
- `bin/pramnos events:status`: each queued listener's transport as set and as it would go — a
  dry run, with `--json`.
- `Event::events()`: the names something listens for.

### Documentation

- Queue guide: *Which transport carries a listener's events*; Console guide: `events:status`.

## The event stream, on the database

### Added

- The `stream` transport: an event is one entry in `event_log`, written in the caller's
  transaction, for every queued listener set to it; each listener is a consumer group reading from
  its own position (`event_consumers`). One row per event instead of one task per listener
  (FW-235 P2).
- `bin/pramnos events:consume`: the daemon that reads the groups — one consumer per group by lease;
  failures retried with a growing wait and kept as dead past the listener's attempts
  (`event_deliveries`); folded listeners handed to the queue, so they fold as before; idempotency
  keys as on the queue.
- `bin/pramnos events:prune` (scheduled daily): entries past `events.log_days` (30) that every
  group has read.
- Migration `create_event_log_tables` (`queue` feature). `event_log` and `event_deliveries` are
  declared personal data.
- `QueuedEvents::payload()` and `QueuedEvents::arguments()`: what travels for a firing, and the
  arguments built again — shared by the queue and the stream.

### Documentation

- Queue guide: *The stream: one entry per event*; Console guide: `events:consume`, `events:prune`.

## The event stream on Redis Streams

### Added

- `'events' => ['stream' => 'redis', 'redis' => [...], 'max_length' => 100000]`: the stream's
  groups read a Redis stream. `event_log` stays the outbox, written in the caller's transaction; a
  relay appends what is committed, at once outside a transaction and on every pass of
  `events:consume`, so nothing is lost between the commit and Redis. Consumer groups with
  `XREADGROUP`/`XACK`; what was read and never acknowledged is claimed again once it has waited;
  dead entries go to `event_deliveries` as on the database (FW-235 P3).
- A Redis whose `maxmemory-policy` is `allkeys-*` is refused for the queue, asked through
  `CONFIG GET` or, where that is disabled, `INFO memory`.
- On the Queue screen, a group's name is its class, the namespace beside it; with no consumer
  holding any group in the last minute, the card says no `events:consume` daemon is reading.

### Documentation

- Queue guide: *On Redis Streams*, and how an application adds a transport of its own — Kafka
  among them — with `Transports::register()` (FW-235 P5: the extension point, documented; a Kafka
  transport comes when an application's producer is brought into the framework).

## Conversations: the beacon, for when the server is down

### Added

- `Conversations\Beacon`: a second server with the same code, PHP and Redis that keeps an emergency
  channel and direct messages going while the primary does not answer, and gives them back once it
  does (FW-236, phase 3b). `/beacon/*` is served by `www/beacon.php` without the application or its
  database: the watcher's health (on the primary too) and alarms, the primary's sync, export and
  acknowledgement, and the browsers' session, messages and reactions.
- Emergency keys: Ed25519, minted by the primary alone (`/admin/Conversations/emergencykey`), checked
  by the beacon, thirty days, renewed daily; servers sign their requests with HMAC.
- `conversations:beacon sync|import|test|keys`; sync and import scheduled every minute.
- The page and the dock turn to the beacon after three failed requests, and back when the server
  answers; a drill sends one person's page there for five minutes.
- `scaffolding/templates/beacon.php.stub`.

### Fixed

- The primary's health found its database only in `app/settings.php`: it now takes `settings_file`
  from `app/beacon.php`, else `app/config/settings.php` or `app/settings.php`, or the application's
  own `db_check` — so a primary with its settings elsewhere is not reported down (FW-238).
- `beacon.php` requires `app/beacon.bootstrap.php` first when it is there, for the constants an
  application's autoloaded files need, and defines `DS`; it said nothing and answered an empty 200
  where they were missing (FW-238).

### Documentation

- Conversations guide: *When the server is down — the beacon*. Console guide: `conversations:beacon`.

## Reactions: every emoji its own, on MySQL too

### Fixed

- On MySQL and MariaDB a person's second, different emoji on a message was silently dropped
  (FW-254). `conversation_reactions.emoji` was `utf8mb4_unicode_ci`, which compares every
  character outside the Basic Multilingual Plane as equal (😍 = 💝), so the unique key on
  message, person and emoji took the second for the first. The framework migration
  `make_conversation_reactions_emoji_binary` makes the column `utf8mb4_bin` and keeps every row;
  PostgreSQL needed nothing.
- A column's `charset()` and `collation()` were stored and never written: the schema grammar now
  writes them on MySQL and MariaDB, after the type.

### Documentation

- Schema Builder guide: *Column Modifiers*, a column's collation and the one for emoji.
- Conversations guide: what a reaction is.
- Upgrade Guide: `collation()` and `charset()` reach the column.
