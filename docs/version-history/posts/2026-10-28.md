## Planned: the next release raises the minimum PHP version to 8.4

### Documentation

- Nothing has shipped yet — `composer.json` still says `"php": ">=8.1"`. This is advance notice,
  in the same "planned, not yet in effect" section the bundled-addon deprecation timeline
  already uses: PHP 8.1 and 8.2 no longer receive security patches at all, PHP 8.3's own
  security window closes in November 2026, and this framework's CI has tested only PHP 8.5 for
  some time regardless of what `composer.json` claimed. The release after this one raises the
  floor to PHP 8.4; from there on, a framework version is expected to track roughly which PHP
  versions PHP itself still supports.
- An application that cannot move off PHP 8.1–8.3 yet should pin `"mrpc/pramnosframework"` to
  the last tagged release before that bump, rather than `dev-main`, so `composer update` does
  not pull in a requirement its runtime cannot satisfy.
- See [`Pramnos_Upgrade_Guide.md`](../../Pramnos_Upgrade_Guide.md#planned-not-yet-in-effect) and
  the main `README.md`'s Requirements/Guidelines sections.

## Scaffolded development containers no longer start on every boot

### Changed

- The `daemons` service in the development `docker-compose.yml` that `pramnos init` writes had
  `restart: unless-stopped`. Docker starts such a container — and the database and cache it
  depends on — whenever the Docker daemon starts, so every scaffolded project with background
  work came up on every boot of the developer's machine, used or not. It now has no restart
  policy.
- The policy existed for one failure: a supervisor started before the database accepts
  connections boots the framework into maintenance and exits 0. The database service now has a
  healthcheck (`pg_isready` / `mysqladmin ping`), and `daemons` depends on it with
  `condition: service_healthy`, so it starts only once the database answers.
- Existing projects keep their file; to get the same behaviour, delete the `restart:` line
  from `daemons` and add the healthcheck. A production deployment that wants the supervisor
  back after a reboot keeps `restart: unless-stopped` (or systemd's `Restart=always`) — see
  [the Workers and Daemons guide](../../Pramnos_Workers_And_Daemons_Guide.md).

## The test scripts stop the containers they started

### Changed

- `./dockertest` — the framework's own and the one `pramnos init` writes — starts the
  project's containers when they are down, as before, and now stops them again on exit, pass
  or fail. Containers that were already up are left alone. `--keep` leaves up what the run
  started. On a shared development machine a single test run used to leave a whole database
  stack running for days.
- The scaffolded `./dockernpm` starts the app container when it is down, instead of refusing
  to run, and stops it afterwards. The scaffolded `./testjs` and the framework's own do the
  same instead of falling back to the host's `node`; the host is used only where there is no
  Docker at all.

### Fixed

- Since a run now usually starts the stack cold, `./dockertest` waits for the databases to
  answer, not only for the PHP container: the framework's pings MySQL and PostgreSQL, the
  scaffolded one waits for the database's healthcheck instead of a fixed five-second sleep.
  Without it the first integration test met `Connection refused`.
- `./testjs` (the framework's and the scaffolded one) exited 0 when the tests failed inside the
  container: the run was made from an `if`, where `set -e` is off, and the function returned 0
  regardless. It now exits with the test run's own status.

- [Testing guide](../../Pramnos_Testing_Guide.md#dockertest-stops-the-containers-it-started).

## The `stopped` queue-status migration no longer fails on an enum `status` column

### Fixed

- `add_stopped_to_queueitems_status` (queue, `2026_10_20_000001`) failed with
  `invalid input value for enum queue_status: "deleted"` on a PostgreSQL installation moved
  over from MySQL, and stopped the bootstrap with it. There `queueitems.status` is not the
  `varchar` the framework creates but a column *of* the `queue_status` enum, carrying only the
  labels its application used; the migration's `CHECK (status IN (…, 'deleted', 'stopped'))`
  named labels the enum lacked. On such a column the migration now adds each missing status to
  the enum (`ADD VALUE IF NOT EXISTS`) and adds no constraint, since the type already refuses
  anything else. `down()` leaves an enum column alone: PostgreSQL cannot drop an enum label.
  An installation where the migration failed simply runs `migrate` again.

## `migrate --pretend`: the SQL pending migrations would run, without running it

### Added

- `migrate --pretend` prints, under each pending migration's slug, every statement its
  `up()` would send, and sends none of them: no DDL, no DML, no history row, no lock, no
  maintenance mode. Reads still run, so a migration that decides by looking at the
  database shows the branch it would take there. A migration that would throw is listed with
  `Would fail:`.
- `Database::startPretending()` / `stopPretending()`: while pretending, statements through
  `query()`, `execute()` and `upsert()` that might write are recorded and answered with an
  empty result. A `SELECT` runs only if it calls known read-only functions and neither locks
  nor creates anything; anything not recognisably a read is held back.
- `MigrationRunner::pretend()`: the runner's half, returning each slug's statements, failures
  and declines.

### Documentation

- [Migration guide — Seeing the SQL first](../../Pramnos_Migration_Guide.md#seeing-the-sql-first-pretend).

## Ask keeps tables, lists and texts as artifacts

### Added

- The model has a `save_artifact` tool: a table (`columns`, `rows`), a list of records
  (`entity`, `ids`, `labels`) or a text, given as data rather than left in the answer's
  Markdown. Kept in the new `chat_artifacts` table, linked to the conversation and the answer,
  carrying the conversation's data tags; the answer comes back with it as `artifacts`. What does
  not fit a kind is refused with the reason. It goes with its conversation and on account
  erasure.
- `Pramnos\Llm\Chat\Artifacts` (create, find, list, delete within a `Scope`), the chat API's
  `GET /chat/artifacts`, `GET|DELETE /chat/artifacts/{id}`, and
  `Chat\Web\ArtifactView::html()` for the markup. The chat page in every theme and the SPA chat
  component draw each artifact under its answer.
- The LLM tables health check names `chat_artifacts` until the migration has run.

This is the first step towards sharing a conversation or an artifact, turning a list into a
group, and acting on a list in bulk. A project whose chat views were copied before this keeps
them as they were: copy the `ArtifactView` line from a freshly scaffolded `chat.html.php`; a Svelte SPA
takes the new component with `project:resync --spa-components`.

### Documentation

- [LLM guide — Artifacts](../../Pramnos_LLM_Guide.md#artifacts-tables-lists-and-texts-kept-from-an-answer).

## Sharing an Ask conversation or artifact

### Added

- A person shares one of their Ask conversations or artifacts with others by username or
  email: `Share` on the conversation page (every theme, the analyst's too) and in the SPA chat
  component, or the API. The recipient is told and finds it under "Shared with you".
- A conversation is shared as it stands: the recipient sees the messages up to the share, and
  sharing again moves that point on. Opening it takes a copy — a conversation of the recipient's
  own, with the original's data tags and artifacts — which they read and continue with their own
  rights; an artifact arrives inside a conversation of its own. Opening again returns to the
  copy. Withdrawing, or deleting what was shared, stops it; a copy taken stays.
- New: `chat_shares` (state; one row per recipient), `Pramnos\Llm\Chat\Shares`,
  `Chat\SharePolicy` (`chat.share_policy`: who may share, with whom, where the notification
  leads), `Chat\SharedWithYou` (`chat.share_notification`), `Chat\Web\SharesConversations` and
  `Chat\Web\ShareView`; API `POST /chat/{id}/share`, `POST /chat/artifacts/{id}/share`, their
  `GET …/shares`, `DELETE /chat/shares/{id}`, `GET /chat/shared`,
  `POST /chat/shared/{id}/open`. Account erasure removes what a person shared and what was
  shared with them; the health check names the table until the migration has run.

### Documentation

- [LLM guide — Sharing](../../Pramnos_LLM_Guide.md#sharing-a-conversation-or-an-artifact).

## Bulk actions on a list, and adding an Ask list's people to a group

### Added

- `Pramnos\Bulk\BulkActions`: actions on many records at once, declared per kind of record
  (`define($entity, $key, $label, $params, $run, ability:, allowed:, filter:)`) and offered
  wherever such a list appears. Who may run one is asked when it runs and again for every queued
  chunk; required fields are required; a filter narrows the ids; up to 200 records run in the
  request and longer lists go to the queue (`bulk.action`) in chunks of 500; each run is written
  to the audit log.
- The framework's own: `user` → `group_add`, put people in an existing user group or a new one,
  behind `admin.groups`, through `Audience\Groups::add()`.
- An Ask list artifact offers the actions for its kind of record — on the page in every theme
  and the analyst's, in the SPA chat component, and through `GET /chat/artifacts/{id}/actions`
  and `POST /chat/artifacts/{id}/actions/{key}`.

## Ask can propose changes for a person to approve (off by default)

### Added

- With `'llm' => ['chat' => ['propose_actions' => true]]`, the model gets `list_actions` and
  `propose_action`: it proposes one of the application's declared bulk actions on some records,
  with its fields and a reason. The proposal is kept under the answer (an artifact of kind
  `proposal`) and changes nothing until the person approves it; approving runs it as them through
  `BulkActions::run()` — rights asked again, audit log, queue for a long list — once, and
  rejecting leaves it marked. Only its owner settles it; scheduled runs never get the tools.
- `Pramnos\Llm\Chat\Proposals`, `Artifacts::keep()`, `BulkActions::everything()`, the page's
  `approve/{id}` and `reject/{id}` (every theme, the analyst's), `Web\BulkView::decision()`,
  the SPA chat component's buttons, and `POST /chat/artifacts/{id}/approve|reject`.

## Ask's memory corrects itself, can learn after an answer, and can be shared by an organisation

### Added

- `remember` takes `replaces`: a memory that no longer holds is rewritten in place, the latest
  word winning; memories reach the prompt dated. `Memory::keep()` is the code form.
- `'memory' => ['learn' => true]` (off by default): after each answer a short second call keeps
  what the person stated about themselves or their work, corrects what changed and forgets what
  they took back; what it keeps is marked `learned` and shown so on the memory list. It never
  fails an answer.
- `'memory' => ['organization' => true]` (off by default; `organization_max`, 40): what people
  in an organisation tell the assistant about their shared work, kept with `userid` 0, read by
  everybody there, shown in the prompt apart from the person's own.
- `chat_memory.source` (`model` or `learned`).

## Reading checked fields out of a document with a model

### Added

- `Pramnos\Llm\Extractor`: named fields read out of a document's text (or a file —
  `DocumentText`'s types, and a PDF where `pdftotext` is installed) through one tool whose
  arguments are the fields, then checked — required, numbers as people write them, real dates,

  `Extractor::check()` checks what a person corrected.

  options — so a change proposed from a document is checked again before it can run.

## Analyst reports never reach readers below the analyst's floor; guests sign in and come back

### Changed

- A shared analyst report is not sent to, nor readable by, anybody below the analyst's floor
  (`'llm' => ['analyst' => ['floor' => N]]`, else the administration's default) whatever its

## Ask learns in batches, summarises long conversations, and does both on the cheapest model

### Changed

- Memory learning no longer costs a call after every answer. It waits for `learn_every` (5) of the
  person's messages in a conversation, or for the conversation to be quiet for `learn_idle`
  seconds (900); `llm:routines` picks those up every minute (`Conversations::learnQuiet()`). An
  explicit "remember…" or "forget…" is still done at once, through the model's own `remember` and
  `forget`.
- A long conversation is no longer cut at `turns()`. Past `turns()` turns and half as many again,
  its older exchanges are folded into a summary by one call and sent with the system prompt.
  `'llm' => ['chat' => ['summarize' => false]]` keeps the old cut.

### Added

- `Client::askCheaply()`: the cheapest priced model the provider lists, falling back to the
  connection's own model when that one fails. Learning and summaries use it.
- Migration `2026_10_28_000022`: `summary`, `summary_upto` and `learned_upto` on
  `chat_conversations`. Existing conversations count as already learned up to their last message.

### Documentation

- [LLM guide — conversations](../../Pramnos_LLM_Guide.md#conversations) and
  [memory](../../Pramnos_LLM_Guide.md#memory).

## An organisation's shared memory is written by a root account only, never by learning

### Changed

- What an organisation's Ask memory holds goes into the prompt of everybody in it, so it is no
  longer written by any member. Only an account that `Memory::mayShare()` allows can keep, correct
  or forget a shared memory: a root account, or one given the `admin.ai.memory` ability. It has to
  ask explicitly (`remember` with `about: organization`). Other members are not offered the
  parameter at all, and `keep()`/`forgetShared()` refuse them.
- Learning keeps memories about the person only. A change the model marks as about the
  organisation is dropped, so it is neither shared nor kept as personal.

### Documentation

- [LLM guide — memory](../../Pramnos_LLM_Guide.md#memory).

## An upload directory's `.htaccess` no longer breaks the Apache log under php-fpm

### Fixed

- The `.htaccess` that `MediaObject` gives an upload directory had a bare `php_flag engine off`,
  a directive only mod_php knows. Under php-fpm, Apache logged
  `[core:alert] Invalid command 'php_flag'` on every request into the directory. Uploads were
  still protected, because the rewrite refusing `.php`, `.phtml` and `.phar` does the work. The
  line now sits inside `<IfModule mod_php.c>` / `<IfModule mod_php7.c>`.
- An existing `.htaccess` that is exactly the earlier framework version is rewritten on the
  directory's next upload. One the application changed is left as it is, as before. To stop the
  log lines at once, without waiting for an upload into each directory, delete the bare
  `php_flag engine off` line by hand.

## `symfony/mime` below its patched versions is refused (CVE-2026-45070)

### Security

- CVE-2026-45070 (email header injection through non-token characters in MIME parameter names)
  was re-issued today because the first fix was incomplete. It now covers every `symfony/mime`
  below 5.4.55, 6.4.49, 7.4.22 and 8.1.10. The framework sends email through `symfony/mailer`,
  so the framework's `composer.json` now declares a `conflict` with those versions. An
  application's next `composer update` therefore has to bring in a patched one, and cannot keep
  a vulnerable version behind the framework. To patch without updating anything else, run
  `composer update symfony/mime`.

## A scheduled task's "Run now" runs in the worker, and the task says it is running

### Changed

- "Run now" on the scheduled page, and `POST /chat/routines/{id}/run`, ran the task inside the
  request, so the page waited the whole minute a report took to read. The run now goes to the
  queue through `Routines::runNow()`, as a question in Ask does, whatever `task_queue` says.
  The API answers 202. See the Upgrade Guide row.
- A task waiting in the queue, or under way, says `running`. The page shows "Running…", offers no
  second run, and reloads until the run is done (every 15 s; the SPA reads the list again). A
  second press is refused with "It is already running.". A run the policy refuses is refused at
  once, before anything is queued.
- No queue worker: `'llm' => ['chat' => ['answer_in_request' => true]]` runs it in the request.
  A queue that will not take the task also gets the run in the request.

### What breaks in subclasses

- An application that overrode `scheduledrun()` to queue the run can delete the override: the
  base class now does what it did.
