## Conversations\Files: CSV, and more kinds besides, no longer refused

A CSV sent in a conversation was refused: `finfo` reports every `.csv` as `text/plain`, and
`text/plain` only carried `txt`/`log`/`md`. Both `text/plain` and `text/csv` (and `application/csv`,
`text/x-csv`) now carry `csv` and `tsv`.

### Added

- `Files::TYPES` also accepts RTF, JSON, XML, email (`.eml`, `.msg`), old OLE-container Office
  (`.doc`/`.xls`/`.ppt`/`.msg`), audio (MP3, M4A, WAV, OGG, AAC), HEIC/HEIF/TIFF images, and rar/7z
  — by content, as before, never by name.
- `Files::types()`: `Files::TYPES` merged with an application's own, from `'conversations' =>
  ['file_types' => ['mime' => ['ext', …]]]` — adding extensions to a mime already listed, or a mime
  of its own.
- `Files::extensions()`: every extension `Files::store()` accepts, the application's own included,
  flat — for a client's upload picker (`accept`) and its own guard against a dropped or pasted file
  that will only be refused.
- A refusal now names the extension it was refused by, and writes one warning log line: the user,
  the conversation, the type `finfo` read, the extension and the size — a refusal was otherwise
  indistinguishable from a bug with nothing to go on.

### Documentation

- `Pramnos_Conversations_Guide.md`: the Files section covers the full allowed list, `types()`,
  `extensions()` and the refusal log line.

## Push: opened/dismissed tracking, and a device buried under notifications is held off a second one

A production push subscription stopped working: Chrome on Android had auto-revoked notification
permission after enough of them went unseen. Nothing recorded whether a push was ever opened, so
there was no way to tell "arriving but ignored" from "not arriving" — and no way to stop sending
more to a device that was clearly piling them up.

### Added

- `pushlog.opened_at` / `dismissed_at`: the shipped service worker now reports
  `notificationclick` / `notificationclose` back to the server (`data.report`, `data.pushid` —
  both already in every push payload), never for the self-closing `pf-quiet` notification.
  `POST /push/report`, no session, no CSRF.
- `Log::reserve()` / `Log::complete()`: a push's row now exists **before** it is sent, so its own
  id can ride inside the payload the browser receives — `PushChannel::deliver()` reserves one
  per subscription rather than logging once after the whole batch.
- `Log::opened()` / `Log::dismissed()` / `Log::unresolved()` / `Log::openRate()`; `Log::stats()`
  gains `opened` and `dismissed` counts.
- The hold-unopened rule (FW-495): `'push' => ['hold_unopened' => 'mobile'|'all']` stops a second
  conversation push from going to a device that already has an earlier one sitting there
  unopened — cleared by opening or dismissing it, by any activity on any client since it was
  sent, or by catching up on that push's own conversation.
  `ConversationNotification::heldFor()` opts in; anything that implements no such method (a
  reminder, a to-do, an application's own notification class) is simply never held.
  `PushChannel::send()` checks it with `method_exists()`, never assumed.
- `pushlog.token`: `pushid` is a plain auto-increment, so `POST /push/report` now also checks a
  per-row token (`Log::reserve()` generates one, `Log::verifyToken()` checks it with
  `hash_equals`) before writing anything — without it, a bare id would let anyone report against
  a push that was never theirs.
- The analyst's `push` tool: `opened`, `dismissed`, `open_rate` and `open_rate_by_kind`, counting
  only pushes sent after the token column existed — an older row has nothing to tell "cannot
  say" from "never opened", so it is left out rather than counted against the rate.
- `/admin/PushLog`: an **Opened**/**Dismissed** column per row, and a **By device** summary
  above the list — `Log::deviceSummary()`, every account's figures grouped once rather than
  looped per account — each with the account's name, linked, and its device in plain English
  (phone/computer, OS, browser) instead of the raw user agent.

### Fixed

- `/admin/PushLog` is now translatable (`resources/language/el.php`), the detail page
  (`view.tpl.php`, all three themes) included: every label and `Log::outcome()`'s own
  explanation sentences, not only the list's labels — the Greek for the explanations themselves
  was missing from `el.php` in the first pass, since `t()` wrapping the code is not the same as
  the catalogue having the joined string. The account column showed a bare `#id`, now the
  account's name (on the detail page too, not only the list), still linked to its card. The
  detail page's own `<title>` (`PushLogController::view()`) went through string concatenation
  rather than `t()`, even though the list already had the translated form.

### Documentation

- `Pramnos_Push_Guide.md`: a new section, *Opened, dismissed, and the hold-unopened rule*, the
  `/push/report` endpoint, and `Log::deviceSummary()` with what the list and the by-device
  summary show once opened/dismissed are tracked.
- `Pramnos_Conversations_Guide.md`: *Held while unopened*, beside *Told in the client the person
  is in*.

## The analyst's SQL reads the database's own replica (FW-496)

Measured against production: the analyst's `sql`/`export_csv` ran against the **main** database.
`ReadOnlyConnection::for()` only ever looked at `database_readonly_dsn`, which nothing had set,
while `Metrics` already reads from a configured replica for exactly this reason (FW-346).

### Added

- `ReadOnlyConnection`: without `database_readonly_dsn`, `'llm' => ['analyst' => ['replica' =>
  true]]` reads the database's own replica (`Database::replicaConnection()` — the same
  `replica`/`read` settings block `Metrics` already reads through), rather than a second copy
  of the connection details in a setting of its own. A replica that does not answer falls back
  to the database itself and says so in the log, the same trade `Metrics` already makes.
- `Database::isReadOnly()` and `Database::querySessionControl()`.

### Fixed

- `ReadOnlySql::each()`'s own `BEGIN`/`SET`/`ROLLBACK` were routed as writes by
  `isWriteQuery()` — correct for picking a pool on an ordinary two-pool connection, where a
  transaction has to stay pinned to the pool its writes will use, but this transaction never
  writes anything. On a connection with no write pool at all — a dedicated read-only account,
  or a replica — `BEGIN` simply threw; on an ordinary two-pool connection it silently split one
  "read-only transaction" across two connections that never heard of each other's `READ ONLY`.
  Fixed through `Database::querySessionControl()`, which also covers a `WITH … SELECT` (`WITH`
  was never in `isWriteQuery()`'s read-keyword list either) and MariaDB's `SET STATEMENT …
  max_statement_time … FOR <select>` wrapping.

### Documentation

- `Pramnos_LLM_Analyst_Guide.md`: the replica setting, beside `database_readonly_dsn`.

## The analyst's ceilings are configurable, and it can hand off a multi-step question (FW-496)

### Added

- `Analyst\Limits::of()`: one place for a per-application, per-role ceiling —
  `'llm' => ['analyst' => [$key => …]]` as a plain number or `fn(User): int|float`. `sql_rows`
  (`SqlTool::MAX_ROWS` otherwise), `export_rows` (`ExportCsvTool::MAX_ROWS` otherwise) and
  `rounds` (the framework's own default otherwise) all read through it now.
- `deep_analysis`: a `Pramnos\Llm\Subagent` given this answer's own tools, minus anything that
  writes or is gated, with its own `subagent_rounds`/`subagent_cost` — for a question that needs
  several reads cross-checked against each other rather than one tool call. Off unless
  `'llm' => ['analyst' => ['subagents' => true]]`.

### Documentation

- `Pramnos_LLM_Analyst_Guide.md`: the ceilings, and the new *Subagents* section.

## A reaction has a read point too (FW-497)

A reaction opened the Activity badge for a conversation the reader already had open in front —
a mention or a reply is "read" once past `lastreadid`, but a reaction is not a message, has no
id to be read "up to", and nothing ever marked it read on its own.

### Added

- `conversation_members.readat`: set by `Conversations::markRead()` every time it runs, even
  when `lastreadid` itself does not move — exactly the "already caught up, a reaction arrives"
  case.
- `Inbox::unseenActivity()` counts a reaction past its conversation's `readat`, the same way it
  already counts a mention or a reply past `lastreadid`.

### Documentation

- `Pramnos_Conversations_Guide.md`: `readat` beside the existing `markRead()`/`lastReadId`
  passage.

## A thread has its own read point too (FW-498)

The same fault as FW-497, for threads: a conversation's `lastReadId` moves with its top-level
messages, never a reply, so a reply in a thread open and in front still opened the Activity
badge, and — the opposite fault — a reply older than the newest top-level message read as
"read" without the thread ever having been opened. `Inbox::threads()`'s own `newReplies` had
the matching gap: reading a thread, without replying in it, left every reply in it "new" for
ever.

### Added

- `chat.thread_reads(conversationid, rootid, userid, lastreadid, readat)`: state (rule 14), one
  row per person and thread.
- `Pramnos\Conversations\Threads`: `markRead($root, $person, $messageId)` — never back on
  `lastReadId`, `readAt` always moves, the same idea as `Conversations::markRead()`; `read()`
  and the batched `readMany()`.
- `POST threadread/{root}` (`{message}`), told on the person's own channel as `thread.read`
  (`{conversationId, rootId, lastReadId}`) rather than `conversation.read`.
- `Inbox::unseenActivity()` counts a reply past its thread's own read point, falling back to the
  conversation's `lastReadId` when the thread was never read (today's behaviour, unchanged).
  `Inbox::threads()`'s `newReplies` counts past the later of the reader's own last word there
  and the thread's read point.

### Documentation

- `Pramnos_Conversations_Guide.md`: `Threads`, beside FW-497's `readat` passage; the endpoint
  and the realtime event in their own tables.

## Chart annotations are hidden by default, shown on hover/focus (FW-499)

`pf-utils.js`'s `pfNotes` plugin drew each annotation's text permanently on the canvas, at a
fixed offset from the top — with two notes close together on the X axis, the labels overlapped.

### Fixed

- The dashed line stays, fainter (0.5 alpha); the text is no longer drawn on the canvas at all.
  A small triangular marker sits on the axis instead, and the full label is a DOM card positioned
  over the canvas (`.pf-chart-notes-overlay`), revealed only on hover or focus of its marker via
  a CSS opacity transition — so overlapping labels can no longer happen; only one is open at a
  time, by the reader's own pointer or Tab key.
- The marker is a real `<button>`, already in the Tab order with no `tabindex` needed; its
  `title` attribute and `aria-describedby` (pointing at the label) are the fallback for a screen
  reader or a page with the theme's CSS missing.

### Documentation

- `Pramnos_Metrics_Guide.md`: the *Notes on the charts* section describes the marker/hover
  behaviour in place of the permanent label.

## The history panel can be filtered by event type (FW-499)

`HistoryPanel::render()` already drew a record's whole history correctly — pagination with no
script, who may read it, feed and events in one feed — but a long, mixed history (saves and
several kinds of application event) had no way to narrow down to one kind short of paging
through everything else.

### Added

- `ChangelogReader::events($entity, $itemid, $origins = ['events'])`: the record's own distinct
  event codes, most recently used first, never repeated — capped at the newest 1000 rows.
- `ChangelogRenderer::eventLabel($entity, $event)`: the same lookup `describe()` uses for an
  event code, exposed for a filter built before any row names one.
- `HistoryPanel::render()`: once a record has more than one distinct code, a row of chips above
  the list — "All" and one per code — each a plain link (`?history_event=post.pinned`, the
  `eventParam` option) that resets the pager to page 1. A code that is not genuinely one of the
  record's own is ignored, back to "All", rather than trusted into a query.
- `HistoryApi`: `data.events`, the same codes, for a SPA to build the same filter from —
  computed from `entity`/`itemid`/`origins` alone, never narrowed by a chosen `event`, so the row
  of options never collapses to one once it is picked.
- `HistoryPanel.svelte` (the scaffolded template): the same chips, as buttons; picking one
  re-asks the API from page 1 with `event=`.

### Documentation

- `Pramnos_Change_Feed_Guide.md`: *Showing a record's history* gains a *Filtered by event type*
  passage, the PHP and the SPA side both.

## A browser for every change, across every record (FW-499)

`HistoryPanel` draws one record's own tab. There was no screen for "what happened, anywhere" —
an admin asking that question had nothing, even though `ChangelogReader::listing()` already
takes every filter such a screen needs without an `itemid`.

### Added

- `Pramnos\Html\HistoryBrowser::render($options = [])`: a form reading `entity`, `event`,
  `logtype`, `source`, `from`, `to` from the query string — `listing()`'s own filters — and
  resubmitting as a plain GET; a list of matching lines, each named by its own `entity`/`itemid`;
  older pages as links that keep the current filters (`?log_page=2`). `entities` offers the
  entity field as a `<select>`.
- Permission is the same `History::allows()`/`allowUsing()` as the panel, but a listing with no
  single `entity`/`itemid` never gets the "my own account" shortcut: by default this is whoever
  may open the administration, full stop.

### Documentation

- `Pramnos_Change_Feed_Guide.md`: a new *Browsing every change* section, beside *Showing a
  record's history*.

## `ChangelogRenderer::describe()` no longer trusts a changed value

A column holding a serialized blob — a gateway's raw response — landed verbatim in a history
line when an application forgot to list it in `$changeIgnoreFields`. Correct behaviour on our
side; the one thing every application using this forgets sooner or later, so the renderer now
guards against it rather than trusting the caller.

### Fixed

- A value that starts with `serialize()`'s own prefix (`s:5:"…`, `a:2:{…`, `O:8:"stdClass"…`) is
  redacted outright — a truncated fragment of it would be unreadable anyway — naming
  `$changeIgnoreFields` as the real fix. Anything else over 500 bytes is truncated with a byte
  count instead of printed whole. Ordinary values are untouched.

### Documentation

- `Pramnos_Change_Feed_Guide.md`: a note under *Reading it back*.
