## `schedule:list` sees the `work` process that is running

### Fixed

- **"No `work` process is running" beside one that was, executing tasks.** `schedule:list` built
  its `WorkerLock` from the name `pramnos-work.lock`, and the lock's default path adds `.lock`, so
  it read `var/pramnos-work.lock.lock` — a file nothing writes. It asks `Work::lockFilePath()`, the
  path the worker itself uses, supervisor's override included. Its test had taken the lock the same
  wrong way, which is why it passed (FW-208).

## `work` no longer skips a minute

### Fixed

- **A task due in a minute no pass looked at did not run.** Each pass asked about the current
  minute only, ran what was due one task after another, then slept sixty seconds from when it
  ended. A nine-second mail flush was enough: passes at 03:19:59 and 03:21:09, nothing asked about
  03:20, and a task on `5,20,35,50` did not run — a weekly one would have waited a week. A pass
  now asks about every minute since the last one, at most `Work::CATCH_UP_MINUTES` (15) back, runs
  each due task once, and sleeps to the next minute's start (FW-210).
- **`--interval` below sixty ran an every-minute task twice a minute.** A minute already asked
  about is not asked again.

## `broadcast:serve` holds its lock, so the orchestrator stops restarting it

### Fixed

- **The orchestrator restarted the WebSocket server every cycle**, dropping every open page:
  its entry declares `var/pramnos-broadcast-serve.lock`, and `broadcast:serve` never took a lock
  or wrote a heartbeat, so it stayed "started-unverified" and was gracefully stopped to be
  started again. The Services screen, reading the same absent file, showed the running server as
  stopped and offered to start a second. It takes the lock, heartbeats from the event loop every
  ten seconds, and releases it on exit; a second one refuses while the first holds it (FW-209).
  An application that set `'requireLockFile' => false` on the entry to get by can remove it.

## A page signed in by an application's own login gets the realtime connection

### Fixed

- **`<meta name="pf-realtime">` was written only for a session holding a framework token.** An
  application whose login is its own sets `uid` and `logged` and no `usertoken`, so none of its
  signed-in pages connected and the notification bell never went live. The meta now follows
  `Session::staticIsLogged()` as well — the test `getCurrentUser()`, and so `/broadcasting/auth`,
  already made (FW-211).

## `queue:process` writes a line per task into a file instead of its dashboard

### Fixed

- **A worker run into a file painted its whole dashboard there, five times a second.** Only a
  supervised worker skipped it; one started by hand with `>> var/logs/ask-worker.log` and
  `--sleep=2` wrote borders, escape sequences and "Press Ctrl+C to exit" until the file was 542
  MB, the task results lost inside it. The dashboard is painted only on a terminal; otherwise each
  task is one plain line — time, id, type, status, duration, message — and an empty pass writes
  nothing (FW-214).

## A link can open its page in a dialog — `data-pf-modal`

### Added

- **`data-pf-modal` on a link** opens its page in a `<dialog>` over the current one: fetched with
  `X-Pf-Fragment: 1`, closed by Escape, the × or the backdrop, focus back on the link afterwards.
  Without `<dialog>`, on a modified click or a failed fetch it is an ordinary link (FW-213).
- **`Document::isFragmentRequest()`**, and the request with that header gets the `raw` document,
  so any screen answers with its content alone — no per-screen code. The page cache keys the
  fragment apart from the page, and `Breadcrumb::admin()` draws no trail into it.
- **The queue screen's "Statistics — last 48 hours" and each task's id** open in the dialog
  instead of leaving the list.

## The services screen is the state of the workers; a pool's settings have a page of their own

### Changed

- **`/admin/Services` shows the workers' state and nothing to configure**, in reading order:
  the supervisor, the services (with Restart all), the worker pools — their task types,
  workers, backlog, load, decision, state, Stop / Start — and the batches. The pool forms that
  sat above the services, so that seeing whether anything was running meant scrolling past
  settings, are gone from it; **Configure pools** links to them.
- **Every label on the screen goes through `t()`**, with the Greek in the framework's
  catalogue, and the ten-second refresh writes its sentences in the page's language. Restart
  all asks through `data-confirm` instead of an inline `onsubmit`.

### Added

- **`/admin/Services/pools`** (`ServicesController::pools()`), linked from the services screen
  and from Settings: a card per pool. Task types are boxes to tick, from those with a handler
  (the framework's, `queue.handlers`, the queue's task classes), those in the queue table and
  those a pool names, with a field for any other. Every limit has a label in words and a line
  under it saying what it does — "Always keep at least this many workers running", "Start
  another worker when more than this many tasks are waiting". A code pool shows its declared
  values as placeholders and keeps them for a blank field; nothing ticked keeps its declared
  types. Save, Stop / Start, and Reset to code or Remove (asked first) on each card, and a
  last card to add a pool.
- `poolsave` accepts `types[]` and `types_other` beside the plain `types` string, so a
  published form of an application's own keeps working. Save and Remove return to the pools
  page; Stop and Start return to the screen they were pressed on (`back=pools`).

## A slow command no longer holds the schedule, and every run is recorded

### Added

- **`ScheduledTask::runInBackground()`** for command tasks: started detached through the hidden
  `schedule:background`, which holds the overlap lock until the command exits and records its
  end — the pass does not wait. A four-minute command due every minute of an hour had held
  `work` for the whole hour on one installation; the tasks due at :15 and :20 behind it never
  ran, and the catch-up gave up after fifteen minutes (FW-216).
- **The run history, `scheduleruns`** (migration `2026_10_21_000001`): every run, whoever started
  it, with its duration, result, exit status and the end of its output; `RunLog` to read it,
  and to ask for a run that the next pass takes once. Runs older than `schedule.history_days`
  (14) are removed (FW-212).
- **`CronExpression::nextRunAfter()`, `previousRunBefore()` and `describe()`** — a task's next
  run, the last one it was due, and the expression in words.

## A page opened in a dialog shows its content, centred

### Fixed

- **Every `data-pf-modal` dialog opened empty.** A fragment request was given the `raw`
  document, and a controller takes its view's type from the document, so each screen looked for
  `history.raw.php`, found nothing and answered 200 with no body. The document stays `html` and
  leaves only the theme and the head out (FW-213).
- **The dialog sat in the top-left corner** under Tailwind, whose preflight sets every margin to
  0 and so cancels the browser's own centring. `.pf-modal` puts `margin: auto` back in every
  theme.

## `data-confirm` on a form asks when it is sent, not at every click inside it

### Fixed

- **A form carrying `data-confirm` asked at every click inside it** — on a field, a checkbox, a
  label, the empty space — because the click handler matched the nearest `[data-confirm]`, the
  form. Cancel then prevented the click, so a box could not even be ticked. A form's question is
  asked once, on `submit`, and not when the button that sent it has its own (FW-217).

## Every tab of a site shares one realtime connection

### Changed

- **`window.pfRealtime` runs over a SharedWorker where the browser has one.** N tabs made N
  sockets and N `/broadcasting/auth` calls, and every page change closed one socket and opened
  another. `pf-utils.js` now runs itself as the shared worker `pf-realtime`, which holds one
  connection for every tab: tabs subscribe through it, a private channel is signed by a tab that
  listens on it (the next one if that tab leaves first), events go to every tab on the channel,
  a channel no tab wants is left, and after a reconnect each tab gets one
  `pf:notifications:refresh`. Without `SharedWorker` each page keeps its own connection. The API
  is unchanged; `pfRealtime.shared` says which way a page is connected (FW-215).

## `./dockertest` opens the coverage report only when asked

### Changed

- **The framework's `./dockertest --coverage` no longer opens the report in a browser** unless
  given `--browser`. Most runs are made by scripts and tools, and each opened a tab.
  `--nobrowser` is still accepted and is now the default.

## A shared realtime connection that cannot start leaves each page its own, and says what it is doing

### Fixed

- **A page whose shared worker did not start had no connection at all.** The worker now answers a
  tab's `hello` at once; without that answer in five seconds, or on the worker's `error`, the
  page opens a connection of its own with the channels it asked for (FW-215).

### Added

- **`window.pfRealtime.status()`**, in every tab: the socket's state and id, the channels the
  server confirmed, the last error — a refused signature, a `pusher:error` — whether the
  connection is shared, and why it is not where it tried to be. The worker sends its state to
  every tab as it changes.

## A page can offer its forms to an AI agent in the browser (WebMCP), and the debug bar shows them

### Added

- **`data-pf-tool` on a form** makes it a tool an AI agent in the visitor's browser can call,
  registered by `pf-utils.js` with WebMCP (`document.modelContext.registerTool()`, a W3C
  Community Group draft). The input schema comes from the fields and their labels; a call fills
  the form and sends it as the page would — current CSRF token, `X-Pf-Fragment: 1` — and answers
  with the resulting page's text. A POST form is marked consequential.
- **`window.pfTools`**: `list()`, `call()`, `calls()`, `register()` for a tool written in script,
  `supported`; `pf:tool:call` and `pf:tools:change` events. There with or without WebMCP.
- **The debug toolbar's Tools tab**, on a page that offers tools: each with its schema and a Run
  that calls it as an agent would, and every call — an agent's or the panel's — with its input,
  result and time.

## The schedule has a screen: what runs, when, how it went, and what is late

### Added

- **`/admin/Scheduler`** (System → Scheduler), the framework's own controller: every task with
  its expression in words, its next run, its last run — when, how long, how it ended — and
  whether it runs without overlap, on one server, in process or in the background. A task is
  marked **late** when the last minute its expression asked for has no run since, **failed** when
  its last run ended in an error, and **running** while a run is in progress. A note says when no
  `work` process holds its lock (FW-212).
- **A page per task**, opened in a dialog from the list: its runs, newest first, each with its
  exit status, host and output.
- **Run now**: a POST, audited, that asks the next pass of `work` or `schedule:run` to run the
  task once; nothing runs in the request.
- **A dashboard card** with the late, failed and running counts, and
  `Pramnos\Scheduling\ScheduleStatus`, which the screen and the card both read.

### Added

## A rich-text editor: pictures with captions, uploads, a link search, and plugins

### Added

- **`'messaging' => ['editor' => 'rich']`** and `MessageEditor::RICH`: `pf-rich-editor.js`, TipTap
  bundled into one file that ships with the other `pf-*.js`. Pictures as
  `<figure><img alt><figcaption>`, uploaded by drop, paste or choice to `messaging.rich.upload`; a
  link panel that searches `messaging.rich.links`; the selection kept while a panel has the focus;

  push. The [Rich Text Editor guide](../../Pramnos_Rich_Editor_Guide.md) has the rest.
- The sources are in `resources/js/rich-editor/`, built by `npm run build:editor`; a test fails

## The query string reaches `$_REQUEST` behind a rewrite without QSA

### Fixed

- **An unsubscribe link said "This link is not valid", and one-click POST answered 400,** on a
  site that routes through `RewriteRule ^(.*)$ index.php?r=$1` without `QSA`: the query was only
  in `REQUEST_URI`, `Request` parsed it into `$_GET` but not into `$_REQUEST`, and the token is read
  with `get('u', '', 'request')`. What `Request` parses from the query reaches `$_REQUEST` too,
  where it has no such key — a POSTed value still wins (FW-225).

## Events that run in the queue

### Added

- **`Pramnos\Event\QueuedListener`**: a listener `Event::fire()` queues instead of calling. A worker
  runs it with the event's arguments, as a task of type `event.listener` that the framework
  registers itself. Its place in `fire()`'s results is the task id, and it never stops the
  listeners after it (FW-227).
- **The task is written in the caller's transaction** on the application's connection: a rollback
  takes it with the change. A transaction on another connection does not cover it.
- **Folding by key** — `debounceKey()`, `debounceWindow()` (60 s), `debounceCeiling()` (600 s):
  events with one key are one waiting task with the last event's arguments, counting the others in
  `absorbed`. `QueueManager::addKeyed()` does the same for any task.
- **Work done once per key** — `idempotencyKey()`, `idempotencyTtl()` (30 days): a used key queues
  nothing, and a task that finds it taken completes as skipped. A failed run gives it back.
- **`Event::fireAs(?int $userid, …)`**: who fired it, for a cron, a webhook or a worker; null is
  the system.
- Every task carries its event — id, time, who, `source` (web, cli, queue), `causedBy`, `rootId`,
  `depth` — and a chain deeper than ten is refused and logged. The Queue screen shows all of it,
  with the folding key and the count.
- An argument that cannot travel as JSON throws in development and under tests. In production it
  is logged to `events`, and that task is skipped.
- Migrations `2026_10_21_000005_add_event_columns_to_queueitems` and
  `2026_10_21_000006_create_queue_idempotency_table`. Without them, queued listeners still queue,
  unfolded.

## `work` loses no minute to a restart

### Fixed

- **A task due while `work` restarted never ran** (FW-230). Each pass asks about every minute
  since the previous pass, but that minute was kept only in memory, so a new process looked at
  the current minute alone. A deploy restarts the worker, and the old process finishes its pass
  first, which leaves a gap of one or two minutes. On a day with 21 deploys, a task on
  `18 7 * * *` never ran, and it left no row in `scheduleruns`, not even a skipped one. The last
  minute asked about is now kept in `var/pramnos-work.lock.minute`, beside the lock, and a new
  process starts after it, capped at `Work::CATCH_UP_MINUTES` (15) as before.

## The outbox deadline sweep gets an index

### Fixed

- **`mail:flush` read the whole `mails` table every minute** (FW-231). Its deadline sweep,
  `UPDATE mails … WHERE status = 2 AND date < ?`, has nothing to narrow it on a `mails` with no
  index on `status`. That is an installation whose table predates the framework's migrations. On
  35 million rows it took nine seconds a run, with an empty outbox. Migration
  `2026_10_21_000007_add_status_date_index_to_mails` adds `(status, date)` where no index leads
  with `status`, and does nothing where one does: the framework's own `idx_mails_status`, or one
  an installation built itself under any name.

## Domain events as classes

### Added

- **`Event::dispatch(object $event)`**: fires the class's `EVENT` constant, or the class name when it
  has none, with the object as its one argument. A listener in the request receives that instance
  itself, models included, so what it changes on the caller's objects is what the caller saves next
  (FW-233).
- **`Pramnos\Event\QueueableEvent`** (`jsonSerialize(): array`, `static fromQueue(array $data): static`):
  an event object that can reach a `QueuedListener`. The task carries its data and its class, and the
  worker hands `handle()` the object `fromQueue()` builds. One `handle(JobPostCreated $event)`
  therefore serves the request and the queue. `debounceKey()` and `idempotencyKey()` are asked at
  dispatch, with the object.
- **Listener classes typed with their event** — `handle(JobPostCreated $event)` — registered by
  class name, are called by `fire()` without implementing `ListenerInterface`.
- `create:event` writes the convention: `EVENT` (`JobPostCreated` → `jobpost.created`), a readonly
  payload, and `jsonSerialize()`/`fromQueue()`. `create:listener` takes `--event=` for a typed
  `handle()` and `--queued` to extend `QueuedListener`.

### Changed

- `QueuedListener` no longer implements `ListenerInterface`: no typed `handle()` could satisfy that
  interface's `handle(mixed ...$args)`. It is callable instead, and calling it runs it at once, so an
  instance can still be registered with `Event::listen()`, and `fire()` still queues it.

### Documentation

- Queue guide: new section "Domain events as classes", covering when to use a class rather than a
  bare name, that listeners in the request act on the caller's object, and that a listener which
  changes other data goes to the queue. Console guide: the new options.

## Scheduled tasks an operator may adjust

### Added

- **`->adjustable($id, $label, $group, presets:, limit:)`** on a scheduled task: from the task's
  page on the Scheduler screen, an operator can pause it, give it another frequency from a fixed
  list, keep it to an hours window, and set a per-run limit (FW-232).
  - The list of frequencies: every 1, 5, 10, 15 or 30 minutes; every 1, 2, 3, 6 or 12 hours; daily
    at a time; weekly on a day at a time. No free cron.
  - The hours window may cross midnight. Outside it, and while paused, the task is not due and
    writes nothing.
  - The limit reaches a command as `--limit=N` and a callable or a job's `handle()` as its
    argument, held to the declared `[min, max]`.
- **Applied without a restart.** Settings live in `scheduleoverrides` (migration
  `2026_10_21_000008_create_scheduleoverrides_table`), keyed by the application's id. `work` and
  `schedule:run` read them once a pass. *Back to the schedule in the code* deletes the row.
- **Not late.** `ScheduleStatus` treats a paused task, or one outside its hours, as not late, and
  lists it as *Paused since …* or *Outside hours · next 09:00*. Its next run is the first one
  inside the window.
- **Audited.** A save is `scheduler.adjusted` in the audit log and a reset is `scheduler.reset`,
  each with the settings before and after. The task's page says who changed it and when.
- **`scheduler.adjust`** (`Scheduler::ADJUST_ABILITY`): changes adjustable tasks, and opens the
  screen to an account that holds it, showing the adjustable tasks only, grouped, with no *Run
  now*. Where the application defines no rule for it, `admin.scheduler` adjusts as well.

## Audiences: attributes of a person, and filters over them

### Added

- **`Pramnos\Audience`**: the first part of segments, rules and A/B tests (FW-234). A person is a
  row of `users`; an application declares what can be asked about one, and a JSON filter of
  conditions grouped "all" / "any" chooses people by it.
- **Attributes** (`Attributes::define()`): a column of `users`, a column of a one-to-one table
  (LEFT JOINed once, only when used), a one-to-many table (asked with `EXISTS`, so counts stay
  counts of people), or an SQL expression per driver; typed text, number, date, boolean, list or
  many, with a label, a heading, choices and an ability. The framework declares account type,
  language, registered, last sign-in, status, email verified and groups. `Attributes::scope()`
  says who is a person at all.
- **`Filter`**: checked when made, with the path of what is wrong; compiled to the query builder;
  `count()`, `sample()`, `ids()` in keyset pages, `matches()`, `breakdown()` per value, and
  `explain()` — every condition with ✓/✗ and the person's actual value.

### Documentation

- New Audience guide.

## Segments: named audiences kept up to date

### Added

- **`Pramnos\Audience\Segments`** (FW-234): a filter with a name, owner and description, and
  `segment_members` — who was in it, one row per stay, `entered_at` to `left_at` (migration
  `core/2026_10_21_000009_create_segments_tables`).
- **Recomputed** in full by `segments:recompute`, which the framework schedules hourly, and per
  person with `recomputePerson()` — in the queue, folded per person, on the events an application
  names with `Segments::refreshOn()`.
- **`segment.entered` / `segment.left`** as event classes (`SegmentEntered`, `SegmentLeft`) on each
  change. A segment's first recomputation records its members without them.
- **Filters can name segments** (`{"segment": id, "op": "in" | "not_in"}`), computed in dependency
  order. A segment that would name itself is refused, and one in use — by another segment, or by
  what an application reports through `Segments::usage()` — is not deleted.
- **Audience reads fail loudly**: `Filter` and `Segments` read with `getAllOrFail()`, so a
  mistyped side table is an error on PostgreSQL too, not an audience of nobody.

### Documentation

- Audience guide: Segments. Console guide: `segments:recompute`.

## Consent lists: what a send asks before it reaches somebody

## What people did: person events, recorded from event classes, pages, email and the past

### Added
