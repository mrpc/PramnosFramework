# 21 October 2026

Six entries today:

- `schedule:list` sees the `work` process that is running
- `work` no longer skips a minute
- `broadcast:serve` holds its lock, so the orchestrator stops restarting it
- A page signed in by an application's own login gets the realtime connection
- `queue:process` writes a line per task into a file instead of its dashboard
- A link can open its page in a dialog — `data-pf-modal`

<!-- more -->

## `schedule:list` sees the `work` process that is running

### Fixed

- **"No `work` process is running" beside one that was, executing tasks.** `schedule:list` built
  its `WorkerLock` from the name `pramnos-work.lock`, and the lock's default path adds `.lock`, so
  it read `var/pramnos-work.lock.lock` — a file nothing writes. It asks `Work::lockFilePath()`, the
  path the worker itself uses, supervisor's override included. Its test had taken the lock the same
  wrong way, which is why it passed (FW-208).

## `work` no longer skips a minute

### Fixed

- **A task due in a minute no pass looked at did not run.** Each pass asked about the current
  minute only, ran what was due one task after another, then slept sixty seconds from when it
  ended. A nine-second mail flush was enough: passes at 03:19:59 and 03:21:09, nothing asked about
  03:20, and a task on `5,20,35,50` did not run — a weekly one would have waited a week. A pass
  now asks about every minute since the last one, at most `Work::CATCH_UP_MINUTES` (15) back, runs
  each due task once, and sleeps to the next minute's start (FW-210).
- **`--interval` below sixty ran an every-minute task twice a minute.** A minute already asked
  about is not asked again.

## `broadcast:serve` holds its lock, so the orchestrator stops restarting it

### Fixed

- **The orchestrator restarted the WebSocket server every cycle**, dropping every open page:
  its entry declares `var/pramnos-broadcast-serve.lock`, and `broadcast:serve` never took a lock
  or wrote a heartbeat, so it stayed "started-unverified" and was gracefully stopped to be
  started again. The Services screen, reading the same absent file, showed the running server as
  stopped and offered to start a second. It takes the lock, heartbeats from the event loop every
  ten seconds, and releases it on exit; a second one refuses while the first holds it (FW-209).
  An application that set `'requireLockFile' => false` on the entry to get by can remove it.

## A page signed in by an application's own login gets the realtime connection

### Fixed

- **`<meta name="pf-realtime">` was written only for a session holding a framework token.** An
  application whose login is its own sets `uid` and `logged` and no `usertoken`, so none of its
  signed-in pages connected and the notification bell never went live. The meta now follows
  `Session::staticIsLogged()` as well — the test `getCurrentUser()`, and so `/broadcasting/auth`,
  already made (FW-211).

## `queue:process` writes a line per task into a file instead of its dashboard

### Fixed

- **A worker run into a file painted its whole dashboard there, five times a second.** Only a
  supervised worker skipped it; one started by hand with `>> var/logs/ask-worker.log` and
  `--sleep=2` wrote borders, escape sequences and "Press Ctrl+C to exit" until the file was 542
  MB, the task results lost inside it. The dashboard is painted only on a terminal; otherwise each
  task is one plain line — time, id, type, status, duration, message — and an empty pass writes
  nothing (FW-214).

## A link can open its page in a dialog — `data-pf-modal`

### Added

- **`data-pf-modal` on a link** opens its page in a `<dialog>` over the current one: fetched with
  `X-Pf-Fragment: 1`, closed by Escape, the × or the backdrop, focus back on the link afterwards.
  Without `<dialog>`, on a modified click or a failed fetch it is an ordinary link (FW-213).
- **`Document::isFragmentRequest()`**, and the request with that header gets the `raw` document,
  so any screen answers with its content alone — no per-screen code. The page cache keys the
  fragment apart from the page, and `Breadcrumb::admin()` draws no trail into it.
- **The queue screen's "Statistics — last 48 hours" and each task's id** open in the dialog
  instead of leaving the list.
