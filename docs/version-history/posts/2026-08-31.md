## Mail bodies leave the database by default, and the size threshold is gone

The mail body store — gzipped bodies under `var/mails/`, the row keeping a path — was opt-in, and
it had a floor: anything under 512 bytes stayed in the `content` column. Both are now gone. The
store is on unless an installation writes `'enabled' => false`, and every non-empty body goes to
it whatever its size.

### The default was backwards

The reasoning for opt-in was that moving an audit trail onto a disk nobody has decided to back up
should be a decision somebody makes. It reads well and it points the wrong way: the installations
that never make the decision are precisely the ones whose `mails` grows unwatched, and the body
is the whole of that growth. A password reset is two hundred bytes of facts — when, to whom,
which module, did it send — wrapped around forty kilobytes of HTML. The facts are what anybody
queries; the HTML is read by one screen, occasionally, and is never joined, filtered or
aggregated on.

An installation that has not thought about this is better served by the arrangement it would have
chosen had it thought about it.

Nothing is at risk in the switch, and that is what made it safe to make:

- A body that cannot be written **falls back to the column it used to live in**. An installation
  with no writable `var/mails` behaves exactly as it did.
- `BodyStore::bodyOf()` is the single reader and takes the body from wherever it is, so rows
  written before and after the change read the same.
- `'enabled' => false` still turns it off.

### The threshold cost more than it saved

512 bytes was not an arbitrary number. Below it a file genuinely costs more than the column
does — a 4 KB block and an inode to hold two hundred bytes, plus a seek to read them. The
arithmetic was right.

It was still the wrong trade, because of what it bought the saving with. The sentence this store
exists to make true is *the body is not in the database*. With a floor, that sentence has an
**unless** in it, and every answer resting on it inherits the same "unless":

- **What a GDPR erasure has to clear.** If the body is always in a file, erasure removes a file.
  With a floor it removes a file *sometimes*, and has to clear a column the rest of the time —
  and a rule with a branch in it is a rule somebody implements only half of.
- **How large `mails` can get.** "Bounded by the metadata" becomes "bounded by the metadata plus
  however many short messages this installation sends", which is not a bound.
- **Whether `var/mails` is the backup that matters.** Not on its own, if some bodies were never
  written there.

One rule that always holds is worth more than a block per short message. `BodyStore::MIN_BYTES`
stays, at `0` and deprecated, because it is public and something outside the framework may name
it.

### Reading it back

`mail:archive` moves what is still in the database, and now moves everything rather than
everything above the floor:

```
./yourapp mail:archive              # what it would move, and nothing else
./yourapp mail:archive --apply
./yourapp mail:archive --gc --apply # …and collect files no row names any more
```

Measured on one installation: 7.2 MB of bodies in the database became 212 KB on disk, and 2,916
archived bodies are 198 files — the store is content-addressed, so a campaign to forty thousand
people is one body written once.

The guide's [Where a sent message's body lives](../../Pramnos_Email_Guide.md#where-a-sent-messages-body-lives)
carries both changes.
