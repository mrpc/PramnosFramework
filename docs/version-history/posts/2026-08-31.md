## Mail bodies leave the database by default, and the size threshold is gone

The mail body store — gzipped bodies under `var/mails/`, the row keeping a path — was opt-in, and
it had a floor: anything under 512 bytes stayed in the `content` column. Both are now gone. The
store is on unless an installation writes `'enabled' => false`, and every non-empty body goes to
it whatever its size.

### The default was backwards

The reasoning for opt-in was that moving an audit trail onto a disk nobody has decided to back up
should be a decision somebody makes. It reads well and it points the wrong way: the installations
that never make the decision are precisely the ones whose `mails` grows unwatched, and the body
is the whole of that growth. A password reset is two hundred bytes of facts — when, to whom,
which module, did it send — wrapped around forty kilobytes of HTML. The facts are what anybody
queries; the HTML is read by one screen, occasionally, and is never joined, filtered or
aggregated on.

An installation that has not thought about this is better served by the arrangement it would have
chosen had it thought about it.

Nothing is at risk in the switch, and that is what made it safe to make:

- A body that cannot be written **falls back to the column it used to live in**. An installation
  with no writable `var/mails` behaves exactly as it did.
- `BodyStore::bodyOf()` is the single reader and takes the body from wherever it is, so rows
  written before and after the change read the same.
- `'enabled' => false` still turns it off.

### The threshold cost more than it saved

512 bytes was not an arbitrary number. Below it a file genuinely costs more than the column
does — a 4 KB block and an inode to hold two hundred bytes, plus a seek to read them. The
arithmetic was right.

It was still the wrong trade, because of what it bought the saving with. The sentence this store
exists to make true is *the body is not in the database*. With a floor, that sentence has an
**unless** in it, and every answer resting on it inherits the same "unless":

- **What a GDPR erasure has to clear.** If the body is always in a file, erasure removes a file.
  With a floor it removes a file *sometimes*, and has to clear a column the rest of the time —
  and a rule with a branch in it is a rule somebody implements only half of.
- **How large `mails` can get.** "Bounded by the metadata" becomes "bounded by the metadata plus
  however many short messages this installation sends", which is not a bound.
- **Whether `var/mails` is the backup that matters.** Not on its own, if some bodies were never
  written there.

One rule that always holds is worth more than a block per short message. `BodyStore::MIN_BYTES`
stays, at `0` and deprecated, because it is public and something outside the framework may name
it.

### Reading it back

`mail:archive` moves what is still in the database, and now moves everything rather than
everything above the floor:

```
./yourapp mail:archive              # what it would move, and nothing else
./yourapp mail:archive --apply
./yourapp mail:archive --gc --apply # …and collect files no row names any more
```

Measured on one installation: 7.2 MB of bodies in the database became 212 KB on disk, and 2,916
archived bodies are 198 files, because the store is content-addressed.

That last property has a limit worth stating with it: it deduplicates *identical* bodies. A mailed
campaign is personalised — a per-recipient unsubscribe token in the wrapper, a per-recipient
tracking pixel — and `Email::send()` logs the rendered body deliberately, because the mailer sends
that string and the audit log has to record the same one. So a mailed campaign is one file per
recipient. The inbox copies of a mass message are identical and do collapse to one.

The guide's [Where a sent message's body lives](../../Pramnos_Email_Guide.md#where-a-sent-messages-body-lives)
carries both changes.

## `messages` uses the body store too, which is what a mass send needed

The store moved to `Pramnos\Storage\BodyStore` and `messages` now writes its bodies to it, the
same way `mails` does. `Pramnos\Email\BodyStore` still resolves and still works; the
configuration key is still `mail.body_store`.

### The inbox is the worse case, not the milder one

`mails` grows a row per message. `messages` grows a row per **recipient**: a campaign to forty
thousand people writes forty thousand rows, each carrying its own copy of one identical body.

The store is content-addressed, so those copies collapse to forty thousand path strings and one
file. On the mail side that deduplication was a bonus; here it is the entire reason to do it. The
integration test asserts exactly that — 40 recipients, one file — because if it ever stops being
true, this is the table that fills a disk.

```
./yourapp messages:archive            # what it would move, and nothing else
./yourapp messages:archive --apply
```

New messages write to the store on their own, through `Message::save()` and through the mass-send
dispatcher. `messages:archive` is the migration for rows that were already there. `Message::load()`
brings the body back, so `$message->text` means what it always meant.

### Three things that had to be right

**The listing.** The inbox draws a preview line under every subject, from the body. With the body
in a file that is one decompression per row — two hundred to paint the screen people open most
often. So `excerpt` is written at send time and kept on the row: a listing wants a summary, and a
summary is metadata. Without it the store would have been correct and unusable, which is the
failure mode worth naming — every read still returns the right body, and the page takes a second
to draw.

**The garbage collection.** `BodyStore::orphans()` deletes files that no row names. It was written
when `mails` was the only table naming one. Sharing the store without teaching it about `messages`
would have made every message body look unreferenced, and `mail:archive --gc` would have deleted
them all. `REFERENCED_BY` is now the list it consults, and adding a table to it is not bookkeeping
— it is the whole safety of the sweep.

**Which absences are safe.** A missing table is two different events wearing one face, and the
sweep has to tell them apart because it deletes files. `messages` belongs to a feature an
installation can switch off: absent, no row ever pointed into the store from it, so it is skipped —
refusing instead would make `--gc` report "nothing to collect" for ever with the reason invisible.
`REQUIRED_TABLE` — `mails` — is the other kind: the store was built for it, every file is presumed
to have come from it, and reading "nothing is referenced" out of its absence hands the caller the
whole archive. Its absence stops the sweep.

### Migration

`2026_08_31_000001_add_bodypath_to_messages` adds `bodypath`, `bodybytes` and `excerpt`. Additive
and empty on arrival: an installation that changes nothing keeps writing bodies inline. Existing
rows are not touched — `messages:archive` moves them, a batch at a time, safe to interrupt and
safe to repeat.

The guide's [Where a sent message's body lives](../../Pramnos_Email_Guide.md#where-a-sent-messages-body-lives)
covers both tables now.

## The store moves to the layout applications were already using

`BodyStore` was written without looking at what applications on this framework had been doing for
years, and they had been doing it better. It now stores at `Y/m/d/H/<digest>.html.gz` — year,
month, day, **hour** — instead of putting a whole month in 256 hash buckets.

### Because the bucket does not scale and the hour does

A directory holds an hour of mail. Anything that has to walk the store walks an hour of it.

The old layout could not be walked in pieces at all: at ten million messages a month, 256 buckets
is forty thousand files each, and the only way through them is all at once. That is not a
performance note — it is the difference between a maintenance job that finishes and one that
cannot be run.

It costs deduplication across the boundary: the same body sent again next week is two files. The
case that matters is unaffected, because a send writes its identical copies within minutes, and
those still collapse to one. The burst is what makes the store large; a week apart is two events.

### Nothing rewrites a row, which is why this was safe

A body is read from the path recorded on its row — no directory name is ever recomputed. So rows
written under the previous layout keep working, and there is a test that says so, because the
alternative failure is the quiet kind: invisible until somebody opens an old message, by which
time the deploy is a week old.

### One reader, three places a body can be

`BodyStore::bodyOf($row)` now also reads **`mails.path`** — relative to `ROOT`, which is where
applications recorded a gzipped body long before this class existed. Before, those rows returned
an empty string: the screens went blank on exactly the installations with the most history to
show.

That makes this store something an existing application can *adopt* rather than migrate to. It
points the root at the tree it already has and keeps its rows.

**And `path` joined the list the garbage collection consults**, which is the dangerous half. An
installation that points the store at those files — the reason the root is configurable — would
otherwise get every one of them reported as unreferenced and deleted in a single sweep. Years of
history, in one run of `--gc`. `REFERENCED_BY` names both columns, and the sweep compares absolute
paths, because the two columns spell the same file differently and a string comparison would find
the legacy one unreferenced.

### `hash` now means what the schema always said

`mails.hash` is documented as "MD5 hash of the email content", and applications read it that way —
one compares it against `md5($content)` to decide whether a body needs storing again.
`Email::send()` wrote an identity of the *message* there instead: recipient, subject and time.
Nothing in the framework ever read it, and everybody outside it read something else. It is the md5
of the rendered body now.
