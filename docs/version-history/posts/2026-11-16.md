## A metric can be broken down or filtered by a segment or an audience attribute (FW-515)

BI roadmap phase 7d (`docs/Metrics-BI-Design.md` §15.2.3/15.2.4). The audience's own segments and
person events were already metrics, with nothing declared (phase 7c, `Audience\AudienceMetrics`);
this generalises the join the other way — any metric over its own table, not the audience's, can
now be broken down or filtered by a segment or an audience attribute, once it says which column
of its own query names the person.

### Added

- `Metric::person(string $column)`: the declared query's column naming the person each row is
  of. Required before breaking down or filtering by a segment or an attribute — a clear
  `\LogicException` otherwise, naming which breakdown asked for it.
- `Metrics::personDimension(string $name, \Closure $resolve)`/`resolvePersonDimension()`: how a
  breakdown name joins in whatever it needs and answers the GROUP BY expression, for `person()`
  to use. The framework registers `segment` (where `pramnos.segment_members` exists) and every
  audience attribute that can be broken down by (not a date, not a one-to-many kept on anything
  but the person) — an application's own resolver or `Dimension` under the same name wins.
- `segment` is read **as of each period's end**, from the segment's stays, not as of today — a
  LEFT JOIN, so a person in no segment keeps their row (grouped under no segment) instead of
  disappearing from a total that also breaks down by it. A person in two segments at once is
  counted in both; a sum by segment does not add up to the metric's own total, the same as
  anywhere else segments are not a partition.
- An audience attribute's breakdown reuses `Attribute::sql()`/`alias()`/`table()`/`foreignKey()`
  directly — the same primitive `Filter` itself is built on — LEFT JOINed on the person column, so
  an attribute means the same thing in a report as it already does in a filter or a segment.
  `Dimension::ability()` still gates it.
- A new `userid` attribute (`Audience\Attributes`), deliberately never a dimension (every person
  is their own value): what turns a cell's own people into a segment needs nothing else —
  `Segments::create($name, ['conditions' => [['attribute' => 'userid', 'op' => 'one_of', 'value'
  => $ids]]])` over the ids `rows()` already carries. A rule for that segment is an ordinary rule.
- The PostgreSQL many-breakdown prefetch (`prefetch()`/`prefetchSets()`) does not build this join:
  such a breakdown is always computed one query at a time instead, in `declaredSource()`.

### Documentation

- `Pramnos_Metrics_Guide.md`, "A segment or an attribute as a dimension" (new, under "The
  audience's own metrics").
- `Metrics-BI-Design.md` §15.3's 7d row marked built.

## An alert can start a rule; a rule and a test are measured; both annotate the charts (FW-516)

BI roadmap phase 7e (`docs/Metrics-BI-Design.md` §15.2.5–15.2.7): the three ways the automation
module and the metrics join, each reusing a mechanism the other already has rather than writing
its own.

### Added

- `Metrics\MetricAlertFired` (`metric.alert`): dispatched once for each person an alert's
  `notify.users` tells (`Alerts::fire()`), carrying the rule, the person, the metric, what it said
  and when. An audience rule whose trigger is `{"type": "event", "event": "metric.alert"}` takes
  that person in exactly as it would for any other event — the existing generic event trigger
  needed nothing new.
- `Audience\AudienceMetrics`'s `audience.rule.entered`/`.sent`/`.goal`/`.exited`, by `rule` and
  `version` (and `channel` for `.sent`), read straight from `pramnos.rule_log`'s own outcomes
  (`entered`, `sent`, `goal`, `exited`) — no declaration, the same way phase 7c's segment/event
  metrics need none.
- `Metrics\Widgets\ExperimentWidget` (`report.experiment`): a report card over the already-built
  `Experiments::results()` — people, converted, rate, confidence per variant.
- `Rules::update()` (a changed definition only) and `setStatus()` (a status that actually moves),
  `Experiments::start()`/`stop()`/`decide()`, and `Segments::update()` (a changed filter only)
  each write a `Metrics\Annotations` note (kind `rule`, `test` or `segment`) the moment it
  happens, drawn on a chart's periods beside a deploy's.

### Not built

- An alert's own default notify (the bell, the conversation line) is not re-expressed as a
  literal stored rule — it already does what one would, so turning it into one would add a row
  without changing what happens. An application wanting `webhook`/`ai`/`conversation_post`
  beyond the plain notify writes a rule triggered on `metric.alert` instead, as above.

### Documentation

- `Pramnos_Audience_Guide.md`, "The rules and the metrics" (new, after "A/B tests") and a mention
  of `report.experiment` under "A/B tests".
- `Pramnos_Metrics_Guide.md`: the four `audience.rule.*` metrics added to "The audience's own
  metrics"; `report.experiment` added to the report cards table; "Notes on the charts" documents
  the automatic rule/test/segment notes.
- `Metrics-BI-Design.md` §15.3's 7e row marked built.

## A metric's own health; a report to a webhook, a channel or storage; a link that opens one with no account (FW-517)

BI roadmap phase 7f (`docs/Metrics-BI-Design.md` §15.1.3–15.1.5): the three gaps that stayed
closest to the ground — a metric that breaks silently, a report with nowhere to go but an inbox,
and nobody to open one but an account holder.

### Added

- `Metrics::health(int $now = 0, int $recentPeriods = 3): array` — for every declared metric, at
  each grain it is kept at: the newest period's own `computed_at`, the last run's time and
  failure (`pramnos.metrics_health`, written by `Metrics::computeAll()` around every grain and
  every live metric's aggregate), whether it is late against `expect()`, and which of the last
  three periods have no figure (`Metric::gapOf()`).
- `metrics:status` prints it; exits `1` under the same condition `MetricsHealthCheck` reports
  **degraded** on the operators' Health card and `/health` — nothing to say with no metric
  declared, and resolving nothing until it runs, the same discipline every health check here
  already keeps.
- `Reports::destinations(string $text): array` — a bare token is a mail address as `recipients`
  always was; `webhook:https://…`, `conversation:<channel or account id>` and the bare word
  `storage` are the others, any mix, an invalid one dropped silently like a bad address always
  was. `metrics:reports-send` sends every destination of a due report: a webhook is POSTed
  `{report, csv}`, a conversation channel gets the title (`SystemPost::post()`), storage gets the
  same CSV at `metrics-reports/<id>/<period>.csv` (`Storage::put()`) — and **mail now gets the
  CSV attached**, which it never did before. One destination failing fails the whole send; the
  next run tries every destination again.
- `Pramnos\Metrics\SharedLinks` (`pramnos.metric_links`): a signed token that opens a saved report
  with no account, read with the scope of whoever made it — `Reports::find()` exactly as an
  ordinary signed-in read would, so a maker's own narrowing access narrows the link too.
  `MetricReports::share()`/`unshare()`/`shared()` — the last the screen's only public action
  (`$adminPublicActions`), a plain page rather than the admin theme, and every open written to the
  audit log regardless of whether the token still worked.

### Documentation

- `Pramnos_Metrics_Guide.md`: new "Health" section; "Mailing" renamed "Destinations" and rewritten
  for the three new kinds and the mail's own attachment; new "Shared links" section.
- `Metrics-BI-Design.md` §15.3's 7f row marked built.
- The report form's "To" field, in every theme, says the new syntax.

## Funnels over person events; an alert for the unusual hour; a metric faked for a test (FW-518)

BI roadmap phase 7g (`docs/Metrics-BI-Design.md` §15.1.6, §15.1.9, §15.1.8): a funnel, "the
weekday's usual band" as an alert condition, and a way to check a metric in a test without a real
table or a real `metrics:compute`.

### Added

- `Alerts::UNUSUAL`: the last completed hour outside the band it usually falls in at the same
  weekday and hour — the mean of the last four weeks (`Goals::WEEKS`), `value` standard
  deviations either side (2.0 left out). A reference week never yet computed means no band to
  judge by, so it does not fire — the same discipline `stopped` already has for a hole.
- `Pramnos\Audience\Funnels::run()`: steps over person events, in order — a query over the event
  log (`pramnos.changelog_events`), not a stored metric. The same cohort narrows at each step;
  `share` is its part of the first step's own; `median_seconds` the median gap from the step
  before's own first occurrence, across the people who reached both. `by` breaks the first step's
  own people down, a segment (`segment:<id>`) or an audience attribute's own key — through
  `Filter::breakdown()`, the same count of people every other breakdown in the audience module
  already goes through, restricted to the cohort by its own `userid` attribute (the same
  mechanism FW-515's "a number to its people" uses).
- `report.funnel` (`Metrics\Widgets\FunnelWidget`): the card over it — `events` (comma-separated,
  in order, at most six, dropping any nobody declared) and `by`.
- `Metrics::fake()`: values kept in memory, metric => period => filters => value, read back by
  `Metrics::value()` without the metric even needing to be registered — an application's own test
  checks one number without building a table. An empty call turns it off, back to the database.
- `Pramnos\Metrics\Testing\AssertsMetrics::assertMetric()`: one value checked, against the fake or
  the database, the same assertion either way — a trait an application's own test case uses.

### Documentation

- `Pramnos_Metrics_Guide.md`: "unusual" added to Alerts; new "Funnels" section; new "Testing an
  application's metrics" section.
- `Metrics-BI-Design.md` §15.3's 7g row marked built.

## Many periods read at once on MySQL too, for a day; an organisation's figure read as an attribute (FW-519)

BI roadmap phase 7h (`docs/Metrics-BI-Design.md` §15.1.7, §15.2.8) — the last of the "metrics and
audience" gaps before metrics without code (7i).

`Metric::prefetch()`'s many-periods-at-once read was PostgreSQL only: `date_trunc(…, zone)` has no
MySQL equivalent that is both zone-correct across a DST change and free of the server's own time
zone tables, which are not guaranteed to be loaded on every installation. Rather than guess wrong
twice a year, the framework takes the one shortcut that needs no zone conversion at all — the UTC
zone, bucketed straight from the epoch — and only for an hour's or a day's grain, where reading
many periods actually matters. A week, a month, a quarter, or any other zone on MySQL still falls
back to one query a period: slower, never wrong.

`Attribute::metric()` closes the other half of phase 7: an organisation's own stored figure,
usable anywhere any other audience attribute is — "members of organisations whose revenue fell"
is now `Attribute::metric('org_revenue_fell', 'organizationid', 'revenue', Window::MONTH, trend:
true)` compared with the ordinary `lt(0)`.

### Added

- `Metric::prefetch()` reads an hour's or a day's grain at once on MySQL, when the metrics' zone
  is UTC: the epoch truncated by `MOD()`, no `date_trunc()`/`CONVERT_TZ()` needed. Every other
  grain, or any other zone, falls back exactly as before.
- `Pramnos_Metrics_Guide.md`'s new "MySQL and PostgreSQL" table: what each database does for
  `prefetch()`, `prefetchSets()`, live metrics and compression, and why the UTC limit above is
  there.
- `Attribute::metric(string $key, string $byColumn, string $metric, string $grain =
  Window::MONTH, int $version = Store::VERSION, bool $trend = false)`: a `NUMBER` attribute that
  reads the metrics store directly — one indexed read of the latest kept period for the row's own
  tenant (`$byColumn`), never computed per person. `trend: true` reads the period before it too
  and answers the difference. Resolves the store's `schema.table` into each driver's own quoted
  form without a live connection, the MySQL half behind the `#PREFIX#` token the query builder
  already substitutes when the expression's own query compiles.

### Not built

- A breakdown of the organisation's metric other than its own total (`dims: {}`) — the design
  doc's own example reads the whole organisation's figure, not one of its dimensions.

### Documentation

- `Pramnos_Audience_Guide.md`: `Attribute::metric()` added to the Attributes section's examples.
- `Metrics-BI-Design.md` §15.3's 7h row marked built.
