## `Model`/`Database`: a connected instance no longer breaks `session_write_close()` (FW-287)

### Fixed

- A `Model` holds `$controller`, set in every constructor — which chains to the `Application`
  and from there to the live database connection, neither serializable. A model with
  lazy-loaded relations (each one its own `Model`, each with its own `$controller`) landing in
  `$_SESSION` failed `session_write_close()` at the end of *every* request that had touched
  one, not only the one that first noticed, with "Serialization of 'PgSql\Result' is not
  allowed" — appended after the response on an HTML page, and breaking the response outright
  on a JSON/AJAX endpoint. `jsonSerialize()`/`getData()` already excluded `$controller` for
  JSON output, but `serialize()` does not go through either — it walks every property by
  default and respects only `__sleep()`, which this class had none of. `Model::__sleep()` now
  keeps every property except `$controller` and `Base::$_parentObject` (set by reference, to
  whatever was given), and every property declared `private` on `Model` itself — PHP cannot
  return a parent class's `private` property name from `__sleep()` for a subclass instance
  (every model actually used is one) without a "returned as member variable from __sleep()
  but does not exist" warning, a documented engine quirk rather than something to serialize
  around.
- `Database::__sleep()`/`__wakeup()`, defense in depth for a `Database` instance reaching
  `serialize()` by some other path: keeps the safe configuration (host, user, database, type,
  schema, …), drops every connection handle, prepared statement, query result and file-handle
  log target, and comes back on `__wakeup()` the same way a freshly constructed instance
  would — disconnected, ready to reconnect lazily on its next query.
- Reported by nannuka-be, urgent ahead of a production cutover to PostgreSQL: confirmed with
  a reflection dump of `$_SESSION['user']` on a real admin request, and that MySQL's own
  connection object is exactly as unserializable, so this was never PostgreSQL-specific — it
  had simply gone unnoticed there, likely because of how rarely every single connection in a
  request happened to be the live one a lazy-loaded relation's `$controller` chain reached.

### Documentation

- None — a model's or a database connection's own public contract is unchanged; this is
  what `serialize()` does with either, which neither page documented as supported before.

## Moving from MySQL: `LIMIT a, b` with placeholders substitutes its values in the right order (FW-288)

### Fixed

- The translation rewrote MySQL's comma form of `LIMIT` as `LIMIT b OFFSET a` — correct SQL,
  but it moves `a` and `b` to the other side of each other in the *text*. `prepareQuery()`
  fills a statement's placeholders by where they fall in the final text, with the values in
  the order they were given — so when `a` or `b` was a placeholder rather than a literal
  number, the value meant for one landed in the other's slot. `offset=0, count=10` became
  `LIMIT 0 OFFSET 10`: no rows, not the ten a reader was told were there. PostgreSQL takes
  `OFFSET`/`LIMIT` in either order, so the translation now writes `OFFSET a LIMIT b` — the
  same two arguments, exactly where they already were, literal or not.
- Reported by nannuka-be, urgent ahead of the same production cutover as FW-287: found as a
  search answering "1 result nearby" with an empty list — a `LIMIT 0, 10` whose `SELECT` never
  returned the one row `LIMIT 0` (not `10`) asked it to skip past entirely.

### Documentation

- `docs/Pramnos_Database_API_Guide.md`'s `translate_mysql` table, the `LIMIT a, b` row.

## `Model::save()`: a failed update now throws, the same as a failed insert already did (FW-290)

### Fixed

- `_save()`'s UPDATE branch never looked at `updateTableData()`'s return value — the INSERT
  branch three lines above it does, and throws `QueryException` on `false`. `updateTableData()`
  itself already catches its own `\Throwable` and returns `false` (the same shape
  `insertDataToTable()` has), so a wrapping `try`/`catch` around the call never actually ran
  either: a failed update fell through as a success, with `$model->sqlError` never set. Fixed
  to check the return value, matching the INSERT branch, and to roll back a transaction the
  caller had open before the exception reaches it — on PostgreSQL a failed statement aborts
  the whole transaction, and every later statement on that connection fails with "current
  transaction is aborted", far from here, until something issues a `ROLLBACK`.
- Found the same swallow-and-return-false shape, and the same unreachable debug branch, in
  `insertDataToTable()`'s own debug mode: `$debug=true` echoed `$qb->insert()`'s return value —
  already-executed `Result`, not SQL text — as a string, a `TypeError` on every debug call for
  either method. `_save()`'s old blanket `catch (\Throwable)` was hiding this one too. Both now
  `var_dump()` the result instead of concatenating it.
- Reported by nannuka-be as a chase on an intermittent "current transaction is aborted" on an
  unrelated later statement, traced back to a swallowed update failure upstream.

### Documentation

- `docs/Pramnos_ORM_Guide.md`, a new *Error handling* section under *Update* — `save()`'s
  exception contract and the transaction rollback.
- `docs/Pramnos_Upgrade_Guide.md`, a row under `## Since v1.2 — unreleased` for the now-thrown
  exception on an existing row's failed save.
